# 题目导入轮询超时修复方案 v1（2026-10-13 实测专项）

- **版本**: v1.0（拟稿，待用户批准）
- **触发**: 用户 2026-10-13 08:53 实测上传 docx：前端 status 轮询连续 3 次 10s 超时，后端解析 2s 即完成（PREVIEW 100 题）
- **状态**: ⚠️ 待批准——未经用户同意不得实施

---

## 一、问题现象

- 前端控制台：`question_import.vue:703 [fetchWithRetry] Timeout after 10000ms, attempt 1/3 → 2/3 → 3/3`
- 后端终端：upload 202（0.064s）→ 解析完成 PREVIEW（2s）→ `connection closed`
- 用户重试（约 3 分钟后）成功拿到预览

## 二、根因分析（代码级证据链）

### 证据 1：后端完全正常（排除后端问题）

`backend/logs/app.log` 完整时间线：

| 时间 | 事件 |
|---|---|
| 08:53:34.467 | POST /upload 完成 202（0.064s） |
| 08:53:36.460 | [import-async] 解析完成 → PREVIEW（100 题） |
| 08:53:36 ~ 08:57:29 | **后端 3 分 53 秒完全空白**（前端轮询请求从未到达） |
| 08:57:33.910/944/982 | 3 个 GET /records/1544/status，**每个 0.018~0.022s 完成** |

结论：`/status` 端点实测 0.02s（毫秒级），解析 2s 完成。前端在解析完成后 3 分钟内**没有发出任何到达后端的 status 请求**——请求卡在前端/Vite 层。

### 证据 2：主根因——Vite dev watcher 监听范围包含后端数据目录

`vite.config.ts:106-108`：
```ts
watch: {
  ignored: ['**/.worktrees/**'],   // ← 仅忽略 worktree，backend 完全在监听范围内
},
```

而导入流程中，后端会**高频写文件**到 Vite 项目根目录下的 backend 子目录：
- 图片落盘：`backend/app/static/questions/{marker}.png`（`_extract_and_save_images`）
- 数据库：`backend/data/question_bank.db` + `-wal` + `-shm`（`_set_progress` 每阶段 `db.commit()` → WAL 文件 mtime 变化）
- 日志：`backend/logs/app.log`（middleware 每个请求都写）

`.db` / `.png` / `.log` 均非可 HMR 模块 → Vite 收到变更事件后触发 **页面 full-reload**。时间线吻合：
1. 08:53:34-36 解析期间大量文件写入 → Vite full-reload 触发
2. 页面 reload → 轮询 fetch 中断 → 前端 console 打出 Timeout（abort timer 触发）
3. reload 后组件 state 丢失（import_id 没了）→ 流程中断
4. `connection closed` = reload/abort 时连接被客户端断开
5. 08:57:33 文件已稳定（无新写入）→ 用户重新操作成功

### 证据 3：放大因素——前端轮询零容错

`.vtj/vue/question_import.vue` `_pollImportStatus`（:787-822）：
```js
var res = await this.fetchWithRetry('/status?light=true', {...}, 10000, 2);
```
`fetchWithRetry` 3 次尝试（30s）后**抛错**，`_pollImportStatus` **无 try-catch** → 异常直达调用方 → 整个导入流程失败。即使链路抖动 1 秒，也会以「3×10s 空转 + 报错」收场，而不是「重试一次就成功」。

### 证据 4：A-1 超时下调放大了暴露面

上一轮修复把 status 轮询超时 30000→10000（计划 A-1）。10s 对正常后端足够（0.02s），但对「Vite reload 中断」类链路抖动没有冗余。原 30s 下同一链路抖动可能被掩盖（reload 后用户手动重试也能成），10s 下必现失败。**结论：超时值本身不是根因，但 10s 过紧需要回调。**

## 三、修复方案（3 个修复点，均最小化改动）

### Fix 1（主根因）——Vite 忽略 backend 目录

**文件**：`D:\砺安题库\砺安题库\vite.config.ts`

```ts
watch: {
  ignored: ['**/.worktrees/**', '**/backend/**'],
},
```

**多角度思考**：
- **为什么这样写**：后端写文件（db-wal/日志/图片）与前端开发无关，必须排除在 watcher 外。忽略整个 `backend/**` 最彻底（数据库、日志、上传图片、临时文件全覆盖），不会因新增数据目录再次踩坑。
- **好处**：根治 full-reload 风暴；Vite CPU 占用下降；其他功能模块（教师端/管理端）同样受益（此前任何后端写库都可能触发全页刷新）。
- **安全**：纯 dev server 配置，不影响生产构建。
- **运维**：一条配置消除整类「前端随缘刷新」问题；`backend/**` 语义清晰，后人一看即懂。
- **文件位置正确性**：vite.config.ts 是唯一控制 dev watcher 的文件，改动点正确。
- **VTJ 一致性**：不涉及 .vtj 页面/DSL，与设计器无冲突。

### Fix 2（前端容错）——轮询单次失败不终止

**文件**：`.vtj/vue/question_import.vue`（raw 页面，**只改 `<script>` 的 `_pollImportStatus` 方法，禁止 DSL 同步**）

改动逻辑：
```js
async _pollImportStatus(importId, budgetMs, onTick) {
  var deadline = Date.now() + (budgetMs || (this.PDF_OCR_TIMEOUT_MS || 960000));
  var delay = 1500;
  var waited = 0;
  var consecutiveFailures = 0;
  while (Date.now() < deadline) {
    await new Promise(function (r) { setTimeout(r, delay); });
    waited += delay;
    try {
      var res = await this.fetchWithRetry(
        '/api/questions/import/records/' + importId + '/status?light=true',
        { method: 'GET', headers: this.getAuthHeaders(), cache: 'no-store' },
        15000, 1          // 单次 15s、仅重试 1 次，失败走 catch 而不是整体抛错
      );
      consecutiveFailures = 0;
      var st = await res.json();
      // ...（原逻辑不变）
    } catch (e) {
      consecutiveFailures++;
      if (consecutiveFailures >= 5) {   // 连续 5 次失败 ≈ 网络/后端不可用
        throw new Error('查询解析状态连续失败 ' + consecutiveFailures + ' 次：' + this.handleFetchError(e, ''));
      }
      delay = Math.min(delay + 1000, 5000);  // 失败后缓慢加长间隔
      continue;                              // 继续轮询，不放弃
    }
  }
  // deadline 到 → 原超时提示
}
```

**多角度思考**：
- **为什么这样写**：轮询的本质是「最终一致性」——单次失败不该中断整体。连续失败才说明链路真的断了。
- **好处**：链路抖动（Vite reload 除外，见 Fix 1）自愈；用户不再因 1 次抖动看到「上传失败」。
- **安全**：`cache: 'no-store'` 防止代理/浏览器缓存 status 响应；失败上限 5 次防止无限循环。
- **运维**：失败计数与报错文案明确，排查时有据可依。
- **文件位置正确性**：`_pollImportStatus` 只被导入轮询调用，改它不影响其他模块。
- **VTJ 一致性**：只改 script，不碰 template/DSL；raw 页面严禁 `vtj_sync_vue_to_dsl`。

### Fix 3（参数回退）——超时 10000→15000、重试次数 2→1

理由：后端实测 0.02s，15s 是「短请求」的充裕冗余；重试次数由轮询循环接管（Fix 2），fetchWithRetry 内无需再 ×3。避免「30s×3=90s 空转」和「10s 过紧」两个极端。

## 五、风险与回滚

| 风险 | 缓解 |
|---|---|
| 忽略 `backend/**` 后开发时改后端代码不触发前端刷新 | 后端代码本身无需前端刷新；前端感知后端接口变化靠手改前端，本来就不靠 watcher |
| Fix 2 轮询失败上限误伤真故障 | 5 次失败 ≈ 75s，之后抛错信息明确；deadline（960s）仍兜底 |
| raw 页面改动 | 只改 `_pollImportStatus` 方法体，改前 `vtj_read_vue_file(id,'script')` 读、写前 dryRun；禁 DSL 同步 |

**回滚**：`git revert` 对应 commit 即可，无 schema/迁移改动。
