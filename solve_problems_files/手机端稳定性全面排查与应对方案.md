## 一、本次已解决的紧急问题（已修复，待重启验证）

### 1.1 ECONNRESET 崩溃（WebSocket 同步链路）

| 项 | 内容 |
|----|------|
| **现象** | 手机端登录后，前端终端报 `read ECONNRESET` + `Unhandled 'error' event`，dev server 崩溃 |
| **根因** | `backend/app/api/v1/websocket.py` 的 `/ws/connect` 使用了**错误导入** `from security import decode_token, TokenType`（`security` 模块不存在）。登录成功后 `src/auth.ts` 的 `initSyncSocket()` 建立 WebSocket 时抛 ImportError → 在 `accept()` 之前 `close()` → 后端异常断开连接 → Vite 代理收到 RST 崩溃 |
| **修复** | ① 导入改为 `from ...core.security import decode_token, TokenType`；② WebSocket **先 accept 再校验 token**（消除 accept 前 close 的异常断开）；③ `ConnectionManager.connect()` 去掉重复 accept；④ `proxy.config.ts` 三个代理条目加 `configure` 错误容错（兜底） |

### 1.2 database is locked（SQLite 并发写锁）

| 项 | 内容 |
|----|------|
| **现象** | 登录报 500 + `sqlite3.OperationalError: database is locked`（`UPDATE sys_user` 失败） |
| **根因** | 后台 `news_scraper` 逐条入库时 `db.flush()` 取 id 后**未立即 commit**，随后图片下载（Playwright 导航 + 内联图下载，秒级~几十秒）期间**一直持有 SQLite 写锁**；同时 `database.py` 中 `PRAGMA busy_timeout=5000`（5秒）**覆盖**了 `timeout=30`，锁等待上限仅 5 秒 |
| **修复** | ① `news_scraper.py` 的 `scrape_cpd_news`/`scrape_people_news`：`flush()` 取 id 后**立即 `commit()` 释放写锁**，再执行图片下载；② `PRAGMA busy_timeout` 5秒 → **30秒** |

### 1.3 登录 401（连锁反应）

| 项 | 内容 |
|----|------|
| **现象** | `GET /api/practice/type-summary` 返回 401 |
| **根因** | 登录 500（database is locked）导致 token 未签发，后续请求因无有效 token 全部 401 |
| **修复** | 随 1.2 修复登录成功即自动解决 |

### 1.4 登录写库自动重试（本次加固新增）

| 项 | 内容 |
|----|------|
| **目的** | 即便爬虫/定时任务与登录偶发锁冲突，也能自动重试，避免登录 500 |
| **实现** | `backend/app/core/database.py` 新增 `commit_with_retry(db, max_retries=3, base_delay=0.5)`（指数退避：0.5s/1s/2s），仅在捕获到 `"database is locked"` 时重试，其余异常直接抛出；`auth.py` 全部 5 处 `db.commit()` 已替换 |

## 二、潜在问题排查与应对方案

### P1 SQLite 单写者并发（全局风险）

- **风险**：SQLite 仅支持单写者，登录、答题提交、签到、金币、错题收录等所有写端点竞争同一把写锁，高并发下易锁冲突。
- **现状**：已通过 WAL + `busy_timeout=30s` + 爬虫提交时机修复 + `commit_with_retry` 缓解。
- **应对**：
  1. 将 `commit_with_retry` 推广到**所有关键写端点**（答题提交、签到、金币、错题收录等），而非仅 auth。
  2. 减少长事务：任何写操作前避免夹带网络/耗时逻辑（本次爬虫即此类）。
  3. **长期**：生产环境从 SQLite 迁移 MySQL（`settings.DB_TYPE` 已预留 `mysql` 分支），彻底解决单写者限制。

### P2 熔断器全局误伤

- **风险**：`CircuitBreaker` 是**全局单例**（`security.py`，`failure_threshold=5, recovery_timeout=60`），任意端点连续 5 次 500 → 全系统 503 60 秒。`database is locked` 若集中爆发会触发熔断，波及其余正常功能。
- **应对**：
  1. 提高 `failure_threshold`（5 → 20），降低误触发概率。
  2. 按「路径/端点」隔离熔断（而非全局单一熔断器）。
  3. 熔断触发时返回**友好中文提示**（"服务繁忙，请稍后重试"）而非裸 503。

### P3 限流阈值评估

- **风险**：`RateLimiter(rate=300, per=60)`（每 IP 300 次/分钟）+ `LeakyBucketRateLimiter(capacity=100, leak_rate=1.67)`。移动端若做高频轮询/下拉刷新，可能触发 429。
- **应对**：统计移动端实际峰值请求量，必要时调高阈值或对已登录用户放宽；保留对登录接口的独立限流防爆破。

### P4 WebSocket 双管理器（代码异味）

- **风险**：`websocket.py` 用 `ws_connection_manager`（实际生效），`security.py` 另有一个 `WebSocketManager` 实例 `ws_manager`，且 `main.py` 第 29 行 `from .core.security import ws_manager` 是**死导入**（未使用）。两个管理器并存易造成维护混淆、误用。
- **应对**：清理 `main.py` 的 `ws_manager` 死导入与 `security.py` 中未被使用的 `WebSocketManager`，统一使用 `ws_connection_manager`。

### P5 WebSocket 同步链路健壮性

- **风险**：`src/auth.ts` 的 `initSyncSocket()` 断线后 10 秒重连，但**无心跳保活**；token 过期后重连会持续失败；重连无退避。
- **应对**：
  1. 断线重连改为**指数退避**（10s→20s→40s，封顶）。
  2. 增加**心跳**（定期发送 heartbeat，后端已支持 `MessageType.HEARTBEAT`）。
  3. token 过期时先走 `refreshAccessToken()` 刷新，再重建连接。

### P6 前端移动页边界情况

- **风险**：重建后的 `mobile_practice.vue` 与 `mobile_answer.vue` 需完善：空态、加载失败重试、快速切换科目的竞态、未登录跳转、无网络。
- **应对**：
  1. 统一「空态 + 加载失败重试」组件（练习页已加基础空态，需补重试）。
  2. 科目切换加**请求取消/序列号校验**，丢弃过期响应（防竞态）。
  3. 未登录访问练习/答题页跳转登录，登录后回跳。
  4. `mobile_answer.vue` 补齐 `mode` 参数处理（专项突破按题型筛选、错题重练取错题），当前仅按 `kpIds` 取题。

### P7 Token 过期 / 刷新统一

- **风险**：JWT 访问令牌 120 分钟过期，`auth.ts` 有刷新逻辑，但部分接口（如直接 `fetch`）未统一走 `apiFetch` 的 401 处理，过期后可能静默失败。
- **应对**：统一请求封装，401 时先刷新 token 重试一次，仍 401 则跳登录；移动端各页面统一走 `window.__VTJ_AUTH__.apiFetch`。
