## 1. 诊断结论（全部基于实测，非推测）

### 1.1 复合题组建设现状（`question_bank.db` 只读实测）

| 科目 | 题目数 | 有 group_id | 占比 | 题组数 | 每组小题数 |

| 申论 | 12 | 8 | 66% | 4 | 仅 1 组正常（8 题），3 组空壳 |

**⚠️ 题组成员实况（区分 status 后修正）**

|---|---|---|---|---|

### 1.2 五条根因链（每条带 file:line）

#### 根因 1 —— 申论补救函数恒不生效（**P1 直接原因**）

`question_import.py:687`

```python
if q is not None and q.group_id is None:   # ← 恒为假
    q.group_id = gid
```

实测 `SELECT COUNT(*) FROM question_bank WHERE group_id IS NULL` = **0 / 3226**。
列定义 `models.py:214` 是 `Column(Integer, default=0)`，插入后必为 `0`，永不为 `NULL`。

**后果**：`_link_shenlun_material_groups` 里那段精心写的「文档级材料继承」（`:665-677`，专门解决"解析器只在第一题挂 material_text，其余题 material_text 为空"）**一次都没执行过**。它只创建了题组行却挂不上题 → 组 22/23/25 的成员始终为 0（后经软删才被误读为"空壳"，详见 §1.1）。

**实证**：申论 q3749~q3752（18:38 导入）`group_id=0`，题干却是「请根据"给定资料1"，概括F市…」—— 明确引用材料却查不到材料。

#### 根因 2 —— 申论走 upsert 时只有「第一题」拿得到材料

`upsert.py:264-274`

```python
_material = question_data.get('material_text') or question_data.get('material') or ''
if _material:
    _shenlun_gid = _get_or_create_shenlun_material_group(...) or 0
_group_id = _shenlun_gid or int(question_data.get('group_id') or 0)
```

每题独立判断 `_material`。解析器为省内存**只把整卷材料挂第一题**，其余题为空 → `_shenlun_gid=0` → `group_id=0`。
这本来该由根因 1 的函数兜底，但根因 1 已失效。**两个缺陷叠加 = 同卷题一部分有组、一部分没组。**

#### 根因 3 —— 行测材料归组只产出「瞬态元数据」，从不落库（**P2 直接原因**）

`question_import.py:2731-2738`（`_separate_match_xingce` 内）

```python
q['material_group'] = ({
    'ordinal': g['ordinal'], 'group_type': g['group_type'],
    'section': g['section'], 'sort_order': ...,
} if g else None)          # ← 没有 shared_content，也没有 group_id
```

`match_xingce_material_groups`（`composite_matcher.py:330`）确实算出了正确的成员题号，
但结果只挂在**预览态的内存字典**上，**从不写 `question_groups` 表**。

唯一真正落库的行测题组代码在 `scripts/import_xingce_all.py:134`（离线批量脚本）——
**走 UI 导入根本不会执行它**。这解释了为什么行测题组数为 0。

#### 根因 4 —— 行测走通用 confirm 路径时匹配不到题组头

`_detect_and_link_composite_groups`（`:693`）依赖 `match_group_head(question_content)`。
`composite_matcher.py:35-47` 的四条规则要求题干里含「根据以下材料…回答第X-Y题」「根据以下情境」「阅读以下文章」等标记。

**资料分析的材料在「题本文档」里，不在 `question_content` 里**（题本是材料+题目分离版式），
所以标记根本不在题干中 → `match_group_head` 返回 None → 不建组。

#### 根因 5 —— 公专产生「单题假题组」（**P2 直接原因**）

`question_import.py:753-759`

```python
member_ids = [head_qid]
claimed.add(i)
for mqn in member_qnums:
    jid = qn_to_id.get(mqn)
    if jid and jid not in claimed:      # ← 已被 claimed 的会被过滤掉
        member_ids.append(jid)
```

`member_qnums` 非空才建组（`:738` 有校验），但 **`member_ids` 在过滤后可能只剩 head 一道**，
代码**没有「成员数 < 2 则不建组」的后置校验**，于是直接写库。

**实证**：公专 20 个题组，每组恰好 1 题（min=1, max=1, avg=1.0），且全部 `status=1`（在用）。
建了材料、挂了一题、其余小题游离在外 —— 界面上看起来"有关联"，实际是假关联。

#### 根因 6 —— 第 6 轮回填脚本造出「垃圾占位符材料」（**自引入缺陷**）

`backend/scripts/backfill_shenlun_groups.py:85`

```python
mat = '（材料待恢复）' + (qs[0][1][:200] if qs and qs[0][1] else '')
```

该脚本在**取不到真实材料**时，用「`（材料待恢复）` + 首题题干前 200 字」拼一段假材料写进 `question_groups.shared_content`。

**实测后果**：
- 组 23 的 `shared_content` = `（材料待恢复）"给定资料2"反映了乡干部小雷…（15分）`
- 组 25 的 `shared_content` = `给定资料4中提到"创新是有风险的…写一篇文章。（40分）`（题干本身，非材料）

即：**这两行的 `shared_content` 根本不是材料，是题干 + 我加的占位符**。
一旦它们的成员被恢复（软删回滚），前端会直接把题干当材料展示给用户。

**这是我在第 6 轮引入的缺陷**，必须清理，不能让它留在生产库里。

#### 根因 7 —— 同卷重复导入未被去重拦住

实测：
- 组 24：题号 `1,2,3,4` **各出现 2 次**（q3623~3626 与 q3627~3630），全部 `status=1`
  → 同一份申论语料被导入了两次，题库里是 12 行（8 在用）而不是 8 行
- 全库 14 组重复内容：**全部是公专、全部 x2、全部 `status=[1,1]`**
  → 无一例外都是「同卷导入两次」，不是跨卷真重复

去重逻辑 `_detect_duplicate` 存在但未生效，需在 W6 定位其失效原因。

## 3. 分步实施

### Wave 1 —— 修复申论补救函数（最小改动，最高收益）

**改动点**：`question_import.py:687`
```python
# 现状（恒假）
if q is not None and q.group_id is None:
# 改为
if q is not None and not q.group_id:      # group_id 默认 0，falsy 才是「未挂组」
```

**为什么这样写**：`models.py:214` 定义 `default=0`，语义上 `0` 就是「非复合题」（列注释原文：`group_id=0 表示非复合题`）。
用 falsy 判断与列的既有语义一致，且对历史 NULL 数据同样成立，比写 `q.group_id is None or q.group_id == 0` 更简洁。

**安全性**：只放宽条件，不改任何其他逻辑；原本 `is None` 永不成立，故此改动**只可能增加挂组，不可能减少**。

**运维便利**：一行改动，可被未来的 schema 变更（若改为 NULL 默认）继续兼容。

**验收**：用 18:38 那份申论语料重导 → 该卷**全部**小题 `group_id` 非 0 且指向同一题组；
`SELECT COUNT(*) FROM question_groups` 与有组题数一致（无新增空壳组）。

### Wave 2 —— 行测材料归组落库

**改动点**：`question_import.py` `_separate_match_xingce` 的 **confirm 阶段**
（预览阶段的 `material_group` 保持不变，前端已在用）。

设计：
1. confirm 时读取预览态存下的 `groups`（`:2805` 已存入 `xingce_report.material_groups`）
2. 对每个 group：用 `start`/`end` **字符区间**从题本文本切出材料正文（材料正文本来就在 `questions_text` 里，只是没被提取）
3. 调既有 `_upsert_question_group(group_type=g['group_type'], shared_content=<切出的材料>, subject='行测', source=...)`
4. 按 `member_qnums` 回填 `group_id` / `sort_order`

**为什么这样设计**：
- `match_xingce_material_groups` 的 `confidence` 是 1.0（`:387`），因为成员是**位置区间内**的题，不是关键词猜测 —— 可信度最高的一类，直接落库合理
- 材料正文不需要新算法：`start`/`end` 是字符位置，`questions_text[start:end]` 即材料，**一行切片**
- `group_type` 直接用 `XINGCE_SECTION_GROUP_TYPE`（`:322`）已有映射：资料分析→`data_analysis`、言语→`passage` 等

**安全性**：
- 只读 `questions_text` 切片，不改文本
- 建组失败走既有 try/except 兜底（`:1238` 已有「分组失败不影响导入结果」的独立事务模式）
- `group_type` 取自白名单字典，无注入面

**运维便利**：题组建出来后，资料分析题在教师端/学生端自动获得材料，无需二次处理。

**前端影响**：行测 `need_review` 会因「资料分析未归组」规则（`:3147`）产生真实信号，教师端能看到哪些题缺材料。

**验收**：导一份含资料分析的完整行测卷 → 题组表新增行、资料分析小题全部挂组；
`GET /api/questions/group/{新组id}` 返回材料正文 + 成员列表；
`need_review` 中「材料关联异常」类计数与预期一致。

### Wave 3 —— 公专单题假题组修复

**改动点**：`question_import.py:753-759`

两处修改：
1. **后置校验**：`member_ids` 去重过滤后，若 `len(member_ids) < 2` → 不写库（不建组），与 `:738` 的既有防御风格一致
2. **补挂成员**：当 `member_qnums` 因 `claimed` 过滤而丢失成员时，**不静默丢弃**，记 `logger.info` 记录丢失题号，便于后续补挂脚本定位

**为什么这样设计**：宁可**不建组**也不要建假组 —— 不建组时 `group_id=0`，前端 `showDetail` 不发请求，行为与现状一致且诚实；
建假组则会让教师以为有关联，实际查不到小题，是**更坏的误导**。

**安全性**：纯防御性收紧，不会让已有正确分组退化。

**运维便利**：`logger.info` 输出「建组时丢失的题号」，W4 的存量修复脚本可直接消费这份日志。

**验收**：重导一份公专场景题卷 → 不再产生单题组；真复合题（多小题）正常建组且成员数 ≥2。

### Wave 4 —— 存量数据修复脚本

新建 **1 个**脚本：`backend/scripts/fix_composite_groups_r8.py`（与既有 `backfill_shenlun_groups.py` 同目录同风格）

处理项（**全部只读检测 + 打印预案，默认 dry-run，加 `--apply` 才写库**）：

| 项 | 依据 | 动作 |
|---|---|---|
| **组 23、25 垃圾占位符材料** | `（材料待恢复）`+题干，`backfill_shenlun_groups.py:85` 自引入 | **优先处理**：置空或删除这两行 `shared_content`，防成员恢复后把题干当材料展示 |
| 组 11 唯一真空壳组（材料被前文污染） | 0 成员 + 首行是悬空判断题残句 | 打印清单，人工确认后删除（**不自动删**） |
| 组 24 题号 1-4 重复（8 在用题实为 4 题×2） | 实测 | 打印清单，确认后软删其中一批 |
| 组 22 材料（7656 字真实材料）成员全软删 | 实测 | **不删材料**，材料是真实语料；待对应题目恢复或重导后自动挂组 |
| 2 题未解析 `[IMAGE:` 标记 | 实测 | 走 `sanitize_image_placeholders` 重新解析 |
| 14 组重复内容（全公专同卷 x2） | 实测 | **只报告不删除**，交由你决策 |

**为什么不自动删空壳组**：题组是业务数据，自动删除有误伤风险；打印清单让你拍板更安全。
**为什么垃圾占位符要优先清**：它是假数据，且一旦软删回滚就会把题干当材料展示给用户，属于会扩散的错误。

**验收**：dry-run 输出清单与 §1.1 实测数一致（1 真空壳 / 2 垃圾占位符 / 1 题号重复组 / 14 重复题组 / 2 残留标记）。

### Wave 5 —— 教师端题目管理展示材料

**这是 P1 用户可见的最后一段。** Wave 1 修好后，申论题能拿到 group_id，`showDetail()` 就会自动请求并显示材料 —— **可能无需改前端即可生效**。

因此 Wave 5 分两步走：

## 10. 执行结果与诊断修正（2026-10-14 实施后回写）

方案已获批并执行 W1~W4（commit `c6871f5`）。执行过程中的实测**推翻了两处原始诊断**，
本节如实记录，不改写上文原文。

### 修正 A —— 公专「单题组」的材料等于题干，是既有设计而非垃圾数据

**原始诊断（§1.2 根因 5）**：公专 21 个单题组是 claimed 过滤造成的假关联组。

**实测修正**：W4 脚本检测 `shared_content == 成员题干` 时发现，这 21 个组的
`shared_content` **恰好等于其唯一成员的题干**。对照代码
`_detect_and_link_composite_groups:784` —— `shared_content=q.get('question_content')`，
即**「材料」本就取自头题题干**。

对公专情境分析题而言，情境文字就是题干本身，题组材料=题干、单成员属**正确建模**：

| | 公专情境题 | 申论 |
|---|---|---|
| 材料语义 | 情境 = 题干的一部分 | 给定资料，与题干完全无关 |
| 材料=题干是否正常 | **正常** | 退化（材料本该是独立的上万字给定资料） |
| 处置 | 保留 | 需人工确认 |

**对 W3 的影响**：W3 的 `<2` 拦截依然正确且有价值 —— 单成员组会让详情弹窗把
同一段文字（材料 + 题干）显示两遍，且不携带任何额外信息。但它**只拦截新建**，
存量 21 个组保持不动（删除会移除教师端已习惯的题组徽标，属超出批准范围）。

**对 W4 的影响（关键安全边界）**：脚本**必须**只删「带 `（材料待恢复）` 占位符前缀」
的组。若按原始诊断把「材料==成员题干」一并删除，会误删 21 个正常公专组 ——
正是「越修改问题越多」。脚本已收窄删除范围，并在报告第三项写明该边界。
