## 一、各问题根因与证据（代码级）

### P7/P3 轮询超时、匹配不及时（根因已确证）

- **主根因**: `vite.config.ts` watch 范围未忽略 `backend/**`。导入期间后端高频写文件（`backend/data/*.db-wal`、`backend/logs/*.log`、`backend/app/static/questions/*.png`）→ Vite full-reload → 前端轮询 fetch 中断 → 误报超时。
- **证据**: `backend/logs/app.log` 显示 08:53:36 解析完成后 3 分 53 秒后端零请求；08:57:33 文件稳定后 3 个 status 请求全部 0.02s 完成。
- **放大因素**: 前端 `_pollImportStatus`（question_import.vue:787）单次轮询失败零容错，fetchWithRetry 抛错即整体失败。
- 修复 = v1 的 Fix 1（ignore）+ Fix 2（轮询容错）+ Fix 3（超时参数）。

### P1 行测答案 PDF 解析配图不显示

- **断点 a**: `/separate-match`（question_import.py:2454）与 `/separate-match-xingce`（:2769）两个端点**未调用 `_sanitize_preview_images`**，响应里 `[IMAGE:]` 裸 marker 被前端 `convertImageMarkers`（questionRender.js:66-72）剥空。前端主流程虽已重接线到 `/parse`（`_backendSmartMatch` 是死代码），但这两个端点仍可被调用，必须补齐。
- **断点 b（重复导入丢图）**: `_extract_and_save_images`（question_ingest/images.py）在 confirm 落库时会 `os.remove(src_file)` **删除暂存扁平图**；而 `_extract_text_from_pdf` 有 **md5 文本缓存**（text_cache）——同一 PDF 再次导入时缓存命中返回旧 `[IMAGE:...]` marker，但暂存文件已被删除 → sanitize 定位失败 → 图片全灭。
- **断点 c（待验证）**: `ContentCleaner.clean_text` 是否剥离 `[IMAGE:]` marker（实施时先跑验证脚本确认）。
- 修复: F-1/F-2/F-3。

### P5 预览图片完全不展示（合并导入 Word/PDF 主路径）

- **断点 d（主路径）**: 前端合并导入 Word/PDF 后走 `raw_text_preview` + **前端本地解析** `parseRawTextToQuestions`，或直接消费后端 questions——但本地解析路径产生的题目内容**未经后端 sanitize**，`[IMAGE:]` 残留被前端剥空。
- **断点 e**: 前端 `convertImageMarkers` 设计为「后端已 sanitize，残留即真丢图→剥空」，无保底。
- 修复: F-4（后端 /status 与 raw_text_preview 出口统一 sanitize）+ F-5（前端保底策略）。

### P2 Word/PDF/扫描件解析

- **Word**: docx_reader 上一轮已修（表格图标记、qn_re 伪题号）；需真实语料回归确认无新问题。
- **PDF 文本层**: pdf_reader 主干正常（85 套行测实测通过）。
- **扫描件**: 三级回退链（pdfplumber → MinerU → PaddleOCR 子进程）存在，但依赖环境配置：本机 Python 3.13 不支持 PaddleOCR，需 `OCR_PYTHON` 指向 ≤3.12 环境或 MinerU venv 就绪。失败时前端提示不明确。
- 修复: F-6（扫描件失败原因显式化 + 前端可操作提示）。

### P4 单题内容编辑缺失（新功能）

- **现状**: 前端预览页 **0 处** contenteditable/paste/clipboard。`QuestionPreviewList` 组件仅有元数据编辑事件（edit-question 改题型/难度等），**题干/选项/答案/解析内容不可编辑**。图片只有 attach-image（上传文件），不支持剪贴板粘贴。
- 后端已有 attach-image 端点（预览态加图）；文字编辑可纯前端实现（改 state 后随确认入库提交），图片粘贴可复用 attach-image。
- 修复: F-7（预览内容编辑：文字 + 图片粘贴）。

### P6 复合题预览切割（产品形态）

- **现状**: 后端 `_build_preview_groups` 已产出组结构 `[{group_key, material_text, material_length, question_count, questions:[...]}]`（questions 与扁平列表共享引用）。但:
  - 前端 `question_preview_list.vue` 把**全部材料头渲染在列表顶部**，随后**逐题平铺成独立卡片**——材料框与子题卡片分离，子题各自成卡；
  - `previewGroups` 只在 /upload 的 questions 分支赋值（question_import.vue:1043），Excel 简单列表不用它，separate/OCR/本地解析路径**未赋值** → 组预览在主流程中几乎失效；
  - 后端 `/parse` 与 `/separate-match-xingce` 未返回 groups。
- 修复: F-8（后端全路径返回 groups）+ F-9（前端按组渲染：材料 + 组内子题同框）。

## 二、修复方案（9 项，均最小化改动、复用现有机制）

### F-1 两个 separate-match 端点补 sanitize（P1-a）
**文件**: `backend/app/api/v1/question_import.py`
**内容**: `/separate-match`、`/separate-match-xingce` 返回前对 questions 的 content/analysis 调 `_sanitize_preview_images`（复用现有，不新写）。
**思考**: 与 /parse（A-2 已修）同款口径；死代码端点也要正确，防止任何调用方踩坑；改动 2 行级。

### F-2 暂存图不删除 / 缓存与文件一致性（P1-b）
**文件**: `backend/app/services/question_ingest/images.py`（+ 必要时 text_cache 策略）
**内容**: `_extract_and_save_images` 落库后**不再 os.remove 暂存扁平文件**（或改为延迟清理）。评估方案二选一:
- 方案 A（推荐）: 保留暂存文件，靠「暂存目录容量上限 + 按时间清理旧文件」回收（新增一个简单清理函数，挂到现有调度器）。
- 方案 B: text_cache 缓存键加入「暂存文件存在性」，缺失时强制重提取。
**思考**: 方案 A 改动最小、根治重复导入丢图；容量治理放调度器与现有爬虫任务同机制，不新建体系。

### F-3 ContentCleaner 对 marker 的验证与修复（P1-c）
**文件**: `backend/app/services/text_parser.py`
**内容**: 实施时先写 5 分钟验证脚本：`ContentCleaner.clean_text('[IMAGE:a1b2c3d4_5_0] 本题考查…')` 是否保留 marker。若剥离则修复（marker 行豁免清洗），若不剥离则记录结论无需改。
**思考**: 先验证后动手，避免瞎改；豁免规则加注释说明真实案例。

### F-4 /status 的 raw_text_preview 出口 sanitize（P5-d）
**文件**: `backend/app/api/v1/question_import.py`（/status 端点）
**内容**: PREVIEW 返回时，对 `raw_text_preview`（及 legacy `items`）中的 `[IMAGE:]` marker 执行 `sanitize_image_placeholders`（复用 /status 已用的同款逻辑），前端拿到的文本里 marker 已变为 `<img>` 或已剔除。
**思考**: 前端本地解析 `parseRawTextToQuestions` 是**按行切分纯文本**的——实施前必须验证它容忍 `<img>` 标签混入（若不容忍，改为在切分后对每段再做 marker 处理，见 F-5）。此改动让所有走 raw_text_preview 的前端路径天然拿到已解析图片。

### F-5 前端渲染保底（P5-e）
**文件**: `src/utils/questionRender.js`
**内容**: `convertImageMarkers` 在剥空之前，先尝试一次**已知扁平路径**直连: `[IMAGE:{marker}]` → `<img src="/static/questions/{marker}.png">`（仅当 marker 匹配 `^[a-f0-9]+_\d+_\d+$` 形态——这是 docx/PDF 暂存图的确切命名，不是「猜路径」，是「已知约定」）。
**思考**: 问题 3 注释强调「绝不猜路径」是因为旧规则 URL 与落盘不符；本保底只用与落盘**严格一致**的扁平命名，且 onerror 兜底已有。既保留 sanitize 主路径，又给前端本地解析/老数据一条生路。安全: 白名单形态 + onerror 占位图。

### F-6 扫描件失败原因显式化（P2）
**文件**: `backend/app/services/question_ingest/pdf_reader.py` + 前端错误提示
**内容**:
- 后端: OCR 失败时 error_messages 写入**具体原因**（MinerU 未启用 / OCR_PYTHON 不存在或版本不兼容 / OCR 超时 N 秒 / 页数超上限），不再笼统「解析失败」。
- 前端: FAILED 状态展示可操作建议（如「该 PDF 为扫描件且 OCR 未配置，请联系管理员启用 MinerU 或拆分后重试」）。
**思考**: 后端异常已有落库通道（error_messages），只补文案；前端已渲染 error 字段，只改展示文案。零新机制。

### F-7 预览单题内容编辑（P4，新功能）
**文件**: `.vtj/vue/question_preview_list.vue`（script 部分）+ `question_import.vue`（script 部分）+ 后端复用 attach-image
**内容**（分两期，先文字后图片）:
- **文字编辑**: 每题卡片加「编辑内容」入口，弹层内 textarea 编辑题干/选项/答案/解析；保存时更新 state 中该题字段（确认入库随 payload 提交，后端 /batch-parsed、/confirm 无需改——它们本就读 items）。
- **图片粘贴**: 编辑弹层监听 paste 事件，剪贴板图片 → blob → FormData → 复用 `/records/{id}/attach-image` 端点 → 返回 URL 插入内容。
**思考**: 纯前端 state 编辑 + 复用已有 attach-image 端点 = 后端零改动；粘贴图片走既有 `_extract_and_save_images` 的安全管线（尺寸/类型/SSRF 防护全复用）；模板弹层属 UI 结构——**弹层布局需在 VTJ 设计器完成或经用户授权后改 .vue**，script 逻辑可先落地。

### F-8 后端全路径返回 groups（P6）
**文件**: `backend/app/api/v1/question_import.py`
**内容**: `/parse`（unified_parse）与 `/separate-match-xingce` 响应补 `groups` 字段（复用 `_build_preview_groups`，Word/PDF 上传路径已用）。
**思考**: 同一函数三处复用，不新建逻辑；前端 `previewGroups` 赋值点随之补齐（separate/OCR/本地解析路径）。

### F-9 前端复合题同框渲染（P6）
**文件**: `.vtj/vue/question_preview_list.vue`
**内容**: 渲染改为「按组分区」: 有 groups 时，每个组渲染一个容器（组头材料 + 组内全部子题卡片依次排列在**同一个框**内）；无组的题保持现状平铺。
**思考**: 数据已就绪（groups[].questions 与扁平列表共享引用，script 里加 computed 分区即可）；**模板结构改动属设计器领地**——需用户在 VTJ 设计器（http://localhost:9527/__vtj__/）拖拽完成，或经用户明确授权后由我改 .vue 文件（该文件非 raw 页面时可行；若是 raw 页面则必须设计器操作，禁止 DSL 同步铁律不变）。

## 七、MinerU / PaddleOCR 环境实测结论（2026-10-13）

| 项 | 实测结果 |

```
MINERU_ENABLED=True
MINERU_PYTHON=C:\mineru_env\Scripts\python.exe
MINERU_TIMEOUT=600
MINERU_MODEL_SOURCE=modelscope
OCR_PYTHON=D:\ocr-env\Scripts\python.exe
```
长期稳定性已由既有封装保证（子进程隔离 + GPU 串行锁 60s 排队上限 + 健康检查 TTL 缓存 + 失败一律回退 PaddleOCR 契约）。剩余风险（MinerU 输出空、GPU 排队超时、模型网络依赖）由 F-6 的失败原因显式化覆盖。
