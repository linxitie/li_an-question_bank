## §1 三条地基（其余全部由此派生）

1. **事实先行**：任何数量/路径/行为断言，必须来自 `事实基线` 或现场命令输出 + 文件:行号。旧文档的数字一律当线索，不当事实（基线 §2 列了 8 项错值，其中 2 项高风险）。
2. **红线不可协商**：R1–R12 是物理约束，不是风格建议。触及即停手报告，不"顺手做"。
3. **一分支一任务、一逻辑一提交、一改一验证**：任何"顺手"都记入反模式（A4/A12/A22）。

## §2 七条设计原则

| # | 原则 | 含义 | 违反的可观测症状 |
|---|---|---|---|
| P1 | **事实先行** | 断言附命令/行号；不确定写「置信度 + 验证方式」 | 出现"大约/应该/我记得" |
| P2 | **不做什么优先** | 方案必须先写排除项，再写做法 | 方案越写越大、开始"顺便重构" |
| P3 | **单一事实来源** | 同一口径只写一处（如计数口径、颜色 token、可见性 WHERE） | 三端各写一套、两处常量漂移 |
| P4 | **先量后改** | 优化必须先有基线数字，改完复量 | "我感觉快了" |
| P5 | **契约只增不改** | 端点/字段/事件类型 add-only，破坏性变更一律拦 | 老客户端解析失败 |
| P6 | **复用优于新建** | 已有开源实现或内部机制先评估（CTC-11）；平板复用手机页（R12） | 同类组件第 3 份副本 |
| P7 | **证据即完成** | 没有命令输出的"完成"判未完成；未跑的层标「未验证」 | "应该可以了" |

## §3 九角色矩阵（角色 × dsh 形态 × 真实技能 × 否决权）

> **事实**：本机 harness 提供 `subagent` / `subagent_fork` / `workflow` / `send_message`，**没有独立 agent-team 服务**。九角色的落地形态是「主 agent 顺序换帽 + subagent 并行 + workflow 大扇出」。

| 代号 | 角色 | dsh 形态 | 真实技能（仓库 `.agents/skills/` 或会话插件） | 否决权 |
|---|---|---|---|---|
| **ARCH** | 系统架构师 | 主 agent 换帽（Lead） | `codebase-design`、`decision-mapping`、`brainstorming`(插件)、`improve-codebase-architecture` | 跨域直连、新建第 44 个 API 模块、把重构塞进功能任务 |
| **PM** | 项目管理师 | 主 agent 换帽 | `li-an-workflow`(**强制**)、`writing-plans`(插件)、`executing-plans`(插件)、`to-prd`、`to-issues`、`triage` | 无验收命令的任务行、一分支两件事、CTA/预算超档 |
| **DATA** | 数据建模师 | subagent / 换帽 | `domain-modeling`、`ubiquitous-language`、`diagnose` | 违反 R10、无迁移加字段、三端各写一套 WHERE |
| **BE** | 后端建模师 | subagent / 换帽 | `tdd`(仓库) 或 `test-driven-development`(插件)、`implement` | 裸 SQL 拼接、跨域 import api 层、整读 models.py |
| **API** | 接口建模师 | subagent / 换帽 | `design-an-interface`、`request-refactor-plan` | 未批准的端点增删改（R11） |
| **FE** | 前端建模师 | subagent / 换帽 | `li-an-workflow` §5、`prototype`、`design-taste-frontend`(插件，仅纯手写页 UI)、`diagnose-windows-sandbox-acl`(环境) | 直改 `<template>`（R3）、raw 页同步（R2）、复制平板页（R12） |
| **SEC** | 网络安全检测与保障员 | subagent（**只读**） | `review`、`git-guardrails-claude-code`、`check_secrets.py` | 密钥入文档/源码/提交、IDOR、越权 |
| **QA** | 系统测试与问题反馈员 | subagent / 换帽 | `verification-before-completion`(插件)、`qa`、`systematic-debugging`(插件)、`diagnosing-bugs` | 无证据的"完成"、用一层测试冒充全量 |
| **DOC** | 归档与索引官 | subagent / 换帽 | `handoff`、`obsidian-vault`、`zoom-out` | 只展示不落盘、索引不更新 |

**仲裁链**：`SEC > API > ARCH > PM > DATA > BE ≈ FE > QA > DOC`。
**跨角色工具**：`using-superpowers`、`subagent-driven-development`、`dispatching-parallel-agents`、`resolving-merge-conflicts`、`using-git-worktrees`、`finishing-a-development-branch`。

**换帽三要素**（缺一即判角色混用，本轮作废重来）：
1. 声明头（§5.1）；
2. Handoff 单（§9.4，≤10 行）；
3. 同一段回复**只能戴一顶帽子**——不能在同一段里又设计、又改代码、又宣布测试通过。

## §4 模式分层与模型路由（标准 / 创造 / PTC）

| 模式 | 何时用 | 路由策略 | 本模式中的位置 | 硬纪律 |
|---|---|---|---|---|
| **标准** | 常规 CRUD、契约比对、测试、归档、文档 | 本地/低成本优先，云端兜底；长会话靠 compaction | 默认，全状态 | 不为常规任务升级模型 |
| **创造** | 架构创新、组卷/判题算法、新页面结构 | 高 reasoning effort + 多提供商 fallback | 仅设计态 D2 | 产出必须当轮归档，否则不许用 |
| **PTC** | 批量语料清洗、题图索引、统计、压测 | 本地沙箱执行，**只回流结论** | 测试态/优化态的批量处理 | 660MB 语料 / 静态资源**禁入上下文**（F14） |

**诚实边界（必须随方案一起声明）**：本仓库当前**没有** DeepInfer 适配器配置文件（无 `.dsh/`、无 `cordis.patch.yml`，见 F10）。因此：
- 模式只定义**路由契约**（上表）；具体适配器落地属于独立任务（缺口 G12），不得在功能任务里顺手写。
- 任何"已接入 DeepInfer / 已走 PTC"的声称，必须给出**配置路径 + 一次实际调用的日志片段**，否则记为未验证（P7）。

## §5 Token 零浪费契约

> **诚实界定**：「token 使用率 100%」物理上不可度量。本模式把它操作化为 **5 个可审计零指标 + 3 张账单**；全部为 0 即等价于"零无效 token"。

### 5.1 五个零指标（Z1–Z5）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **Z1 重复读=0** | 同一文件同一行区间一次任务内不读第二遍（除非内容已变，且须注明） | LOAD 账单 |
| **Z2 未验证断言=0** | 每条事实断言附命令/行号，或标「置信度 + 验证方式」 | 断言清单 |
| **Z3 返工=0** | 因"没读够就写"导致的二次修改 = 0 | `git diff` 次数 |
| **Z4 超预算=0** | 单轮装载 ≤ 预算档上限 | LOAD 账单 |
| **Z5 归档遗漏=0** | 方案/计划/报告 100% 落盘 + 索引更新 | 归档清单 |

### 5.2 预算分档

| 档 | 场景 | 装载上限 | 允许写文件 | 强制产物 |
|---|---|---|---|---|
| **T0** | 问答 / 查证 / 解释 | ≤8k | 0 | 结论 + 取证 |
| **T1** | 单文件改动 / 单点查证 / 契约比对 | ≤25k | ≤2 | 改动 + 命令输出 |
| **T2** | 3–5 文件 / 跨层 | ≤60k | ≤5 | CTC-11 + 计划 + 测试 |
| **T3** | 模块级 / 十域级 | 分 2 段，每段 ≤60k | 分段提交 | 分段计划 + 每段验收 |

超档即停：先出「降档方案」（拆任务 / 只读摘要 / 委派 subagent），PM 确认后继续。**同一轮内既超档又"继续试试"= A12**。

### 5.3 装载协议（四步，禁跳步）

1. **定位**：`grep`/`glob` 得「文件:行号」清单，**不读内容**。
2. **切片**：`read offset/limit` 只取 30–120 行；长文件两段夹逼。
3. **摘要代理**：>500 行文件、>1MB 数据，先用脚本算统计（行数/类数/键数/差集），只把统计入上下文。
4. **记账**：回帖列 `[LOAD]` 清单。

### 5.4 明文禁用清单

- ❌ 全库 `tree` / `Get-ChildItem -Recurse` 全仓列举
- ❌ 读取 `题库/`（F14）、`backend/app/static/` 的**文件内容**
- ❌ 原样贴回 pytest/门禁全量输出（只贴尾部 ≤20 行 + 退出码）
- ❌ 重复读同一段落后"再确认一遍"
- ❌ "为了保险"预读 10 个不相关文件
- ❌ 读 `docs/archive/`、`.omo/`、`.sisyphus/` 的历史计划全文（用 grep 定位片段即可）

### 5.5 三张账单（回复里随产物交付）

```
# LOAD 账单（每轮）
[LOAD] <文件>:<行区间> ×N | 预算 T2 | 已用 ~xx k | Z1 重复读 0

# TOOL 账单（涉及工具链时）
[TOOL] grep×3 | read×5 | pwsh×4 | mcp:vtj_check_consistency×1 | 失败重试 0

# OUTPUT 账单（收尾）
[OUT] 新增/修改 <n> 文件 | 归档 <n> 份 | 未验证项 <n> 条
```

### 5.6 前缀稳定性（缓存友好）

固定顺序：**角色声明头 → 事实基线引用 → 任务书 → 可变内容**。稳定前缀命中 prompt cache，把固定开销摊薄；反之每轮重排段落 = 缓存全失效。

### 5.7 省 token 的五个固定手法

1. **一次取证多处复用**：一个 `grep` 结果同时喂 ARCH/API/QA，不重复取。
2. **热加载件**：日常任务只读角色卡（≤8KB）+ 作战卡（≤5KB），不读总纲。
3. **门禁即证据**：跑一次 `gate_all.py --quick` 就够交差，不再"读代码确认一遍"。
4. **subagent 隔离**：≥6 个独立文件的只读审计用 `workflow` 扇出，保护主上下文。
5. **结论回流**：PTC/脚本只回统计数字，不回原始数据。

## §6 工作流 Q0–Q6 + 三态管线

### 6.1 Q0–Q6（主流程）

| 阶段 | 主导 | 动作 | 退出条件（可命令验证） | 可跳 |
|---|---|---|---|---|
| **Q0** | PM | 复述需求、划边界、定预算、建/切子分支 | 用户确认范围 + `git rev-parse --abbrev-ref HEAD` 输出 | 否 |
| **Q1** | ARCH+DATA | 事实测绘（受影响端点/表/页面/测试/事件） | 影响文件清单（路径:行号） | 小改可裁剪 |

| **Q6** | DOC | 归档三件事 + 只向父域合并 | 索引已更新 + 未覆盖项已列 | 否 |

### 6.2 三态管线（命令级）

| 态 | 步骤 | 产物 |
|---|---|---|
| **设计态** | D0 复述/分支 → D1 测绘 → D2 方案+CTC-11 → D3 契约/迁移/安全 → D4 任务表 → D5 逐文件实施 → D6 门禁+归档 | spec + plan + 附件 |
| **测试态** | T0 选矩阵 → T1 契约/边界/数据 → T2 域测+前端 spec → T3 页面+三端 → T4 事件幂等 → T5 报告归档 | 验收报告 |

> 优化态铁律：**没有基线数字就不叫优化**（P4）。复量必须同一命令、同一数据。

### 6.3 CTC-11（Q2 放行闸，逐条作答，缺一不放行）

| CTC-2 | 安全问题：SQL 注入 / XSS / 越权？ | 参数化证据 / `Depends(...)` / 输出转义点 |
| CTC-3 | 后期运维便利吗？ | 迁移可回滚、开关/日志位置 |

| CTC-6 | 后端字段够吗？迁移考虑了吗？ | 字段表 + 迁移 SQL + 回滚 SQL |

## §7 分支拓扑

### 7.1 模型（与用户 2026-10-26 规则等价，但路径用 `-`）

```
main                         稳定基线，只接模块工作域
└── feat/<模块>                模块工作域（新工作域用 feat/ 前缀）
    └── feat/<模块>-<子任务>     子分支，一分支一任务
```

**为什么用 `-` 而不是 `/`**：Git 不允许 `feature/forum` 与 `feature/forum/x` 同时作为 ref（会报 "cannot lock ref"）。本仓库 `feature/forum` 已存在，所以子分支必须写 `feature/forum-personalization` 这种连字符形式；`feat/<模块>-<子任务>` 是同一语义的安全写法（v1 §8.2 已于 2026-10-25 统一为此）。

### 7.2 硬约束

| # | 约束 |
|---|---|
| B1 | 子分支**禁止**对 `main` 的任何合并/PR；只能对父域 `feat/<模块>` |
| B2 | 一子分支一任务；混入无关改动 = 打回 |
| B3 | 提交前缀只允许 `feat/fix/test/refactor/docs/chore` |
| B4 | 提交前必须跑改动域测试；失败先修复，不提交 |
| B5 | 合并顺序：孙 → 子 → 模块域 → main，永不跳层 |
| B6 | `git add -A` 禁用；逐文件 `git add <精确路径>` |
| B7 | 大件与密钥不进提交（`题库/`、`static/` 内容、`.env`、`*.bak_*`、`.superpowers/`） |
| B8 | 开工先同步父域：`git fetch origin` + `git pull --ff-only`（父域存在上游时） |
| B9 | **无 upstream 时不许假装 pull 成功**：先 `git rev-parse --abbrev-ref --symbolic-full-name @{u}` 确认；没有就如实报「本地分支未推送，无法 pull」，由用户决定是否 push |

### 7.3 当前仓库现状（例外，F16/F2）

- 存在**两套命名**：`feature/*`（旧，论坛/工具链工作在用）与 `feat/*`（新，教师端工作在用，只在远端）。
- 当前分支 `feature/forum-personalization` **没有 upstream**（`origin/feature/forum` 不存在）。按 B9：开工按本地为准并把"未 push"写进报告，不伪造同步。
- 历史同名分支 `feat/forum-personalization` 停在 `1d897d1`，与当前分支无关——**不要在上面继续开发**，也不要在报告里混用两个名字。

## §8 门禁与验收矩阵

| 后端 API 逻辑 | `python backend/scripts/gates/gate_l4_api_contract.py` + `check_module_boundary.py` | `cd backend; python -m pytest tests/<域> -q` | 端点数 = **343 条路由条目**（或已批准增量） |
| 数据模型/迁移 | `gate_l1g_field_fingerprint.py` | 域测 + 迁移 dry-run | `db_tables.json` 差异可解释；回滚 SQL |
| 前端 `.vtj` 页面 | `gate_l5_frontend_contract.py` | `npx vitest run <spec>` | `vtj_check_consistency` 的 `versionMatch=true`；**不执行** `vtj_sync_vue_to_dsl`（raw 页，F6） |
| 手写 SFC 页面 | — | `npx vitest run src/...` + Playwright | 浏览器断言（选择器 + 计算样式），不是"看着像" |
| 解析/导入 | `gate_l1_parser.py` / `gate_l1h_composite_material.py` / `gate_l2_matching.py` / `gate_l3_ingest.py` | 对应 tests | 材料指纹与基线一致 |
| 红线/凭据 | `gate_l0_redlines.py` + `check_secrets.py` | — | 无密钥入库 |
| 全量提交前 | `python backend/scripts/gates/gate_all.py --quick` | `npm run typecheck`（基线 63 条 error / 9 文件，F15） + `npx vitest run`（28 files / 362 tests） | 三条数字不劣化 |

**三层汇报口径**：`PASS/FAIL` + `命令 | 退出码 | 关键输出 ≤20 行` + `未覆盖项`。**全量 pytest 在本机会挂起**（历史实测），需要全量时用单文件超时扫：`python -m pytest tests -q --timeout=90`（或分批），并如实标注 HANG。

## §9 交付物模板

### 9.1 方案（spec）

```
# <主题> 设计方案 v<n>
## 1 问题与边界（含「不做什么」）
## 2 事实证据（表：事实 / 实测值 / 取证命令 → 引用事实基线编号）
## 3 方案对比（≥2，含代价）
## 4 选定方案（分层 / 契约 / 数据）
## 5 影响面（端点 / 表 / 页面 / 测试 / 事件）
## 6 验收标准（每条可命令验证）
## 7 风险与回滚
## 8 CTC-11 作答
```

### 9.2 实施计划（plan）

```
## Global Constraints（红线 + 命名 + 备份方式）
## 任务表：ID | 动作 | 文件 | 验收命令 | 依赖 | 预算 | 角色
## 提交拆分（每提交一句话 + 文件清单）
## 每阶段验证命令
```

### 9.3 验收报告

```
## 结论：PASS / FAIL / PARTIAL
## 证据：命令 | 退出码 | 关键输出（≤20 行）
## 与基线对比（vitest / typecheck / pytest / 门禁）
## 未验证项与原因
## 风险与回滚
## 归档路径
```

### 9.4 Handoff 单（换帽必填，≤10 行）

```
FROM: <代号> → TO: <代号>   MODULE: <id>
已定：<3 行内>
未定：<3 行内>
风险：<1–2 行>
证据：<命令/文件:行号>
```

### 9.5 归档三件事（DOC 强制）

1. 写权威位置 `docs/plans/`（或 `docs/superpowers/{specs,plans}/`）；
2. 写副本 `solve_problems_files/`（该目录仍存在时）；
3. 更新 `docs/README.md` 索引（+ 副本目录的 README）。
