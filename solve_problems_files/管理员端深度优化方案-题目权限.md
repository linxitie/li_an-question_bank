### 问题 2：权限管理

**核心根因：权限配置「写入成功但从未被读取」**

权限编辑的完整链路断裂：

```
前端 admin_permissions.vue「保存修改」
  → PUT /api/admin/permissions
  → update_permissions() 写入 SysConfig 的 role_permissions_{role} 键  ✅ 写入成功
  → 前端提示"更新成功"、日志记录成功
  ↓
运行时权限校验链（完全无视 SysConfig）：
  get_user_permissions(user)  ← 只读硬编码 ROLE_PERMISSIONS 字典 ❌
    → JWT 登录时生成 permissions（硬编码）❌
    → check_permission / require_permission（硬编码）❌
    → 前端路由 meta.roles（角色判断，非细粒度权限）❌
```

**结论**：编辑权限后，后端运行时、JWT、前端路由守卫**全部仍用硬编码 `ROLE_PERMISSIONS`**，配置只是"存了但没用"。所以学生提权「管理用户」「导入题目」后，学生端既没有对应前端模块（路由不存在），后端接口也用 `role_level`/`user_type` 硬判断而非 `check_permission`。

## 二、方案设计

### 问题 1：题目管理

#### 1.1 题型筛选 + 判定机制统一

**目标**：新增「题型」筛选（全部类型/单选题/多选题/判断题/论述题），题型判定公用教师端 `typeDisplayName` 机制。

**修复**：
- 前端 `admin_questions.vue` 筛选区补「题型」下拉，`load()` 加 `type_id` 参数。
- 后端 `list_all_questions` 补 `type_id: Optional[int]` 查询参数。
- **题型判定单一事实来源**：教师端已有 `typeDisplayName(typeInfo)`（以 `type_name` 字符串为唯一依据），前端管理员端复用同一函数。题型列表以 `question_type` 表实际存在的 `type_name` 为准（单选/多选/判断/论述），**不硬编码"写作题/简述题"**（数据库无此题型，避免制造不存在的筛选项）。

**为什么这样改**：
- 复用教师端判定逻辑，保证三端题型分类一致，不各写一套。
- 以 `type_name` 字符串而非 `type_id` 数字为事实来源，规避 `type_id=1/3` 都叫"单选题"的错位问题。

#### 1.2 乱码修复

**根因**：上轮 PowerShell 测试污染了题目 10。

**修复**：从备份库 `data/backups/pre_cleanup_20260824_163443/question_bank.db` 恢复题目 10 的 `question_content`、`answer_analysis`、`answer`（备份实测有完整数据）。

**为什么这样改**：备份是干净数据源，直接恢复最可靠，不重新生成内容。

**安全/运维考量**：写幂等数据修复脚本，可重复执行，`--dry-run` 预览。

#### 1.3 字体颜色

**修复**：`admin_questions.vue` 的 `.content-link` 颜色 `#409eff` → `#1a2b5f`（深色），难度星级、统计值等蓝色也统一为深色系，保证可读性。

#### 1.4 来源识别

**修复**：
- 后端 `list_all_questions` 的 `source` 字段：null 与空串统一返回 `""`。
- 前端 `q.source || '-'` 已能处理，但需补：来源为空时显示「未标注」，有值时正常显示。

### 问题 2：权限管理

#### 2.1 权限运行时生效（核心）

**目标**：编辑权限后，后端 `get_user_permissions` 能读到 SysConfig 里的自定义配置，真正生效。

**修复**：
- 后端 `security.py` 的 `get_user_permissions(user)` 改为：
  1. 先查 `SysConfig` 的 `role_permissions_{role}` 键。
  2. 若有自定义配置，解析 JSON 作为权限列表返回。
  3. 若无（未编辑过），回退到硬编码 `ROLE_PERMISSIONS` 默认值。

**为什么这样改**：
- 保持向后兼容：未编辑过的角色用默认权限，编辑过的角色用自定义。
- 单一读取入口：所有权限校验（check_permission/require_permission/JWT 生成）都走 `get_user_permissions`，改一处即可全局生效。

**安全考量**：
- `get_user_permissions` 需要 DB session，但当前函数签名无 `db` 参数。需注意：`security.py` 被多处调用（含无 db 上下文场景）。方案：新增 `get_user_permissions_with_db(user, db)`，`check_permission` 等带 db 的地方用新函数；`get_user_permissions` 保持纯函数（无 db）作为默认回退。避免在无 db 场景（如 token 解析）崩溃。

#### 2.2 三端权限体现（功能模块映射）

**目标**：提权后，学生端/教师端能出现对应功能模块。

**现状**：前端路由 `meta.roles` 用角色（student/teacher/admin）判断，学生端根本没有「用户管理」「导入题目」等页面组件。

**方案（需你决策，见决策点 2）**：

**方案 A（推荐，改动最小）**：**后端接口级权限 + 前端菜单按权限动态显示**。
- 后端：已有 `require_permission`/`check_permission` 装饰器，将「用户管理」「导入题目」等敏感接口从 `require_admin` 改为 `require_permission(Permission.USER_MANAGE)` 等。
- 前端：学生端/教师端顶部导航菜单按「当前用户 permissions 列表」动态渲染（JWT 已含 permissions），有权限才显示对应入口。
- 但学生端/教师端**没有**「用户管理」「导入题目」的前端页面组件，需为这些角色补充对应页面（或复用管理员端页面）。

**方案 B（更大改动）**：三端统一菜单渲染系统，根据 permissions 动态生成导航，并为学生/教师补全被提权后可见的页面组件。

**为什么需要你决策**：这涉及"学生端是否真的要新增用户管理/导入题目的完整页面"，属于产品功能范围决策，而非纯技术修复。
