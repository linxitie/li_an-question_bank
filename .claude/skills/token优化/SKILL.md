# DeepSeek 缓存命中优化与 Token 降本方案

## 1. 核心机制与原则
DeepSeek 的上下文缓存（Context Caching）是服务端自动触发的机制，核心逻辑是**“前缀字符串绝对匹配”**。只要多次请求的 Prompt 前缀完全一致，命中部分即按极低折扣价计费。

### 1.1 缓存落盘与命中规则
- **请求结束位置落盘**：每次请求的用户输入结束位置与模型输出结束位置，会产生独立的缓存单元。
- **公共前缀检测落盘**：系统检测到多次请求存在公共前缀时，会主动将其作为独立单元落盘，大幅提升命中率。
- **固定间隔落盘**：针对超长输入/输出，系统按固定 Token 间隔截取缓存单元，避免长文本无法被缓存。

### 1.2 核心铁律
**Cache-first 原则**：系统提示词前缀（Base Prompt + Tools + Memory）在多轮对话中必须保持**字节级稳定（Byte-stable）**。中途绝不可修改前缀，有变化的内容必须全部塞到 Prompt 的末尾。

## 2. 代码与架构层面的实操规范

### 2.1 严格隔离动态与静态内容
- **固定 System Prompt**：将长篇系统指令、Few-shot 示例放在对话最前面，保持前缀绝对一致。
- **禁止动态时间戳**：绝不要在 System Prompt 中拼接如 `当前时间：2026-08-17 10:00:00` 这种每秒都在变的字符串，这会导致整个长上下文缓存瞬间失效。请将动态信息放在 User Message 中。
- **按需加载技能（Skills）**：Skill 只将“名字+描述”的索引塞进前缀，正文内容在用到时才加载，绝不进入 Prefix。

### 2.2 输入 Token 极致精简
在发送请求前，编写预处理函数剔除无效 Token，积少成多：
- 去除首尾空白、多余换行、重复空格。
- 删除 HTML 标签、Markdown 格式符，仅保留纯文本。
- 统一数字、日期格式，避免冗余表达。
- 长列表使用缩写或符号代替文字描述。

### 2.3 监控与验证
在 API 返回的 `usage` 字段中，必须监控以下两个指标以评估优化效果：
- `prompt_cache_hit_tokens`：本次请求输入中缓存命中的 Tokens 数。
- `prompt_cache_miss_tokens`：本次请求输入中缓存未命中的 Tokens 数。

## 3. 进阶降本与调度策略

### 3.1 智能模型路由（Router）
拒绝无脑调用高配模型，根据任务复杂度动态分发：
- **Flash 模型**：处理意图识别、JSON 格式化、简单问答、基础代码改写等。
- **Pro 模型**：处理复杂逻辑推理、长代码生成、深度分析等。

### 3.2 错峰调度架构
针对 DeepSeek 的峰谷定价机制，引入消息队列（如 Redis/RabbitMQ）进行延迟调度：
- **实时刚需任务**（用户在线问答、实时调试）：正常调用，依靠模型降级控成本。
- **可延迟任务**（批量文档摘要、数据清洗、离线代码审查）：推入消息队列，集中调度至夜间空闲时段（18:00后、凌晨）或周末执行，直接节省一半费用。

### 3.3 本地结果缓存
对于高频重复的问答场景，使用 Redis 实现问答级缓存。基于对话内容和模型生成唯一 Hash Key，相同问题直接返回结果，完全跳过 API 调用。
