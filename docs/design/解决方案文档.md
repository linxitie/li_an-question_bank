## 三、详细修复方案

### 3.1 问题一：错题集版本不一致

#### 3.1.1 根因分析

VTJ `@vtj/renderer` 在 dev 模式下执行版本校验流程：
```
1. 加载 .vtj/files/wrong_questions.json → 提取 __VERSION__
2. 渲染 .vtj/vue/wrong_questions.vue → 提取 useProvider({version})
3. 比较两者 → 不一致则抛出 "[ WrongQuestionSet ] 组件源码版本与运行时版本不一致"
```

当前源码版本一致（`1785385300000`），但浏览器仍报错，可能原因：
1. **Vite 预构建缓存**（`node_modules/.vite/`）中保留了旧版 DSL 转译产物
2. **浏览器 IndexedDB**（VTJ LocalService 使用）中缓存了旧版 DSL
3. **浏览器硬缓存**未刷新

#### 3.1.2 修复步骤

**步骤 1**：提升 `wrong_questions.vue` 和 `wrong_questions.json` 的版本号至新时间戳 `1785750000000`，强制 VTJ 重新加载。

**步骤 2**：清理 Vite 缓存：
```powershell
Remove-Item -Recurse -Force "d:\砺安题库\砺安题库\node_modules\.vite" -ErrorAction SilentlyContinue
```

**步骤 3**：重启前端开发服务器，浏览器硬刷新（Ctrl+Shift+R）并清理浏览器缓存。

#### 3.1.3 多角度思考

| 维度 | 评估 |
|------|------|
| **为什么这样写** | 主动提升版本号是 VTJ 官方推荐的"强制刷新 DSL"机制，比单纯清缓存更彻底 |
| **好处** | 一次修复彻底，避免反复出现版本不一致 |
| **安全风险** | 无，仅修改字符串常量 |
| **运维便利** | 版本号采用时间戳，便于追踪修改时间；统一格式便于审计 |
| **文件正确性** | 必须同时修改 .vue 和 .json，缺一不可 |
| **预期效果** | 浏览器加载新版 DSL，版本校验通过，错误消失 |

### 3.3 问题三：收藏模块 favorites.vue 修复

#### 3.3.1 现状

`favorites.vue` 存在 4 个问题：

| 行号 | 问题 | 严重性 |

| 140 | `import { Star } from '@element-plus/icons-vue'` —— 错误图标源 | 高 |

#### 3.3.2 修复步骤

**步骤 1**：修正图标导入（第 140 行）：
```javascript
// 修改前
import { Star } from '@element-plus/icons-vue';

// 修改后
import { Star } from '@vtj/icons';
import { XIcon } from '@vtj/ui';
```

**步骤 2**：注册 XIcon 组件（第 145 行）：
```javascript
// 修改前
components: { NavBar },

// 修改后
components: { NavBar, XIcon },
```

**步骤 3**：修正 `viewNewsDetail` 中的 `fetch` 调用（第 235 行）：
```javascript
// 修改前
const res = await fetch('/api/news/' + item.news_id);

// 修改后
const res = await window.__VTJ_AUTH__.apiFetch('/api/news/' + item.news_id, { headers: this.getJsonHeaders() });
```

**步骤 4**：同步提升 `favorites.vue` 和 `favorites.json` 的 `__VERSION__` 至 `1785750000002`。

#### 3.3.3 多角度思考

| 维度 | 评估 |

| **为什么这样写** | 严格遵循 VTJ.md 第 3.2 节：XIcon 必须从 @vtj/ui 导入；图标必须从 @vtj/icons 导入；前后端通信必须使用 apiFetch |
| **好处** | ① 统一图标源，避免混用 element-plus 与 vtj/icons 造成视觉不一致；② XIcon 注册后模板才能渲染；③ apiFetch 保证认证头注入，避免 401 错误 |
| **安全风险** | 修复了认证绕过风险（fetch → apiFetch） |
| **运维便利** | 与 notes.vue、wrong_questions.vue 保持一致的组件注册模式，便于统一维护 |
| **文件正确性** | 修改 favorites.vue 是正确的，因为问题代码在此文件中 |
| **预期效果** | /page/favorites 正常渲染 favorites.vue，显示收藏列表，交互功能正常 |

## 七、强化方案（用户已确认采用完整强化方案）

经深度反思，原方案仅解决眼前显示问题，在健壮性/稳定性/持久性上存在不足。经用户确认，补充以下强化措施：

### 7.1 强化项清单

| 序号 | 强化项 | 类型 | 目标维度 |
|------|--------|------|----------|
| S1 | 版本号自动同步脚本 `scripts/sync_vtj_version.mjs` | 新增 | 稳定性/持久性 |
| S2 | npm 脚本集成 `sync:vtj-version` + `prebuild` 钩子 | 修改 | 稳定性 |
| S3 | ErrorBoundary 组件 `src/components/VtjErrorBoundary.vue` | 新增 | 健壮性 |
| S4 | App.vue 包裹 ErrorBoundary | 修改 | 健壮性 |
| S5 | API 错误处理工具 `src/utils/api-helpers.ts` | 新增 | 健壮性 |
| S6 | favorites.vue 使用 api-helpers + fav_id 校验 | 修改 | 健壮性 |
| S7 | 模块职责边界文档 `solve_problems_files/模块职责边界.md` | 新增 | 持久性 |

### 7.2 设计原则

1. **不破坏现有逻辑**：`auth.ts` 的 `apiFetch` 保持不变，新增工具为可选增强
2. **不引入循环依赖**：ErrorBoundary 不依赖 ElMessage，使用原生 DOM 提示
3. **向后兼容**：强化项均为新增或可选，不影响现有组件运行
4. **遵循 VTJ 规则**：所有 .vue 文件保持 `defineComponent` + `useProvider` 模式

### 7.3 强化项详细设计

#### S1：版本号自动同步脚本

**文件**：`scripts/sync_vtj_version.mjs`
**作用**：扫描 `.vtj/vue/*.vue` 的 `useProvider({version})`，同步到 `.vtj/files/*.json` 的 `__VERSION__`
**触发**：`npm run sync:vtj-version` 或 `npm run build` 前自动执行
**收益**：从根本上消除"版本不一致"问题

#### S3：ErrorBoundary 组件

**文件**：`src/components/VtjErrorBoundary.vue`
**作用**：捕获子组件渲染错误，显示友好提示，避免整页白屏
**实现**：Vue 3 `onErrorCaptured` + 原生 DOM 提示（无 ElementPlus 依赖）
**收益**：单点故障不影响全局

#### S5：API 错误处理工具

**文件**：`src/utils/api-helpers.ts`
**作用**：封装 `apiFetch`，统一处理 403/500/网络错误，提供 `safeApiCall` 工具函数
**收益**：消除组件内重复 try/catch，统一错误反馈
