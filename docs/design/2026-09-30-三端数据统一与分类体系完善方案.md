> **文档状态**：待审批（本文档仅设计方案，**未实施任何代码改动**）
> **版本**：v1.0　　**日期**：2026-09-29
> **已确认决策**：知识点治理范围＝合并+拆分｜考点层＝全 35 个知识点｜未关联题归类＝先兜底再精确（实测 913 道）

## 摘要

本方案针对前端实测暴露的三类问题给出完整解决方案：

1. **三端数据实时同步** — 教师端导入题目后，手机/平板/电脑端自动同步
2. **分类体系完善** — 细化知识点与考点层级，解决"点击练习缺少题目"
3. **开发期 WebSocket 噪音** — 消除登录时终端反复刷屏

**两个核心结论**：

- **无需数据迁移**：手机端/平板端是无后端的纯前端工程，三端本就共用 `question_bank.db`
- **无需新建分类机制**：项目已有 **896 行专业分类器** `question_classifier.py`，含分级加权算法与置信度阈值，方案为**扩展既有机制**而非另建

### 1.2 分类体系：完整但有缺口

```
question_subject（科目表）    (1,行测)  (3,公专)           ← ❌ 缺 (2,申论)
sub_categories（子科目表）    subject_id=1 → 7 个
                              subject_id=2 → 5 个
                              subject_id=3 → 3 个
knowledge_point（知识点表）  行测 34 / 申论 25 / 公专 35 = 94 个
```

**关于「申论科目缺失」——v1.4 复核结论：这不是缺陷，勿手工补录**

初稿把「科目表无 `subject_id=2`」列为缺陷 A。经代码验证，该判断**错误**：

`question_import.py:68` 定义科目映射，`_get_or_create_subject()`（`:313-334`）在导入时会**查不到就自动创建**：

```python
SUBJECT_NAME_MAP = {'行测': 1, '申论': 2, '公专': 3, '公安专业知识': 3, '其他': 4, '综合': 4}
# :313  先按 SUBJECT_NAME_MAP 查 → :328 查不到则 db.add(QuestionSubject(...)) 创建
```

**推论**：当前无申论题目，故科目表无申论行——这是**正确行为**。教师一旦导入申论题目，申论科目会被自动创建，届时练习页自然出现。

因此**不建议手工 INSERT 申论行**：那会在无题情况下产生一个空科目入口，学生点进去空空如也，反而是缺陷。

| 真正要做的是 | 说明 |
|---|---|
| 验证自动创建链路 | 导入申论题目后，确认科目行、子科目、知识点是否齐备 |
| 依赖方案四的同步 | 申论科目行由导入时创建 → **必须配合广播同步**，否则学生端练习页不会自动出现新科目 |
| 补齐申论知识点关联 | 申论 25 个知识点当前 0 题，导入后需纳入归类流程 |

> ⚠️ 附带风险：`question_bank.subject_id` 虽声明了外键指向 `question_subject`，但 **`PRAGMA foreign_keys = 0`（未强制）**。当前无孤儿记录，但约束形同虚设。若日后 `SUBJECT_NAME_MAP` 新增科目（已含 `'其他':4`/`'综合':4`）而科目行未创建，会静默产生孤儿数据。建议开启外键约束或补建科目行。

**缺陷 B**：2484 道题全部 `subject_id=3`（公专，**已按您确认保留**），已关联的 1572 道题也全挂公专知识点；行测/申论知识点下一题未挂（交叉校验：`kp.subject_id != q.subject_id` 的记录为 0，无错挂）

**缺陷 C**：
```
可下钻取到题：1572 / 2484 (63%)
取不到：       913 / 2484 (37%)   ← 即"点击练习缺少题目"
```

### 1.5 同步机制：框架完备，触发点缺失

| 环节 | 位置 | 状态 |
|---|---|---|
| 前端 WS 客户端 | `src/auth.ts:220-260` | ✅ 含心跳 + 指数退避 |
| 后端管理器 | `websocket.py:98` `broadcast_all` | ✅ |
| 消息类型枚举 | `websocket.py:21` `MessageType` | ⚠️ **枚举内无 `SYNC`**，但含 `IMPORT_COMPLETED` 等导入专用类型 |
| **既有广播范例** | `scheduler.py:29-63` `_broadcast_sync()` | ✅ 新闻/招考已在用，发送字符串 `"sync"` |
| 前端派发 | `src/auth.ts:244` 派发 `__VTJ_SYNC__` | ✅ |
| 前端消费 | `.vtj/vue/mobile_home.vue` | ⚠️ **仅首页 1 处**，练习/题库/答题页均未监听 |
| **题目导入触发广播** | `question_import.py` | ❌ **无任何 broadcast 调用** |
| 题目编辑审计表 | `question_edit_log` | ✅ 存在，330 行，含 `old_data`/`new_data` |

**关键结论**：
1. 既有 `_broadcast_sync()` 发送的是**字符串字面量** `"sync"`（不在 `MessageType` 枚举内），前端按 `msg.type === 'sync'` 松耦合判断——属**约定优于枚举**。本方案改用枚举内既有的 `IMPORT_COMPLETED`，更规范且兼容旧路径。
2. 同步能力目前**只覆盖首页**。要达成"导入后各端同步"，练习/题库/答题页需**新增监听**，这是实打实的工作量，非零成本。
3. `question_knowledge` 表结构（`question_id` + `knowledge_point_id`）**天然支持一题多知识点**，但实测当前仅 1 道题用了多关联，实践中仍是 1:1——归类时需明确是否启用多标签。

### 1.6 WebSocket 噪音：三处根因（已实测）

```
[直连 8000]  OPEN → CLOSE 4001 Authentication required
[经 9527]    OPEN → CLOSE 4001 Authentication required
```
后端与代理**均健康**。ECONNRESET 是**正常关闭在 TCP 层的表现**，被误判为错误。

| # | 根因 | 位置 |
|---|---|---|
| 1 | 鉴权类主动关闭被误报为 ECONNRESET | `vite.config.ts:22-26,63-75` |
| 2 | `onclose` 无条件重连，不区分关闭码 | `src/auth.ts:253-256` |
| 3 | 缺 `visibilitychange`，手机息屏即断连 | `src/auth.ts`（无） |

### 1.7 重大运维发现：数据库是活的（竞态风险）

> 本节为 v1.3 新增，**优先级高于所有分类改造任务**。

调研期间实测到 `question_import_record` 有**正在进行中**的导入：

| import_id | 文件 | 题数 | 状态 | 导入时间 |
|---|---|---|---|---|
| 1353 | `sz_ans.pdf` | 90 | **PREVIEW** | 2026-09-29 16:28:49 |
| 1352 | `sz_doc.docx` | 90 | **PREVIEW** | 2026-09-29 16:27:57 |
| 1351 | 国家公务员考试《公安专业知识》 | 70 | COMPLETED | 2026-09-29 16:09:14 |

**今日（2026-09-29）新增 160 题**（15 时 90 题、16 时 70 题），其中 **69 题未关联知识点**。

**这直接导致本方案早期读数失效**：同一份库在不同时间点读数不同（2324 → 2484；未关联 753 → 913）。所有数字必须以执行时刻的实测为准。

**竞态风险（本方案必须规避）**：

若在教师导入过程中执行知识点合并/拆分，会产生**孤儿数据**：
- 教师正按旧 `point_id` 写入 `question_knowledge`
- 我方同时删除/改写该 `point_id`
- 结果：题目关联丢失，或关联指向已删除节点

**执行约束**：

| 约束 | 措施 |
|---|---|
| **维护窗口** | 知识点合并/拆分**必须在无导入活动时执行**（判定方式见下方修正） |
| **停机窗口** | 建议阶段二、三执行时**暂停后端服务**（`uvicorn` 单实例），确保无并发写入 |
| **ID 禁复用** | 被合并/删除的 `point_id` **永不重新分配**给新知识点，避免历史题目错挂 |
| **废弃知识点处置** | ⚠️ **v1.7 修正**：`knowledge_point` 表**无 `status` 字段**（实测字段仅 `point_id/point_name/subject_id/parent_id/level/description/sort_order/sub_category_id`），原「置 `status=0` 软删除」方案**无法执行**。三选一，需您定：<br>① **加 `status` 列**（推荐）——一次 DDL 变更，代价小，永久解决软删除<br>② **先迁题再删节点**——把该知识点下题目改挂到目标知识点后物理删除，不留审计痕迹<br>③ **改挂不删**——保留空节点，仅停止新题进入 || **分批事务** | 每批操作独立事务 + 备份快照，失败可回滚到批次起点 |
| **执行期复核** | 执行前重新统计题数，与方案数字不符则以实测为准并更新方案 |

> **v1.5 重要修正 — 前置检查的正确写法**
>
> 初稿的检查项为「确认 `question_import_record` 无 `PREVIEW`/`PROCESSING` 记录」。**该条件永远无法满足**：实测 `import_status` 分布为 `COMPLETED 1063` / **`PREVIEW 284`** / `PARTIAL 6`。这 284 条 PREVIEW 是**教师上传后未确认的废弃预览**（历史横跨 09-28 及更早），属长期堆积，**不会自行消失**。若按原检查项，阶段二将**永久阻塞**。
>
> **正确判定（按时效而非状态）**：
> ```sql
> -- 最近 30 分钟内无新建导入 → 视为无并发写入
> SELECT COUNT(*) FROM question_import_record
> WHERE import_time >= datetime('now','localtime','-30 minutes');
> -- 期望结果：0
> ```
>
> **时区陷阱**：实测 `julianday('now') - julianday(import_time)` 得出**负值**（-421 分钟），说明 **SQLite `now` 为 UTC，而业务表存的是本地时间**。所有时间窗判定必须使用 `datetime('now','localtime', ...)`，否则判定结果完全错误。

**运维便利性**：建议在 `question_import_record` 增加「维护模式」标记，或提供一键停写开关，避免未来维护时再次踩到此坑。

| 原则 | 说明 |
|---|---|
| **扩展而非新建** | 复用 `question_classifier.py`（896行），只增关键词与考点层 |

### 方案二：三端数据实时同步

#### 2.1 设计目标

```
教师端导入完成 → 后端广播 sync（复用 scheduler.py:29 模式）
                → 三端收到 __VTJ_SYNC__
                → 若正浏览该科目则自动刷新
```

#### 2.2 后端改造（复用既有，零新建）

**实测复核（2026-09-29）**：既有 `MessageType` 枚举**并不包含 `SYNC` 值**，其取值为：

```
HEARTBEAT / EXAM_START / EXAM_PROGRESS / EXAM_SUBMIT / EXAM_RESULT
QUESTION_ANSWER / NOTIFICATION / CHAT_MESSAGE / SYSTEM_ALERT
IMPORT_PROGRESS / IMPORT_QUESTION / IMPORT_COMPLETED / IMPORT_FAILED
```

`scheduler.py:29` 的 `_broadcast_sync()` 实际发送的是**字符串字面量** `{"type":"sync"}`（不在枚举内），前端 `src/auth.ts:243` 正是按 `msg.type === 'sync'` 判断——即**约定优于枚举**，二者靠字符串松耦合。

**因此本方案采用枚举内既有的 `IMPORT_COMPLETED`**，而非新造 `SYNC`：

```python
# 复用既有 MessageType 枚举值，不新增类型
await ws_connection_manager.broadcast_all({
    "type": MessageType.IMPORT_COMPLETED.value,   # 已存在的枚举值
    "data": {"scope": "question_bank", "subject_id": 3,
             "action": "import", "count": 50},   # 仅统计信息
    "timestamp": datetime.utcnow().isoformat()
})
```

| 考量 | 措施 |
|---|---|
| **不新增枚举** | 复用 `IMPORT_COMPLETED`，避免污染既有枚举契约 |
| **兼容旧路径** | 前端同时识别 `'sync'` 与 `'import_completed'`，两代广播都能触发 |
| 运维 | 广播用 try/except 包裹，失败仅记日志，**不中断导入主流程** |
| 安全 | 广播**只含统计信息（科目/数量/动作），不含题目正文**，避免信息泄露 |

#### 2.3 前端消费

**实测现状**：`__VTJ_SYNC__` 全仓**仅 `mobile_home.vue` 一处监听**，练习页、题库页、答题页**均未监听**——即当前同步能力只覆盖首页。

需新增监听：

| 页面 | 文件 | 触发动作 |
|---|---|---|
| 练习页 | `.vtj/vue/mobile_practice.vue` | 重新拉取当前科目子科目与知识点 |
| 题库页 | `.vtj/vue/mobile_question_bank.vue` | 刷新题量统计与分类树 |
| 答题页 | `.vtj/vue/answer_page.vue` | 仅提示「题库已更新」，不打断进行中的作答 |
| 已有 | `.vtj/vue/mobile_home.vue` | 已监听，保持不变 |

- **防抖**：同科目 3 秒内多次事件合并为一次刷新
- **降级**：WS 不可用时退回"进入页面即拉取"，不阻塞使用

#### 2.4 边界场景

| 场景 | 行为 |
|---|---|
| WS 未连接 | 不影响使用，页面加载正常拉取 |
| 无其他端在线 | 广播无接收者，下次进入自然可见 |
| 刷新中断 | 保留旧数据不白屏，下次事件重试 |

### 方案三：WebSocket 噪音治理

#### 3.1 重连策略分流（`src/auth.ts:253`）

| 关闭码 | 含义 | 处置 |
|---|---|---|
| 4001 | 缺少 token | ❌ 不重连 |
| 4002 | token 类型错误 | ❌ 不重连 |
| 4003 | token 载荷无效 | ❌ 不重连（需重新登录） |
| 4004 | token 校验失败 | ❌ 不重连（需重新登录） |
| 1006/其他 | 网络异常 | ✅ 指数退避重连 |

#### 3.2 移动端生命周期感知

```javascript
document.addEventListener('visibilitychange', () => {
  if (document.hidden) closeSyncSocket();
  else if (isLoggedIn()) initSyncSocket();
});
```

**收益**：根治手机息屏断连，降低服务端无效连接占用（运维友好）

#### 3.3 终端日志降级（`vite.config.ts:63-75`）

- 鉴权类关闭降为 `debug` 级
- 网络异常保留 `warn`
- 现有 10 秒限流保留

#### 3.4 Vite 内置 proxy 报错日志（v1.8 补充，原方案遗漏）

> 用户原始日志含 **4 种**消息格式，本方案 3.1–3.3 只覆盖其中 2 种。逐一溯源：

| # | 日志格式 | 来源 | 本方案覆盖 |
|---|---|---|---|
| 1 | `[vite:socket] … 客户端连接中断(ECONNRESET)，已安全关闭` | `vite.config.ts:69`（`devRuntimeSafety` 自定义） | ✅ 3.3 降级为 debug |
| 2 | **`[vite] ws proxy socket error: Error: read ECONNRESET`** | **Vite 内置 proxy 错误记录器** | ❌ **原方案未覆盖** |
| 3 | `[vite-proxy:ws] 连接中断(…)，已释放` | `proxy.config.ts:79`（自定义 `configure`） | ❌ 未处理（当前只在非 ServerResponse 分支触发，日志中未出现） |
| 4 | `[vite:socket] http 客户端连接中断(…)，已安全关闭` | `vite.config.ts:61` 兜底 `route='http'` | ✅ 3.3 降级为 debug |

**关键判断**：`proxy.config.ts:54` 已通过 `proxy.on('error', …)` 接管了 `/ws` 代理的 error 事件，但 **Vite 自身仍保留了内置的 proxy 报错记录器**，二者并行输出，故日志中同时出现格式 1 与格式 2。

**因此 3.1 的重连修复是根治手段**：消除无效重连后，socket reset 不再发生，格式 1/2/4 自然一并消失。**但若修复后格式 2 仍有残留**（说明仍有真实 reset 发生），需按以下顺序处理：

1. 先确认是否为**真实后端异常**——直连 `ws://127.0.0.1:8000/ws/connect` 复测，区分代理问题与后端问题
2. 确认为代理层噪音时，可在 `proxy.config.ts` 的 `error` 处理器中对 `ECONNRESET` **显式标记已处理**（`response` 不可写时直接 `return`，避免落入 Vite 默认分支）
3. 任何情况下**不得屏蔽非 `RECOVERABLE_CODES` 的错误**——真实故障必须可见

**验收标准**：完成 3.1 后，手机端登录一次，终端**连续 10 分钟内不应出现任何 `ECONNRESET` 相关输出**（四种格式均需消失）。

| **为什么不复用 `scheduler.py:29` 的 `_broadcast_sync`** | 它发送的是字符串字面量 `"sync"`，**不在枚举内**，属约定优于枚举的松耦合。直接复用会让「导入完成」与「定时同步」两类事件无法区分，故改用枚举值并**保留对旧字符串的兼容** |
| **为什么只广播统计不广播题目** | 题目正文可能含未发布内容；广播统计可满足「学生端列表刷新」需求，泄露面最小 |
| **安全性** | 广播失败必须 `try/except` 包裹**且不中断导入主流程**——导入是教师侧关键操作，不能因推送失败而回滚 |
| **运维便利** | 断线降级为「进入页面即拉取」，WS 不可用不阻塞任何功能；三端离线时广播无接收者亦不影响，下次进入自然可见 |

**方案三 · WS 噪音**

| 维度 | 论证 |
|---|---|
| **为什么按关闭码分流而非统一退避** | 4001–4004 是**鉴权类确定性失败**，重连必然再次失败，属纯资源浪费；1006 类才是真网络异常需退避重连。区分后消除无效重连 |
| **为什么加 `visibilitychange`** | 手机息屏即杀 socket，PC 不触发——这是「手机端比电脑端严重得多」的**根因**。在源头主动断开/重连，比被动等 TCP 超时更快、更省服务端连接数 |
| **为什么日志要降级但不删除** | 鉴权类关闭对开发者无诊断价值（必然发生），降为 debug；网络异常保留 warn，避免真实故障被淹没 |
| **副作用评估** | 仅影响开发期终端输出与重连时机，**不改动任何业务逻辑**，无回归风险 |
