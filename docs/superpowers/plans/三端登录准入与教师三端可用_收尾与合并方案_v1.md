## 4. F-1 修复方案（D-37：题目批量导入 100% 失败）

### 4.1 现象（实测证据）

`POST /api/questions/import/confirm` 返回 **200**，但 `success_count=0 / failed_count=90`，每条错误：

```
422: [{'field': 'status', 'rule': 'R-ENUM', 'message': 'status 必须是 [0, 1]'}]
```

### 4.2 根因

`backend/app/foundation/validation.py` 第 196–200 行：

```python
for name, allowed in (('status', {0, 1}), ('audit_status', {0, 1, 2})):
    if name in present:                 # ← 只看字段在不在
        value = _as_int(data.get(name))  # None 也会被当成"要校验的值"
        if value not in allowed:
            issues.append(ValidationIssue(name, 'R-ENUM', f'{name} 必须是 {sorted(allowed)}'))
```

前端把解析结果原样回传，题目项里 `status` 为 `null` → `_as_int(None) = None` → 不在 `{0,1}` → 90 题全被判失败。
同一处的 `difficulty`、`score` 也用 `present` 判断，存在同类风险。

### 4.3 改法（最小改动，只改判断，不改业务语义）

1. `status` / `audit_status`：改为 `if name in present and data.get(name) is not None:`
2. `difficulty`、`score`：同样跳过 `None`（空值 = 未填写，交给库默认值/后续必填校验，不在此处判枚举）
3. 不新增接口、不改前端、不改表结构。

### 4.4 为什么安全

- 校验语义本就是"**填了才校验**"，`None` 表示未填；现行写法把"未填"判成"填错"。
- 真正必填的字段有独立规则（`R-REQUIRED`），不依赖这里。
- 改动只影响"空值是否报枚举错"，不会让非法值（如 `status=9`）通过。

### 4.5 回归测试

新增 `backend/tests/test_import_confirm_null_enum.py`：

| 用例 | 断言 |
|---|---|
| `status=None` 的题目项 | 校验不产生 `R-ENUM` 问题 |
| `status=9` | 仍产生 `R-ENUM`（防止改宽） |
| `difficulty=None`、`score=None` | 不产生枚举/负值问题 |
| `audit_status=None` | 不产生 `R-ENUM` |

### 4.6 验收标准

1. 单测 4 例通过。
2. E2 重跑：同一份真实真题 docx → `success_count=90 / failed_count=0`，库题量 397 → 487。
3. 验证后**回滚数据库**，题量回到 397，并核对无残留。
4. `gate_all` 仍 10/10。
