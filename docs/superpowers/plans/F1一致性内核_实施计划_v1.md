## 1. 目标与边界

**目标**：在**不引入 Redis、不新增服务**的前提下，让「Outbox → 投递 → 投影 → 对账」在现有 FastAPI 单体 + SQLite（WAL）上跑通，并把「写入准确 / 容量卫生 / 内容完整性」固化为可执行校验与门禁。

**只增不改**：新增 7 张表（§6.2）；新增 `app/foundation/` 包；新增审计与门禁脚本。
**明确不动**：`api/v1/**`（343 端点基线）、`models/**`、`.vtj/**`、`src/**`、`static/**`、`题库/**`、任何既有表结构与备份（R1–R12）。

**开关**：`FOUNDATION_ENABLED`（默认 `true`）。关闭时除 `main.py` 的注册外零行为差异；接口返回与 F0 一致。

## 3. 七步执行顺序（每步一个 commit）

### Step 1 — 表结构可重复应用（N1/N2/N3/N4/N5 + 测试）
- 验证：`python backend/scripts/migrate/apply.py --dry-run` → `--apply` → 再 `--apply`（第二次 0 变更）→ `--verify` 通过；`sqlite_master` 中 73 张既有表定义逐字不变。
- 回滚：`drop` 7 张新表（仅当用户批准）；开关默认未接入，业务零影响。

### Step 2 — 事务性发件箱（N6 + `test_foundation_outbox.py`）
- 验证：业务写 + `append` 同事务提交 → 各 1 行；异常回滚 → 双 0；同 `dedupe_key` 第二次返回 None；`aggregate_ver` 连续 +1。
- 回滚：删 `outbox.py` 与测试；表保留（空表无副作用）。

### Step 3 — 投递与投影（N7/N8/N11/N12/N13 + `test_foundation_dispatcher.py`）
- 验证：100 条事件 → 投影 100 行；处理到第 50 条模拟中断 → 重启续跑、不重不漏；同事件投 10 次 → 行数不变；v1/v2 乱序 → 终态 v2；连续失败 → `dead` + jsonl。

### Step 4 — 对账、健康与接线（N9/N10/M1/M2/M3/M5）
- 验证：`/health/foundation` 200 且字段齐全；人为改坏 1 条投影 → `reconcile sample` 报 mismatch → `rebuild` 后 drift=0；关闭开关后启动日志无 dispatcher、接口响应与 F0 一致。

### Step 5 — 审计脚本（N14/N15 + `test_capacity_hygiene.py`/`test_write_integrity.py`）

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| SQLite 写锁竞争 | 投递器与业务写冲突 | 单条一事务 + `busy_timeout=30s` + 批量上限 100；L7-1 与冒烟 P95 兜底 |
| 后台任务拖慢启动 | 冷启动变慢 | `ensure_schema` 幂等快；dispatcher 独立 asyncio task，启动不等待首轮 |
| `main.py` 改动与 P3B 冲突 | 合并冲突 | 只改 2 处、各 ≤15 行；P3B 未动 `main.py` 的 lifespan 区 |
| 门禁误报 | 阻塞开发 | 检查 6–15 先 WARN；仅 1–5 FAIL；先在 `--layer L7` 独立跑 |
| 事件爆炸 | 库增 | 投递后 `dispatched` 保留 7 天后由 GC（F3）清理；F1 只建表不接业务写 |
