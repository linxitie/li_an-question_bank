# 资料卡片导入 D1：类型被启发式分类器覆盖 — 修复报告 v1

> 缺陷：D1（阻断级）　报告来源：合作同伴 `D1导入卡片类型缺陷_报告_v1.md`（2026-10-27）

> 结论：已修复并补回归测试；`xlsx` 卡片导入后 `study_material.type` 恒为 `card`

---

## 1. 现象

管理员用 Excel 导入备考资料卡片（正面 / 背面双列），接口返回 `200 {"created":N}`，
但落库的每一条 `study_material.type` 都是 `article`：

- 卡片进入学生端「备考指南」（文章区），而不是「知识卡片」区；
- 卡片翻转 UI 已实现但永远没有 `type='card'` 的数据可渲染，功能等于未上线；
- 返回体看起来完全成功，用户无法察觉 → 每次导入都在产生需要事后清洗的错数据。

复现：`upload → confirm`（`column_mapping={"front":0,"back":1,"category":2}`）后直查
`study_material.type` = `article`（同伴实测 3 批，100% 复现）。

## 2. 根因

`backend/app/api/v1/library/materials.py` 的 `import_confirm` xlsx 分支：

1. `build_cards(rows, col_front, col_back, col_cat)` 用「正面/背面」双列**已唯一确定**
   这一行就是一张卡片，`card_front` / `card_back` 均非空；
2. 却对每张卡再调用 `classifier.classify(".xlsx", content=combined, title=card_front)`；
3. `MaterialClassifier._classify_spreadsheet(title)` 只看标题里的「卡片/知识/要点/口诀/速记」
   关键词，卡片正面是题目正文，命中不了 → 返回 `article`；
4. `type=classification["type"]` 用启发式结果**覆盖了确定性业务事实**。

docx/pdf 分支做同样的调用是**正确**的（文档本来就该由分类器判类型），问题只出在
「输入契约已确定类型」还必须再猜一次的 xlsx 卡片分支。

## 3. 修复

```python
# backend/app/api/v1/library/materials.py（xlsx 卡片分支）
-            # 智能分类
-            classification = classifier.classify(
-                ".xlsx", content=combined, title=card_front
-            )
+            # 类型由「正/背面双列」这一输入契约唯一确定，不再交给启发式分类器：
+            # 分类器只看扩展名+标题关键词，卡片正文短会判成 article，导致卡片
+            # 落入文章区、翻卡 UI 永不触发（D1）。此处只按业务事实写 card。
             content_hash = content_cleaner.calculate_content_hash(combined)
             m = StudyMaterial(
-                subject=subject, type=classification["type"],
+                subject=subject, type="card",
                 category=c["category"] or category,
```

说明（与同伴方案 A 的差异）：

- 同伴方案保留了 `classification` 作 `category` 兜底，但 `MaterialClassifier.classify()`
  的返回字典只有 `type/confidence/reason`，**没有 `category` 键**，保留该调用是死代码，
  未来也容易再次把 type 改回去；因此本实现直接删除该分支的分类器调用。
- 未采用方案 B（给 `classify()` 加 `hint_type`）：分类器契约变更需回归全部调用点，
  收益仅此一处；也未采用方案 C（导入后批量 PUT）：运维绕行且易漏。
- docx/pdf 分支未改动，分类行为不变。

## 5. 存量数据清洗

本仓库生产库 `backend/data/question_bank.db` 实测 `study_material` 为 **0 行**，无需清洗；
同伴环境里被误判的记录（material_id 4–8）需执行：

```sql
-- 先看：有正/背面内容却仍为 article 的记录
SELECT material_id, type, substr(title,1,30)
FROM study_material
WHERE card_front IS NOT NULL AND card_front <> '' AND type <> 'card';

-- 再修（确认上面结果符合预期后）
UPDATE study_material SET type='card'
WHERE card_front IS NOT NULL AND card_front <> '' AND type='article';
```

回滚代码：`git revert <本修复提交>`；回滚数据：反向 `UPDATE ... SET type='article' WHERE ...`。
