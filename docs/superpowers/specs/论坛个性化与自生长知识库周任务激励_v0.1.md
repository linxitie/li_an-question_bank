# 论坛个性化与「自生长知识库 + 周任务」激励 — 思路稿 v0.1

> 性质：方向讨论稿，不是实施计划；本文不含代码改动。
> 基线：2026-10-22 对 `backend/app`、`src/modules`、`.vtj` 的实测。

---

## 0. 结论先行

1. **论坛四项需求里，两项是数据模型缺口，一项是前端缺口，一项是内容安全风险。**
   - 点赞表情：`forum_like` 无「表情类型」字段，唯一约束写死为「一人一帖一个赞」。
   - 头像/昵称/签名：`sys_user` 只有 `avatar` 与 `avatar_frame`，没有昵称、个性签名字段，论坛昵称直接用 `username`。
   - 个性化评论区：`forum_comment.parent_comment_id` 已存在（楼中楼数据层已就绪），但手机详情页只平铺渲染，未使用。
   - 富文本/表情文字：`forum_post.content` 是纯文本 `Text`，前端是 `textarea`；直接放开 HTML 会引入 XSS。
2. **每周随机任务的底座已有约 80%。** `Task` 已支持 `daily/weekly/season/random`，`UserTaskProgress` 已按 `(user_id, task_id, period_key)` 幂等，`_period_key_for()` 已能生成 ISO 周键，`APScheduler` 已在跑，金币已有唯一合法入口 `reward/contract.py`。缺的是：周随机分配、质量型判定、自动结算、奖励配置化。
3. **自生长知识库是全新域，建议不要一上来做「AI 自动写笔记」。** 先做「题目 → 知识节点 → 掌握度 → Obsidian 兼容导出」，让知识库的每个节点都有答题证据，才具备可解释性与专利上的技术特征。
4. **专利风险要提前看。** 「任务+积分」本身是商业规则，单独立项容易被《专利法》第 25 条挡住；必须把创新点绑定到「证据驱动的数据结构 + 服务端判定 + 双向同步协议 + 防篡改账本」这些技术特征上。

## 2. 论坛改造思路

### 2.1 发帖功能：先补测试，再谈增强

**现状问题**
- 只有一条「成功发帖」路径被间接测到，缺失败路径与安全用例。
- 正文是纯文本，没有图片、没有 @、没有话题、没有表情短码。
- 附件字段能存 JSON，但没有通用图片上传端点，实际发不出图。

**建议的测试基线（先做，不改产品行为）**

| 用例 | 期望 |
|---|---|
| 未登录发帖 | 401 |
| 标题/正文为空、纯空格 | 422 或业务错误 |
| 标题 201 字 / 正文 10001 字 | 422 |
| 命中 blocked 词 | 拒绝，返回 `SENSITIVE_CONTENT_BLOCKED` |
| 命中 masked 词 | 发布成功，正文被替换为掩码 |
| attachments 非 JSON / 非数组 | 422 |
| 正文含 `<script>` / `onerror=` | 原样存储但前端不执行；若转 HTML 必须白名单 |
| 同一帖子重复触发 `forum.posted` | 事件只发一次（已有用例，保留） |
| 高频连发（如 10 秒 10 帖） | 触发限流 |

**发帖增强的优先级**
1. 图片：新增 `/api/media/image`（MIME 白名单 + 2MB + 重编码去 EXIF + 随机文件名），帖子 `attachments` 复用现有 JSON 结构。
2. 表情短码：正文存 `:smile:` 之类的短码，渲染层映射为内置表情图；不入库 HTML。
3. 话题标签：`#话题#` 解析后写入 `tags`，并提供按话题筛选。
4. @提及：解析 `@用户名`，写 `forum_mention` 表并推送通知。
5. 富文本：**最后做**。建议「Markdown 子集 + 白名单渲染」，不要存任意 HTML。需要先定编辑器（轻量 contenteditable 或成熟库），且要评估包体积与 VTJ 兼容性。

### 2.2 点赞表情（Reaction）

**推荐方案：新增 `forum_reaction`，不动 `forum_like`。**

理由：现有 `forum_like` 的唯一约束是「一人一帖一个赞」，直接加 `reaction_type` 会让旧约束失效，迁移风险高；新增表可以双写一段时间，`like_count` 继续作为「总反应数」或「点赞数」的兼容字段。

概念结构：
- `forum_reaction(id, target_type[POST|COMMENT], target_id, user_id, reaction_code, created_at)`
- 唯一约束：`(target_type, target_id, user_id)` —— 一人对同一目标只能选一个表情，切换即替换。
- 索引：`(target_type, target_id)`、`(user_id, created_at)`。
- `reaction_code` 只接受白名单：`like / love / haha / wow / sad / angry`（或 6 个内置 emoji id），**不接受任意文本/任意图片**。

API 形态：
- `POST /api/forum/reactions` body `{targetType,targetId,reactionCode}`（幂等切换）
- `DELETE /api/forum/reactions` body 同上（取消）
- 列表/详情返回 `reactions: {like:3,love:1,...}` 与 `myReaction`。

交互与视觉（需 @designer 出方案）：
- 桌面：悬浮/长按 300ms 弹出 6 表情浮层；移动端长按弹出，单击仍是默认「赞」。
- 选中后：图标弹跳 120ms、计数滚动 +1、自己的表情高亮。
- 评论区：每条评论右侧一个小表情入口，聚合展示前 3 个表情 + 总数。
- 空状态不显示浮层，避免误触。

风控：
- 每人每目标每 1 秒最多 3 次切换；同一 IP 高频写入进审计日志。
- 表情不计入金币/成就，避免刷反应。

### 2.3 头像、昵称、签名的个性化

**数据层缺口**
- `sys_user` 增加：`nickname`（2-20 字）、`signature`（≤60 字）、`name_color`（称号/颜色，可复用 `badge_title`）、`avatar_frame` 已有。
- 论坛序列化改为「nickname 优先，缺省 username」，并返回 `avatarFrame / title / level / signature`。

**头像上传**
- **已存在** `/api/auth/avatar`（`identity/auth.py:442`）：jpg/jpeg/png/gif/webp、≤2MB、UUID 重命名。后续只需补「裁 1:1 + 重编码去 EXIF + 最小尺寸」。
- 旧头像不立即删，保留 7 天由调度器清理，避免缓存裂图。

**展示层**
- 统一 `UserBadge` 组件：头像 + 头像框 + 称号 + 等级 + 签名（详情页展示，列表页截断）。
- 头像框来自金币商城 `deliverable_type=avatar_frame`，已有发放服务 `deliverable_service.py`，可直接复用。

**审核**
- 昵称/签名走同一套敏感词过滤；签名禁止外链与联系方式。
- 头像做「人工抽检 + 举报下架」，不做全量机审（成本）。

### 2.4 评论区个性化、多样性

分四层做，避免一次改太多：

1. **结构层（低成本，收益最大）**：前端真正使用 `parent_comment_id` 渲染两层楼中楼；父评论删除时子评论保留并标注「原评论已删除」。
2. **排序层**：默认「热度 = 点赞×2 + 回复×3 + 时间衰减」，可切换「最新」；楼主评论与作者回复加标签并优先。
3. **表达层**：评论支持表情短码、图片（可选）、@；评论也可加表情反应（复用 2.2）。
4. **身份层**：评论显示称号/等级/头像框；「楼主」「铁粉」「本周活跃」等徽章由成就系统驱动，不硬编码。

**不建议现在做**：评论盖楼无限层级、匿名评论、语音评论。前三者都会显著提高审核与性能成本。

### 2.5 必须遵守的工程约束

- `.vtj/vue/*.vue` 的 `<template>` **不能由 AI 直接改**（AGENTS.md R3）。论坛列表页 `forum.vue / mobile_forum.vue / tablet_forum.vue` 的表情浮层、头像框、评论区结构，需要用户在设计器里拖拽；AI 只能改 `<script>`，且要先 `dryRun`。
- 可自由改模板的是 `src/views/student/mobile/mobile_forum_create.vue` 与 `mobile_forum_detail.vue`（手写页）。
- 排期时必须把「用户在设计器操作」算成依赖，否则会卡住。

### 2.6 论坛验收口径

- 发帖：9 条测试用例全绿；图片可上传、可回显、可删除；敏感词三级行为与现网一致。
- 表情：6 种表情可切换/取消；刷新后计数一致；并发重复提交不产生重复行；列表与详情一致。
- 头像：上传非法格式/超大/过小均被拒；昵称/签名过滤生效；论坛三端显示一致。
- 评论：楼中楼、排序、楼主标识、表情反应、删除父评论五个场景通过。

## 3. 自生长 Obsidian 知识库

### 3.1 定义（避免概念漂移）

「自生长」不是让模型无限生成内容，而是：

> 以用户真实答题证据为种子，自动生成/补全知识节点与节点间的边，并随着复习行为持续更新掌握度；知识库可无损导出为 Obsidian 兼容 vault，用户本地编辑后可回流。

四个动作：
1. **抽取**：题目 → 知识点/错因/方法（结构化，不是散文）。
2. **连接**：新节点与既有节点建立双链（同知识点、同错因、前置/后继）。
3. **更新**：每次答题/复习更新掌握度与边的权重。
4. **回流**：用户导出到 Obsidian 编辑，再导入合并。

### 3.2 概念数据模型（不落地代码）

- `knowledge_node`：`node_id, user_id, title, aliases, subject_id, chapter, node_type(概念/公式/错因/方法), mastery(0-1), evidence_count, last_review_at, source(seed/user/llm), version`
- `knowledge_edge`：`from_node, to_node, relation(前置/相关/对比/错因), weight, evidence_count, last_updated`
- `knowledge_evidence`：`node_id, question_id, practice_record_id, delta, reason, created_at` —— **可解释性的核心**
- `note_revision`：`node_id, content_md, editor(user/system), base_version, created_at` —— 冲突合并用
- 复用：`QuestionNote`（题目笔记）可作为证据来源，不必另起炉灶。

### 3.3 生长算法（可解释、可复现）

- 初始种子：题目自带的 `knowledge_point` / 章节 / 错因标签。
- 掌握度更新：`mastery = clamp(mastery + α·(correct - mastery))`，α 随题目难度（已有 IRT 难度）调整；连续答对加速，遗忘按天衰减。
- 边权重：共现次数 × 时间衰减；仅当证据数 ≥ 2 才建边，避免噪声。
- 生成新节点：只允许「聚类 + 模板」，例如同一知识点下错因 ≥ 3 道题才生成「错因节点」；LLM 仅用于起标题/归纳，**不直接写正文**。
- 每个节点必须能回答：「你凭什么认为我掌握了？」→ 列出证据题号与时间。

### 3.4 与 Obsidian 的兼容与同步

Obsidian 没有官方写入 API，采用「文件级互操作」，不要试图直接改用户本地库：

- **导出**：生成 zip，结构 `vault/科目/章节/节点.md`；frontmatter 写 `node_id, mastery, last_review, evidence_count, tags`；正文用 `[[双链]]` 与 `#标签`。
- **导入**：只接受本系统导出过的 vault（用 `node_id` 对齐）；用户新增的 `.md` 作为 `source=user` 节点导入；冲突按「用户编辑优先，系统只补元数据」合并，保留 revision。
- **同步模式**：一期手动导出/导入；二期做「Obsidian 插件/本地 agent 监听文件变化」，但要走用户授权目录，服务端不直接触碰本地磁盘。
- **合规**：导出文件不含他人隐私与未授权题库原文。

### 3.5 风险

- 知识抽取准确率不足会污染知识库 → 先只做「章节/知识点」两级，错因节点后置。
- 节点爆炸 → 每人节点上限（如 2000）与合并策略。
- Obsidian 同步冲突 → 必须版本号 + revision，禁止 last-write-wins 覆盖用户长文。
- 纯文本/Markdown 注入 → 导出时转义 frontmatter，导入时限制文件类型与大小。

## 4. 每周任务与金币奖励

### 4.1 系统可以制定哪些每周任务

按「能否服务端自动判定」分八类，括号内是判定指标：

| 类型 | 示例 | 判定 |
|---|---|---|
| 数量型 | 本周刷题 200 道；完成 3 套试卷；复习错题 50 道 | 已有 `week_questions`，其余需加 metric |
| 质量型 | 本周正确率 ≥ 80%；错题重做正确率 ≥ 70%；平均每题 ≤ 45 秒 | 正确率已有；用时需新增 |
| 覆盖型 | 覆盖 3 个章节；薄弱知识点覆盖 ≥ 60%；完成 10 个知识节点 | 需知识图谱 |
| 时间型 | 本周学习 ≥ 5 小时；连续 5 天学习；完成 10 个番茄钟 | 需服务端计时 |
| 社区型 | 发 2 帖；优质回复 3 条；获赞 10 次；被采纳 1 次 | 发帖/点赞已有；「优质/采纳」需定义 |
| 知识库型 | 新建/完善 5 个节点；建立 10 条双链；复习 20 个到期节点 | 依赖第 3 节 |
| 挑战型 | 限时套卷达标；连续答对 20 题；攻克 5 道标记错题 | 需事件流 |
| 恢复型 | 重做上周错题并正确率 ≥ 80% | 需周维度错题快照 |

**建议每周固定 4 个任务**：1 个保底（如「本周刷题 50 道」，人人可完成）+ 2 个随机（从薄弱子图抽）+ 1 个挑战（可选，高奖励）。总量控制在 30–90 分钟/天，避免任务焦虑。

### 4.2 随机分配：从「纯随机」升级为「诊断性随机」

现有 `_ensure_random_tasks()` 是 `random.sample(pool, N)`，按天、纯随机。周任务建议：

- 周期键：`2026-W43`（`_week_key()` 已存在）。
- 抽样权重：`w = 0.7 × 薄弱度 + 0.2 × 新鲜度 + 0.1 × 探索`。
  - 薄弱度：该知识点掌握度越低权重越高。
  - 新鲜度：近 4 周未出现过的任务加权。
  - 探索：完全没做过的任务保留 10% 概率，防止信息茧房。
- 可复现：`seed = hash(user_id, week_key, salt)`，便于审计、客服复盘与专利实施例复现。
- 保底任务不随机，保证「本周一定有可完成任务」。

### 4.3 判定：定时 + 定量 + 质量

- **定时**：周一 00:00 生成，周日 23:59 截止；所有时间以服务端为准。
- **定量**：`current >= threshold`；`calc` 实时重算，`event` 事件累计（现有两种模式都保留）。
- **质量**：新增 `quality_gate`，例如「正确率 ≥ 80%」；质量不达标时 `completed=0`，但进度保留，允许继续刷。
- **状态机**：`assigned → in_progress → completed → claimed → expired`。
- **补做**：每周最多 1 次「补做券」，消耗金币，避免直接放宽判定。

### 4.4 奖励配置与通胀控制

- 现有 `Task.reward_coins` 可直接用；建议加一个模板表 `task_template`：`metric, mode, threshold_min/max, reward_min/max, weight, season, enabled`。
- 单任务奖励 = `base + difficulty_coeff × threshold`，设上限；每周个人金币产出上限（如 200），超出转为成长值。
- 奖励要「可解释」：每笔 `coin_record` 写 `related_id`（task_id + period_key）与 `description`，用户能点开看到「因为完成了哪条任务」。
- 商城价格锚定周产出，避免「一周暴富、三周通胀」。
- 连续完成 4 周 → 成就/称号（复用 `Achievement` 的 `condition_code/threshold/tier_times`，数据驱动，不硬编码）。

### 4.5 自动结算的落点

已有 `APScheduler`，建议新增两个 job：

- 周一 00:10：为所有活跃用户生成当周任务（或懒生成，首次访问时生成，降低批量压力）。
- 周一 00:20：上周未领取且已达标的任务自动结算/发提醒；过期任务置 `expired`。
- 结算必须走 `reward/contract.py` 的 `grant_coins`，不允许直接改 `total_coins`（现有 `tasks.py:316-326` 是直接改余额 + 写流水，属于待收敛点）。
- 幂等：`(user_id, task_id, period_key)` 唯一约束已能兜底；结算 job 重跑不得重复发币。

### 4.6 防作弊（专利里也是技术特征）

- 服务端时间戳，不信客户端。
- 最短答题间隔（如 < 2 秒/题标记异常）、同题短时间重复不计入。
- 正确率异常突增、整卷秒过 → 进入人工抽检，奖励延迟发放。
- 社区任务：发帖被删除/折叠不计；互赞刷量识别（同一对用户高频互赞）。
- 每日/每周上限 + 设备/IP 维度限流。
- 审计表记录「任务-证据-发币」三元组，支持申诉。

## 5. 闭环：知识库 → 任务 → 奖励 → 知识库

```
答题/复习 ──► 知识节点掌握度更新 ──► 找出薄弱子图
                    ▲                      │
                    │                      ▼
              完成任务 ◄── 周任务（诊断性随机 + 保底 + 挑战）
                    │
                    ▼
              金币/成长值/成就 ──► 商城消费 ──► 头像框/称号 ──► 论坛展示
```

这条闭环的意义：
- 任务不是拍脑袋的运营活动，而是由知识库状态驱动。
- 奖励不是纯积分，而是能改变「下周任务分布」的反馈信号。
- 论坛个性化（头像框/称号/徽章）成为奖励的可见出口，形成社交激励。

## 6. 专利构思（[专利申请] 方向）

### 6.1 拟名称

> 一种基于学习证据链的自生长知识库构建与周任务激励方法、系统及存储介质

### 6.2 权利要求方向（草案级）

1. **方法主权利要求**：采集答题证据 → 构建/更新知识节点与边 → 基于薄弱子图加权随机生成周任务 → 服务端按定时/定量/质量三阈值判定 → 通过金币账本结算 → 用结算结果反向更新掌握度与下周任务分布。
2. **从属**：随机种子 `hash(user_id, week_key)` 的可复现抽样；7:2:1 权重（薄弱/新鲜/探索）。
3. **从属**：Obsidian 兼容 vault 的导出/导入与基于 `node_id + revision` 的冲突合并。
4. **从属**：可解释账本（任务-证据-金币三元组）与防篡改校验。
5. **从属**：防作弊判定（间隔、重复、异常速度、互赞识别）。
6. **系统权利要求**：知识图谱模块 + 任务编排模块 + 判定引擎 + 账本 + 同步模块。
7. **存储介质**。

### 6.3 新颖性组合（相对现有技术的差异点）

现有技术：Anki/SuperMemo 的间隔重复、Duolingo 的连续打卡与任务、知识图谱自适应学习、Obsidian 双链笔记。

建议主张的组合差异：
- **证据驱动生长**：节点与边的建立必须有答题证据，而非用户手动或模型自由生成。
- **诊断性随机**：周任务不是纯随机，也不是纯推荐，而是「薄弱子图加权 + 探索保留」的抽样。
- **三阈值判定 + 可解释账本**：完成判定不只看数量，还看质量与服务端时间，且每笔奖励可追溯。
- **闭环自适应**：奖励结果改变下周任务分布，形成可观测的收敛过程。

### 6.4 法律风险（必须提前处理）

- 《专利法》第 25 条：智力活动的规则和方法不授予专利权。纯「发任务给积分」大概率被驳回。
- 规避方式：把方案写成「数据处理方法 + 系统架构」，强调数据结构、同步协议、服务端判定、防篡改、设备交互等技术特征。
- 需要做检索（中文 + 英文），重点看：自适应学习、知识图谱、任务激励、笔记同步。
- 建议由代理机构出权利要求书；本稿只提供技术交底素材。

### 6.5 交底材料清单

- 系统架构图、数据流图、状态机图。
- 3 个实施例：新用户冷启动、薄弱知识点、Obsidian 导入冲突。
- 对比表：与 Anki、Duolingo、普通积分商城的技术差异。
- 实验数据：任务完成率、次周留存、金币产出/消耗比（上线后补）。

## 8. 需要你拍板的 6 个问题

1. 论坛表情用「6 个内置 emoji」还是「可扩展表情包」？前者可控，后者运营成本高。
2. 富文本是否必须？如果只是加粗/列表/图片，用 Markdown 子集就够，风险远低于富文本编辑器。
3. 昵称/签名是否允许用户自由填写？还是「系统生成 + 有限修改」？
4. 周任务奖励是「自动到账」还是「手动领取」？自动体验好，但需要更强的防作弊。
5. 知识库一期是否只做「导出 Obsidian」，暂不做「导入回流」？导入的冲突合并是最难的部分。
6. 专利是「发明专利」还是先做「软件著作权 + 技术秘密」？两者成本与周期差很多。
