## 2. 【任务一交付物】兑换比例 + 商品池 + 防通胀

### 2.1 双轨锚定（含计算过程）

**锚 A（用户感知锚）**：`100 金币 ≈ 1 元` ⇒ 单枚面值 `PV = 0.01 元`。所有定价按"参考现价 × 100 × 上浮系数"换算，用户一眼能算清。

**锚 B（成本约束锚）**：`年发行量 × 单枚兑现成本 × 兑换率 ≤ 年收入 × (1%~3%)`

计算依据（可替换的业务假设，全部显式列出）：

| 参数 | 取值 | 依据 |
|---|---|---|
| 年收入 R | 3,000 万元 | 5 万付费用户 × ARPU 600 元/年 |
| 预算系数 k | 2%（1%~3% 中位） | 行业激励预算常见区间 |
| 年度兑付预算 B | R×k = **60 万元** | — |
| 加权兑现成本率 f̄ | **52.5%** | 虚拟 15%×40% + 实物 65%×35% + 电商 95%×25% = 6.0%+22.75%+23.75% |
| 单枚兑现成本 c | PV×f̄ = 0.01×0.525 = **0.00525 元/枚** | 只有被兑换的金币才产生成本 |
| 目标兑换率 r | **5%**（区间 3%~8%） | 12 个月有效期 + 分层商品下的经验值 |
| 年发行上限 I_max | B/(r×c) = 60万/(0.05×0.00525) ≈ **22.85 亿枚** | 发行≠成本，成本只随兑换发生 |
| 实际计划发行 I | **≈ 17 亿枚/年**（5 万 MAU × 52 周 × 650 枚/人/周） | 留 25% 安全余量 |
| 预期兑付成本 | I×r×c = 17亿×0.05×0.00525 ≈ **44.6 万元 = 年收入 1.49%** | 落在 1%~3% 目标带内 ✅ |

> 结论：**发行量可以很大（激励感），成本靠"兑换率 + 有效期"兜住**。这也是为什么必须有 2.4 的防通胀机制——没有它，r 从 5% 涨到 20%，成本立刻变 5.9%（超预算）。

### 2.2 分层定价规则

```
金币价 = round(参考现价(元) × 100 × 上浮系数)
上浮系数：虚拟权益 1.00 ／ 实物 1.25 ／ 电商卡 1.30
```

上浮系数的依据：让"成本占比"回到同一可接受带。

| 品类 | 成本率(成本/现价) | 上浮 | 折算后 成本/面值 |
|---|---|---|---|
| 虚拟权益（会员/解锁券/头像框） | 10%~80% | 1.00 | 10%~80% |
| 实物（书/文具/配件） | 60%~72% | **1.25** | 48%~58% |
| 电商卡 | 95% | **1.30** | **73%** |

> 实物与电商卡上浮 20%~30%，正是把 73%~95% 的原始成本率压回 48%~73% 的手段（用户要求 2 的落地依据）。

### 2.4 金币有效期（12 个月滚动清零）

- 采用**批次制**：每次发放生成一条 `coin_lot(user_id, amount, remaining, available_at, expire_at, source)`，`expire_at = 发放日 + 365 天`。
- 消费按 **FIFO（先到期先消耗）**扣减，`sys_user.total_coins` 仍作为冗余余额用于快速展示，但**扣减必须与批次表同事务双写**，每日定时对账。
- 到期扫描（每日 03:00）：`remaining>0 且 expire_at<=now` → 写 `coin_record(coin_change=-remaining, transaction_type='EXPIRE')` 并清零批次。
- 到期前 7/3/1 天各推一次提醒（复用 notifications 域）。

### 2.5 混合兑换通道（金币 + 少量现金）

- 规则（写在服务端，前端只做展示）：
  1. 仅对 `tier != small` 的商品开放；
  2. 金币抵扣上限 = 商品金币价的 **70%**，现金至少 **30%**（避免"零元购"套利）；
  3. 实际现金 = `ceil(面值 × 30%)`，剩余部分金币按 100:1 折算；
  4. 一张兑换单最多应用 1 张券，券后现金不低于 0。
- 例：题库年卡 12000 币（120 元）→ 混合兑换需 `8400 币 + 36 元`；若有 8 折券，现金 36×0.8 ≈ 28.8 元。

### 2.6 防通胀指标（监控 + 自动刹车）

| 指标 | 公式 | 正常带 | 触发动作 |
|---|---|---|---|
| 人均周获得 | 周发行 / 周活跃 | 500–800 币 | >1000：置顶奖励系数 ×0.85，连 2 周则关停 1 个置顶槽 |
| 兑换率 r | 周消耗 / 周发行 | 3%–8% | >8%：新增商品延迟上架 + 提高大额价 10%；<2%：下调大额价或上新 |
| 存量（未过期未消耗） | Σ coin_lot.remaining | ≤ 半年发行量 | 超限：缩短有效期至 9 个月 + 暂停一次性大额发放 |
| 预算占用 | 年累计兑付成本 / 年收入 | ≤3% | ≥2.5%：全站提价 15%，并冻结混合兑换 |
| 单用户异常 | 单日获得 > 日上限 300 币 | 0 次 | 直接触发风控复核（见 6.2） |

## 3. 【任务二交付物】周任务系统

### 3.1 核心原则落地

- **签到只做习惯触发**：沿用 `daily_checkin`，单次 **10 币**（现库 `coin_reward` 字段已有），连续 7 天额外 30 币；周签到上限 100 币，占总周获得的 **≤15%**。
- **主要奖励在任务完成**：单个周任务 150–450 币，周任务预算占总发行 **≥70%**。
- **置顶是稀缺资源**：每周全站只置顶 **2–3 个**（按用户分群最多 3），置顶任务奖励系数 **1.3~1.5**。

### 3.2 奖励模型

```
奖励 = 基础值 base × 难度系数 k_difficulty × 稀缺系数 k_scarcity
base ∈ [150, 300]（中等难度锚点 = 200 币 ≈ 2 元感知）
k_difficulty ∈ {1.0, 1.2, 1.4, 1.6}   # 按"目标量 / 人均产出"分档
k_scarcity  = 1.30（置顶）/ 1.15（限时最后 48h）/ 1.00（普通）
单任务上限 500 币；单用户周上限 900 币（防刷）
```

难度系数依据：以"人均周产出"为基准，`目标量 ÷ 人均周产出` 落到 1.0/1.2/1.4/1.6 四档。

### 3.3 周任务配置表（A/B/C 三类，8 个样例）

| # | 类型 | 任务 | 判定规则（服务端可验证） | 基础值 | 难度 | 置顶加成 | 最终奖励 | 数据来源域 |
|---|---|---|---|---|---|---|---|---|
| 1 | A 定量 | 本周完成 300 道题 | `count(practice_record where practice_date ∈ 本周) ≥ 300` 且 `exam_answer_detail` 合并去重 | 200 | 1.5→1.6 | ×1.30 | **416** | exam |
| 2 | A 定量 | 本周完成 3 套真题 | `count(exam_record where is_completed=1 and submit_time ∈ 本周) ≥ 3` | 180 | 1.4 | ×1.30 | **328** | exam |
| 3 | A 定量 | 重做 50 道错题且正确率 ≥80% | 错题集合 = `exam_answer_detail.is_correct=0`；重做记录在本周且 `correct/50 ≥ 0.8` | 220 | 1.6 | ×1.00 | **352** | exam |
| 4 | B 连续 | 本周 5 天有刷题记录 | `count(distinct practice_date ∈ 本周) ≥ 5` | 150 | 1.2 | ×1.30 | **234** | exam |
| 5 | B 连续 | 连续 7 天每日一练（每日≥10 题） | 逐日聚合，7 天全部 `daily_count ≥ 10` | 200 | 1.35→1.4 | ×1.00 | **280** | exam + checkin |

> 数值自查：8 个任务中置顶 3 个（#1#2#4），占比 37.5%；置顶均奖励 326 vs 普通 262，**+24%**（要求 +30%~50%，故实际配置取 ×1.30~×1.50，见 3.4 的落地修正）。

### 3.4 置顶机制

- 表结构：`badge_task` 增加 `pinned_slot (0=普通/1..3=槽位)`、`difficulty_factor`、`scarcity_factor`、`period_type('week')`。
- 每周一 00:05 由 `growth/tasks.py` 的排期任务重算：从任务池按"分群 × 覆盖知识点"抽 2–3 个置顶，写入 `weekly_task_pool(week_key, task_id, pinned_slot, audience)`。
- 置顶系数取 **1.30 / 1.45 / 1.50**（按槽位 1/2/3 递减），保证置顶均奖励比普通高 **30%~50%**。
- 普通任务不置顶但每周仍可完成，奖励系数 1.0。

### 3.5 任务状态机

```
                 ┌─────────── 失效（周期结束未达标）──────────┐
                 │                                            │
未开始 ──首条进度──> 进行中 ──达标──> 待判定 ──校验通过──> 已发放
  │                   │                  │                    │
  │                   │                  └──校验失败──> 已失效  │
  └──周期结束─────────┴───────────────────────────────────────┘
                                               已发放 ──风控回溯──> 已回滚
```

| 状态 | 进入条件 | 落库字段 |
|---|---|---|
| 未开始 | 周期开始，无进度记录 | 无 `user_task_progress` 行 |
| 进行中 | 首次产生进度 | `current>0, completed=0` |
| 待判定 | `current ≥ threshold` | `completed=0` 但标记 `pending_verify=1` |
| 已发放 | 服务端二次校验通过且发放成功 | `completed=1, claimed=1, claimed_at` |
| 已失效 | 周期结束未达标 / 校验失败 | `completed=0, expired=1` |
| 已回滚 | 风控判定作弊 | 反向 `coin_record` + `revoked=1` |

幂等约束：`unique(user_id, task_id, period_key)`；发放走 `coin_record(related_id=progress_id)` 唯一索引防重复发放。

## 4. 【任务三交付物】自生长知识图谱 + 随机周任务（专利方向）

### 4.1 权利要求书草案

> 说明：全文**不出现任何特定笔记软件名称**，编辑端仅表述为"客户端编辑界面"。

**权利要求 1（独立权利要求）**

一种基于自生长知识图谱的任务生成方法，其特征在于，包括：

S1、采集用户在客户端编辑界面与答题界面产生的学习行为数据，所述学习行为数据至少包括答题结果、错题标记与内容编辑事件；

S2、根据所述学习行为数据，更新知识图谱中知识节点的节点状态量，所述节点状态量至少包括掌握度与生长热度；

S3、在所述知识图谱中，当同一知识节点在预设时间窗内同时接收到错题标记与内容编辑事件时，新增该知识节点与关联知识节点之间的边，或按事件权重提升既有边的边权重，使所述知识图谱的拓扑结构随用户行为持续演化；

S4、按预设周期获取所述知识图谱的演化状态，所述演化状态包括各边的权重变化率与各节点的生长热度；

S5、以所述边的权重变化率与节点生长热度构造非均匀采样分布，按该分布从候选任务集合中抽取预设数量的任务作为本周任务，其中权重变化率或生长热度越高，其被采样概率越大；

S6、根据被抽取任务所覆盖知识节点的生长贡献度确定该任务的金币奖励额度，所述生长贡献度与节点的生长热度正相关、与节点的掌握度负相关；

S7、将确定的任务与奖励额度下发至客户端并在用户完成后，经服务端校验所述任务的完成条件成立，向用户账户发放所述金币奖励。

**权利要求 2（从属）** 根据权利要求 1，其特征在于，S3 中边权重的更新满足：`w(t+1) = w(t) × (1-λ) + λ × Σ(事件权重)`，其中 λ 为遗忘因子，事件权重按"错题标记 > 内容编辑 > 普通浏览"降序取值。

**权利要求 3（从属）** 根据权利要求 1，其特征在于，S5 中所述非均匀采样分布由下式构造：`p_i = softmax( (α·Δw_i/Δt + β·heat_i) / T )`，其中 `Δw_i/Δt` 为第 i 个节点的边权重变化率，`heat_i` 为生长热度，`T` 为温度参数，且 `T` 随用户学习活跃度自适应调整。

**权利要求 4（从属）** 根据权利要求 1，其特征在于，S6 中所述生长贡献度满足：`contribution = heat_i × (1 - mastery_i)`，且当 `mastery_i` 高于第一阈值时该节点不参与任务采样；当 `heat_i` 高于第二阈值但 `mastery_i` 低于第三阈值时，奖励额度乘以大于 1 的加成系数。

**权利要求 5（从属）** 根据权利要求 1，其特征在于，还包括对被采样任务设置冷却期：同一节点在预设冷却周期内不被重复采样，且冷却周期长度与该节点的生长热度负相关。

**权利要求 6（从属）** 根据权利要求 1，其特征在于，所述任务被置顶显示时按稀缺系数提高奖励额度，且同一周期内被置顶的任务数量受上限约束，所述上限由服务端按用户分群动态配置。

### 4.2 技术方案流程图（文字版）

```
【采集】用户答题 / 标错题 / 编辑笔记
   ↓（事件总线，异步）
【节点状态更新】
   mastery_i ← EMA(正确率, 遗忘曲线)
   heat_i    ← 指数衰减 + 本次事件增量
   ↓
【边演化】
   若 错题 与 编辑 在同一窗口内命中同一节点 → 新建边 / w += λ·Δ
   否则仅衰减：w ← w·(1-λ)
   ↓
【采样】
   Δw_i/Δt = (w_i(t) - w_i(t-Δ)) / Δ
   p_i = softmax((α·Δw_i/Δt + β·heat_i)/T)
   抽 N 个节点 → 生成任务模板（做题/重做错题/整理笔记）
   ↓
【奖励】
   contribution_i = heat_i × (1 - mastery_i)
   reward = base × Π(1 + γ·contribution_i)  （封顶 500 币）
   ↓
【下发与校验】
   growth 域记录本周任务 → 用户完成 → exam 域聚合校验 → reward 域发放
   ↓
【回流】
   完成结果再次写回节点状态（形成闭环，图谱继续生长）
```

### 4.3 与现有技术的差异点

| 维度 | 现有个性化任务推送 | 现有知识追踪密集奖励 | 本方案 |
|---|---|---|---|
| 任务来源 | 静态规则 + 用户画像标签 | 基于掌握度预测的固定题库 | **图谱结构自身演化速度**驱动采样 |
| 结构变化 | 不建模知识结构 | 假设结构固定（如先修关系表） | **边由行为动态新增/加权**，结构本身随时间变 |
| 奖励依据 | 完成量 / 难度标签 | 掌握度提升量 | **生长贡献度 = 热度×(1-掌握度)**，奖励"正在快速生长但尚未掌握"的节点 |
| 冷启动 | 依赖历史标签 | 依赖做题量 | 错题+编辑事件即可建立首批边，冷启动更快 |

**可专利性关键**：不是"随机出题"，而是"**用图谱演化的速度分布替代均匀随机**"，且奖励函数与结构演化耦合。建议查新检索式（供代理人使用）：
`(knowledge graph OR 知识图谱) AND (task generation OR 任务生成) AND (weight update OR 权重更新) AND (sampling distribution OR 采样分布)`。

### 4.4 落地建议

1. **编辑端只做外壳**：任意支持 Markdown/双链的客户端均可作为编辑端，通过统一事件上报（`node_ref`, `event_type`, `ts`）接入；服务端不依赖任何特定软件的数据格式。
2. **独立后端服务**（挂在 knowledge 域内，不新建大域）：
   - `kg_node_state(point_id, mastery, heat, updated_at)`
   - `kg_edge_weight(from_node, to_node, rel_type, weight, heat, updated_at)`
   - `kg_event(event_id, user_id, point_id, event_type, weight, ts)`
   - 服务：`kg_sampling.py`（采样分布）、`kg_contribution.py`（贡献度与奖励加成）、`kg_decay.py`（每日衰减）
3. **奖励联动**：knowledge 域产出"任务候选 + 贡献度"，growth 域落任务，reward 域发放；知识域不写金币。
4. **上线顺序建议**：先上线"图谱+采样"的只读版本（只在后台算、不真的发任务），积累 4 周数据后再开放真实任务，避免采样质量差导致用户反感。

### 9.1 问题（用户实测发现）

用户兑换「视频会员日卡」后问"兑换的商品在哪看"。实测发现两层问题：

1. **没有交付物**：种子数据把 18 个商品的 `deliverable_type` 配成了 `none`，
   `deliverable_service.deliver()` 对未知类型只记日志不发货 → 扣币成功、订单落库、什么都没拿到；
2. **没有查看入口**：`gold_purchase.vue` 的 5 个页签里「明细」是金币流水，不是兑换订单；
   `GET /api/shop/exchange/mine` 是我 M1 才加的接口，前端尚未接入。

### 9.2 落地内容

| 模块 | 实现 |
|---|---|
| 数据模型 | 新表 `shop_code`（卡密池，唯一码 + status + 领取人）；`coin_exchanges` +3 列（`delivered_code`/`delivered_at`/`shipped_at`） |
| 交付层 | `deliverable_service` 新增 `code`（从码池按最早入库领取，写回兑换单）与 `manual`（实物/待开通，兑换单置 `pending`）两种类型；头像框 payload 兼容 `frame`/`frame_id`/`avatar_frame` |
| **交付防线** | 兑换前校验：`deliverable_type` 不在 `{title, avatar_frame, code, manual}` → 400「该商品尚未配置交付方式（已阻止扣币）」；`code` 类无可用码 → 400「暂无可用卡密（未扣币）」；交付失败（并发抢完）→ 整体回滚，用户不扣币 |
| 接口 | `POST /api/shop/exchange` 返回 `delivered_code` / `status` / 提示语；`GET /api/shop/exchange/mine` 返回 `deliverable_type`/`delivered_code`/`delivered_at`/`shipped_at`/`status_text` |
| 管理端 | `POST /api/admin/shop/products/{id}/codes`（批量导入，重复码跳过）、`GET .../codes/stats`（可用/已分配/停用）、`GET /api/admin/shop/orders?status=pending`、`POST /api/admin/shop/orders/{id}/ship`（标记发货/开通） |
| 种子修正 | 20 个商品的交付类型改为真实值：`code` 4 个（视频会员日卡/周卡、电商卡 30/100）、`manual` 14 个（教辅/文具/数码/题库会员/虚拟道具）、`avatar_frame` 1 个；`none` 清零 |
| 历史数据 | 回填 2 条历史兑换单的交付类型；把「题库月卡」那单置为 `pending`（待运营开通） |
