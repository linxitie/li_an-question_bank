## 0. 一页结论

### 0.1 现在要不要做容器化

**不建议现在把日常开发环境迁进容器；建议现在完成“部署态容器化”的设计和可验证编排，等学校服务器参数确定后一次切换。**

| 场景 | 现在做 | 结论与理由 |
|---|---|---|
| 教师/开发者本机日常开发 | **否** | VTJ 设计器依赖 9527、前端热更新、Python 3.13 与 MinerU 的 Windows 差异、7.1 GB 题图 bind mount 在 Windows 上性能差；容器化只会增加调试成本。保留现有 start_system.bat / Vite / uvicorn 方式。 |
| 学校单台服务器部署 | **是，推荐** | 需要可复现、可回滚、资源隔离、最小权限、统一日志；这些正是容器的价值。 |
| 多人协作 | **部分** | 协作问题主要靠 Git 分支纪律解决，容器只保证“大家跑的是同一个运行时”，不能替代分支规范。 |
| 多实例 / 高可用 | **否，当前架构不支持** | SQLite 单写者；要多实例必须先迁 PostgreSQL/MySQL + 共享对象存储 + Redis，属于下一阶段架构改造，不在本方案内。 |

**决策：本方案现在只交付“部署态设计 + 可执行编排 + 验收/回滚手册”，不切换生产、不改业务代码。** 等学校服务器 OS、CPU/内存、磁盘、域名、TLS、数据迁移窗口确定后再执行 P6。

### 0.2 目标拓扑（最小）

~~~
浏览器
  │ 80/443
  ▼
web（nginx + 前端 dist，1 个容器，非 root）
  │ /api /static
  ▼
backend（FastAPI 单体，1 个容器，非 root，单 worker）
  ├── /app/data          SQLite + 四库投影目录（宿主 bind）
  ├── /app/app/static    题图/题组图/图片（宿主 bind，7.1 GB）
  ├── /app/uploads       上传文件（宿主 bind，886 MB）
  └── /app/logs          应用日志（宿主 bind）
        │ 仅 OCR 需要
        ▼
parser（MinerU sidecar，可选 profile，非 root）
~~~

- **核心只有 2 个容器：web + backend。**
- parser 是可选 profile，只在扫描件 OCR 导入时启动。
- Redis 是可选 profile，只在多 worker / WS 中继时启动。
- MinIO / Neo4j / Milvus 是四库投影的可选后端，默认不启动。
- **SQLite 不是容器，是宿主上的一个文件。** 把 SQLite 放进独立容器只会增加丢数据风险，不会带来任何好处。

### 0.3 与旧方案的最大区别

| 旧方案 v1 | 本方案 v2.0 |
|---|---|
| 13 个服务 + PostgreSQL + Redis + 微前端 | 2 个核心容器；SQLite 文件；parser/Redis 可选 |
| 按业务拆“模块” | 不拆模块；题目管理/试卷管理等只是同一 FastAPI 进程内的路由域 |
| 前端挂宿主机 dist | 前端 dist 打进 web 镜像，不可变交付 |
| 命名卷 qimg 首次为空 | 宿主目录 bind，preflight 拒绝空题图目录 |
| 无资源限制、无只读根文件系统 | limits / read_only / cap_drop / pids_limit / no-new-privileges |
| 无备份恢复编排 | sqlite3.backup() + 静态清单 + 恢复演练 |
| 只验证过 YAML | 分阶段验收，P2 起在 staging 真跑 |

## 1. 范围、术语与不做的事

### 1.1 范围

**做：**

1. 单机 Docker Compose 部署编排（web / backend / 可选 parser / 可选 Redis）。
2. 四库映射在容器环境中的“状态有家”：SQLite、图片、文档、图、向量各自挂哪里、备哪里、能否重建。
3. 安全、资源、生命周期、网络、交付、可观测性六类约束。
4. 数据迁移、备份恢复、回滚、验收。
5. 配套 GitHub 拉取/更新/上传/合并操作手册。

**不做：**

1. 不拆微服务，不引入消息队列，不做微前端。
2. 不改任何 /api/v1 路径，不改 .vtj 页面模板，不改业务表结构。
3. 不把 7.1 GB 题图打进镜像，也不把 SQLite 主库打进镜像。
4. 不在本阶段迁 PostgreSQL/MySQL，不做多实例。
5. 不默认启用 MinIO/Neo4j/Milvus；只有显式切换四库后端时才加 profile。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| 部署态 | 学校服务器/长期运行环境，不是开发者本机 |
| 状态 | 容器删除后必须仍然存在的数据：数据库、题图、上传、日志、备份 |
| 四库 | 关系库（SQLite 为 SoT）+ 图片库 + 文档库 + 图库 + 向量库（后四类是可重建投影，详见四库文档） |
| 投影 | 从 SQLite 事实重新生成的数据，允许删除重建；不是新的事实源 |
| 不可变镜像 | 同一 IMAGE_TAG 对应同一份代码与前端产物，部署时不改镜像内容 |

## 2. 现状实测（2026-10-30）

### 2.1 架构事实

| 项 | 实测 |
|---|---|
| 后端 | 单一 FastAPI 单体，backend/app/main.py，约 343 个端点 |
| 前端 | VTJ / Vue 3 / Vite，构建产物 dist（23 MB） |
| 数据库 | SQLite，WAL 模式，唯一事实源；主库 58,118,144 字节，WAL 5,401,352 字节 |
| 运行方式 | uvicorn 单 worker；WEB_CONCURRENCY>1 且 WS_RELAY 非 redis 时启动期拒绝 |
| 必需中间件 | 无 PostgreSQL、无 Redis 也可运行 |
| OCR | MinerU sidecar（Python 3.11），主后端 Python 3.13 不能直接装 MinerU/PaddleOCR |
| 反向代理 | nginx，/api 与 /static 反代 backend，SPA fallback |
| Docker | Docker 29.8.2（Docker Desktop，overlayfs），Compose v5.6.0 |

### 2.2 数据体量

| 路径 | 实测 | 说明 |
|---|---:|---|
| backend/app/static/questions | 7.1 GB | 题图主库，绝不入镜像 |
| backend/app/static/question-groups | 182 KB | 题组材料图 |
| backend/uploads | 886 MB / 5960 文件 | 用户上传 |
| backend/data/foundation/objects | 29 MB / 898 文件 | F3 对象存储本地后端 |
| backend/data/foundation/docs | 16 MB | F4 文档投影 |
| backend/data/foundation/vectors | 未单列 | F6 向量投影，默认关闭 |
| dist | 23 MB | 前端构建产物 |
| backend/data/question_bank.db | 58,118,144 字节 | SQLite 主库 |
| backend/data/question_bank.db-wal | 5,401,352 字节 | 必须与主库一起看待 |
| backend/data 下的 .bak* | 41 份 | 历史备份，不挂进容器运行目录 |
| backend/data/init_data.sql | 309 MB | 初始化脚本，不是运行时数据 |
| D: 盘 | 274 GB / 已用 187 GB / 可用 87 GB | 单机 staging 够用，生产需另算 |

### 2.3 已有容器资产及缺陷

已有文件：backend/Dockerfile、backend/parser/Dockerfile、docker-compose.yml、deploy/nginx.conf、deploy/.env.example、backend/.dockerignore、backend/docker-entrypoint.sh。

**这些文件是“半成品”，不是可直接交付的部署方案。** 主要缺陷：

| # | 缺陷 | 后果 | 本方案处理 |
|---|---|---|---|
| C1 | qimg 使用命名卷，首次创建为空 | 题图全 404；entrypoint 只警告不阻断 | 改为宿主目录 bind，preflight 空目录直接失败 |
| C2 | parser 被 backend 无条件 depends_on | 不需要 OCR 也要起一个数 GB 的 sidecar | parser 改 optional profile，PARSER_URL 默认空 |
| C3 | 无 CPU/内存/pids/read_only/cap_drop/security_opt | 单容器可吃满宿主；被攻破后权限过大 | 全服务加 limits / read_only / cap_drop / no-new-privileges |
| C4 | nginx 挂宿主机 dist | 交付物可变，回滚不可复现 | 前端 dist 打进 web 镜像 |
| C5 | 无前端构建镜像 | 部署依赖“本机先 npm run build” | 新增 deploy/Dockerfile.web 多阶段构建 |
| C6 | 无 TLS/域名 | 只能 HTTP，登录凭据明文 | P4 决定学校网关终止还是 nginx 终止 |
| C7 | 无日志轮转 | json-file 无限增长，磁盘被日志吃满 | 20 MB × 5 轮转 + 应用日志目录 |
| C8 | 无备份/恢复编排 | 容器删了数据就没了 | P5 新建 backup/restore 脚本并演练 |
| C9 | env_file 固定找 deploy/.env.development | 全新机器直接 config 失败 | 显式 APP_ENV_FILE，preflight 校验 |
| C10 | 镜像注释仍写 static 4.27 GB | 与实测 7.1 GB 不符，容量规划失真 | 文档与脚本按实测值 |
| C11 | 从未执行过 docker compose up | 现有 compose 只是“YAML 能过” | P2 起 staging 真跑，未跑不算完成 |
| C12 | Dockerfile 注释引用 backend/scripts/backup_db.py / restore_db.py | 仓库实测不存在这两个通用脚本 | P5 新建，不引用不存在的路径 |

## 3. 必要性判断：现在做，还是等学校服务器

### 3.1 判断矩阵

| 维度 | 权重 | 现在做的收益 | 现在做的成本 | 结论 |
|---|---:|---|---|---|
| 可复现部署 | 高 | 高；一次构建，多处运行 | 中；需补 web 镜像、preflight | 现在做 |
| 回滚能力 | 高 | 高；按 IMAGE_TAG 回滚 | 低 | 现在做 |
| 资源隔离 | 中 | 中；limits 防止单容器吃满 | 低 | 现在做 |
| 安全基线 | 高 | 高；非 root/只读/最小权限 | 中；parser 需改非 root | 现在做 |
| 开发效率 | 高 | **负收益**；Windows bind mount 慢、VTJ 调试复杂 | 高 | 现在不做 |
| 多人协作 | 中 | 中；运行时一致 | 低 | 配套 Git 手册 |
| 高可用 | 低（当前） | 无；SQLite 单写者 | 极高 | 不做 |

### 3.2 触发条件（满足任一组再切换生产）

**必须全部满足：**

1. 学校服务器 OS 已确定（建议 Ubuntu 22.04/24.04 LTS 或 Debian 12）。
2. CPU ≥ 4 核、内存 ≥ 8 GB、数据盘可用 ≥ 100 GB（题图 7.1 GB + 上传 0.9 GB + 备份空间）。
3. 域名与 TLS 方案确定（学校网关终止，或服务器 80/443 可直接访问）。
4. 有至少 2 小时停机窗口做数据迁移与回滚演练。
5. 备份目标（另一块盘/NAS/对象存储）可用。

**任一不满足：只做 staging，不上生产。**

### 3.3 结论

**“现在做容器化”应理解为“现在做容器化交付物”，不是“现在把开发机搬进容器”。**
等服务器到位再从零设计，会把风险堆到上线当天；现在把编排、数据迁移、备份、回滚、验收做出来，上线只是执行。

## 4. 七条硬约束的落实

### R-01 安全左移：默认不信任、最小权限

| 要求 | 落实 |
|---|---|
| 非 root | backend 以 APP_UID 运行；web 用 nginx-unprivileged；parser 新建 uid 10001，禁止 root |
| 只读根文件系统 | 三个服务 read_only: true，仅 /tmp 与数据卷可写 |
| 能力最小化 | cap_drop: ALL；web 不监听 80，容器内监听 8080，由宿主映射 |
| 禁止提权 | security_opt: no-new-privileges:true |
| 进程数限制 | pids_limit，防 fork 炸弹 |
| 密钥不入镜像 | .dockerignore 排除 .env*；运行时 env_file 注入；镜像构建后扫描 |
| 镜像扫描 | P4 用 trivy 或 docker scout 扫描 HIGH/CRITICAL；不通过不部署 |
| 依赖最小 | 基础镜像固定 tag；不装编译器；parser 与 backend 分离 |

### R-02 资源与生命周期：没有 limits 就没有稳定性

| 要求 | 落实 |
|---|---|
| CPU/内存上限 | 每个服务 deploy.resources.limits；按 8 GB / 16 GB 两档预设 |
| 健康检查 | backend /health；web /healthz；parser /health；start_period 覆盖冷启动 |
| 自动重启 | restart: unless-stopped；但配置错误导致的崩溃不靠重启掩盖，preflight 先失败 |
| 优雅关闭 | stop_grace_period: 30s；tini 转发信号；uvicorn 收到 SIGTERM 后停止接收新请求 |
| 启动顺序 | web 等 backend healthy；backend 不强制等 parser |
| 磁盘保护 | 日志轮转、备份保留策略、镜像/悬空卷清理 |

### R-03 数据与状态：容器无状态，状态必须有家

| 状态 | 容器内路径 | 宿主路径 | 是否可重建 |
|---|---|---|---|
| SQLite 主库 + WAL | /app/data/question_bank.db | DATA_ROOT/question_bank.db | 否，唯一事实源 |
| 四库投影目录 | /app/data/foundation | DATA_ROOT/foundation | 文档/图/向量可重建；对象文件按资产登记 |
| 题图/题组图 | /app/app/static | STATIC_ROOT | 否，原始资产 |
| 上传 | /app/uploads | UPLOAD_ROOT | 否 |
| 应用日志 | /app/logs | LOG_ROOT/backend | 可丢弃，但审计期保留 |
| parser 模型缓存 | /home/parser/.cache | parser_cache 命名卷 | 可重新下载，非业务数据 |

**硬规则：docker compose down -v 会删命名卷；业务数据一律不用命名卷，只用宿主 bind。**

### R-04 网络：从“能通”到“可控”

| 网络 | 成员 | 是否出公网 | 说明 |
|---|---|---|---|
| edge | web, backend | 否（web 只入站） | 只承载浏览器到 web、web 到 backend |
| app | backend, parser | **internal: true，禁止出公网** | 后端与 parser 的内部调用 |
| egress | backend | 是 | 新闻/招聘/外部 API 抓取；由宿主防火墙做域名/IP 白名单 |
| 宿主端口 | 仅 web 的 HTTP_PORT/HTTPS_PORT | — | backend 8000、parser 8080 一律不 publish |

- 生产环境删除 backend 的 127.0.0.1:8000 调试端口。
- parser 运行期不出公网；模型在构建/首次部署时预置到 parser_cache。
- 若学校要求完全离线，禁用 egress 网络的出站，新闻抓取功能降级并明确告知。

### R-05 交付与配置：不可变镜像 + 外置配置

| 要求 | 落实 |
|---|---|
| 镜像不可变 | IMAGE_TAG 用 git commit sha 或 vX.Y.Z；禁止 latest；生产 pull 后不 build |
| 前端不可变 | dist 打进 web 镜像；生产不挂宿主机 dist |
| 配置外置 | 所有环境差异走 APP_ENV_FILE；镜像内只有默认值 |
| 构建可复现 | 固定基础镜像 tag；package-lock / requirements 锁定；CI 构建 |
| 回滚 | 保留上一版 IMAGE_TAG；docker compose up -d 即回滚；数据库回滚单独演练 |

### R-06 可观测性：容器会消失，日志和指标不能

| 层 | 手段 |
|---|---|
| 存活 | docker healthcheck + /health |
| 就绪 | backend /health、/health/foundation；web /healthz |
| 指标 | 现有 /metrics、/metrics/system 返回 JSON；P5 决定是否加 Prometheus 适配器，不假设已有 Prometheus |
| 日志 | json-file 20 MB × 5；应用日志挂 LOG_ROOT；nginx access/error 走 stdout |
| 审计 | 导入/发布/删除等业务操作仍写库；容器日志不作为唯一审计源 |
| 告警 | 健康检查连续 3 次失败、磁盘 >80%、备份超过 26 小时未成功、5xx 比例异常 |

### R-07 协作与变更控制

单独成册：docs/ops/GitHub协作与容器化交付手册_v1.md。核心规则：

- main 保护，禁止直接 push；一任务一分支；PR 合并。
- 容器镜像由 CI 构建，开发者本机不 push latest。
- 数据（.db、static、uploads、.env）不进 Git，不通过聊天工具传。
- 发布必须带 IMAGE_TAG、备份路径、回滚命令、验收记录。

### 4.1 与 AGENTS.md 红线的对应

| AGENTS 红线 | 本方案是否触碰 | 说明 |
|---|---|---|
| R1 .vtj 禁止移动/改名/删除 | 否 | 容器只读构建上下文，不 reorganization |
| R2 raw 页禁 sync | 否 | 不改任何 .vtj 页面 |
| R3 .vtj 模板禁 AI 改 | 否 | 无前端模板改动 |
| R4 device.ts 保留 | 否 | 不涉及 |
| R5 mobile_*/tablet_* 前缀 | 否 | 不涉及 |
| R6 题库/ 禁止删除/移动 | 否 | 题库只作为构建上下文排除对象，不挂载进运行容器 |
| R7 backend/app/static 禁止删除 | **重点保护** | 只 bind，不 COPY，不 down -v |
| R8 data/*.bak* 禁止清理 | 否 | 运行目录只选主库，不碰 41 份备份 |
| R9 audit/待推断清单不是垃圾 | 否 | 不挂载、不清理 |
| R10 数据库备份禁用 shutil.copy2 | **重点保护** | 统一 sqlite3.backup()，恢复同时处理 -wal/-shm |
| R11 /api/v1 冻结 | 否 | nginx 只透传，不改写 |
| R12 不为平板复制手机页 | 否 | 无前端改动 |

## 5. 目标架构

### 5.1 组件清单

| 组件 | 镜像 | 必需 | 职责 | 对外端口 |
|---|---|---|---|---|
| web | 自建 web 镜像（nginx-unprivileged + dist） | 是 | 静态前端、/api 与 /static 反代、TLS 终止（可选） | 80/443 |
| backend | 自建 backend 镜像 | 是 | FastAPI、SQLite、四库读写、业务 API | 无，仅 expose 8000 |
| parser | 自建 parser 镜像（MinerU） | 否 | 扫描件 PDF → Markdown | 无，仅 expose 8080 |
| redis | redis:7-alpine | 否 | 多 worker 的 WS 中继/事件总线 | 无 |
| minio | minio/minio | 否 | 图片对象存储后端（F3 切换时） | 无 |
| neo4j | neo4j:5 | 否 | 图投影后端（F5 切换时） | 无 |
| milvus | milvusdb/milvus | 否 | 向量投影后端（F6 切换时） | 无 |

**默认只启动 web + backend。** parser、redis、minio、neo4j、milvus 全部用 profiles 控制，避免“一上来起 13 个服务”。

### 5.2 为什么数据库不容器化

1. SQLite 是文件，不是网络服务；容器化只会多一层挂载与权限问题。
2. SQLite WAL 对文件系统语义敏感；容器层/网络卷可能破坏锁与 fsync 语义。
3. 备份必须用 sqlite3.backup()，容器化不改变这一事实；反而更容易误把 -wal/-shm 留在匿名卷里。
4. 单机部署下，宿主文件 + 单 backend 写入是最简单、最可恢复的形态。

**什么时候才考虑数据库独立容器：** 需要多实例/高可用时，迁 PostgreSQL/MySQL，并配 PgBouncer/连接池；那是架构升级，不是“容器化”。

### 5.3 为什么前端要进镜像

- 挂宿主机 dist 时，git pull 后忘记 npm run build 就会出现“代码是新版、页面是旧版”。
- 回滚镜像时 dist 不会跟着回滚。
- 前端构建需要 Node 22、依赖 lock、VTJ 资源；这些应固化在 CI，而不是部署机。

**开发例外：** 本地调试可挂 dist 覆盖，但必须在文档中标注“仅开发”，生产 preflight 拒绝该挂载。

## 6. 四库映射在容器中的落地

> 四库的权威定义见 docs/superpowers/specs/题目入库知识图谱与四库映射_v1.md。本节只回答“容器里放哪、怎么备、能不能重建”。

### 6.1 一张表

| 库 | 事实/投影 | 容器内位置 | 宿主位置 | 备份 | 可重建 | 说明 |
|---|---|---|---|---|---|---|
| 关系库 SoT | SQLite 全部业务表 | /app/data/question_bank.db | DATA_ROOT/question_bank.db | sqlite3.backup()，每 6 小时 + 每日 | 否 | 唯一事实源；WAL 同目录 |
| 图片库（元数据） | media_assets 937 行（active 896 / missing 41） | SQLite 内 | 随主库 | 随主库 | 否（元数据） | P1 已登记 |
| 图片库（文件） | /static/questions、question-groups、images | /app/app/static | STATIC_ROOT | rsync 增量 + 周度离线 | 否 | 7.1 GB；源文件不可再生 |
| 图片库（对象） | F3 本地对象 896 个 / 27,767,544 字节 | /app/data/foundation/objects | DATA_ROOT/foundation/objects | 随 DATA_ROOT 增量 | 部分（有源文件可重登） | MinIO 仅在切换时启用 |
| 文档库 | question_documents / group_documents / import_snapshots / exam_resources | /app/data/foundation/docs + SQLite | DATA_ROOT/foundation/docs | 可选，随 DATA_ROOT | **是**（从 SoT 重建） | 投影，不是事实 |
| 图库 | foundation_graph_node / foundation_graph_edge | SQLite 表；Neo4j 可选 | 随主库 | 随主库 | **是** | local 后端就在同一 SQLite |
| 向量库 | text_questions / text_materials | SQLite 表 + /app/data/foundation/vectors | DATA_ROOT/foundation/vectors | 可选 | **是** | 默认关闭；可重建 |
| 上传 | 用户上传文件 | /app/uploads | UPLOAD_ROOT | rsync 增量 | 否 | 886 MB |
| 导入快照 | import_snapshots 等 | /app/data/foundation 或 SQLite | DATA_ROOT | 随 DATA_ROOT | 部分 | 审计价值，按保留策略 |

### 6.2 三条硬规则

1. **四库不是四个容器。** 关系库是文件；图片库是文件 + SQLite 元数据；文档/图/向量是投影。只有显式切换后端时才加 MinIO/Neo4j/Milvus 容器。
2. **投影可以重建，事实不能丢。** 文档/图/向量库损坏时，停投影、从 SQLite 回填、对账；不要反向用投影覆盖 SoT。
3. **对象存储切换要成对切换。** OBJECT_STORE_BACKEND=local 时对象在 DATA_ROOT/foundation/objects；切 minio 时必须有迁移与回滚方案，不能只改环境变量。

### 6.3 容量预算

| 项 | 当前 | 容器部署建议 |
|---|---:|---|
| 题图 | 7.1 GB | 数据盘 ≥ 20 GB 余量 |
| 上传 | 886 MB | 按 3 年增长预留 5 GB |
| 主库 + WAL | 63.5 MB | 备份保留 14 天约 1 GB |
| 对象/文档/向量 | 45 MB | 预留 5 GB |
| 镜像 | 未实测 | backend + parser 预计 5-8 GB（Playwright/MinerU） |
| 日志 | 未实测 | 每服务 100 MB 上限 |
| 备份 | 未实测 | 至少 2 倍数据量 |

**8 GB 内存服务器：** 可跑 web + backend；parser 只在导入窗口启动，不能与大规模 OCR 并发。
**16 GB 内存服务器：** 可常驻 parser，但仍建议按需启动。

## 8. Docker Compose v2 设计

> 下面是设计稿，不是已落盘文件；P1 才写入 deploy/docker-compose.yml 并用 docker compose config 校验。占位符 ${...} 在最终文件中是正常的 Compose 变量插值。

### 8.1 顶层与日志

### 8.2 web（前端 + 反代，唯一对外）

~~~yaml
  web:
    image: ${REGISTRY:-ghcr.io/linxitie}/li_an-question_bank-web:${IMAGE_TAG:?IMAGE_TAG required}
    build:
      context: .
      dockerfile: deploy/Dockerfile.web
    restart: unless-stopped
    ports:
      - "${HTTP_PORT:-80}:8080"
    depends_on:
      backend:
        condition: service_healthy
    networks: [edge]
    read_only: true
    tmpfs:
      - /tmp:size=64m,mode=1777
      - /var/cache/nginx:size=64m
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    pids_limit: 128
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 128M
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/healthz"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    logging: *default-logging
~~~

要点：

- 镜像内 nginx 监听 8080，宿主映射 80；不用 root 绑定 80。
- 不挂 ./dist；dist 已在镜像里。
- 只读根文件系统；nginx 需要写的只有 /tmp 与 /var/cache/nginx。
- depends_on 用 service_healthy，不用 service_started。

### 8.3 backend（FastAPI + SQLite）

~~~yaml
  backend:
    image: ${REGISTRY:-ghcr.io/linxitie}/li_an-question_bank-backend:${IMAGE_TAG:?IMAGE_TAG required}
    build:
      context: ./backend
      dockerfile: Dockerfile
    restart: unless-stopped
    env_file:
      - "${APP_ENV_FILE:-./deploy/.env.production}"
    environment:
      TZ: Asia/Shanghai
      SQLITE_PATH: /app/data/question_bank.db
      UPLOAD_DIR: /app/uploads
      OBJECT_STORE_ROOT: /app/data/foundation/objects
      DOC_STORE_ROOT: /app/data/foundation/docs
      VECTOR_LOCAL_ROOT: /app/data/foundation/vectors
      PARSER_URL: "${PARSER_URL:-}"
      WEB_CONCURRENCY: "1"
      PYTHONDONTWRITEBYTECODE: "1"
      UVICORN_LOG_LEVEL: info
    user: "${APP_UID:-1000}:${APP_GID:-1000}"
    volumes:
      - type: bind
        source: ${DATA_ROOT:?DATA_ROOT required}
        target: /app/data
      - type: bind
        source: ${STATIC_ROOT:?STATIC_ROOT required}
        target: /app/app/static
      - type: bind
        source: ${UPLOAD_ROOT:?UPLOAD_ROOT required}
        target: /app/uploads
      - type: bind
        source: ${LOG_ROOT:?LOG_ROOT required}/backend
        target: /app/logs
    expose: ["8000"]
    networks: [edge, app, egress]
    read_only: true
    tmpfs:
      - /tmp:size=512m,mode=1777
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    pids_limit: 512
    stop_grace_period: 30s
    deploy:
      resources:
        limits:
          cpus: "2.00"
          memory: 2G
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://127.0.0.1:8000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s
    logging: *default-logging
~~~

要点：

- 单 worker 是硬约束，不是性能建议；SQLite 写并发靠单进程串行化。
- 数据全部 bind，不用命名卷；down -v 不会删业务数据。
- 只读根文件系统；题图目录必须可写（导入会落图），其余数据卷可写。
- 不 publish 8000；调试时用 docker compose exec，不开放宿主端口。
- 健康检查用已有 /health，不新增重复端点。

## 9. 资源、生命周期与启动顺序

### 9.1 资源预设

| 服务 | 8 GB 服务器 | 16 GB 服务器 | 说明 |
|---|---|---|---|
| web | 0.5 CPU / 128 MB | 1 CPU / 256 MB | 静态与反代，压力小 |
| backend | 2 CPU / 2 GB | 4 CPU / 4 GB | Playwright/PDF 解析会吃内存 |
| parser | 2 CPU / 4 GB（按需） | 4 CPU / 6 GB（按需） | MinerU 模型大；不 OCR 就停 |
| redis | 0.5 CPU / 256 MB（可选） | 1 CPU / 512 MB | 仅 scale |
| 合计常驻 | 约 2.2 GB | 约 4.3 GB | 留足系统与页缓存 |

**不要**把 limits 设成等于宿主机全部内存；SQLite 依赖页缓存，留 25% 余量。

### 9.2 生命周期

| 事件 | 行为 |
|---|---|
| 宿主重启 | Docker 自启 + restart: unless-stopped；web 等 backend healthy 后可用 |
| backend 崩溃 | 自动重启；连续失败由 healthcheck 标记 unhealthy，需人工看日志 |
| 配置错误 | 启动即失败；preflight 在 up 之前拦截，不靠重启循环 |
| 发布 | pull 新镜像 → 备份 → up -d → 健康检查 → 烟测 → 失败回滚旧 tag |
| 停机 | docker compose stop；30s 优雅关闭；不要 kill -9 |
| 删栈 | docker compose down；**禁止 -v**；业务数据在宿主，不受影响 |

### 9.3 启动顺序

1. 宿主目录/权限/磁盘 preflight。
2. backend 启动：entrypoint 检查 DB、题图目录、日志目录；uvicorn 监听 8000。
3. backend healthcheck 通过。
4. web 启动，nginx 反代 backend。
5. parser 仅在 ocr profile 下启动，不影响核心链路。

**parser 不能成为 backend 的硬依赖。** 没有 OCR 需求时，backend 必须能独立工作。

## 10. 安全设计

### 10.1 镜像

- 固定基础镜像 tag；生产用 digest 更佳。
- backend 非 root（现有 Dockerfile 已是 app 用户）；web 用 nginx-unprivileged；parser 必须改非 root。
- 不在镜像里放 .env、密钥、数据库、题图、上传。
- 构建后扫描：trivy image --severity HIGH,CRITICAL；有未修复严重漏洞则阻断发布，记录例外与到期日。
- 不在生产镜像里装编译工具链；parser 的 apt 依赖单独层，构建完清理 apt lists。

### 10.2 运行时

| 项 | 设置 |
|---|---|
| 根文件系统 | read_only: true |
| 可写 | /tmp tmpfs、数据 bind、日志 bind |
| capabilities | cap_drop: ALL |
| 提权 | no-new-privileges |
| 进程数 | pids_limit |
| 用户 | 数字 uid，与宿主目录属主一致 |
| 端口 | 只有 web 发布 |
| 密钥 | env_file 600；不写命令行参数（避免 ps 泄露） |

### 10.3 网络

- app 网络 internal，parser 不出公网。
- egress 仅 backend；学校防火墙按域名白名单放行新闻/招聘站点。
- 不对公网开放 8000/8080；调试用 exec 或临时 SSH 隧道。
- TLS：优先学校网关终止；本机终止时只开 443，80 跳转 443；禁用 TLS 1.0/1.1。

### 10.4 数据

- 备份文件权限 600；备份目录不放 Web 根目录。
- 恢复前先备份当前库；恢复后校验 integrity_check 与关键表计数。
- 不把数据库文件放在 NFS/SMB；SQLite 锁语义不可靠。
- 不在容器内跑 sqlite3 CLI 直接改库；用应用/脚本，保持 WAL 语义。

## 11. 数据迁移、备份与恢复

### 11.1 首次迁移步骤

**Step 0 冻结**

- 公告停机窗口；停止教师端写入（导入/发布/编辑）。
- 记录当前版本、题目数、题组数、media_assets 数、static 文件数、uploads 文件数。

**Step 1 备份数据库（R10）**

不要用 cp/shutil.copy2。用 Python sqlite3.backup()：

~~~bash
python - <<'PY'
import sqlite3, datetime, pathlib
src = pathlib.Path("backend/data/question_bank.db")
dst = pathlib.Path("backups/db") / f"question_bank_{datetime.datetime.now():%Y%m%d_%H%M%S}.db"
dst.parent.mkdir(parents=True, exist_ok=True)
with sqlite3.connect(src) as s, sqlite3.connect(dst) as d:
    s.backup(d)
print(dst)
PY
~~~

校验：

~~~bash
python - <<'PY'
import sqlite3
p = "backups/db/REPLACE.db"
with sqlite3.connect(p) as c:
    print(c.execute("PRAGMA integrity_check").fetchone())
    for t in ("question_bank", "question_groups", "media_assets"):
        print(t, c.execute(f"SELECT COUNT(*) FROM {t}").fetchone()[0])
PY
~~~

**Step 2 静态资产清单**

~~~bash
find backend/app/static -type f -printf '%P\t%s\n' | sort > backups/static_manifest_before.tsv
wc -l backups/static_manifest_before.tsv
du -sb backend/app/static
~~~

**Step 3 复制到部署目录**

~~~bash
rsync -a --info=progress2 backend/app/static/ /srv/liankao/static/
rsync -a --info=progress2 backend/uploads/ /srv/liankao/uploads/
rsync -a --info=progress2 backend/data/foundation/ /srv/liankao/data/foundation/
cp backups/db/REPLACE.db /srv/liankao/data/question_bank.db
~~~

不要复制 backend/data 整个目录；只复制主库与 foundation。

**Step 4 权限**

~~~bash
chown -R 1000:1000 /srv/liankao/data /srv/liankao/static /srv/liankao/uploads /srv/liankao/logs
chmod 600 /srv/liankao/secrets/.env.production
~~~

如果 APP_UID 不是 1000，按实际值改。

**Step 5 启动与烟测**

~~~bash
cd /srv/liankao/app
docker compose --env-file /srv/liankao/secrets/.env.production up -d
docker compose ps
curl -fsS http://127.0.0.1/healthz
curl -fsS http://127.0.0.1/api/v1/health 2>/dev/null || true
~~~

烟测至少覆盖：登录、题目列表、题图 200、复合题材料、开考、交卷、导入预览、教师端题目详情。

**Step 6 迁移后校验**

- 题目数、题组数、media_assets 数与迁移前一致。
- static 文件清单行数与总字节一致；抽查 20 张图 HTTP 200。
- 上传文件数一致；抽查 5 个文件可下载。
- SQLite integrity_check=ok。
- 旧环境保持只读，观察 24 小时后再停。

**Step 7 回滚**

- 停止新栈：docker compose down（不加 -v）。
- 恢复旧启动方式（start_system.bat / uvicorn + vite）。
- 用迁移前备份恢复数据库；同时处理 -wal/-shm。
- 旧环境未删，回滚时间目标 ≤30 分钟。

### 11.2 备份策略

| 对象 | 频率 | 方式 | 保留 | 校验 |
|---|---|---|---|---|
| SQLite | 每 6 小时 + 每日 | sqlite3.backup() | 14 日 + 8 周 | integrity_check + 关键表计数 |
| 题图/上传 | 每日增量 | rsync 硬链接/快照 | 14 日 | 清单行数/字节 |
| foundation | 每日增量 | rsync | 14 日 | 文件数 |
| .env.production | 变更时 | 加密离线 | 3 版 | 人工核对 |
| 镜像 tag | 每次发布 | 保留最近 5 个 | — | 可 pull |

**RPO/RTO 建议：** 学校单机场景 RPO ≤ 6 小时（数据库），RTO ≤ 30 分钟。
**重要：** 备份必须复制到另一块盘或另一台机器；同盘备份遇到磁盘故障等于没有。

### 11.3 恢复步骤

1. 停 backend（web 可留，返回维护页）。
2. 备份当前故障库（即使坏了也留证）。
3. 删除 question_bank.db、-wal、-shm（R10：三者一起处理）。
4. 用 sqlite3.backup() 生成的备份恢复；不要直接覆盖正在使用的库。
5. chown 到 APP_UID。
6. 启动 backend，等 healthcheck；跑 integrity_check 与关键计数。
7. 抽查题图、登录、取题、交卷。
8. 记录恢复时间、数据丢失窗口、原因。

| 告警 | 阈值 | 动作 |

## 13. 实施路线（P0–P6）

### P0 决策与冻结（0.5 天）

- 用户确认：是否按本方案执行；学校服务器参数；数据根目录；TLS 方案；parser 是否常驻。
- 记录基线：题目数、题组数、media_assets、static/uploads 文件数、DB 大小。
- 备份数据库与静态清单。
- 产出：本方案批准记录 + 基线报告。

**退出条件：** 用户明确批准 P1；服务器参数表填齐。

### P1 编排与镜像骨架（1–2 天）

- 新增 deploy/docker-compose.yml（v2 设计）。
- 新增 deploy/Dockerfile.web、根 .dockerignore。
- 修改 deploy/nginx.conf 为 8080 + unprivileged。
- 新增 deploy/.env.example（补齐 DATA_ROOT/STATIC_ROOT/...）。
- 新增 deploy/preflight.sh：检查变量、目录、空题图、DB、磁盘、端口。
- parser Dockerfile 改非 root（或明确 P3 再做，但 P1 先设计）。
- 只跑 docker compose config 与 build，不碰真实数据。

**验收：** config EXIT 0；镜像构建成功；preflight 对空目录/缺变量能失败；无密钥进镜像。

**回滚：** 只新增文件，不影响现有启动。

### P2 staging 核心启动（1 天）

- 在 staging 目录复制数据库 + 静态 + 上传（不全量生产）。
- 启动 web + backend。
- 烟测：登录、题目列表、题图、复合题材料、开考、交卷。
- 验证重启后数据仍在；验证 down 不加 -v 不丢数据。

**验收：** 核心链路全绿；数据计数一致；容器无 root；limits 生效。

**回滚：** 停栈，回旧启动；staging 数据可丢弃。

### P3 OCR 与导入（1–2 天）

- parser 非 root 改造；模型预热；OCR profile 启动。
- 扫描件导入烟测（取题库/行测/安徽行测真实 PDF）。
- 文本导入、预览、确认、题组材料、图片落盘。
- 验证 PARSER_URL 为空时文本导入不受影响。

**验收：** OCR 成功；导入后题图可访问；parser 停掉后 backend 不崩。

**回滚：** 停 parser，PARSER_URL 置空，回到纯文本导入。

### P4 前端镜像、TLS 与加固（1–2 天）

- web 镜像构建；不再挂 dist。
- TLS 方案落地（学校网关或 nginx）。
- 只读根文件系统、cap_drop、pids_limit 全量验证。
- 镜像扫描；修 HIGH/CRITICAL 或记录例外。
- 资源 limits 压测：导入大 PDF 时 backend/parser 不 OOM。

**验收：** 生产镜像可回滚；HTTPS 可用；扫描通过；压测无 OOM。

### P5 备份、恢复、可观测性与 CI（1–2 天）

- 新建 backup/restore 脚本（仓库当前没有通用脚本，Dockerfile 注释中的路径不存在）。
- 定时任务 + 备份校验 + 异地复制。
- 恢复演练：从备份恢复到一个空目录，跑烟测。
- 日志轮转、告警、巡检脚本。
- CI：构建镜像、跑门禁、推 GHCR；禁止本地 latest 上生产。

**验收：** 恢复演练成功；RTO 达标；备份失败有告警；CI 产出可追溯。

### P6 学校服务器切换（0.5 天 + 观察）

- 按 11.1 迁移；停机窗口内完成。
- 切换 DNS/网关；观察 24 小时。
- 旧环境保留 7 天；确认无回滚需求再清理。

**总工期估算：6–10 人日**（不含学校服务器采购/网络审批）。
