## 2. 发现的三个真实缺陷

### 2.1 MinerU 超时固定 600s，必然被强杀

- 部署日志实测 CPU pipeline **71.2s/页**；
- 答案解析卷常见 20~30 页 → 需 **1400~2100s**；
- 固定 `MINERU_TIMEOUT=600` → 子进程被 `TimeoutExpired` 杀掉 → 每次静默回退 Paddle。

**修复**：按页动态预算
`timeout = min(MINERU_TIMEOUT_MAX, max(MINERU_TIMEOUT, 120 + MINERU_SECONDS_PER_PAGE × 页数))`
默认 `75s/页`、封顶 `3600s`；页数由 PyPDF2 快速读取，读不到则退回 base 值。

### 2.2 PaddleOCR 只处理前 8 页，答案卷被截断

- `OCR_MAX_PAGES=8`，而答案卷 20~30 页；
- 后 12~22 页的答案/解析完全没进文本 → 与题本按题号匹配时大面积落空（与"答案对不上"同源）。

**修复**：默认 **30 页**，子进程超时 240s → **600s**（20s/页余量，仍由硬超时兜底）。

### 2.3 文本缓存只按文件 md5，引擎结果互相污染

- `text_cache` 键 = `v3_<md5>`，不区分 MinerU / Paddle；
- 先启用 MinerU 导入一次（写入 MinerU 文本），之后关闭 MinerU 再导入同一文件 → **直接命中旧 MinerU 文本**，看起来"配置没生效"；
- 这也是 `TestScannedPdfMineruFallback` 两个用例长期失败的真正原因：三个用例共用同一段 `buf`，第一个用例的 MinerU 结果被后两个命中。

**修复**：缓存键加入**引擎作用域** `v3_<scope>_<md5>`（`mineru` / `paddle`）；
旧版无作用域缓存仅在 `meta.engine` 与当前 scope 一致时复用，否则重跑（宁可慢，不可错用）。

## 3. 性能调优

| 项 | 改动 | 依据 |
|---|---|---|
| Paddle 线程 | `paddle.set_num_threads(min(8, cpu-1))` | 纯 CPU 环境默认单线程，是导入最大时间黑洞 |
| 方向分类 | `use_angle_cls=False`、`show_log=False` | 试卷扫描件均为正向，每页省一次模型推理 |
| 页数上限 | 8 → 30 页 | 覆盖答案卷全长 |
| MinerU 超时 | 固定 600s → 按页放大（封顶 3600s） | 71.2s/页实测 |
| 缓存 | 引擎作用域隔离 | 防跨引擎误用 |

## 5. 使用建议与边界

1. **扫描件导入是分钟级任务**：24 页 CPU MinerU ≈ 20~30 分钟，导入已异步化（`import_id` + 轮询），前端不要用同步接口等结果。
2. **串行锁**：`_SEM_WAIT_SECONDS=60`，并发上传第二份扫描件会排队；超过 60s 自动回退 Paddle，属预期降级。
3. **MinerU 只对无文本层 PDF 生效**：有文本层的试卷仍走 pdfplumber（秒级），不要为了"用上 MinerU"去强制走 OCR。
4. **重导同一文件不会重复付 OCR 成本**：缓存命中 ~0.02s；但切换 MinerU 开关会各存一份（设计如此）。
