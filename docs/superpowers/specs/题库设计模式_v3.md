# 「题库设计」模式 · QBDM v3（会话执行版）

> **一句话激活**：说「按题库设计模式做 <需求>」，本模式自动进入：**标准模式 → 九角色换帽 →
> 台账定位模块 → 技能加载 → vtj MCP 取证 → 门禁验收 → 归档**。
>
> **模式栈**：标准模式（dsh）→ v1（角色/流程/门禁/预算）→ v2（模块台账 + D/O/T）→ **v3（会话编排）**。
> v3 不新增角色、不改门禁，只回答「一次会话里，谁先上、用什么技能、调哪个 MCP、交什么产物」。
> 红线唯一出处仍是 `AGENTS.md` R1–R12。

## §1 为什么需要 v3

v1 解决了「角色与流程」，v2 解决了「模块事实与三段清单」，但一次真实的设计会话仍会卡在三处：

1. **不知道先叫谁。** 拿到「错题斩题优化」，是先 ARCH 还是先 DATA？谁有否决权？
2. **技能与 MCP 靠临场想起。** `vtj-frontend` 该在哪一步加载？`vtj_check_consistency` 什么时候必须调？
3. **多角色变成独角戏。** 同一段回复里又设计、又写码、又宣布通过，没有交接、没有证据。

v3 把这三件事变成**固定管线 + 机器可读绑定 + 一条命令**。

## §2 模式分层：标准 / 创造 / PTC

依据 `deepseek-harness使用说明.md` §2.3，默认走**标准模式**，只在明确场景升级：

| 模式 | 何时用 | 路由与 token 策略 | 本模式中的位置 |
|---|---|---|---|
| **标准** | 常规设计、测试用例、契约比对、归档 | `ctx.llm.stream` + 正常重试；compaction + 缓存 + 本地兜底 | 默认，所有状态 |
| **创造** | 架构创新、组卷/判题算法、新页面结构 | 高 reasoning effort + 多提供商 fallback | 仅设计态 D2，产出即归档 |
| **PTC** | 批量语料、题图索引、统计、压测 | 本地沙箱；大文件只传统计结果 | 测试态/优化态的批量数据处理 |

**纪律**：创造模式不用于常规 CRUD；PTC 不把 662MB 语料或 4.3GB 题图读进上下文。

## §3 角色团：九角色 × dsh 形态 × 技能 × 否决权

| 代号 | 角色 | 当前 dsh 落地 | 主用技能 | 否决权 |
|---|---|---|---|---|
| ARCH | 系统架构师 | 本会话主 agent（Lead 等价） | `brainstorming`、`codebase-design` | 跨域直连、第 38 个 API 模块 |
| PM | 项目管理师 | 本会话主 agent | `li-an-workflow`、`plan-first-workflow`、`scope-guard`、`writing-plans` | 无验收命令的任务行、一分支两件事 |
| DATA | 数据建模师 | subagent / 换帽 | `domain-modeling`、`fact-guard` | 破坏 R10、无迁移加字段 |
| BE | 后端建模师 | subagent / 换帽 | `tdd`、`completion-verifier` | 裸 SQL、跨域 import api 层 |
| API | 接口建模师 | subagent / 换帽 | `fact-guard` | 未批准的端点增删改 |
| FE | 前端建模师 | subagent / 换帽 | `vtj-frontend`（强制）、`agent-browser` | 直改 `<template>`、raw 页同步 |
| SEC | 网络安全检测与保障 | subagent（只读） | `enterprise-compliance-checker`、`license-checker` | 密钥入文档/源码/提交 |
| QA | 系统测试与问题反馈 | subagent / 换帽 | `completion-verifier`、`systematic-debugging` | 无证据的「完成」 |
| DOC | 归档与索引 | subagent / 换帽 | `context-rollup`、`token-optimization` | 只展示不落盘 |

> **事实修正（Z2）**：上游说明书写的是 dsh「agent-team / teammate / Lead」。本机 harness 实际提供的是
> `subagent` / `subagent_fork` / `workflow` / `send_message`，**没有独立 agent-team 服务**。
> 因此 v3 的落地形态是：**主 agent 顺序换帽 + subagent 并行 + workflow 大扇出**，语义等价、工具不同。

**仲裁链不变**：`SEC > API > ARCH > PM > DATA > BE ≈ FE > QA > DOC`。

## §4 三态管线（命令一次打印全量）

```powershell
python scripts/qbdm/qbdm.py design wrongbook --state design    # 设计态 D0–D6
python scripts/qbdm/qbdm.py design wrongbook --state test      # 测试态 T0–T5
python scripts/qbdm/qbdm.py design wrongbook --state optimize  # 优化态 O0–O4
python scripts/qbdm/qbdm.py design wrongbook --roles           # 附角色×技能对照
```

### 4.1 设计态（D0–D6）

| 步 | 角色 | 动作 | 技能 | MCP | 退出条件 |
|---|---|---|---|---|---|
| D0 | PM | 复述、划边界、定预算与分支 | instruction-source-guard / scope-guard / intent-clarifier | — | 用户确认范围 |
| D1 | ARCH+DATA | 测绘影响面 | context-minimal-loader / fact-guard | project_info / list_pages / routing / page_structure | 影响文件清单确定 |
| D2 | ARCH | ≥2 方案 + ADR | brainstorming / codebase-design | read_dsl_file / read_vue_file | 用户批准 |
| D3 | DATA+API+SEC | 冻结契约、迁移单、安全五问 | domain-modeling / license-checker | component_detail / material_catalog | 差集=∅ 或已批准 |
| D4 | PM | 任务表（每行带验收命令） | plan-first-workflow / writing-plans | — | 用户批准 |
| D5 | BE+FE | 一文件一改一验证；FE 先 dryRun | tdd / vtj-frontend | write_vue_script / write_dsl_file / check_consistency / add_route | 每文件自检通过 |
| D6 | QA+DOC | 门禁+域测+归档 | completion-verifier / context-rollup | check_consistency | 退出码 0 + 未覆盖项 |

### 4.2 测试态（T0–T5）

| 步 | 角色 | 动作 | 通过标准 |
|---|---|---|---|
| T0 | QA | 按台账选 T1–T8 矩阵 | 矩阵确定、未覆盖项列出 |
| T1 | QA+API | 契约/边界/数据 | gate_l4 + module_boundary + 差异可解释 |
| T2 | QA+BE+FE | 域测 + 前端 spec | 全 PASS / 无 HANG |
| T3 | QA+FE | 页面可开 + 三端手工 | gate_l5 + 三端记录 |
| T4 | QA | 事件回归与幂等重放 | 重复=0、计数差异=0 |
| T5 | DOC | 报告落盘双写 | 索引更新 |

### 4.3 优化态（O0–O4）

| 步 | 角色 | 动作 | 铁律 |
|---|---|---|---|
| O0 | DATA+QA | 取基线 | 数字可复现，无基线不优化（A20） |
| O1 | ARCH+BE | 选一条优化点 | 一条一改，写清收益/代价/回滚 |
| O2 | BE+FE | 实施 | 逐文件验证 |
| O3 | QA | 复量对比 | 达标或如实报未达标 |
| O4 | DOC | 优化报告归档 | 前后对比 + 风险 |

## §5 多角色扮演协议

### 5.1 单会话顺序换帽（默认）

v3 声明头（在角色卡 5 行基础上加 3 个字段）：

```
[MODE] 题库设计 v1 | STATE design|test|optimize
[ROLE] <代号> <角色> v3
[MODULE] <id>（台账里的模块）
[SKILL] <本步加载的技能，≤3>
[MCP] <本步要调的 vtj 工具，可空>
[TASK] <编号> <一句话>
[BUDGET] T1|T2|T3
[LOAD] <文件:行区间> ×≤3
[GATE] <门禁命令>
```

换帽必须留 Handoff（≤10 行）：`FROM/TO + 已定 + 未定 + 风险 + 证据`。
**同一段回复只允许一顶帽子**；发现越界 → 停手 + Handoff + 回 PM。

### 5.2 subagent 并行（文件集不相交才允许）

| 场景 | 形态 | 约束 |
|---|---|---|
| 两个独立模块的只读测绘 | `subagent` × 2 | 各自带声明头与模块 id |
| 需要本会话上下文的续作 | `subagent_fork` | 明确「只读/可写」 |
| 只读巡查（SEC 扫描、QA 复核） | `subagent` 只读 | 产出报告，不改文件 |
| ≥6 个独立文件的审计/迁移 | `workflow` 扇出 | 脚本内按 phase 分组，结果结构化 |

**禁止**：同一文件两角色并写；为了「显得努力」把能内联的活扇出（A22）。

### 5.3 角色混用的判定

出现下列任一情况即判混用，本轮作废重来：

- 同一条回复既给方案又改代码又宣布测试通过；
- 未声明 `[ROLE]` 就开始改文件；
- FE 步骤里出现后端端点增删；
- QA 步骤里直接修实现（QA 只能开缺陷单）。

## §9 注意事项与坑（实测，带出处）

| # | 坑 | 规避 |
|---|---|---|
| 1 | Windows 控制台 GBK，脚本打印 ✅ 会抛 `UnicodeEncodeError` | 子进程 `PYTHONIOENCODING=utf-8`（AGENTS §7） |
| 2 | 全量 `pytest tests` 会挂起（CPU 5 分钟几乎不动） | `test_sweep.py --timeout 90` 拿 OK/FAIL/HANG |
| 3 | 工作区 ACL 使沙箱 `grantWrite` 抛 Win32 5，所有命令启动失败 | 会话切 full access，或 `diagnose-windows-sandbox-acl` 修复 |
| 4 | 343 端点冻结，改路径即破坏契约 | 先对 `api_surface.json` 出差集并批准（R11） |
| 5 | 2 个 raw 页禁 `sync_vue_to_dsl` | 先查域卡/`grep "raw: true"`（R2） |
| 6 | `.vtj` 模板 AI 禁改 | 只改 `<script>`，模板由用户在设计器拖拽（R3） |
| 7 | 平板页复制会双份维护 | 复用 `@/views/mobile_*.vue`（R12） |
| 8 | 事件 `trigger_type` 改语义会打断成就判据 | add-only，只增不改（A19） |
| 9 | 备份 `shutil.copy2` 在 WAL 下不完整 | `sqlite3.backup()`，回滚删 `-wal`/`-shm`（R10） |
| 10 | `题库/` 662MB、`static/` 4.3GB | 只统计，不读内容（v1 §6.4） |
| 11 | 默认模型 flash + low | 架构讨论升创造模式；批量数据走 PTC |
| 12 | MCP `cwd` 固定本仓库 | 换工作区时先禁用 mcp-vtj 行 |

## §10 产物契约与完成判定

| 状态 | 必需产物 | 完成判定（缺一不算完） |
|---|---|---|
| 设计态 | 方案（v1 §10.1 骨架）+ 实施计划（§10.2）+ 契约/迁移/安全附件 | 用户批准 + 计划每行有验收命令 |
| 测试态 | 验收报告（结论/证据/未覆盖/归档） | 退出码 + 关键行 + 未覆盖项 |
| 优化态 | 优化报告（基线/改法/复量/回滚） | 前后数字 + 回归结论 |

**总则**：没有命令输出的「完成」判未完成；未跑的层标「未验证」；失败报失败。
