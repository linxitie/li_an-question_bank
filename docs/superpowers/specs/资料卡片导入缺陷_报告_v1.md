> **日期**：2026-10-27
> **取证方式**：对运行中的后端（`:8010`）真实调用 7 次导入（`import_id` 1–6），全部走既有端点
> **数据影响**：探针产生的垃圾卡 `#7`、`#8` 已 `DELETE`，当前 `study_material` 仅 6 条（3 文章 + 3 卡片）
> **结论**：链路是通的，但**「导入卡片」不等于「得到卡片」**，共 **8 个缺陷**，其中 **D1 是阻断性**的

## 1. 缺陷清单

### D1（阻断级）导入的卡片 `type` 恒为 `article`，翻卡 UI 用不上

- **现象**：`POST …/confirm` 后，`study_material.type = 'article'`，而非 `'card'`
- **证据**：`#7`、`#8` 导入后均为 `type=article`；我手工 `PUT /admin/{id} {"type":"card"}` 后才变 `card`
- **根因**：`materials.py` xlsx 分支里对每条卡执行 `classifier.classify(...)`，用分类器结果覆盖了 `type`
- **影响**：卡片落进「备考指南」（article 分区），「知识卡片」区块永远空 → **用户看不到卡片，功能等于没上线**
- **建议修法**：xlsx 分支中，当 `column_mapping` 同时给出 front/back 时**强制 `type='card'`**（或给 `classify` 传 `hint_type='card'`），并加回归测试
- **归属**：独立子分支 `-import-card-type`（不在 `-card` 视觉分支里混改）

### D2（体验级）导入结果一律 `status=0`，必须逐条手工上线

- **现象**：import 后所有卡片 `status=0`（下架态），不批量、不提示
- **证据**：`status=0` 记录曾达 2 条，需我对每条 `PUT /status {"status":1}`
- **影响**：批量导入 50 张要发 50 次请求；管理员容易以为"导入失败"
- **建议修法**：`confirm` 增可选 `publish: true`（默认 false 保持兼容），或提供 `POST /admin/batch/status`
- **归属**：`-upload-format`（导入体验）

### D3（正确性）表头不自动识别，列索引传错即静默产出垃圾卡

- **现象**：传 `front=0` 时把**表头行**当数据，生成标题为 `x` 的卡（`#8`）
- **证据**：P4，`created=1`，`#8 title='x'`
- **影响**：管理员看到"成功 1 张"，实际是垃圾数据，且污染词库
- **建议修法**：自动识别首行是否为表头（与 `正面/背面/分类` 等词表匹配）；无法识别时在 preview 标出"疑似表头行"
- **归属**：`-upload-format`

### D4（反馈）重复内容被静默跳过，`created=0` 却返回 200 成功

- **现象**：重复导入 → `{"created":0,"material_ids":[]}`，HTTP 200，无任何原因说明
- **影响**：管理员无法区分"全部重复"与"解析失败"
- **建议修法**：响应增 `skipped: [{row, reason}]`，前端展示"0 新增 / N 重复"
- **归属**：`-upload-format`

### D5（反馈）行级空值静默丢弃，预览行数误导

- **现象**：表 3 行（1 行缺背面、1 行缺正面）→ 只入库 1 张，无 skipped 明细；`preview` 仍返回 3 行
- **影响**：以为"3 张都进去了"
- **建议修法**：`preview` 返回 `valid_rows / invalid_rows` 与原因；`confirm` 回 `skipped`
- **归属**：`-upload-format`

### D6（完整性）卡片元信息无法从表格带入

- **现象**：`difficulty / read_time / badge / cover_image` 无列映射能力，导入后全为默认值
- **影响**：卡片无法带"难度/预计时长/角标"，视觉上缺少信息层级（见视觉细案 v2 的 chips）
- **建议修法**：`column_mapping` 扩展可选键 `difficulty/read_time/badge`，缺列即跳过
- **归属**：`-upload-format`

### D7（可用性）预览不是「卡片形态」

- **现象**：`preview` 只回 `rows: [[正,背,分类], ...]`，管理员看不到卡面效果
- **影响**：无法在入库前判断排版是否合理（长背面、超长标题）
- **建议修法**：前端将 rows 渲染成卡面预览（**这属前端改动**，需 VTJ 设计器 + 效果图）
- **归属**：`-card`（前端视觉）

### D8（运维）失败/告警只写日志，管理员界面无感

- **现象**：`import_monitor.record_duplicate_match()` / `logger.warning("[materials] import alerts")` 只落日志
- **建议修法**：`GET /admin/import-records` 增 `duplicate_count/alert` 字段并按状态筛选
- **归属**：`-upload-format`

## 6. 勘误与修复进展（2026-10-27 追加）

### 6.1 勘误：D3 是误判

原 §1 D3 称「表头不识别，列索引传错即静默产出垃圾卡（实测 #8 title='x'）」。复核后**该结论错误**：

- `material_parser.py:108 parse_xlsx()` 返回 `{"headers": [...], "rows": [数据行]}`，**表头在第 119 行已单独取出**；
- 那次探针文件为「表头 + 一行 x/y/z」，产出标题 `x` 的卡片属**忠实导入数据行**，非缺陷；
- 反证：带表头的 xlsx 在 D1 测试中断言 `created==2`（2 数据行），若表头未剔除会得 3 张，测试不可能通过。

**正确缺口**是"表头信息未暴露给管理员"，已在 `preview` 回传 `headers` / `row_count` 解决。
