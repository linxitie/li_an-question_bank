## 5. 关键发现与偏差说明

### 5.1 F0 报告里的内容指纹不可复现（必须记录）

`f0_backup.json` 中 `question_bank=376e2ce9…`、`question_groups=643ebc50…` 等哈希，是由 F0 当次临时探针生成的，**序列化/排序细节未落代码**。实测 default/ensure_ascii/compact/dict/list/整表 dump 等常见变体均无法复现（`question_image` 只有 noascii 能对上、`question_knowledge` 只有 default 能对上，口径本身不一致）。

处置：**不篡改 F0 报告**；改用受 R8 保护的 F0 备份库 `backend/data/backups/pre_foundation_20261026_193553.db`，以 `gc_previews.py` 中已落代码的口径重算基线：

| 表 | 行数 | sha256（前 8） |
|---|---|---|
| question_bank | 3357 | `93bbecf0` |
| question_groups | 23 | `83da5e93` |
| question_image | 293 | `80b5b2ac` |
| question_knowledge | 2775 | `e72c20be` |

与当前主库四表**逐表 MATCH**。F1 基线文件为 `backend/data/reports/f1_content_baseline.json`（由 `content_integrity.py --write-baseline` 生成，含 `source_sha256` 与序列化说明）。后续如有人说「F0 指纹变了」，先看本节——那是口径问题，不是数据漂移。

### 5.2 性能未达 5% 目标

见验收 #8。F1 的职责是「正确地多写一行事件」，不是「无感地多写一行」。真实业务写多为批量导入（一次事务多行），摊薄后增幅会显著低于单条冒烟；F2 接 Redis/批量投递时一并优化，并把 P95 判据改为真实导入批次口径。

### 5.3 内容完整性存量缺陷（不清理，只登记）

- 13 行图片路径文件不存在（题 431/433/472/669/1132/1155/1158，目录整体缺失）；
- 10 个 `[IMAGE:hash_p_i]` 令牌无法精确解析（`shared_content_images` 全空、`static/question-groups` 为空）；
- 空组 `question_groups.id=11`；组 id 23 空洞（历史删除）；
- 37 道申论中 24 道未挂组（合法，但材料映射缺失时无法作答）。
均按 D17 记入 `known_issues`，L7-15 只 WARN，不静默删除。
