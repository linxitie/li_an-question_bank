## 1. 执行摘要

### 1.1 一句话结论

**三层分类的问题不是「树没建好」，而是「树建好了、题却全被塞进了树底的『其他』」。**
数据库里 91 个考点、429 个子考点、520 个规范节点全部存在（`knowledge_point` 实测），
但 3750 道题里 **3670 道（97.9%）主考点指向名为「其他（未细分）」的叶子**，
只剩 **5 道**挂在真实考点上、**75 道** point_id 为空。前端按「知识点 → 子节点」展开时，
每个知识点下唯一有题的子节点就是「其他」，于是用户看到满屏「其他」（截图 m02311–m02315）。

所以治理必须做两件事，缺一不可：
1. **把 3670 道题重新分到真实考点**（分类引擎从 12.7% 命中率提到可用水平）；
2. **把「其他」从「每个考点一个叶子」改成「每个知识点一个收容入口」**，并让前端只在考点层下钻、考点以下不再展开。

### 1.2 四条需求的落点

| 需求 | 现状实测 | 本方案动作 | 章节 |
|---|---|---|---|
| ① 三层分类准确 | 5 道题在真实考点；drawio 与库存在 5 处命名漂移、1 个知识点只在一侧 | 以 drawio 为基准做**基线校准**（不重建），再全量重分类 | M1 / M2 |
| ② 下划线写 `____` | 已有 helper，但只覆盖 docx 正文段落；表格、raw-XML 兜底、PDF、XLSX 全丢；30 题已确认缺横线 | XML 级 run 解析覆盖全部容器 + PDF 线条检测 + XLSX 底边框，并对 30 题做源文件回填 | M3 |

## 3. 方案正文

### M1 三层分类基线校准（对应需求 ①）

**目标**：让「科目 → 知识点 → 考点」这一棵树成为可被程序与人工共同信任的基线，且**只允许三层**。

#### M1.1 先把树「写成一份可核对的清单」

现状：树在数据库里，但没有一份与 drawio 逐条对齐的权威清单，导致每次讨论都要重新查库。

动作：
1. 导出快照 `docs/design/三层分类基线_v1.json`：
   - 16 个知识点（sub_categories）→ 91 个考点（level=2 canonical）→ 429 个子考点（level=3 canonical）
   - 每条含：id / 名称 / 父 id / 题量 / drawio 对应名 / 是否 fallback
2. 生成对照表 `docs/design/三层分类对照表_v1.md`（人读版），逐条标注：
   - ✅ 两侧一致
   - ⚠️ 名称漂移（drawio 名写入 alias）
   - ❌ 仅单侧存在（附处置结论）
3. 该 json 在 M2 重分类时作为**白名单**：引擎不允许写出名单外的考点 id。

#### M1.2 命名漂移：写 alias，不改名

实测 5 处漂移（左＝库内既有名，3750 道题正在引用；右＝drawio 写法）：

| 库内名（不改） | drawio 名（写 alias） |
|---|---|
| 定义判断 | 定义推理 |
| 逻辑判断 | 逻辑推理 |
| 事务文书 | 事务写作 |
| 策论文 | 政策文 |
| 政治敏锐性与鉴别力 | 政治敏锐性能够与鉴别力 |

做法：在 `knowledge_point` 插入 status=0 + alias_of=规范节点 id 的别名行（与既有 464 行别名同构），
**不 UPDATE 规范节点名称**。理由：改名会让 3750 行 question_bank.point_id 的语义指向与历史审计对不上，
且 .vtj 页面上已被截图固化的名称会再次变化。

#### M1.3 「其他」从「91 个叶子」改成「每个知识点 1 个收容入口」

这是本次治理最核心的结构改动。现状（实测）：
- 91 个 level=3 节点全名「其他（未细分）」，分属 16 个知识点下的 91 个考点；
- 3670 道题的 point_id 指向它们；
- `question_knowledge` 有 2127 行指向它们。

两种做法，推荐 A：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A（推荐）查询层聚合** | 保留 91 个节点数据不动，新增标记 `is_fallback=1`（迁移加列或复用 description 标记）；所有读接口按「知识点」维度把 91 个节点折叠成 1 条「未细分类」 | 零数据删除、可回滚、question_knowledge 不断链 | 需要改 3–4 处查询 |
| B 物理合并 | 每知识点建 1 个新节点，UPDATE 3670 行 point_id 过去，删旧 91 个 | 数据干净 | 需同步 2127 行 question_knowledge；删错不可逆 |

A 方案要改的查询点（已定位）：
1. `backend/app/api/v1/exam/quick_practice.py:234` `if not l3_question_ids: continue` —— 收容节点不参与「考点展开」，只在知识点下作为一条「直接练习」；
2. `backend/app/api/v1/exam/practice.py:643` `get_knowledge_progress` 取 level==3 全量 —— 已由 v6 的 `_merge_fallback_rows()` 合并，本次只需把判据从「名字叫其他」改为 `is_fallback`；
3. `backend/app/api/v1/catalog/wrong_questions.py` 考点筛选列表；
4. 教师端 `question_import.py:279 _detect_subcategory` 的兜底返回值。

#### M1.4 UI：严格三层，考点以下不再展开

| 层 | 展示 | 交互 |
|---|---|---|
| L1 科目 | 行测 / 申论 / 公专 tab | 切换 |
| L2 知识点 | 卡片网格（现有 .subcard，保留） | 有考点 → 展开考区；只有收容题 → 直接进练习 |
| L3 考点 | 列表行（名称 + 已做/总数 + 箭头） | **点击即进练习**（当前考点全部题） |
| L3 收容 | 知识点下唯一一行「未细分类 N 题 → 直接练习」 | 点击进练习 |
| 禁止 | 任何第 4 层展开、任何「其他」再下钻 | — |

注意（R3 红线）：`.vtj/vue/question_bank.vue` 的 `<template>` 我**不会直接改**。
M1.4 的模板级改动走两条路之一，由你选（见 D2）：
(a) 我用 vtj DSL 节点写入（`vtj_write_dsl_file`，先 dryRun）；
(b) 新建手写页 `src/views/student/shared/practice_center.vue` 承接（该页已存在，v6 已建，可继续扩），
    题库页只保留跳转按钮（改动仅在 `<script>`，符合 R2/R3）。

**验收口径**：三端截图里，任何一次点击都不会出现「其他」作为可展开分类（对应 m03263/m03264/m03265 三张问题截图）。

### M2 考点识别引擎 v2（对应需求 ① 的「分类准确」）

**目标**：把「98% 落其他」变成「≥80% 落到真实考点」，且错误率可控可回滚。

#### M2.1 为什么不直接用大模型

- v6 已明确约定（m00217 第 4 条）：**不做真实 LLM 调用**；
- 离线跑 3528 题，若接 LLM 成本与不确定性都不可控；
- 更重要：考点判定是**闭集分类**（每知识点仅 2–19 个候选），规则引擎在这个规模上通常优于粗提示词的大模型。

因此 M2 是「规则 + 先验 + 小样本学习」的组合，LLM 仅作为**可选的离线辅助**，默认关闭（D4）。

#### M2.2 三级判定流水线

```
输入：question_content / options / question_type / subject_id / 已有知识点标签
  │
  ├─ 第 1 步 先验收缩
  │    有 question_detail_category 标签（3644 行，覆盖 97.2% 的题）→ 候选集 = 该知识点下 2–19 个考点
  │    无标签 → 先跑 _detect_subcategory（现有 16 类关键词）→ 再收缩
  │    仍无 → 落「未细分类」，不猜
  │
  ├─ 第 2 步 规则打分（每考点一个 YAML 条目）
  │    score = Σ(命中关键词 × 权重) + 结构特征加分 − 排他模式扣分
  │    结构特征举例：
  │      图形推理  ⇐ 「如图/图形/折叠/立体/展开图」+ 题型=单选 + 无数字答案
  │      数字推理  ⇐ 题干含数列逗号串（如「2，4，8，16，（ ）」）
  │      数学运算  ⇐ 含「元/千米/小时/百分比/工程/行程/概率/排列组合」
  │      定义判断  ⇐ 「下列属于/不属于…的是」+ 题干含定义句
  │      逻辑填空  ⇐ 「填入划横线部分最恰当的一项」
  │      语句表达  ⇐ 「语序/病句/歧义/衔接最恰当」
  │      资料分析  ⇐ 含「同比/环比/增长率/比重/倍数」且题干引用表格
  │
  ├─ 第 3 步 三档置信度
  │    top1 归一化得分 ≥ 0.75 且 top1−top2 ≥ 0.20   → 自动写入（高置信）
  │    0.45 ≤ 得分 < 0.75 或 top1−top2 < 0.20        → 写入 + 入复核队列（待确认）
  │    < 0.45                                        → 落「未细分类」（不污染考点）
  │
  └─ 第 4 步 落库 + 审计
       写 question_bank.point_id + question_knowledge
```

### M3 下划线 / 填空横线识别（对应需求 ②）

**目标**：Word 里「空白 + 下划线格式」的填空位，导入后变成 `____`，不再丢失。

#### M3.1 现状：helper 存在，但只覆盖一条路径

`backend/app/services/question_ingest/docx_reader.py`（311 行）实测：

| 位置 | 行为 | 是否丢横线 |
|---|---|---|
| `:16 paragraph_text_with_underline(para)` | 把「带下划线的纯空白 run」写成 `____`；「带下划线的文字」包 `<u>…</u>` | 正确 |
| `:248` 段落主循环 | 调用了上面的 helper | ✅ 已修（v6 M8） |
| `:294` 表格单元格 | 仍用 `cell.text.strip()` | ❌ 表格内横线全丢 |
| `:127 _extract_text_from_docx_raw_xml` | 兜底路径自己拼字符串 | ❌ 兜底时横线全丢 |

另两条入口完全没处理横线：
- `pdf_reader.py`（726 行）：PDF 只有文字层，横线是矢量线条，从未被识别；
- `excel_reader.py`（192 行）：单元格底边框即「答题横线」，从未被识别。

实测受影响面：
- 题干含连续下划线的题 **2 道**（GLOB `*___*`）；
- 题干出现「横线/划线」字样但**没有任何占位符**的 **30 道**（这是"用户看得见题、却看不见横线"的真实受害者）；
- 典型样本 question_id 3666：「…这是编译人员在岗位上 的写照。」——「岗位上」与「的写照」之间只剩一个半角空格，
  原始 Word 里是**带下划线格式的空格**（不是字面下划线字符）。

#### M3.2 新实现：XML 级 run 遍历，覆盖全部容器

新增 `backend/app/services/question_ingest/docx_underline.py`：

```
输入：docx 的 word/document.xml（+ word/styles.xml）
  │
  ├─ 遍历全部 w:p（不限正文段落）
  │    正文 / 表格单元格( w:tc ) / 页眉页脚( header*.xml footer*.xml )
  │    / 脚注尾注 / 文本框( w:txbxContent )
  │
  ├─ 逐 w:r 判定「是否带下划线」
  │    1) w:rPr/w:u[@w:val] 且 val != "none"       → 有
  │    2) w:rPr/w:rStyle → styles.xml 里该 style 含 u → 有（继承样式）
  │    3) w:rPr/w:pBdr/w:bottom                     → 段落级下边框，按「整行填空」处理
  │
  ├─ run 文本分类
  │    空白（空格/全角空格/\t/w:tab）且带下划线  → 占位符（长度≥2 才计数）
  │    有文字且带下划线                          → <u>文字</u>（保留原语义，不转 ____）
  │    无下划线                                  → 原样
  │
  ├─ 合并与去重
  │    相邻占位 run 合并成一个 "____"，避免 "____ ____ ____"
  │    已有 "____" / "＿" / "___" 的题不重复插入（幂等）
  │    占位符前后若是「（ ）」空括号，不再叠加
  │
  └─ 输出：段落文本 + underline_spans[{start,end}]（供审计与前端高亮）
```

验收样例（用 question 3666 原始 docx）：
- 修复前：`…这是编译人员在岗位上 的写照。…`
- 修复后：`…这是编译人员在岗位上____的写照。…`

#### M3.3 PDF / XLSX 两条补充路径

| 来源 | 判定方法 | 产出 |
|---|---|---|
| PDF | `page.get_drawings()` 取水平线段（长度 ≥ 40pt、粗细 ≤ 2pt、与文字基线距离 ≤ 6pt）→ 在文本流对应位置插入 `____` | 填空位标记 |
| XLSX | `cell.border.bottom.style` 非空 且 `cell.value` 为空 → `____`；`value` 有内容且有底边框 → `<u>value</u>` | 同上 |

PDF 走的是「几何 + 文本位置对齐」，扫描件（无文本层）不适用，走既有的 OCR/MinerU 路径，
并在导入报告里标注「本文件为扫描件，横线未识别」，不静默丢失（见 M4.4 质量分）。

#### M3.4 30 道存量题的回填

脚本 `backend/scripts/taxonomy/backfill_blanks.py`：
1. 从 `question_bank` 取「题干含横线/划线 但无 `____`」的 30 道（SQL 见 11 章）；
2. 按 question_id → 来源文件名（question_bank.source_file）定位 `题库/` 下的 docx；
3. 用 M3.2 的新解析器重解析该文件，按题干文本相似度（difflib ≥ 0.9）匹配回原题；
4. `--dry-run` 输出 diff 清单（旧题干 / 新题干 / 插入位置），交你逐条确认；
5. `--apply` 写库前先 `sqlite3.backup()`（R10），写审计表。

匹配不到的题单独列「源文件未找到」，**不猜测填空位置**（避免把横线插到错误位置）。

#### M4.2 段落分类器（决定"这一段是什么"）

新增 `backend/app/services/question_ingest/segment_classifier.py`：

```
每个段落 → 打分到 8 类之一
  TITLE     试卷/科目标题（"2024年公安联考行测真题"）
  SECTION   大题标题（"一、单项选择题"）
  MATERIAL  材料（篇幅长、无题号、含"给定资料/材料一"）

  OPTION    选项（A. / A、 / （A））
  ANSWER    答案（"参考答案：C" / "答案：C"）
  ANALYSIS  解析（"解析：" / "【解析】"）

  字体/加粗（段内混合加粗 → SECTION）× 1
```
