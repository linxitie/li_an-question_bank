# 管理员端「用户管理」合并设计 v1

> 状态：✅ 已实施（2026-11-02；P0–P3 主体 + P4-1 权限健康，P3-7 CSV / P4-2–P4-5 延后）
> 日期：2026-11-02
> 范围：管理员端用户管理 × 权限管理合并；批量增删改查；单/多用户权限管理；深度优化与创新设计
> 约束：不改 `.vtj/` raw 页模板、不执行 `vtj_sync_vue_to_dsl`、不在未批准前改业务代码

## 1. 结论摘要

1. **不是“把两个菜单并排放在一起”，而是把“账号生命周期”和“权限生命周期”合成一个工作台。** 顶层只有「用户管理」一个入口，内部用「用户列表 / 权限模板 / 授权审计 / 权限健康」四个 Tab 承载。
2. **权限采用“角色基线 + 能力包 + 个人加授 − 个人拒绝”的四层模型。** 角色模板仍是大多数人的默认值；个人例外只解决“这个人需要多一项/少一项”的问题，不复制一套角色体系。
3. **现有编辑弹窗实际是坏的，必须先修。** `.vtj/vue/admin_users.vue:283` 调用了不存在的 `GET /api/admin/users/{id}`；编辑表单里的 `user_type` 提交给 `PUT /users/{id}`，而 `UserUpdate` 不接收该字段，改角色不会生效（`backend/app/schemas/admin.py:70`）。
4. **删除采用“软删除 + 回收站 + 匿名化 purge”，不做物理 DELETE。** 题目、试卷、考试记录都引用 `user_id`，物理删除会制造悬空引用；彻底删除时保留 `user_id` 作为墓碑，清除 PII 并禁止登录。
5. **批量权限必须“先预览差异，再应用，再可撤销”。** 500 人 × 30 项权限的上限、批次 ID、10 分钟撤销窗口、逐项风险提示，避免“一次点错，全年级教师被提权”。
6. **创新点按价值排序，不平均用力。** 优先做 I1 权限差异预览、I2 临时授权到期收回、I5 批次撤销；I3 权限健康扫描、I4 有效权限解释器放第二阶段；I6 权限套餐、I7 智能分群、I8 双人复核按需。
7. **新建手写页 `src/views/admin/pc/AdminUsersWorkspace.vue` 替换 `/admin/users` 路由。** 现有 `admin_users.vue`、`admin_permissions.vue` 保留不删；`/admin/permissions` 重定向到 `/admin/users?tab=roles`，导航只留一个入口。

## 2. 需求与边界

### 2.1 用户要求（m11158）

- 在管理员端把「用户管理」和「权限管理」合并成一个「用户管理」功能模块。
- 模块内可批量处理用户（增、删、改、查）。
- 同时支持对单个或多个用户执行「权限管理」操作。
- 在需求基础上深度考虑优化、细节下钻、界面交互实用性；在现有基础上做创新设计。

### 2.2 本期做

- 用户列表：筛选、分页、多选、跨页全选、保存视图、批量操作栏、行内详情抽屉。
- 用户 CRUD：新增、编辑、启用/禁用、软删除/恢复/匿名化 purge、批量改资料、批量改角色。
- 单用户权限：查看来源链、Tri-state（继承/加授/拒绝）、临时授权、原因、到期时间。
- 多用户权限：批量加授/收回/清除例外/套用角色模板/临时授权；差异预览、风险提示、批次撤销。
- 权限模板：三个角色的基线矩阵、影响面预览、保存原因、编辑审计。
- 授权审计：按操作者/对象/权限/批次筛选，展开差异，撤销批次。
- 权限健康：高权久未登录、孤立例外、过期未清理、超管数量不足、模板漂移。
- 权限元数据单一来源：`PERMISSION_META`，修掉前端显示原始权限码的问题。

### 2.3 本期不做

- 自定义角色（新增第四种 `user_type`）。这会牵动登录、路由守卫、三端布局与全部角色默认权限，收益低于风险。
- 组织架构树/多学校租户。当前只有 23 个用户、3 个部门，先不做多租户抽象。
- 真正的 subject/class 范围权限判定。字段预留，本期只启用 `global`，避免“界面能选范围、后端不生效”的假功能。
- 物理删除用户、回收用户名。保留 `user_id` 墓碑，保证历史数据可追溯。
- 单点登录、密码策略、二次验证。与本次合并无直接关系。

## 4. 根因树

```
管理员端用户/权限难用
├─ A. 信息架构割裂
│  ├─ A1 用户与权限两个一级菜单，权限页只有角色卡
│  └─ A2 没有“这个人为什么有/没有这个权限”的入口
├─ B. 用户操作能力缺失
│  ├─ B1 无多选/批量；只能逐行点
│  ├─ B2 无删除/回收站；离职、误建账号无法处理
│  ├─ B3 编辑弹窗依赖不存在的 GET 详情 → 打不开
│  └─ B4 角色字段可编辑但后端不接收 → 改了不生效
├─ C. 权限模型缺“个人例外”
│  ├─ C1 只有角色级模板，改一个角色影响全体
│  ├─ C2 能力包只能加、不能减，且 scope 未生效
│  ├─ C3 无到期时间、无原因、无批次、无撤销
│  └─ C4 权限中文名不完整，界面出现原始 code
├─ D. 安全与审计缺口
│  ├─ D1 无“最后一名超管”保护
│  ├─ D2 无“不能修改同级/更高级用户”约束
│  ├─ D3 批量重置密码明文回显
│  └─ D4 权限变更没有可读的 before/after 审计
└─ E. 数据模型缺口
   ├─ E1 SysUser 无 is_deleted/deleted_at/deleted_by
   ├─ E2 无 per-user permission override 表
   └─ E3 无 permission change batch 表，无法撤销
```

## 5. 设计目标与原则

| 原则 | 落地 |
|---|---|
| 一个入口 | 顶层只保留「用户管理」；权限模板、审计、健康都是它的 Tab |
| 默认简单，例外显式 | 大多数人只看角色基线；个人加授/拒绝必须显示来源、原因、到期时间 |
| 先预览再执行 | 所有批量写操作先出 diff：多少人、哪些权限、加还是减、风险等级 |
| 可撤销 | 每次批量写生成 `batch_id`，10 分钟内可撤销；冲突时拒绝并说明 |
| 不可自伤 | 不能禁用/删除/降级自己；不能移除最后一名可用超管 |
| 不制造假功能 | 本期只启用 global scope；subject/class 字段保留但不展示为可选项 |
| 不破坏历史 | 删除=软删除；purge=匿名化墓碑，不物理删行 |
| 统一元数据 | 权限中文名、分组、风险、说明只从 `PERMISSION_META` 出 |

**表格列**

| 列 | 内容 | 交互 |
|---|---|---|
| 复选框 | 本页多选 | 表头全选本页；顶部出现“选择全部 N 人” |
| 用户 | 头像、姓名、`user_no` | 点击打开右侧抽屉 |
| 角色 | 学生/教师/管理员 + `role_level` | 徽章；超管加金色描边 |
| 部门/班级 | `department` / `class_name` | 空值显示“未设置” |
| 权限摘要 | 角色 N 项 · 加授 +a · 拒绝 -d | 悬停浮层显示差异项；点击跳权限 Tab |
| 风险 | 高权久未登录/孤立例外/过期授权 | 红色/橙色 badge |
| 状态 | 正常/禁用/回收站 | 禁用可一键启用；回收站行操作变为恢复/彻底删除 |
| 最近登录 | 相对时间 + 绝对时间 tooltip | 超过 90 天标灰 |
| 操作 | 编辑、权限、更多 | “更多”含禁用、重置密码、删除 |

**筛选与视图**

- 基础：keyword（username/user_no/phone/email）、角色、状态、部门、班级、学校。
- 权限：有个人加授、有个人拒绝、有任意例外、有高风险权限、权限即将到期。
- 时间：注册时间区间、最近登录区间。
- 保存视图：存 `localStorage`（键 `admin-users-views-v1`），支持命名、设默认、删除；首版不做服务端共享视图。
- 智能分群（I7，P4）：按“30 天未登录教师”“有拒绝权限的管理员”“仅剩一名超管”等规则一键生成筛选。

**批量选择语义**

- 本页选择：`selectedIds` 集合。
- 跨页选择：筛选条件 + `expected_count`，提交时服务端按同一 filter 解析，返回实际命中数。
- 安全闸：解析后数量与 `expected_count` 不一致（数据在期间变化）→ 返回 409，要求重新预览。
- 单批上限 500 人；超过时提示“请缩小筛选范围或分批执行”。

### 6.3 用户详情抽屉

宽度 640px，右侧滑出；不跳页，保留列表上下文。三个 Tab：

**概览**

- 头像、姓名、`user_no`、角色、状态、部门/班级/学校、注册时间、最近登录 IP。
- 快捷操作：编辑资料、重置密码、禁用/启用、删除。
- 数据摘要：参与考试数、错题数、最近一次成绩（只读，点击跳对应页面）。
- 风险提示：高权久未登录、孤立例外、过期授权。

**权限**

```

[搜索权限] [只看已变更] [重置为角色默认]
┌ 题目管理 ─────────────────────────────────────────────┐

└───────────────────────────────────────────────────────┘
底部：将新增 1 项、移除 1 项  [取消] [预览变更] [保存]
```

- 三态控件：`继承` / `加授` / `拒绝`。选择加授或拒绝时展开“原因 + 到期时间”。
- 每一行显示：权限中文名、code（等宽小字）、角色基线是否有、个人覆盖、风险 badge、来源。
- 权限分组折叠：题目、试卷、考试、用户、系统与数据、内容与视频、社区与反馈、能力与 AI。
- 顶部“有效权限 N 项”可展开完整清单；提供“为什么有/没有”解释（I4）：列出角色、能力包、加授、拒绝四条来源。
- “重置为角色默认”：清空该用户全部 override，二次确认，写批次。

**活动**

- 最近登录、最近被修改、最近权限变更（时间线）。
- 权限变更条目：操作者、时间、批次、before → after、原因、撤销按钮（若在窗口内）。

### 6.4 批量操作栏

选中后固定在表格底部：

```
已选 3 人  [启用] [禁用] [改角色] [授权] [重置密码] [删除]  [取消选择]
```

- 「启用/禁用」：弹原因输入；禁用自己的账号直接禁用按钮。
- 「改角色」：仅超管；选择 user_type + role_level；预览“3 人将从教师变为管理员”。
- 「授权」：打开批量权限向导。
- 「重置密码」：仅超管；生成一次性 CSV 下载，不在界面显示明文。
- 「删除」：软删除；要求输入原因；若包含管理员/超管，需超管且二次确认。

### 6.5 批量权限向导（核心交互）

三步，右侧 720px 抽屉或居中 880px 弹窗：

**Step 1 选择对象**

- 显示已选人数、角色分布、当前例外数、冲突提示。
- 若跨页选择，显示“按当前筛选命中 137 人，将全部应用”。
- 可移除个别用户。

**Step 2 选择操作与权限**

```
操作：○ 加授  ○ 拒绝  ○ 清除个人例外  ○ 套用角色模板  ○ 临时授权
权限：[搜索] [全选本组]
  题目管理  ☐ 创建 ☐ 修改 ☐ 删除 ☐ 查看 ☐ 审核 ☐ 导入
  试卷管理  ☐ 创建 ☐ 审批 ☐ 发布 ☐ 查看 ☐ 修改
  ...
到期：永久 / 1天 / 7天 / 30天 / 自定义
原因：必填（>= 10 字）
```

- 「套用角色模板」不是改 `user_type`，而是把目标角色的基线权限写成个人加授/拒绝差异；界面必须解释清楚，避免和“改角色”混淆。
- 选择高风险权限时，行内出现红色提示；底部出现“我确认此操作影响 N 人”复选框。

**Step 3 差异预览**

```
影响 3 人 · 新增 6 项 · 移除 2 项 · 无变化 24 项
┌ 用户   权限        当前      变更后    风险  来源冲突 ┐

└──────────────────────────────────────────────────────┘

```

- 冲突检测：同一用户同一权限已有未过期 override；拒绝+加授同时存在；目标用户是超管且要拒绝关键权限；批量中包含自己。
- 预览是服务端计算（`dry_run=true`），不是前端猜测。
- 应用后返回：`batch_id`、成功/失败数、失败原因、下载报告、10 分钟内“撤销本批次”。

## 7. 权限模型

### 7.1 四层来源

```
有效权限 = (角色基线 ∪ 能力包权限 ∪ 个人加授) − 个人拒绝
```

| 层 | 存储 | 作用域 | 本期 |
|---|---|---|---|
| 角色基线 | `ROLE_PERMISSIONS` / `SysConfig.role_permissions_{role}` | global | 启用 |
| 能力包 | `UserCapability` | global（scope 字段预留） | 启用，但 scope 不参与判定 |
| 个人加授 | 新表 `user_permission_override` effect=grant | global | 启用 |
| 个人拒绝 | 新表 `user_permission_override` effect=deny | global | 启用 |

### 7.2 判定伪代码

```python
def get_effective_permissions(user, db):
    base = set(get_user_permissions_with_db(user, db))  # 角色 + 超管 + 能力包
    overrides = db.query(UserPermissionOverride).filter(
        UserPermissionOverride.user_id == user.user_id,
        UserPermissionOverride.status == "active",
        or_(
            UserPermissionOverride.expires_at.is_(None),
            UserPermissionOverride.expires_at > now(),
        ),
        UserPermissionOverride.scope_type == "global",
    ).all()
    grants = {o.permission_code for o in overrides if o.effect == "grant"}
    denies = {o.permission_code for o in overrides if o.effect == "deny"}
    return sorted((base | grants) - denies)
```

### 7.3 优先级与边界

- 同一权限、同一 scope 只允许一条 override；`deny` 覆盖 `grant` 和角色基线。
- 超管保护：`role_level>=3` 的用户不能被移除 `user:manage`、`system:config`、`data:backup`、`log:audit`；不能删除/禁用/降级最后一名可用超管。
- “不可自伤”：任何管理员不能修改自己的角色、状态、权限；编辑自己的资料只允许 phone/email/avatar。
- “不能向上修改”：操作者 `role_level` 必须大于目标；超管可修改除自己外的任何人；修改同级管理员需超管。
- “不能授出自己没有的权限”：非超管操作者的加授集合必须是其有效权限的子集；拒绝不受此限，但拒绝 `user:manage` 等关键权限需超管。
- 过期处理：读取时过滤；每日清理任务把过期行标为 `expired`，并写审计“系统自动过期”。
- 缓存：首版不引入全局缓存；单请求内可复用一次查询。列表页用聚合查询算“角色 N / +a / -d”，不逐行调用权限解析。

### 7.4 权限元数据

在 `backend/app/core/security.py` 新增：

```python
PERMISSION_META = {
    "question:view": {
        "label": "查看题目",
        "group": "题目管理",
        "risk": "low",
        "description": "查看题库题目与解析",
        "scope_support": ["global"],
    },
    # ... 33 项
}
```

- `group` 固定 8 组：题目管理、试卷管理、考试管理、用户与权限、系统与数据、内容与视频、社区与反馈、能力与 AI。
- `risk`：`critical|high|medium|low`。`critical` 至少包含 `user:manage`、`system:config`、`data:backup`、`log:audit`、`practice_admin:grant_teacher`。
- `GET /api/admin/permissions` 的响应改用 `PERMISSION_META` 生成 `groups`/`catalog`，但保留 `roles`/`permission_names` 旧字段，确保旧页回滚可用；删除 `PERMISSION_CN`，修掉 9 项无中文名。
- 前端权限矩阵按 `group` 渲染，按 `risk` 排序；高风险行默认折叠在“显示高风险”开关后。

## 8. 数据模型

### 8.1 `user_permission_override`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增 |
| user_id | INTEGER NOT NULL | 引用 sys_user.user_id |
| permission_code | VARCHAR(64) NOT NULL | 权限码 |
| effect | VARCHAR(8) NOT NULL | `grant` / `deny` |
| scope_type | VARCHAR(16) NOT NULL DEFAULT 'global' | 本期只写 global |
| scope_id | INTEGER NOT NULL DEFAULT 0 | 本期 0 |
| scope_key | VARCHAR(64) NOT NULL DEFAULT '' | 本期空串 |
| status | VARCHAR(16) NOT NULL DEFAULT 'active' | active/revoked/expired |
| reason | VARCHAR(255) NOT NULL | 必填 |
| granted_by | INTEGER | 操作者 |
| granted_at | DATETIME | 默认当前 |
| expires_at | DATETIME NULL | 空=永久 |
| revoked_by | INTEGER NULL | 撤销者 |
| revoked_at | DATETIME NULL | 撤销时间 |
| batch_id | VARCHAR(36) NULL | 批次 |

索引/约束：

```sql
UNIQUE(user_id, permission_code, scope_type, scope_id)
CREATE INDEX idx_upo_user_status ON user_permission_override(user_id, status);
CREATE INDEX idx_upo_permission_status ON user_permission_override(permission_code, status);
CREATE INDEX idx_upo_batch ON user_permission_override(batch_id);
```

> 不用 `UserCapability` 承载通用权限：能力包是“能力码 → 权限集合”的产品语义，长度 32，且没有 deny/expiry；混用会让两个概念都变脏。能力包保留不动。

> 写语义：同一用户同一权限同一 scope 只保留一行。设置 grant/deny 时若已有行则更新 `effect/status/reason/expires_at`；设置 inherit 时把该行置 `revoked`。历史 before/after 由 `permission_change_batch` 保存，不在本表堆版本。

### 8.2 `permission_change_batch`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | VARCHAR(36) PK | UUID |
| operator_id | INTEGER NOT NULL | 操作者 |
| action | VARCHAR(32) NOT NULL | grant/deny/inherit/apply_template/role_template_update；用户 CRUD 走 sys_operation_log，不塞进本表 |
| target_count | INTEGER NOT NULL | 目标人数 |
| reason | VARCHAR(500) NOT NULL | 原因 |
| before_json | TEXT | 逐用户 before |
| after_json | TEXT | 逐用户 after |
| undo_deadline | DATETIME | 创建 + 10 分钟 |
| undone_at | DATETIME NULL | 撤销时间 |
| undone_by | INTEGER NULL | 撤销者 |
| created_at | DATETIME | 创建时间 |

- 批量上限：500 用户 × 30 权限；`before_json/after_json` 超过 5 MB 时拒绝，要求分批。
- 撤销：读取 `before_json`，逐条比对当前 override 是否仍等于 `after`；有冲突则整批拒绝并列出冲突用户，不做部分回滚。
- 审计与撤销共用这张表，不另建日志表；`sys_operation_log` 仍记录一条摘要。

### 8.3 `sys_user` 新增字段

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| is_deleted | INTEGER | 0 | 0 正常 / 1 回收站 / 2 已 purge 墓碑 |
| deleted_at | DATETIME NULL | NULL | 删除时间 |
| deleted_by | INTEGER NULL | NULL | 操作者 |
| delete_reason | VARCHAR(255) NULL | NULL | 原因 |

- `get_current_user`（`security.py:308`）增加 `is_deleted != 0` 拒绝；`get_optional_user` 同样过滤。
- 列表默认 `is_deleted=0`；回收站筛选 `is_deleted=1`。
- 登录查询过滤 `is_deleted=0`；已删除账号返回“账号不存在或已注销”，不泄露删除原因。

### 8.4 删除语义

| 操作 | is_deleted | 数据 | 可登录 | 可恢复 |
|---|---|---|---|---|
| 软删除 | 1 | 保留 | 否 | 是 |
| 恢复 | 0 | 保留 | 是 | — |
| 彻底删除（purge） | 2 | 保留 user_id；清空 phone/email/avatar；username 改为 `已注销用户_{id}`；role 降为 student；status=0 | 否 | 否（仅超管可申请数据修复） |

- 不做物理 `DELETE`：`exam_record`、`question`、`paper` 等都可能引用 `user_id`；物理删会制造悬空引用。
- 用户名/学号不回收：purge 后仍占用唯一键，避免历史记录与新用户混淆；界面提示“该标识已被注销账号占用”。

## 10. 安全设计

### 10.1 分级守卫

| 操作 | student | teacher | admin(2) | super(3) |
|---|---|---|---|---|
| 查看用户列表/详情 | — | — | ✓ | ✓ |
| 编辑学生/教师资料 | — | — | ✓ | ✓ |
| 禁用学生/教师 | — | — | ✓ | ✓ |
| 删除学生/教师 | — | — | ✓ | ✓ |
| 修改管理员资料 | — | — | — | ✓ |
| 删除/禁用管理员 | — | — | — | ✓ |
| 改角色/role_level | — | — | — | ✓ |
| 单用户授权 | — | — | ✓（限自己权限子集） | ✓ |
| 授予关键权限 | — | — | — | ✓ |
| 批量授权 | — | — | ✓（限子集） | ✓ |
| 重置密码 | — | — | — | ✓ |
| 权限模板 | — | — | 只读 | ✓ |
| 撤销批次 | — | — | — | ✓ |
| purge | — | — | — | ✓ |

### 10.2 关键保护

- **最后超管**：任何删除/禁用/降级/拒绝关键权限的操作，先统计 `user_type='admin' AND role_level>=3 AND is_deleted=0 AND is_disabled=0`，结果必须 >= 1；否则 409。
- **自我操作**：不能删除/禁用/降级自己；不能修改自己的权限；资料编辑只允许 phone/email/avatar。
- **提权**：非超管不能授出自己有效权限之外的权限；不能把用户提升到 >= 自己的 role_level；不能修改同级或更高级用户。
- **批量原子性**：先全量校验，再单事务写入；任一目标不合法则整批拒绝，返回具体用户与原因，不做“部分成功”。
- **密码**：批量重置生成 16 位随机密码，写入一次性 CSV（10 分钟过期），接口响应只返回下载 token；不把明文放进 toast/日志/审计。单用户重置同样改为下载，不再回显。
- **敏感字段**：列表手机号默认脱敏（138****1234）；详情点击“显示”再请求完整值；导出默认脱敏，超管可选完整导出并记审计。
- **会话失效**：禁用/删除后，`get_current_user` 每次请求查库并拒绝；无需额外 token 黑名单。

## 11. 交互细节

### 11.1 空/加载/错误三态

- 危险操作：红色按钮 + 输入原因 + 二次确认；删除超管需输入用户名。

### 11.3 键盘与可访问性

- 所有图标按钮有 `aria-label`；状态不只靠颜色，配文字/图标。
- 批量栏出现时 `aria-live=polite` 播报“已选择 N 人”。

### 11.4 视觉规范

- 沿用管理员端深蓝导航 + 浅灰底；主色 `#1A3C6D`，危险 `#C0392B`，警告 `#B7791F`，成功 `#2F855A`。

## 15. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 迁移改 sys_user | 启动失败/登录异常 | R10 备份；迁移脚本 dry-run；失败恢复备份 + 删 -wal/-shm |
| 权限拒绝导致管理员锁死 | 无法管理 | 最后超管保护；关键权限不可拒绝；保留 `admin` 兜底 |
| `get_effective_permissions` 变慢 | 每请求多一次查询 | 单请求缓存；列表聚合；后续再加 60s 缓存 |
| 批量误操作 | 大面积提权 | 预览、风险提示、500 上限、10 分钟撤销 |
| 软删除过滤遗漏 | 已删用户仍可登录/出现在列表 | 统一在 `get_current_user`/登录/列表加过滤；回归测试 |
| raw 页约束 | 无法改模板 | 新建手写页；旧页只读保留 |
| 前端复杂度 | 交付延期 | 先做列表+抽屉+单用户权限，再做批量/审计/健康 |
| 角色模板影响面大 | 全员权限变化 | 保存前影响面预览；原因必填；审计可查 |

**回滚**：恢复 `question_bank_pre_admin_merge_*.db`；删除新增表/字段（或直接恢复备份）；路由切回 `admin_users.vue`/`admin_permissions.vue`；前端保留旧页即回滚点。
