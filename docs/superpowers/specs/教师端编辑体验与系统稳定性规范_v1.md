# 教师端编辑体验与系统稳定性规范 v1

> 状态：**已实施（2026-10-31），待用户验收**
> 关联需求：教师端「编辑题目」弹窗过小/不显示图片；题目管理复合题材料反复缺失；系统卡顿与高并发稳定性。
> 关联文档：`superpowers/plans/复合题材料与答题页滚动修复方案_v1.md`

## 1. 结论摘要

| 问题 | 根因 | 本轮处置 |
|---|---|---|
| 导入页「编辑题目」弹窗太小 | `.edit-dialog` 原 `width:90%;max-width:600px;max-height:80vh`，仅为 1920 屏的 31% 宽 | 改为 **75vw × 78vh**，上限 1600×1000，窄屏 94vw/90vh；编辑区滚动、底部按钮常驻 |
| 弹窗里看不到图片 | 弹窗只有 textarea，没有富文本渲染；图片在 `question_content/options/answer_analysis` 的 `<img>` 里 | 脚本注入「实时预览」面板：材料/题干/选项/答案/解析统一走 `renderQuestionContent`，`/static` 与 data URI 图片都能显示 |
| 复合题材料反复缺失 | PDF 预览里已有材料，但用户最终确认的是无材料的 JSON 批次；JSON 入库链路没有材料输入，静默建成 `group_id=0` | 预览/批量解析/确认三处统一从历史 PDF 预览恢复材料；恢复不到时申论多题直接 422 拒绝入库，不再静默丢材料 |
| 每次导入都提示“材料缺失请补充” | 警告在恢复之前生成，且旧数据从未回填 | 恢复前置到警告之前；已修复 2023 北京申论 4016–4019 等存量组 |
| 列表卡顿 | 列表接口原样返回 `full_content/options/answer_analysis`，单页 579.5 KB；25 道题解析里还存着 5.2 MB base64 图片 | 列表只返回摘要（14.2 KB），详情按 id 懒加载；base64 全部落盘改 `/static` URL；JSON 响应 GZip 后 2.5 KB |
| 多人使用会崩的担忧 | SQLite 单写者 + 无缓存头 + 每次请求写日志 + 缺组合索引 | WAL 基础上补页缓存/mmap、组合索引、静态资源长缓存、API 选择性 GZip、静态请求降噪；容量升级路径见 §5 |

## 2. 编辑题目弹窗

### 2.1 目标

- 占整个电脑屏幕约 3/4，长题干/长解析不再挤在 600px 小框里。
- 编辑时能直接看到题干、选项、答案、解析中的图片与表格。
- 不改 VTJ 设计器领地：`.vtj/vue/question_preview_list.vue` 只改 `<script>`/`<style>`，模板保持原样。

### 2.2 实现

- `.edit-dialog`：`width:75vw;height:78vh;max-width:1600px;max-height:1000px;min-width:720px;min-height:560px`；`@media (max-width:900px)` 降为 `94vw/90vh`。
- 弹窗 body 保持纵向滚动，底部「取消/保存」不随内容滚走。
- `refreshEditPreview()` 在 `.edit-dialog-body` 顶部插入 `<details class="edit-live-preview" open>`：
  - 材料预览（复合题共享材料，含 `<img>`）；
  - 题干预览；
  - 选项预览（按 A/B/C/D 顺序）；
  - 答案预览；
  - 解析预览（图片、表格、公式）。
- `openEditDialog()` 初始化 `editForm.material = q.material_text || q.material || q.shared_content`；`watch(editForm, deep)` + `nextTick` 实时刷新。
- 图片渲染统一走 `renderQuestionContent`：`/static/questions/...`、`/static/question-groups/...`、`data:image/...` 都放行；`img` 限宽 `max-width:100%`，保持比例。
- 粘贴图片仍走原 `handleEditPaste`：data URI 插入字段，保存时后端 `_extract_and_save_images` 统一落盘。

### 2.3 验收

- SFC 编译：`question_preview_list.vue` script 34,646 B / template 32,065 B，0 error。
- 导入页真实上传 `2020年国家公务员考试《申论》真题及答案（省级）【四次元自习室】.pdf`：1600×1000 视口下 `.edit-dialog` = **1200×780**（75vw×78vh）；758px 窄屏降为 712.5px（94vw）；编辑第 6 题时实时预览 2,023 字（含“材料1”正文）。
- 预览图片：向题干注入 `/static/questions/4017/img_0_1e896dff.jpg` 后 `.edit-live-preview` 内 `imgs=1, loaded=1`，弹窗内可正常显示；截图 `tmp-import-edit.png`。
- 教师端题目详情实测（q4017，2023 北京申论）：`.group-material` 文本 7,175 字；`.tq-material-dock` 文本 7,194 字。
- 详情内 5 张图：2 张首屏已加载（naturalWidth=700）；3 张 `/static/questions/4017|4018|4019/img_0_*.jpg` 因 `loading="lazy"` 离屏未加载，直接 curl 均 200，文件存在。

## 3. 复合题材料一步到位

### 3.1 根因链

```
PDF 题本上传 → 预览已切出 material_text（如 import 1636：7,175 字、4 小题）
            ↘ 用户最终确认的是同名 JSON（import 1638）
JSON /batch-parsed → items 无 material_text → 建组逻辑无输入
                    → 4 道小题 group_id=0 → 题目管理看不到材料
```

### 3.2 修复

1. **统一恢复函数** `_recover_composite_materials(db, items, subject_name)`
   - 查最近 40 条含 `preview_data` 的导入记录；
   - 从 `groups[].questions` 的题干指纹建索引，给组内每个成员补 `material_text/material_titles/material_group`；
   - 兼容没有 `groups[]`、材料直接挂第一题的旧预览；
   - 精确指纹不中时用 48 字前缀互相包含兜底（预览题干常比入库题干短）。
2. **三个入口都调用**
   - `/upload` 预览阶段：恢复后再生成 `_material_warnings`，所以预览里就能看到材料，不再先报缺失；
   - `/batch-parsed`：items 校验后恢复；
   - `/confirm`：入库前恢复。
3. **硬闸门**
   - 申论多题（≥2，排除 DUPLICATE/SKIPPED/答案卷）恢复后仍缺材料 → HTTP 422，detail 列出题号，明确要求“改为导入含材料的 PDF 题本”，禁止静默入库。
4. **隐式组头**
   - `question_preview_list.vue` 新增 `groupHeadsWithQnum`：有 `material_text` 但未被任何显式组覆盖的题，补成 `inline_<qnum>` 组头，材料不再被前端吞掉；显式组仍只在组首题映射一次，避免重复。
5. **存量修复**
   - 2023 北京申论 4016–4019 → `question_groups.id=40`，4 成员，材料 7,175 字，`question_level=1`，`sort_order=1..4`。
   - 审计：39 组，`shared_content` 为空 0 组；多成员组 17；`group_id>0` 的题 107 行。

### 3.3 验收

- `GET /api/questions/group/40`：`shared_content` 7,175 字、4 members。
- `GET /api/questions/4017`：`group_id=40`、`shared_content` 7,175、`answer_analysis` 167 字（base64 已换 `/static/questions/4017/img_0_1e896dff.jpg`）。
- 新增 `backend/tests/test_material_recovery.py`：组材料覆盖每个成员；匹配不到不硬塞。

### 3.4 残余风险

- 恢复只扫描最近 40 条预览；若同一套题的 PDF 预览早于 40 条且从未被回填，JSON 导入会走 422 硬拒（可操作，但需要先重传 PDF）。
- 纯图片材料若在解析阶段整段丢失、题干也没有组头文本，规则型警告仍可能抓不到；当前靠解析器保留 IMAGE token + 组材料 `<img>` 兜底。

## 4. 稳定性与流畅性

### 4.1 实测基线（本机，教师 user 3，uvicorn 单 worker）

| 接口 | 改造前 | 改造后 |
|---|---|---|
| `GET /api/teacher/questions?page=1&page_size=20` | 593,357 B / 0.216 s | 14,180 B / 0.040 s；GZip 后 2,562 B |
| `GET /api/teacher/dashboard` | 未单独测 | 485 B / 0.053 s |
| `GET /api/teacher/papers?page=1&page_size=20` | 未单独测 | 1,400 B / 0.063 s |
| `GET /api/teacher/papers/stats` | 未单独测 | 97 B / 0.010 s |
| `GET /api/teacher/scores/overview` | 未单独测 | 164 B / 0.015 s |

- 列表从 579.5 KB 降到 14.2 KB：`_format_question(q, include_detail=False)` 不再返回 `full_content/answer_analysis/options/answer`，只给摘要 + `detail_loaded`；打开详情/编辑时按 id 调 `/api/questions/{id}` 水合。
- 25 道题的解析里存着 5,248,977 字符 data URI；迁移后净减 5,234,708 字符，`answer_analysis LIKE '%data:image%'` 行数 = 0。
- 备份：`backend/data/backups/question_bank_pre_base64_migration_20261031_104617.db`、`question_bank_pre_composite_repair_20261031_104528.db`。

### 4.2 数据层

- SQLite 保持 WAL；新增：
  - `PRAGMA cache_size=-32000`（32 MB/连接）
  - `PRAGMA mmap_size=134217728`（128 MB）
  - `PRAGMA temp_store=MEMORY`
  - 保留 `busy_timeout=30000`、`synchronous=NORMAL`
- 新增索引（`backend/migrations/20261031_001_perf_indexes.sql`）：
  - `idx_qb_status_audit(status, audit_status)`
  - `idx_qb_subject_type_status(subject_id, type_id, status, audit_status)`
  - `idx_pqr_paper_order(paper_id, question_order)`
- 写路径不变；SQLite 仍只有一个写者，这是后续容量的硬边界。

### 4.3 传输层

- `ApiGZipMiddleware`：只压缩非 `/static`、`/uploads` 的文本响应，`minimum_size=1024`；图片不再白耗 CPU。
- `StaticAssetCacheMiddleware`：`/static/` 返回 `Cache-Control: public, max-age=604800, immutable`；`/uploads/` 返回 `public, max-age=86400`。翻页/重进详情不再重复下载题图。
- 静态请求不再逐条写 `RequestLoggingMiddleware` 的 info 日志，但保留 `X-Request-ID` 与 `X-Process-Time`。
- 前端 `apiClient` 已是 15 s 超时 + GET/HEAD/OPTIONS 网络错误/5xx 最多重试 1 次 + 401 统一跳登录；本轮未改，继续作为客户端兜底。

### 4.4 渲染层

- 列表只拉 20 条摘要，详情按需拉全量；题干/解析图片 `loading="lazy"`。
- 编辑预览只渲染当前题目，不在列表阶段渲染大段 HTML。
- 复合题材料在答题页/教师详情按组只渲染一次，组内不重复。

### 4.5 容量与升级路径（未做压测，按边界给触发条件）

| 阶段 | 现状/触发条件 | 动作 |
|---|---|---|
| 单机单 worker | 当前；API P95 < 100 ms（本机实测） | 保持；开 `X-Process-Time` 慢请求告警 |
| 单机多 worker | 并发读明显上升、CPU 未满但请求排队 | uvicorn `--workers 2~4`；SQLite WAL 允许多读，写仍串行；必须确认无进程内可变状态依赖 |
| 读写分离/换库 | 写入 QPS 持续 > 20 或出现 `database is locked` | 按 `DB_TYPE=mysql+pymysql` 出口切 MySQL；Redis 承接限流/缓存 |
| 图片带宽 | `/static` 占出口 > 50% | 已加长缓存；进一步上 CDN/对象存储（F3 已有 `media_assets` 底座） |

### 4.6 监控与降级

- `/health` 已有；每个响应带 `X-Process-Time`，可抽样统计 P95。
- 现有 `RateLimitMiddleware` / `CircuitBreakerMiddleware` 保留；异常时返回 429/503，不让单请求拖垮进程。
- 慢请求建议阈值：API > 1 s 记 warning，> 5 s 记 error；静态资源不计入业务慢日志。
