## 2. 需求拆解与边界

### 2.1 「能在三种设备登录」其实是三层，必须说清做到哪层

| 层 | 含义 | 现状 |
|---|---|---|
| L1 能登录 | 登录接口不拒绝，拿到 token | 学生 ✅ / 教师 ❌ / 管理员 ✅(web) |
| L2 能落地 | 登录后有**该角色的设备首页**，不被守卫弹到 unauthorized | 学生 ✅ / 教师 ❌ |
| L3 能干活 | 设备端能完成该角色主要任务（读/写） | 学生 ✅（部分）/ 教师 ❌ |

**建议本期做满 L1 + L2 + L3-读**（教师设备端可看首页/题目/试卷/成绩，写操作仍引导回电脑端），L3-写（设备端组卷、判分、导入）单独二期，需你拍板（见 §9 Q2）。

### 2.2 非目标（明确不做，避免范围漫延）

1. 不改 `src/utils/device.ts`（R4 冻结）；设备判定规则保持原样。
2. 不改任何 `.vtj/vue/*.vue` 的 `<template>`（R3）；教师设备页全部用**新手写组件**。
3. 不新增后端 API、不改权限模型（`require_*` 守卫不动），因此 R11 清单不变。
4. 不做「管理员在平板只读」这种折中——需求要求管理员**必须**电脑端。
5. 不做登录风控（验证码/锁定/异地提醒），属另一议题。

## 4. 总体设计

### 4.1 准入矩阵（唯一真源，后端为准）

| 角色 | web（电脑） | tablet（平板） | mobile（手机） | 说明 |
|---|---|---|---|---|
| student 学生 | ✅ | ✅ | ✅ | 现状已有，不改 |
| teacher 教师 | ✅ | ✅ **新** | ✅ **新** | 本期新增（需求） |
| admin 管理员 | ✅ | ❌ | ❌ | 需求：必须电脑端 |

实现形态：后端常量 `DEVICE_ALLOWED_ROLES = {"web": {student,teacher,admin}, "tablet": {student,teacher}, "mobile": {student,teacher}}`，并允许用环境变量 `MOBILE_TABLET_ROLES`（默认 `student,teacher`）只调整「设备端允许哪几个角色」，**admin 恒不在可配置集合内**（防误配）。

### 4.2 双层防线（缺一不可）

| 层 | 位置 | 作用 | 失败表现 |
|---|---|---|---|
| ① 登录准入 | `POST /api/auth/login` | 角色×端矩阵判定 | 403 + `code=DEVICE_FORBIDDEN` + 引导 |
| ② 路由守卫 | `src/router/index.ts` beforeGuard | 防"绕过登录页"直接访问设备端路由（含**已登录 admin 在设备端**） | 跳 `/unauthorized?reason=admin_pc_only` |

> 为什么必须双层：仅靠①——admin 可在 PC 登录后把同一 token 复制到手机／或登录接口的 `client_type` 可被脚本伪造（客户端自报）；仅靠②——服务端没有任何记录与约束，第三方客户端直接调 API 仍能拿到 token。**两层都做，且都不承担"安全边界"职责**（见 §5.8）。

### 4.3 分层示意图

```
                        ┌──────────────────────────────────────────────┐
   平板/手机/电脑  ───▶ │ 前端守卫 router/index.ts                      │
                        │  设备前缀(/tablet|/mobile):                   │
                        │   未登录 → 对应端登录页                        │
                        │   admin  → /unauthorized?reason=admin_pc_only │
                        │   teacher→ 放行 + 教师设备首页                 │
                        │   student→ 放行                              │
                        └───────────────┬──────────────────────────────┘
                                        │ POST /api/auth/login(client_type)
                                        ▼
                        ┌──────────────────────────────────────────────┐
                        │ 后端 device_policy.py（唯一真源）              │
                        │  is_role_allowed_on_device(role, client_type) │
                        │  拒绝 → 403 {code, message, action, pc_login}  │
                        └──────────────────────────────────────────────┘
```

### 4.4 组件复用策略（守 R12）

教师设备页做**一套共享响应式组件** `src/views/teacher/shared/*.vue`，由两条设备路由指向同一组件：

```
/tablet/teacher/home     ─┐
                          ├─▶ teacher/shared/TeacherHome.vue   (meta.platform 区分)
/mobile/teacher/home     ─┘
```

与既有 `/tablet/news → student/mobile/mobile_news.vue` 完全同构，**不复制两套页面**。

## 5. 详细设计

### 5.1 后端：策略模块 + 错误契约

**新增** `backend/app/core/device_policy.py`（约 60 行，纯函数、无 IO、易测）：

```python
DEVICE_ALLOWED_ROLES = {
    "web":    {"student", "teacher", "admin"},
    "tablet": {"student", "teacher"},
    "mobile": {"student", "teacher"},
}
ADMIN_NEVER_ON_DEVICE = True          # 硬约束：即使 env 写 admin 也忽略
PC_LOGIN_PATH = "/#/login"

def mobile_tablet_roles() -> set[str]         # 读 env MOBILE_TABLET_ROLES，默认 {student,teacher}
def is_role_allowed_on_device(role, client_type) -> bool
def denial(role, client_type) -> dict          # {code, message, action, pc_login_path}
```

**登录接口改造**（`auth.py:142-152`，只动这一处，约 −11/+22 行）：

```python
if not is_role_allowed_on_device(user.user_type, client_type):
    info = denial(user.user_type, client_type)          # code/message/action/pc_login_path
    logger.warning(f"设备准入拒绝 role={user.user_type} client_type={client_type} code={info['code']}")
    raise DeviceForbiddenError(info["message"], role=..., client_type=..., action=..., pc_login_path=...)
```

**为什么用 `DeviceForbiddenError`（`BaseAPIException` 子类）而不是 `HTTPException`**：
本仓库有全局错误信封（`app/core/exceptions.py`），实测发现
**普通 `HTTPException` 的自定义 headers 会被丢掉**（`http_exception_handler` 只在 `BaseAPIException` 分支转发 headers）。
而前端需要 `X-Auth-Deny` 头 + `error.code` 来区分"设备受限"和"权限不足"，
所以按仓库既有风格新增 `DeviceForbiddenError`（`code=DEVICE_FORBIDDEN`、`details` 带 role/client_type/action/pc_login_path、headers 转发）。

**错误契约（向后兼容，已实测）**：响应体是仓库统一信封——

```json
{"success": false, "detail": "管理员仅支持电脑端登录，请改用电脑访问",
 "error": {"code": "DEVICE_FORBIDDEN", "message": "…",
           "details": {"role": "admin", "client_type": "tablet",
                       "action": "use_pc_login", "pc_login_path": "/#/login"}},
 "request_id": "unknown"}
```

- `detail` 仍是**字符串** → 老前端（`.vtj` 登录页直接渲染 `errData.detail`）零回归；
- `error.code` / `error.details` → 新前端据此弹「去电脑端登录」；
- 响应头 `X-Auth-Deny: DEVICE_FORBIDDEN`（双保险）。

### 5.2 前端：守卫矩阵

**新增** `src/router/loginPolicy.ts`（约 30 行）：与后端**镜像**的矩阵常量 + 注释「仅用于 UI 预判/引导，判定以后端为准」。用于守卫里决定 admin 拦截与教师落地页。

**改造** `src/router/index.ts` 的设备分支（现 965-984）：

```ts
if (to.path.startsWith('/tablet') || to.path.startsWith('/mobile')) {
  const auth = ...
  const devicePrefix = to.path.startsWith('/tablet') ? 'tablet' : 'mobile'
  if (!logged) { ... 跳对应端登录页（不变）... }

  const role = auth.getUserRole()
  // ① 管理员：设备端一律拦（不依赖 meta.roles，因为 canAccess 对 admin 有 bypass）
  if (role === 'admin') return next('/unauthorized?reason=admin_pc_only')
  // ② 教师：放行，但学生首页要换成教师首页
  if (role === 'teacher') {
    const t = resolveTeacherDevicePath(to.path, devicePrefix)   // 新增（本文件内，不改 device.ts）
    if (t) return next({ path: t, replace: true })
    return next()
  }
  // ③ 学生：既有逻辑不变（canAccess 校验权限）
  ...
}
```

同时：PC 分支的 `roleDashboardMap`（现 1050-1060）不变；新增 `resolveTeacherDevicePath()` 负责：

| 进入 | 平板 | 手机 |
|---|---|---|
| `/tablet/home`、`/mobile/home` | `/tablet/teacher/home` | `/mobile/teacher/home` |
| `/tablet/question-bank`、`/mobile/question-bank` | `/tablet/teacher/questions` | `/mobile/teacher/questions` |
| 其 `/teacher/*` 从设备访问 | `/tablet/teacher/home` | `/mobile/teacher/home` |

**登录页 UX（不改模板）**：三个登录页在提交失败分支里加约 6 行脚本 —— 若 `errData.detail` 含「仅支持」或 header 标记为 `DEVICE_FORBIDDEN`，用 `ElMessageBox.confirm` 弹「管理员仅支持电脑端」，确认后 `location.href = location.origin + '/#/login'`。`.vtj` 只改 `<script>`，模板零改动（守 R3）。

### 5.5 管理员仅电脑：三重保障

1. **登录**：`client_type ∈ {tablet, mobile}` 且 `role=admin` → 403（矩阵硬约束，env 不可放开）。
2. **守卫**：任何 `/tablet/*`、`/mobile/*` 且 `role=admin` → `/unauthorized?reason=admin_pc_only`（文案：「管理员仅支持电脑端」+ 一键去电脑端登录）。
3. **页面**：`/unauthorized` 增补第三种 reason 的文案与按钮（改 `src/views/system/shared/unauthorized.vue` 的 `<script>`+条件文案；该文件是手写页，不属 `.vtj`）。

### 5.8 安全评审（重要，必须写进结论）

1. **`client_type` 由客户端自报，可伪造**——它不是安全边界。真正的安全边界是后端每个接口的角色/权限守卫（`require_teacher_or_admin` 等）与 JWT 校验；本期**不放松任何接口权限**。
2. **不能只靠 `meta.roles` 拦 admin**：`canAccess()` 对 admin 有 bypass（`access.ts:27`），因此设备端拦 admin 必须写在守卫的设备分支（§5.2 ①）。
3. **教师设备页复用现有接口**：这些接口本来就要求教师/管理员身份，教师设备登录不新增数据暴露面；学生 token 仍无法访问（回归用例覆盖）。
4. **越权测试清单**：学生 token 调教师接口 → 403/401；教师 token 调管理端接口 → 403；admin token 在设备路由 → 强制跳 unauthorized；伪造 `client_type=web` 的管理员登录仍会被守卫拦（说明"登录成功 ≠ 设备端可用"）。
5. **不记录密码/不含敏感信息**入日志；拒绝日志只记 `role/user_no/client_type`。
