# 资料管理：ID 连续与排序 —— 修复方案（v1）

> **状态**：✅ **已按方案 A 实施**（2026-11-08，D1=A / D2–D5 按建议）→ 交付记录：[资料管理_ID连续与排序_交付记录_v1.md](资料管理_ID连续与排序_交付记录_v1.md)
> **来源**：2026-11-08 你提的 2 个缺陷
> ①列表 ID 从第二页起不像降序；②删除中间资料后 ID 不减少、最大 ID ≠ 总资料数，恢复后应置顶并拿新号
> **分支**：`feat/material-multi-format-import`（不碰 main）

---

## 0. 一句话结论

- **问题①的真因不是排序坏了**：是 **58 条历史资料（ID 48–105）的 `create_time` 为 NULL**，而列表把 NULL 排到最后 → 你看到的 `107,106 → 45,44…` 是"中间那段被塞到末尾"。**排序本身是稳定严格降序**（实测翻 4 页 40 行、0 重复、严格递减）。
- **问题②** 根因是**软删除保号**（`status=-1` 的行仍占 ID）+ 历史缺号（11–13）→ 128 行 / 最大 ID 131 / 在用 119。另外「ID 与试卷绑定」这个前提**不成立**：资料↔试卷的关联键是 **`paper_code`**，`material_id` 没有出现在任何试卷侧。
- **推荐方案 A（展示序号，不动主键）**：列表显示**连续序号**（最上面 = 在用总数，往下递减），删除中间一条 → 后面的序号自动 -1；恢复 → 置顶且序号 = 总数（等价于"最大号"）。**零主键手术、零数据风险**，且与「题目管理列表 ID 改展示序号」的既有先例一致。
- **不建议方案 B（真重排 `material_id`）**：要级联改 3 张表 31 行引用、**519 条审计日志里的 `material:NNN` 全部错位**、旧链接失效；每次删除/恢复都要写 N 行（SQLite 单写者下放大锁竞争）；恢复需要"新行 + 迁移进度/原件/分享"，工期 1.5–2 天且不可逆。

## 1. 诊断证据（全部实测，可复核）

### 1.1 问题①：58 条资料没有上传时间

```sql
select count(*) from study_material where create_time is null;        -- 58
select material_id from study_material where create_time is null;     -- 48..105（连续 58 条）
```

列表排序（`materials.py:1570-1573`）是 `null_last, create_time desc, material_id desc` —— **NULL 被有意排到最后**。所以页面顺序变成：

| 页 | 实测 ID |
|---|---|
| p1 | 127, 126, 125, 124, 123, 122, 121, 120, 119, 118 |
| p2 | 117 … 108 |
| **p3** | **107, 106, 45, 44, 43, 42, 41, 40, 39, 38** ← 你截图里那一段 |
| p4 | 37 … 28 |
| p12（尾部） | 48–105 这 58 条（`create_time=NULL`，时间列显示「—」） |

其余 70 条「ID ↔ 时间」**0 个逆序对**，说明数据本身的时间线是对的，只有这 58 条缺失。

### 1.2 问题②：ID 为什么和总数对不上

| 指标 | 实测值 |
|---|---|
| 总行数 | **128** |
| 最大 `material_id` | **131** |
| 在用（`status>=0`） | **119**（已上架 105 + 未上架 14） |
| 回收站（`status=-1`） | **9** 条（16/20/25/46/47/128/129/130/131，仍占 ID） |
| 从未存在的 ID | **11–13**（历史硬删，3 个） |

**所以**：`128 行 ≠ 131`（缺号 3）+ `回收站 9 条占着号` → 页面最大 ID 永远大于在用资料数。这是**软删除方案的必然结果**（A4b 你拍板 B：删除=软删、回收站可恢复）。

### 1.3「ID 与试卷绑定」不成立（澄清前提）

| 证据 | 说明 |
|---|---|
| `services/paper_registry.py:23 find_exam_by_code(db, code)` | 资料 ↔ 卷 只用 **`paper_code`** 查，不涉及 `material_id` |
| `exam_paper` 表 | 没有任何 `material_id` 列（只有 `paper_code`） |
| 引用 `material_id` 的表 | 只有 `user_material_progress`(24 行)、`material_share`(1 行)、`material_file`(6 行) |

→ 改「页面显示的号」不会影响任何试卷关联；改「真实主键」才会牵连上述 3 张表 + 519 条审计日志（其中 518 条含 `material:` 文本）。

## 2. 你的两条要求 → 方案 A 如何逐条满足

| 你的要求 | 方案 A 的表现 |
|---|---|
| 按上传时间先后给 ID，列表按 ID **降序** | ①默认排序改成 `material_id desc`（ID 就是上传顺序，实测与时间 0 逆序）②补回 58 条缺失时间，时间列不再空白 |
| 删除中间一条后，**比它大的号都 -1** | 序号是**实时算出来的名次**（最上面 = 在用总数，往下递减）。删掉中间 1 条 → 它上方所有行序号 -1，下方不变；删 N 条就减 N |
| 删除后**最大号 == 总资料数** | 成立：最大序号 == 当前筛选口径下的总数（默认视图 = 在用 119） |
| 恢复后**放在最前面**，号 = 当前最大 + 1 | 恢复时给该行打一个"置顶时间"→ 排序置顶；倒序编号下它的序号 = 总数（等价于"最大号 + 1"） |
| 恢复**不复用**原 ID | 序号不来自 `material_id`，天然不复用旧号 |

> ⚠️ 代价（必须说清）：**页面上的"编号"从此是展示序号，不是数据库主键**。真实 `material_id` 只出现在接口路径/审计日志里（抽屉可显示"内部 ID"便于排障）。如果你要的是"数据库主键本身必须连续"，那只能走方案 B。

## 3. 三方案对比

| 维度 | **A 展示序号（推荐）** | B 真重排 `material_id` | C 物理删除 + 重排 |
|---|---|---|---|
| 效果 | 页面连续、删除自动前移、恢复置顶 | 同左，且**数据库**也连续 | 同左 |
| 数据风险 | **零**（只加一列排序时间 + 回填 58 行时间） | 高：改 PK 并级联 3 表 31 行 | 极高：DELETE 行，回收站消失 |
| 审计日志 | 不受影响 | **518 条 `material:` 文本全部错位** | 同 B |
| 旧链接 | 不受影响 | 失效（`/admin/{id}`、分享、下载） | 失效 |
| 恢复语义 | 保留原有（进度/原件都在） | 需"插新行 + 迁移进度/原件/分享"，旧 ID 作废 | 不可恢复 |
| 写放大 | 无 | 每次删除/恢复 UPDATE N 行（SQLite 单写者锁竞争） | 同 B |
| 工时 | **≈0.5 天** | ≈1.5–2 天 | ≈1 天 |
| 可回滚 | 一次 revert / 一列可弃用 | 需快照回滚整库 | 不可回滚 |
| 与既有裁定 | 一致（回车站保留） | 与「软删除+回收站」语义冲突 | **直接冲突**（A4b 裁定 B） |

**结论**：选 A。B 只在"你确实需要数据库主键连续（例如对外承诺编号=主键）"时才值得做，且必须单独立项。
