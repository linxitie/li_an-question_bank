## A6. 彻底删除（回收站闭环）

### 现状（证据）
- 删除只有软删：`materials.py:2114` 置 `status=-1`；**没有任何 purge / permanent 端点**（材料侧 grep 0 命中）
- 回收站现有 4 条历史测试卡（#16/#20/#25/#47），只能恢复不能清
- 引用面（全库扫过，**只有 5 处**）：`material_file`(4 行) / `user_material_progress`(24 行，**收藏 `is_favorite` 也在这里**) / `material_share`(1 行) / `material_duplicate_records`(0 行) / `study_material.source_material_id`（自引用：别人从它"领取"的副本）；`exam_paper` 与 `question_bank` **都没有 material_id 列**

### 到底删什么（2026-11-08 全库扫过，只有这 5 处引用）

| 位置 | 删法 | 说明 |
|---|---|---|
| `study_material` 本行 | **DELETE** | 正文 / 卡片正反面 / `paper_meta` / `doc_meta` / `badge` / 编号 一起没 |
| `material_file` | **DELETE** | 该资料的每条原件登记（file_id、sha256、大小） |
| `user_material_progress` | **DELETE** | 谁学过它、进度百分比、**`is_favorite` 收藏**（收藏就存在这张表里） |
| `material_share` | **DELETE** | 分享/领取记录（`scope`、`adopted_count`） |
| `material_duplicate_records` | **DELETE** | 去重台账里 `original_material_id` / `duplicate_material_id` 指向它的行（当前 0 行） |
| 别人资料的 `study_material.source_material_id` | **置 NULL**（不删行） | 学生"从它领取"过的副本还在，只是不再指回它 |
| 磁盘 `backend/storage/material_files/<ab>/<sha256>.docx` | **有条件的 DELETE** | **仅当该 sha256 不再被任何 `material_file` 行引用**才删（4 个原件目前互不共用） |

**不删的（很重要）**：

| 东西 | 为什么不动 |
|---|---|
| `exam_paper`（可作答卷） | 两边只靠 **`paper_code` 文本关联**，无外键；`exam_paper` 里根本没有 `material_id` 列 |
| `question_bank` / `paper_question_relation` | 同上，题目属于题库，不属于资料 |
| `exam_record`（考试记录/成绩/错题） | 与资料无关；删资料不影响学生历史成绩 |
| `sys_operation_log`（审计） | **唯一的删除凭证**（删完 ID 就没了），必须保留 |
| `material_import_record`（导入台账） | 历史解析记录，保留 |
| 其它资料的 `material_id` / 列表序号 | 不重排；序号是实时算的，删一条后下面的自动前移 |

> ⚠️ **一个必须你确认的口径**：彻底删除一份**试卷资料**时，题库里那张卷怎么办？
> 现在是"不碰"——因为软删时已按 P5 规则把卷置 `DRAFT`（学生看不到），彻底删除只是把资料行清掉。
> 若你希望"彻底删除连卷一起删"，那是另一个动作（会连带题目关系），**默认不做**。

### 要做什么
1. **后端**：`DELETE /api/materials/admin/{id}/permanent`（单条）+ 批量版
   - 前置：**只有 `status=-1` 才允许**（在架/未上架资料调用 → 400「请先移入回收站」）
   - 一个事务里按顺序删：`material_file` →（无引用时）磁盘文件 → `user_material_progress` → `material_share` → `material_duplicate_records` → `source_material_id` 置空 → `study_material`
   - 审计：记 `material_id / 标题 / 原件数 / 受影响进度数 / 分享数`（删完这些数字只能从日志里看到）
2. **影响面预览**：`GET /api/materials/admin/{id}/purge-preview` → 「将删除 2 个原件、3 条学习进度（含 1 条收藏）、1 条分享」
3. **前端**：回收站行加「彻底删除」（红色）+ 确认框（输入标题二次确认）；批量同理
4. **或者先做 CLI**（0.1d）：`scripts/purge_materials.py --ids 16,20 --apply`，不动 API 面

### DoD
回收站一条卡 → 彻底删除 → 行消失、原件（无他人引用时）消失、进度消失、审计可查；**在架资料调该端点必须 400**；重复删除幂等。

### 影响面 / 风险
- **API 面 +1~3 端点**：343 → 344/346，必须更新 `backend/data/refactor_baseline/api_surface.json` 与 `tests/test_api_surface.py` 的白名单（R11 的"冻结"指"不许悄悄少/变"，登记新增是允许的）
- 风险：误删不可逆 → 双重确认 + 只允许删 `-1` + 先出快照；原件共用时只删行不删文件
- 参考实现：用户管理的"回收站批量注销/匿名化 purge"已有先例（`superpowers/plans/管理员端头像与回收站批量注销实施计划`）

### 需拍板
- D-A6-1：谁能用？（仅超管 / 管理员都行）
- D-A6-2：先 CLI 还是直接做 API+UI？
- D-A6-3：确认方式（输入标题 / 输入"删除" / 普通二次确认）

## A7. 批量操作搬进新页

### 现状（证据）
- 新页 `src/views/admin/materials.vue`：**没有勾选框、没有批量操作**（源码注释明写 v1 未做）
- 旧页 `#/admin/materials/legacy`（`admin_materials.vue`）有：`batchDelete` → `DELETE /api/materials/admin/batch`；`batchPublish/batchUnpublish` → **逐条** `PUT /api/materials/admin/{id}/status`
- 新页页头已有「旧版（临时）」入口

### 要做什么
1. 表格加首列 checkbox + 表头全选（**仅当前页**，不做跨页选择）
2. 选中后出现批量操作条：「已选 N 条｜批量上架｜批量下架｜批量删除｜取消选择」
3. 删除走二次确认（复用 `confirmOverlay`）；上/下架给结果提示
4. 结果提示：成功 N / 失败 M + 失败原因（部分失败不整体回滚，逐条报）
5. 完成后刷新列表 + 统计卡（`loadList` + `loadStats`）
6. 兼容 P5 联动：批量下架/删除时，卷会由后端自动同步 `DRAFT`（已实现，无需前端处理）

### DoD
勾 3 条 → 批量下架 → 3 行都「未通过」、统计已上架 -3、对应卷 `DRAFT`（可用巡检确认）；批量删除 → 进回收站；失败条目有红字原因；`vitest` 覆盖组件行为（勾选/全选/禁用态）。

### 影响面 / 风险
- **0 个新端点**（复用 `/admin/batch` 与 status 接口）；也可选新增"批量 status"端点把 N 次请求压成 1 次（需登记 API 面）
- 风险：批量下架会**批量影响学生可见卷**（P5 联动）→ 确认框文案要写清"同时会让 N 场考试对学生不可见"
- 风险：`/admin/batch` 现在是逐条置 -1（P5 改的），批量 50 条时是 50 次 UPDATE，量级可接受

### 需拍板
- D-A7-1：批量上/下架逐条调（0 新端点）还是加批量端点（更快但要动 API 面）
- D-A7-2：是否需要"跨页选择"（默认不做）

## A2. P2 题目线（让上传的试卷变成可考卷）

### 现状（证据）——这就是 #127 卡住的地方
| 环节 | 现状 |
|---|---|
| 上传试卷 | `POST /api/materials/admin/files/upload` → 只建 `study_material(status=0)` + 原件 + 解析出 `paper_code`（如 `GZ-2024-GK-T`），**不建 `exam_paper`** |
| 建卷 | 只能从**别处**建：教师端 `POST /api/teacher/papers`、管理员 `POST /api/papers`、AI 组卷、**题目导入自动建卷**（`question_import.py:3680`，题量≥5 时建 `DRAFT` 并生成新 code） |
| 配题 | `POST /api/questions/import/confirm` 支持 `paper_name`（按名匹配/新建），写 `paper_question_relation`；**不接受 `paper_code`** |
| 结果 | 上传的真题永远进不了学生端；#127 上传 3 天仍是"有资料无卷" |

### 要做什么（4 步闭环）
1. **资料 → 建卷**：新增动作（上传后可点「生成可作答卷」/ 上架时自动）：
   - 用资料的 `paper_code` 建 `exam_paper`（`composition_method='IMPORT'`、`paper_type='DRAFT'`），元数据取 `paper_meta`（年份/地区/卷别/题量/总时长），标题取资料标题
   - 幂等：同 `paper_code` 已存在则不重复建
2. **题目导入挂到这张卷**：`/api/questions/import/confirm` 增加可选 `paper_code`（或"归属试卷"下拉），命中则复用、不命中才新建；写 `paper_question_relation` + 回填 `question_count` / `total_score`
3. **发布**：卷配完题 → 资料「上架」→ P5 已实现自动 `PUBLISHED`（无需新逻辑）；学生端立刻可见
4. **回填 #127**：给它建 `GZ-2024-GK-T` + 导入 119 题 → 学生端从 2 套变 3 套（可验收）

### DoD
一份真题：上传 → 生成卷 → 导题 → 上架 → 学生端能考能交卷出分，全链路一次跑通；`study_material.paper_code == exam_paper.paper_code`；重复导入不产生第二张卷；`question_count` 与 `paper_question_relation` 真实行数一致。

### 影响面 / 风险
- 新增 1–2 个端点（若有"生成卷"动作）→ API 面登记；或者复用现有 `backfill` 思路做成"上传后提示去建卷"
- 风险：题目来源格式差异（PDF 拆题 vs Excel 题库）→ 先做"已有结构化题目"的情况，PDF 拆分另算
- 风险：`paper_question_relation` 与 `question_count` 不一致会导致学生端"开始考试→暂无题目"，需要一致性校验
- 依赖：**A1 会决定"建卷入口"最终长什么样**，若先做 A2 再收敛 A1，需保证新入口与最终形态一致

### 需拍板
- D-A2-1：建卷触发点（上传后手动点 / 上架时自动 / 导入题目时自动）
- D-A2-2：题目从哪来（Excel 题库 / PDF 拆分 / 两者）
- D-A2-3：#127 是否本次就补齐成第 3 套可考卷

## A1. P0–P4 试卷管理收敛（"上架即审批"落到接口层）

### 现状（证据）——**页面层其实已经收敛得差不多了**
| P0–P4 原来要做的 | 实测现状 |
|---|---|
| 删「试卷管理」菜单/页面 | ✅ 侧栏只剩「资料管理」；`/admin/papers` 已是 **redirect** → `/admin/materials?type=paper` |
| 删审批页 | ⚠️ `paper_approval.vue` 还在但**已无路由**（死页）；`admin_approval` 的 **API 仍注册**（`main.py:949`） |
| 单一上传入口 | ✅ 管理端只剩资料页「＋上传试卷」 |
| `exam_paper` 降为投影 | ❌ 未做：**4 处仍能直接写 `PUBLISHED`**（`papers.py:442`、`paper_generation.py:748`、`admin_approval.py:245`、`teacher.py:1383`），教师端 `/teacher/papers/{id}/publish` 仍可直发 |
| 反向不驱动 | ❌ 未做 |

**所以 A1 剩下的主要是"接口层"**：页面已经不给入口了，但 API 还开着，教师端编辑器还在直连。

### 要做什么（按破坏性从小到大）
1. **登记式收敛（低风险）**：所有写 `paper_type` 的入口，在写完后调用 `material_paper_sync`（反向）——让"教师发卷"也顺手建/挂资料，保证两边一致
2. **入口收敛（中风险）**：下线 4 类旁路
   - 审批 API：`POST /api/admin/papers/{id}/approve|reject`、`/api/papers/{id}/approve`
   - 管理员旁路：`POST /api/papers/{id}/publish`（改为只允许资料页触发）
   - 教师直发：`POST /api/teacher/papers/{id}/publish`（改为"提交上架申请"或直接下线）
   - 死页清理：删 `paper_approval.vue` 路由残留/文件、`admin_approval` 路由注册
3. **投影化（高风险）**：`study_material.status` 成为唯一真源；`exam_paper` 只读派生；加"一致性巡检"进 CI（已有脚本可复用）
4. **门禁同步**：API 面 343 → 实际值（要更新 `api_surface.json` + `KNOWN_EXTRA_OPERATIONS`）；页面数若删页需同步 L6/L7

### DoD
- 学生端能考的每一张卷，都能在资料库找到对应资料（一致性巡检恒 0）
- 任意入口改 `paper_type` 都会反射到资料状态（或已被下线）
- 门禁全绿（除 L1-G 数据红），API 面清单与代码一致
- 教师端 8 页工作流有明确的迁移路径（不是"功能没了"）

### 影响面 / 风险（这条最大）
- **会改教师工作流**：教师端试卷管理（`TeacherPaperEditor.vue`，1305 行量级）现在能建卷/发布；下线后要给替代路径（"提交给管理员上架"或"直接在资料页建"）
- **API 面变更**：至少 4–6 个端点下线 → `api_surface.json`、`test_api_surface.py`、`KNOWN_EXTRA_OPERATIONS` 三处要同步，且属于**破坏性变更**（R11 要求逐条比对）
- 风险：AI 组卷 / 小智私卷（`smart_exam.py`）产生的是"练习卷"，本来就不该进资料库 → 需要区分"真题卷（要有资料）"与"练习卷（不必有资料）"，否则一致性巡检会误报

### 需拍板（这条必须先定）
- D-A1-1：**教师是否还能自己建卷/发布**？（能 → 收敛只做"同步"；不能 → 教师流程要改，工作量翻倍）
- D-A1-2：AI 组卷 / 小智私卷是否纳入"必须对应资料"？
- D-A1-3：审批 API 直接删还是先标记 deprecated 观察一版？
