> 状态：**方案，未写业务代码**。按全局规则，批准后才动代码。前置已交付：S-A 单遍解析、S-C OCR 常驻、P2 文章扫描件。

## 0. 一句话结论

| 项 | 结论 | 代价 |
|---|---|---|
| **O5** | 能做，**收益中等**：S-A 之后本机单份上传已经 0.14–0.4s，"立即返回"省的是**大文件/慢盘/远程**的等待，以及**避免网关超时**；扫描件本来就已是异步 | 1.5–2d |
| **P3** | **能做，但只承诺"文字草稿 + 人工核对"**：实测一份真实扫描试卷 2 页 → OCR 9.5s/页、拆出 **6 题、其中 4 题四选项齐全**；**图片/版式一律不还原**，且 41 页整份 OCR ≈**6.5 分钟**，所以 P3 **必须异步**，不能同步解析 | 2–2.5d |

**建议顺序：先 O5，再 P3** —— O5 建立的"上传即返回 + 后台解析 + 状态轮询"正好被 P3 复用（P3 的 6 分钟 OCR 不可能塞进一个同步 HTTP 请求）。

## 1. 实测证据（本机，2026-11-13）

### 1.1 上传链路现状（S-A/S-B/S-C 之后）

| 类型 | 端到端 | 说明 |
|---|---|---|
| 文字版 PDF（17 页） | **143 ms** | S-A 单遍解析后 |
| docx（0.69MB） | **347–391 ms** | 解析本身占大头 |
| 扫描件（1 页） | 17.6s 冷 / **4.7s 热** | S-C 常驻 worker |
| 扫描件（24 页） | **272–357s** | 页数决定 |

> 所以 O5 的"上传即返回"对**本机小文件**体感提升有限（143ms→~50ms），真正的价值在：①41 页扫描件这类长任务；②20MB 大文件上传+解析叠加；③远程/慢盘/反向代理超时。

### 1.2 P3 可行性 PoC（真实扫描试卷）

样本：`题库/公安题目（打印）/2025多省联考公安《公安专业》.pdf`（41 页、56MB、**avg 0 字/页**=纯扫描）。
取前 2 页 OCR + 现有 `splitter`：

| 指标 | 实测 |
|---|---|
| OCR 速度 | 2 页 **19.1s（9.5s/页）** → 41 页 ≈ **6.5 分钟** |
| 文本行 | 66 行 |
| 认出的题号 | 1、2、3、4、5、7（共 6 个） |
| `split_questions` 拆出 | **6 题**，其中**四选项齐全 4 题** |
| 质量缺陷（实测） | ①第 3 题丢 C 项；②页脚 `X`、公众号/店主微信等噪声混进正文；③选项偶有跨行截断 |

**结论**：拆题可用，但**准确率不足以自动入库**；必须走"草稿 → 逐题核对 → 确认"，且要在草稿里明确写"扫描件 OCR，无原图"。

## 2. O5 设计（上传即返回、解析转后台）

### 2.1 现状与问题

- `POST /admin/import/upload`（`materials.py:3489+`）对 **docx / xlsx / 文字版 PDF** 是**同步解析**：请求里把文件写完、解析完、写库完才返回；
- 扫描件已经是异步（`async(ocr)`），P2/S-C 复用同一套；
- 前端三处已经会轮询 `import/{id}/status`（`ArticleBatchUpload`、`CardXlsxImportDialog`），`MaterialBatchUpload` 走的是**另一条** `/admin/files/upload`（只留档，不解析）——**不在 O5 范围**。

### 2.2 设计

| 环节 | 改成 |
|---|---|
| 上传 | 只做：落临时文件、算 sha256、**建记录 + 立即写指纹**、返回 `{import_id, parse_status:"processing"}`（目标 **<300ms**） |
| 解析 | 统一进后台线程池（复用 P2 的 `run_in_threadpool` 模式）：`docx` / `xlsx` / `文字pdf` / `扫描pdf` 各一个 job；扫描走 S-C 常驻 OCR |
| 进度 | 复用 P2 的 `parse_result._ocr` 口径，扩成通用 `parse_result._progress = {phase, done, total, percent}`；`status` 回包 `progress`（已存在，只换数据源） |
| 失败 | 记录 `failed` + 具体原因；不建空资料（与现行为一致） |
| 去重 | 指纹**上传即写**；`_IMPORT_DONE_STATUS` 从 `("consumed",)` 扩为 `("consumed","success","processing")` → 同一文件在解析中再传直接 409「正在解析中」 |
| 前端 | `ArticleBatchUpload` / `CardXlsxImportDialog` 已经是"upload → 轮询 → confirm"，**只需**把 parse 阶段的等待与进度文案统一（部分已有）；`MaterialBatchUpload` 不动 |

### 2.3 风险与回滚

| 风险 | 处置 |
|---|---|
| 上传成功但解析失败（以前是同一个请求里报错） | 状态轮询里明确 `failed` + 原因；前端已按行展示 |
| 后台任务随进程重启丢失 | 复用 P2 的**40 分钟惰性超时**；重启后旧记录查询即判失败 |
| 去重语义变化（processing 也拦） | 加 `force=true` 口子（已有）；前端在 409 文案里提示"正在解析中，稍等" |
| 回滚 | `UPLOAD_SYNC_PARSE=1` 开关切回同步（保留旧分支）；或单次 revert |

## 3. P3 设计（试卷导题扫描件）

### 3.1 现状与问题

- `paper_ingest.read_pdf`（`readers.py:156`）用 `page.get_text("dict")` 取**题号块的 y 坐标**（用于把内嵌图片归属到题），再用 `page.get_text()` 取行文本；
- 扫描件：`get_text()` 为空 → 拆出 0 题；`get_images()` 通常只有**整页大图**，若放行会全部挂到某一题上；
- 导题入口 `POST /admin/{id}/parse`（`materials.py:2068`）是**同步**返回草稿的。

### 3.2 设计（v1 边界先立住）

| 环节 | 做法 |
|---|---|
| 判定 | `read_pdf` 内复用 `parse_pdf_once` 的采样判定（S-A 已交付）；`scanned=True` → 走 OCR 分支 |
| 文本 | `ocr_sidecar.read_pdf_text()`（S-C 常驻）→ 逐行文本；**先经过 P2 的 `ocr_html.drop_noise`** + 追加试卷特有噪声（"店主微信/公众号/其他机构/本 PDF"等） |
| 拆题 | 直接喂现有 `splitter.split_questions(lines)`（**不重写拆题逻辑**） |
| 图片 | **`images=[]`**（不归属、不裁剪）；draft 里写明"扫描件：无原图" |
| 草稿 | 记录 `source="pdf-ocr"`、`warnings` 加两条：①"扫描件 OCR 文本，请逐题核对"；②"题号/选项可能错位，尤其跨页/双栏" |
| 同步/异步 | **异步**：`POST /parse` 立即建 `status="parsing"` 草稿并返回；后台 OCR 完成后置 `pending`；`GET /drafts/{id}` 带 `progress`；前端「导题」按钮轮询直到 `pending` 再开抽屉 |
| 页数上限 | 60 页（与 sidecar 一致）；超限截断并在 warning 里写"仅解析前 60 页" |

### 3.3 明确不做（v1）

- 版式还原（双栏阅读顺序、题图/公式/表格）——**扫描件的图一律不挂**；
- 自动判断题型（单选/多选）以外的语义修正；
- 自动入库（仍然必须人工逐题核对后点"确认入库"）。

### 3.4 验收（DoD）

同一份 41 页扫描试卷（或前 5 页）→ 导题 → 3 分钟内出现 `pending` 草稿、题号连续可编辑、警告可见 → 人工确认入库后题库新增对应题；`pytest` 新增 ≥6 例（扫描判定、噪声过滤、拆题条数、warning、异步状态流转、截断）。
