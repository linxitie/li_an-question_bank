## 1. 先回答你的问题

### 1.1 「先做适配器再进播放器」可行吗？

**可行，且这是我推荐的顺序。** 三个理由：

1. **播放器的输入必须稳定**。播放器一旦开工，所有组件（讲师、板书、场景、题目面板）都按 DSL 字段渲染；字段一变就得改一遍组件。适配器先把字段钉死，播放器只写一次。
2. **适配器完全离线**：只读 Obsidian 库里的 2 个文件 + SQLite 只读 + 不联网、不调 LLM → **`LLM_API_KEY` 为空也不阻塞**（这是 P1 能开工的关键，上一份可行性评估里它是硬阻塞项之一）。
3. **可回滚**：产物是纯 JSON，出问题 `git checkout` 就回去了，没有表结构、没有迁移、没有端点。

### 1.2 但它不是「一步到位」，中间必须有 T5

你的原话是「JSON 树 → 稳定 point_id + 可讲清单 → lecture_source.json（不写前端），再立刻进播放器」。
按实测，`lecture_source.json` 只能给出**讲哪个点、讲多长、有几个考点、有没有题、有没有视频**——它**不含台词**。
播放器要跑起来还差「这段微课的 7 段式台词 + 板书内容 + 检查点」。两份产物必须分开：

| 产物 | 内容 | 谁生成 | 谁消费 |
|---|---|---|---|
| `lecture_source.json` | **事实层**：87 点 / topic 切片 / 考点 / 题量 / 视频 / 分级 | T1–T4 适配器（离线、确定性） | T5 生成器、播放器选片页 |
| `lecture_script.json` | **台词层**：DSL 的 segments（intro/concept/demo/scene/checkpoint/summary）、avatar、scene | T5 规则模板（离线、可复现；LLM 留 P2） | T6 播放器 |
| `lecture/*.vue` | **渲染层** | T6 播放器 | 学生端 |

所以真实链路是：**T1–T4 适配器 → T5 规则讲稿 → T6 播放器**，而 T5 只有 3 个试点的工作量（约 1 天），不是「又一轮设计」。

### 1.3 为什么 T5 不用 LLM（现在）

- `LLM_API_KEY` 实测为空（`backend/.env` 只有占位）→ 调不通；
- 库内《教学画面渲染规范》第 5 条明令：**禁止用生成式模型产出文字/公式/法条**；
- 规则模板出来的讲稿**可 diff、可复现、可审计**，正好符合「LLM 内容必须 approved」的门槛前状态。
LLM 在 P2 只做「把规则稿润色成人话」，且产物必须落 `产出/变更集/` 走审核。

### 3.3 试点单元与知识点的真实关系（**本方案最关键的一条实测**）

| 试点 | 命中知识点 | 说明 |

| p05 继续盘问 | 近似命中 `刑事执法基础知识` | 严格说属人民警察法/程序规定 |
| p46 人民警察法 | `GZ-JC-006 人民警察法基础知识` | ✅ |
| p49 群众工作 | `GZ-JC-011 公安工作基本原则` | ⚠️ 语义偏，待确认 |

## 4. 键体系设计（三层键，发布后不改）

### 4.1 模块 CODE（15 个，已核对与大纲模块顺序一一对应）

| 科目 | 模块 → CODE |
|---|---|
| 行测 | 知觉速度与准确性 `XC-ZJ`｜政治理论 `XC-ZZ`｜言语理解与表达 `XC-YY`｜判断推理 `XC-PD`｜常识判断 `XC-CS`｜数量关系 `XC-SL`｜资料分析 `XC-ZL` |
| 申论 | 归纳概括 `SL-GN`｜提出对策 `SL-DC`｜议论文写作 `SL-YL`｜综合分析 `SL-ZH`｜应用文写作 `SL-YY` |
| 公专 | 职业素养 `GZ-ZY`｜基础知识 `GZ-JC`｜基本警务能力 `GZ-JW` |

### 4.2 三层键

| 层 | 格式 | 示例 | 规则 |
|---|---|---|---|
| 知识点 `point_id` | `{CODE}-{NNN}` | `GZ-JC-010` 行政执法基础知识 | 按大纲 JSON 模块内顺序 001 起；**新增只追加**，插入只允许加在尾部；改名只改 `name` |
| 教学切片 `topic_id` | `{point_id}-T{NN}` | `GZ-JC-010-T04` 传唤与行政强制措施 | 归属必须人工确认（D2）；一个 point 下 T01 起 |
| 考点 `exam_point_id` | `{point_id}-E{NN}` | `GZ-JC-010-E03` | 与 `point_id` 同前缀；`name == "其他"` 的标 `placeholder: true` |

**为什么考点 ID 用序号而不是名字**：403 个考点里 86 个叫「其他」、312 个不同名——**名字不能当主键**，序号才能。名字改，ID 不动。

### 4.3 冲突与稳定性

- 87 个 point_id 生成后**冻结**，写进 `产出/清单/知识点ID.json`（含 `frozen_at`、`sha256`）。
- 若大纲新增知识点：只能 `-NNN` 递增追加；若删：产物里保留墓碑 `status: "deprecated"`，不回收 ID。
- 适配器对「同一 point 下重名考点」保留序号区分，并在 `warnings[]` 里报出来。
- **实测纠偏**：库内《AI讲师数据库创新设计_v1》§1 举的例子 `SL-GN-004 = 影响概括` 与实测不符——`SL-GN-004` 实际是 **特点概括**，影响概括是 `SL-GN-005`（归纳概括模块顺序：问题/对策/原因/特点/影响/过程）。这正是「ID 必须由脚本从源自动生成、不能手写」的又一个证据。

## 5. 「可讲清单」分级规则（可执行、可复算）

每个单元算出 5 个字段，全部由数据决定，不许手填：

| 字段 | 取值 | 计算规则 |
|---|---|---|
| `lectureable` | `true/false` | `有效考点 ≥ 1` **或** 该知识点被人工列入 topic 表；否则 `false`（14 个零考点里没有 topic 的就不讲） |
| `granularity` | `exam_level` / `point_level` / `topic_level` | 有 topic → `topic_level`；否则有有效考点 → `exam_level`；否则 `point_level` |
| `tier` | `P0` / `P1` / `P2` | **P0**：在 topic 表内（12 个试点）；**P1**：题库有题（25 个）或考点名命中程序类关键词（立案/管辖/回避/传唤/听证/处罚/强制/讯问/证据/时限/程序）；**P2**：其余 |
| `coverage` | `{questions: n, video_clips: n, law_cards: n}` | 题数来自 `question_knowledge`（按名称/别名对齐）；视频来自 76 集台账的考点候选映射（当前只能到「系列级」，`video_clips` 多为 0，**如实为 0**）；法条卡目录当前为空 → 0 |
| `est_minutes` | 6–12 | `6 + min(4, 有效考点数)`；有 topic 时用手工时长覆盖；**不四舍五入到失真**（库内铁律第 9 条） |

**排除规则**（写进产物 `excluded[]`，带原因）：
1. 考点名 = `其他` → 不进讲稿（`reason: "placeholder_exam_point"`）；
2. 零考点且无 topic → `reason: "no_teaching_unit"`；
3. 名称含「其他」的知识点（如大纲里的「其他」类）→ 人工确认后再入。

**对 87 个点的预演结果**（按上述规则本周可得的初值，供你判断规则是否合理）：
`exam_level 73 / point_level 14`、`有题 25`、`P0 = 12 个 topic`、`可讲 ≈ 73 + topic 覆盖的零考点数`。

## 7. 生成器设计（`scripts/lecture/build_lecture_source.py`）

| 项 | 设计 | 为什么 |
|---|---|---|
| 位置 | 仓库根 `scripts/lecture/build_lecture_source.py`（与 `scripts/gen_inventory.py` 同级） | 已有 `scripts/` 是「集成/生成脚本」层，不塞进 `backend/`（避免被当成后端代码参与门禁 L1-G 的 DB 检查） |
| 输入 | ①vault JSON ②vault 大纲 md（只读解析标题层级做顺序校验）③`桐哥课程-考点候选映射.md` ④SQLite **只读** `file:…?mode=ro` | 只读一切；`mode=ro` 保证绝不写库 |
| 输出 | `src/assets/lecture/lecture_source.json`（运行时唯一数据源）+ `docs/plans/知识供给清单_可讲知识点_v1.md`（人读）+ `产出/清单/知识点ID.json`（冻结 ID 表） | 运行时用静态 import，**P1 零后端** |
| 确定性 | 全流程按 `(subject_order, module_order, NNN)` 排序；时间戳只出现在 `generated_at`，`--check` 时忽略该字段 | 同一输入必得同一输出，否则 drift 检查无法用 |
| CLI | `--build`（默认）｜`--check`（与磁盘比对，漂移 exit 1）｜`--stats`（只打印 counts） | `--check` 可进 CI，`--stats` 供人快速核对 |
| 编码 | `sys.stdout.reconfigure(encoding='utf-8')` + 文件 `newline='\n'` | 本机 GBK 控制台会崩（本项目已有踩坑记录） |
| 失败策略 | 任一输入缺失/校验不过 → 非 0 退出 + 不写产物（先写 `.tmp` 再原子替换） | 防止半成品 JSON 进仓库 |
| 不做什么 | 不写 vault、不调 LLM、不联网、不写 DB、不生成 Vue | 边界清晰，评审时好切 |

**为什么产物放 `src/assets/lecture/` 而不是 `public/`**：`import lectureSource from '@/assets/lecture/lecture_source.json'` 走 Vite 打包，TS 能推断类型、构建期就能发现字段缺失；`public/` 是运行时 fetch，错误只能在浏览器里暴露，且多一次请求。

## 8. 校验与门禁（三道，全部离线）

## 11. 写码前 11 问自检（按你的全局规则 3）

| 问 | 答 |
|---|---|
| 为什么这样写？ | 单一脚本、单一职责：只做「读事实 → 算分级 → 写 JSON」。不引框架、不用 ORM，因为输入只有 3 个文件 + 1 张只读表，用 sqlite3 + json 最薄 |
| 好处是什么？ | 可复现（确定性排序）、可 diff（JSON + md 双产物同源）、可回滚（纯文件）、零外部依赖（无 key、无网络） |
| 有安全问题吗？ | 输入只读（`mode=ro`）、不联网、不执行输入的 Markdown 里的任何指令（只按正则抽标题/代码块）、输出路径白名单、JSON 里不允许出现 HTML（播放器禁 `v-html`），另外生成器不写 vault 以免污染教研事实源 |
| 对后期运维有什么便利？ | 一条命令重建；`--check` 可进 CI 抓漂移；产物自带 `sources.sha256`，输入变了没重跑会被测试抓到；版本号在 `schema_version`，未来加字段走 1.1 兼容升级 |
| 怎样写才能让未来运维更省事？ | 语义化分段（`subjects` / `units` / `excluded` / `warnings`）+ 每个排除项都带 `reason`；报错信息带「哪一行、哪个文件、怎么修」 |
| 放这个文件里对不对？ | 生成器放 `scripts/lecture/`（不属后端业务代码，不触发 L1-G 的 DB 依赖）；测试放 `backend/tests/`（pytest 已覆盖该目录）；产物放 `src/assets/lecture/`（Vite 静态 import） |
| 改完前端能显示效果吗？ | 本方案**不写前端**；前端效果在 T6，产物只是被 import 的数据。T5 的 DSL 会先做 JSON Schema 校验，T6 才渲染 |
| 后端字段完善吗？ | P1 **零后端**，不新增表/端点，因此不涉及字段；`question_bank.point_id` 全 NULL 是既有事实，方案用 `question_knowledge` 关联，不改表（改表属 P2） |
| 后端路由注册/接口完整吗？ | 不新增路由 → 无需注册；`openapi` 不变（462 个操作），R11 白名单不动；`test_api_surface.py` 不动 |
| 会不会漏掉门禁双改点？ | P1 只加 1 个页面路由：`scripts/verify-modularization-constraints.mjs` 的 `EXPECTED_DYNAMIC_IMPORTS` 104→105、`backend/tests/test_route_roles.py` 的 `104→105`（T7 专列） |
| VTJ 版本一致吗？ | 新页面全部放 `src/views/lecture/`，**不碰 `.vtj/`**，`vtj_version_sync.py --check` 仍 69 一致/0 失败；R1/R3 不触发 |
