# 学生端功能模块化设计方案 v1

> 状态：终稿（已评审通过，作为实施依据）
> 适用分支：`feat/student-containerization` 之后的模块化开发分支体系
> 适用对象：学生端全部功能（题库浏览、答题、练习、组卷、错题、笔记、社区、资讯、资料、成就、商城、签到等）
> 关联基线：`backend/data/refactor_baseline/api_surface.json`（343 端点）、`model_map.json`（71 模型）、`db_tables.json`（72 表）

---

## 摘要

本方案把学生端拆分为 **14 个业务模块**，目标是让一名开发者独立拥有 1..N 个模块，完成「前端页面 + 后端 API + 测试」的全栈闭环；每人一条分支，GitHub 合并零冲突；同时把模块之间的横向通信（星型拓扑）与纵向通信（3 角色 × 3 设备）全部打通。

方案的三条基本判断：

1. **不改目录归属，只建立所有权。** VTJ 页面继续留在 `.vtj/vue/`，后端继续留在 `backend/app/api/v1/`，通过《模块所有权映射表》把「文件」映射到「模块」。这样避免触碰 92 处硬绑定 import、343 个冻结端点与 75 个设计器页面。
2. **成就成长是横向枢纽，但不是代码依赖中心。** 10 个业务模块把行为事件发布到统一事件入口 `record_user_action()`，成就模块只消费事件、不 import 任何业务模块代码；任何模块删掉成就模块都能独立运行。
3. **后端是唯一事实来源。** 前端事件总线只是加速器，页面挂载时的 API 拉取才是正确性兜底；跨设备状态一律落库，`localStorage` 仅保存 UI 偏好。

## 一、目标与红线

### 1.1 目标

| 编号 | 目标 | 可验证的完成标准 |
|---|---|---|
| G1 | 学生端拆成 14 个业务模块 | 《模块所有权映射表》覆盖全部学生端页面与端点，无遗漏、无重复归属 |
| G2 | 一人一模块全栈独立开发 | 任一模块负责人可在不修改他人模块文件的前提下，完成该模块前端页面 + 后端接口 + 测试 |
| G3 | 一人一分支，合并零冲突 | 两条并行分支合并时，冲突文件数为 0；若出现冲突，必属共享文件（三端 home/login、`event-bus.ts` 常量表）且由指定所有者裁决 |
| G4 | 横向通信（模块间星型）打通 | 10 条入边事件全部可从来源模块送达成就模块；3 条非成就边全部有明确落库路径 |
| G5 | 纵向通信（3 角色 × 3 设备）打通 | 教师发布试卷后，学生 PC / 平板 / 手机三端在 WS 在线时秒级看到，离线后重新进入页面也能拉到同一份数据 |
| G6 | 协作可复制 | 《分支使用说明书》7 章齐备，新成员按说明书可在半天内跑通本地环境并提交第一个模块改动 |

### 1.2 红线（均为实测事实，不可协商）

| 红线 | 内容 | 实测依据 | 本方案的遵守方式 |
|---|---|---|---|
| R1 | `.vtj/` 禁止移动、改名、删除 | `src/router/index.ts` 存在 **92 处** `import('$vtj/vue/<id>.vue')` 硬绑定；VTJ 设计器按 page id 读写 | 全部页面原地不动，模块化只做「逻辑分层 + 所有权映射」 |
| R3 | `.vtj/vue/*.vue` 的 `<template>` 禁止 AI 直接改 | 设计器回存会覆盖手写模板；AI 提取不到手写方法 | 模板改动一律由用户在设计器 `http://localhost:9527/__vtj__/` 拖拽完成；AI 只改 `<script>`，且必须先 `dryRun: true` |
| R5 | `mobile_*` / `tablet_*` 文件名前缀禁止重命名 | 前缀是与 `.vtj/vue/` 页面一一对应的唯一线索 | 文件名零改动；设备差异通过 `meta.platform` 与 `src/utils/device.ts` 表达 |
| 版本冻结 | `@vtj/web`、`@vtj/ui`、`@vtj/charts`、`@vtj/icons`、`@vtj/utils`、`@vtj/materials`、`@vtj/pro` 固定 **0.16.35**；`@vtj/cli` 固定 **0.12.19** | `package.json` 实测 | 模块化期间不升级、不降级；任何版本变更须单独提案 |
| R11 | `/api/v1/...` 路径冻结 | `backend/data/refactor_baseline/api_surface.json` 记录 **343 个端点** | 新增能力只允许「新增端点」或「复用既有端点」，禁止改路径、改方法、改响应外壳 |
| R12 | 平板路由复用手机页，不为平板复制副本 | `/tablet/` 21 条路由中部分直接复用 `@/views/mobile_*.vue`，经 `meta.platform` 区分 | 新增平板能力时优先复用手机页；确需差异时用 `meta.platform` 分支，不新建重复组件 |

补充约束（来自 `AGENTS.md`，本方案同样遵守）：

- `.vtj/` 页面数量基线为 75 页（PC 61 / 平板 7 / 手机 7），模块化不新增、不删除页面。
- `src/utils/device.ts` 与 `resolveDevicePath()` 原样保留，设备双轴映射逻辑不改。
- 后端为单一 FastAPI 单体，37 个 `api/v1` 模块、38 处 `include_router`；模块化不拆服务、不拆进程。
- 数据库为 SQLite（WAL），模块化不换库、不改表结构（签到复用 `badge_task`，见 2.14）。

### 2.2 归属判定规则

为避免「一个页面两个主人」，归属按以下优先级判定，遇到歧义以本表为准：

1. **页面主体功能优先。** 页面主要解决谁的诉求，就归谁。例如 `answer_page` 主体是答题，归 ③，即使它会写练习记录、会写错题。
2. **写权归写方。** 数据的写接口归产生数据的模块；读接口可被任意模块调用，但调用方不得直接写对方表。
3. **共享页面单一主人。** 三端 `home`、`login` 由 ① 域独占；其他模块只能通过事件与共享 store 影响首页展示，不改首页文件。
4. **后端域按路由前缀归属。** 同一 `api/v1` 文件被两个模块用到时，按「端点前缀 + 业务语义」拆分归属，另一模块以「只读消费方」身份登记在域卡。
5. **枢纽模块不反向拥有业务。** ⑫ 只拥有 `achievements`、`goals`、`tasks` 三个端点与成就页，不拥有任何业务页面。

### 2.3 模块边界说明（逐模块）

**① 认证 + 个人中心**
拥有登录、注册、找回密码、设备管理（`auth/devices` 3 个端点）、个人资料、帮助、反馈、通知，以及三端首页与「我的」。它是唯一可以修改 `login` 与三端 `home` 的模块。`auth/devices` 的 3 个端点同时承担「三设备登录态管理」职责，是纵向通信中设备维度的身份基础。

**② 题库浏览**
拥有题库列表、筛选、题目详情与题目元数据接口（`/api/questions` 29 个端点，挂载为两个实例）。只负责「看题」，不负责「答题落库」。答题页跳转由 ③ 承接。

**③ 答题练习**
拥有单题作答、练习模式、快刷模式（`practice` 8 + `quick-practice` 5）。它是全系统最大的事件生产方：一次提交会同时触发 E1（成就）、E11（练习记录落库）、E12（错题入库）。这三个动作必须在后端同一事务边界内完成判分与落库，事件在事务提交后发布。

**④ 练习记录**
拥有练习记录列表、详情、统计口径中的「记录侧」数据（`/api/exam-records` 8）。记录由 ③ 写入，④ 只读展示并提供筛选、导出、删除（删除为软删，保留审计）。④ 不参与判分。

**⑤ 智能组卷 + 历年试卷**
拥有智能组卷参数、组卷结果、智能答题页、历年试卷列表与作答入口（`smart-exam` 10 + `papers`）。试卷的「发布」动作跨角色：教师建卷、管理员审批、学生可见，详见第四章。

**⑥ 错题集**
拥有错题列表、错题重练、错题掌握度（`/api/wrong-questions` 12）。错题由 ③ 在判分事务内写入；⑥ 负责复习与「消灭错题」状态流转，状态变更后发布 E4。

**⑦ 笔记 + 收藏**
拥有笔记增删改查（8 个端点）与收藏（6 个端点）。两功能同属「个人知识资产」，合并为一个模块以减少跨模块写入。笔记创建发布 E5；收藏新增同样发布 E5（`trigger_type` 区分）。

**⑧ 成绩分析**
拥有 `/api/stats` 11 个端点：得分趋势、知识点掌握度、薄弱点识别。⑧ 是纵向通信中「学生 → 教师」的数据供给方，也是横向 E13（薄弱知识点 → 历年试卷推荐）的发起方。

**⑨ 论坛社区**
拥有论坛三个页面（列表、详情、发帖/回帖）与 `forum` 12 个端点，以及 `quotes` 7 个端点（金句/语录展示）。发帖、回帖发布 E6。

**⑩ 资讯中心**
拥有每日资讯、考试日历、招考信息（`news` 8 + `calendar` 2 + `recruitment` 3）。阅读行为发布 E7。资讯发布权在管理员，见第四章。

**⑪ 备考资料**
拥有资料列表、资料详情、视频学习（`materials` 20 + `video` 8）。资料上传权在管理员；学生学习行为发布 E8。

**⑫ 成就成长（枢纽）**
拥有成就墙、成长目标（13 个端点）、成长任务（3 个端点）。它是横向星型拓扑的中心：接收 10 条入边事件，自身不向任何业务模块发起代码调用。成就解锁后发布前端事件 `growth:achievement-unlocked`，由 ①（通知）、⑬（金币奖励展示）等按需订阅。

**⑬ 金币商城**
拥有商品列表、兑换、金币流水（`shop` 3 + `coins` 2）。兑换成功发布 E9。金币余额变化发布前端事件 `reward:coins-changed`，供 ①「我的」页面与 ⑭ 签到结果展示刷新。

**⑭ 每日签到**
现状：**系统当前不存在签到功能**（已用全局检索确认，无签到表、无签到端点、无签到页面）。设计上**不新建表**，复用 `badge_task` 表原生能力：

- `t_type` 支持 `daily` / `weekly` / `season`；
- `mode` 支持 `calc`（按计算规则判定）/ `event`（按事件判定）；
- `reward_coins` 与 `reward_growth` 两个奖励字段。

签到实现为 growth 域内一个 `t_type=daily` 的任务 + 一个新增端点（如 `POST /api/v1/growth/checkin`，路径新增而非修改，符合 R11），签到成功发布 E10。连续签到天数由任务完成记录推导，不额外建表、不加字段。

**关于端点计数口径的说明：** 表中数字为归属到该模块的端点数，`/api/questions` 的 29 个端点为两实例合计；同一端点若被两个模块使用，只在「拥有方」计数一次，消费方在域卡「后端端点清单」中以只读方式登记。因此 14 个模块的端点数为归属口径，不追求与 343 总数逐项相加完全相等（存在跨模块共享的认证、通知等通用端点，归 ① 统一持有）。

## 三、横向星型数据流（10 + 3 条边）

### 3.1 拓扑定义

以用户确认的 drawio 图为准：**成就成长（⑫）是中心枢纽**，有 10 条入边；另有 3 条不经过成就模块的业务边。星型拓扑的含义是「所有行为汇聚到成就」，而不是「所有模块依赖成就」。方向严格单向：业务模块 → 成就模块。

```
       ③答题 ──E1──┐
       ④记录 ──E2──┤
       ⑤组卷 ──E3──┤
       ⑥错题 ──E4──┤
       ⑦笔记 ──E5──┼──► ⑫ 成就成长（枢纽）
       ⑨论坛 ──E6──┤
       ⑩资讯 ──E7──┤
       ⑪资料 ──E8──┤
       ⑬商城 ──E9──┤
       ⑭签到 ──E10─┘

       ③ ──E11──► ④    （练习记录落库）
       ③ ──E12──► ⑥    （错题自动入库）
       ⑧ ──E13──► ⑤    （薄弱知识点推荐历年试卷）
```

### 3.2 统一事件入口

10 条入边全部复用后端既有事件机制 `record_user_action()`，**不新增事件框架**。该入口内部发布的事件常量为 `user.action.v1`（即 `events.py` 中的 `EV_USER_ACTION = "user.action.v1"`，P5 已实现），由 `event_consumer.py` 长驻消费。该事件的 payload 约定为：

| 字段 | 含义 | 约束 |
|---|---|---|
| `user_id` | 行为主体 | 必填，来自当前登录态 |
| `trigger_type` | 行为类型，点分命名 | 必填，取值见 3.3 表 |
| `session` | 会话/上下文信息（如练习会话 id、帖子 id） | 可选，JSON 结构，**只增不改**（add-only） |

「add-only」是硬约定：新增行为类型只允许向 `trigger_type` 枚举追加值，不允许修改既有值的语义、不允许删除。这样成就模块的判据可以长期稳定引用历史事件。

现状：`record_user_action()` 在 wrong_questions / forum / quotes / auth / collection / notes 中已有 **19 处调用点**。本方案不重写这些调用，只做两件事：

1. 补齐 ③④⑤⑩⑪⑬⑭ 缺失的调用点；
2. 把 `trigger_type` 命名统一到 3.3 表（既有调用点若命名不一致，做一次幂等映射，不改历史数据语义）。

### 3.3 十条入边明细

| 事件 | 来源模块 | trigger_type | 成就判据示例 | 判据落点 |
|---|---|---|---|---|
| E1 | ③ 答题练习 | `practice.submit` | 累计答题 N 题 | `badge_task`（`mode=calc`，按提交次数/题数累计） |
| E2 | ④ 练习记录 | `practice.record.created` | 单日练习时长 ≥ N 分钟 | `badge_task`（`mode=calc`，按当日记录聚合） |
| E3 | ⑤ 组卷 / 历年试卷 | `paper.completed` | 完成整卷 N 套 | `badge_task`（`mode=event`，按完成事件计数） |
| E4 | ⑥ 错题集 | `wrong.reviewed` | 消灭错题 N 道 | `badge_task`（`mode=event`，按掌握状态流转计数） |
| E5 | ⑦ 笔记 + 收藏 | `note.created` / `favorite.added` | 笔记 N 条 / 收藏 N 条 | `badge_task`（两个 trigger_type 分别判定） |
| E6 | ⑨ 论坛社区 | `forum.posted` | 发帖 N 条 | `badge_task`（`mode=event`） |
| E7 | ⑩ 资讯中心 | `news.read` | 阅读 N 篇 | `badge_task`（`mode=event`，同一篇去重） |
| E8 | ⑪ 备考资料 | `material.opened` | 学习 N 份 | `badge_task`（`mode=event`，按资料 id 去重） |
| E9 | ⑬ 金币商城 | `shop.purchased` | 消费 N 金币 | `badge_task`（`mode=calc`，累加消费额） |
| E10 | ⑭ 每日签到 | `checkin.done` | 连续签到 N 天 | `badge_task`（`t_type=daily`，连续天数推导） |

判据实现原则：

- **判据只在成就模块内。** 业务模块只负责「我发生了什么事」，不负责「这算不算成就」。业务模块不知道成就的存在。
- **判据幂等。** 同一 `trigger_type` + 同一 `session` 重复上报只计一次；去重键由成就模块维护。
- **判据可回放。** 成就模块可基于历史行为数据重算，因此事件丢失不会导致成就永久错误，只会延迟。
- **奖励发放单点。** 金币与成长值发放只在成就模块内执行，业务模块不直接加币（商城消费是扣币，属于 ⑬ 自身的账务，不属于奖励发放）。

### 3.4 三条非成就边

| 边 | 方向 | 语义 | 实现要点 |
|---|---|---|---|
| E11 | ③ → ④ | 练习记录落库 | 答题提交时后端直接写 `exam_records` 相关表；④ 只读。写入与判分同事务，失败一起回滚 |
| E12 | ③ → ⑥ | 错题自动入库 | 判分发现错题时，在**同一事务内**写 `wrong_question` 表；事务提交后再发布事件；⑥ 打开页面时主动拉取兜底 |
| E13 | ⑧ → ⑤ | 薄弱知识点推荐历年试卷 | ⑧ 输出薄弱知识点集合，⑤ 以此作为 `papers` 查询的筛选条件；这是一次读调用，不是写依赖 |

E13 的方向容易被误解为「⑧ 依赖 ⑤」。实际实现是：⑧ 暴露薄弱点查询能力（自身域内的 `/api/stats` 端点），⑤ 在渲染推荐位时**调用 ⑧ 的读接口**或读取共享 store 中的薄弱点快照。依赖方向是 ⑤ 读 ⑧，不是 ⑧ 写 ⑤。域卡中须明确记录这一点，避免两个模块互相 import。

### 3.5 前端事件总线

前端使用 `mitt`，统一收敛在 `src/stores/event-bus.ts`。首批常量：

| 常量 | 触发方 | 语义 | 典型订阅方 |
|---|---|---|---|
| `wrong-questions:changed` | ③ 答题提交成功后 | 错题集合发生变化 | ⑥ 错题页、⑫ 成就页 |
| `reward:coins-changed` | ⑬ 兑换成功、⑫ 发放奖励后 | 金币余额变化 | ① 「我的」、⑬ 商城页、⑭ 签到结果 |
| `growth:achievement-unlocked` | ⑫ 成就解锁后 | 有新成就解锁 | ① 通知、⑫ 成就墙 |

事件命名规范：`<域>:<过去式动作>`，全小写，用连字符分隔，冒号仅分隔域与动作。新增常量必须在此文件登记，禁止在组件内临时 `emit('xxx')` 字符串。

**铁律：事件是加速器，不是正确性来源。** 任何页面在 `onMounted` 时必须执行一次 API 拉取；事件只用于「已经打开着的页面」做增量刷新。这样即使事件丢失、WS 断线、页面在后台被冻结，用户重新进入页面看到的仍然是后端的最新状态。

### 3.6 成就模块的零依赖约束

⑫ 成就成长的代码中**不得出现**对 ②..⑪、⑬、⑭ 任一模块的 import。允许的依赖只有：

- 共享层：`src/services/api/`（HTTP 客户端）、`src/stores/auth.ts`（当前用户）、`src/stores/event-bus.ts`（常量）；
- 自身域：`src/modules/growth/` 下的 store / api / events。

验证方式：在 CI 或本地执行依赖检查，扫描 `src/modules/growth/**` 的 import 语句，若出现 `@/modules/<其他域>` 即判定失败。这条检查纳入合并门禁。

### 3.7 示例：E12 错题自动入库的完整时序

以「学生在手机端提交一道答错的题」为例，逐段说明：

1. **答题提交。** 学生在 `answer_page` 选择选项并点击提交，前端调用 ③ 的作答提交接口，请求体携带题目 id、作答、练习会话 id。
2. **后端判分落库。** ③ 的后端在事务内读取题目标准答案，判定对错，写入作答明细，更新练习会话进度。此时事务尚未提交。
3. **错题写表（事务内）。** 判定为错时，在同一事务内写入 `wrong_question` 表：题目 id、用户 id、首次答错时间、错误次数。若该题已在错题集中，则错误次数 +1，不重复插入。
4. **提交事务。** 事务提交，判分结果与错题记录同时生效。任何一步失败则整体回滚，不会出现「判了分但错题没进库」。
5. **发布事件。** 事务提交后，调用 `record_user_action(user_id, 'practice.submit', {session})`，成就模块据此累计答题数（E1）。同时后端返回给前端本次作答结果与「是否新增错题」标记。
6. **前端广播。** 前端收到成功响应后，向 `event-bus` 发出 `wrong-questions:changed`。若错题页当前处于打开状态（例如平板分屏），其订阅回调触发一次增量拉取。
7. **页面兜底。** 学生稍后打开错题集页面，`onMounted` 主动调用 `/api/v1/wrong-questions` 拉取。即使第 6 步的事件因为页面已销毁而丢失，第 7 步仍然能拿到完整、正确的错题列表。

这个时序体现了三条设计原则：写入同事务（一致性）、事件后置（不阻塞主流程）、拉取兜底（最终正确）。

## 四、纵向通信（三角色 + 三设备）

### 4.1 角色边

角色之间的通信本质是**数据与审批流的可见性变化**，不是点对点消息。三条角色边如下：

| 边 | 方向 | 内容 | 状态机 / 触发 |
|---|---|---|---|
| V1 | 教师 → 管理员 | 题目、试卷提交审批 | `draft` → `pending` → `published`（驳回回 `draft` 并记录原因） |
| V2 | 学生 → 教师 | 错题纠错反馈、答题数据（供成绩分析） | 学生提交纠错 → 教师可见待处理列表；答题数据按班级/试卷维度聚合后供教师查看 |
| V3 | 管理员 → 学生 | 反馈处理结果、备考资料上传、公告发布 | 管理员动作完成后，对应内容进入学生可见集合，并通过 WS 推送变更 |

V1 的实现要点：审批状态字段是唯一权威，教师端只能把 `draft` 推进到 `pending`，管理员端只能把 `pending` 推进到 `published` 或退回 `draft`。学生端只能看到 `published`。任何越权状态跳转必须由后端拒绝，不能只靠前端隐藏按钮。

V2 的实现要点：学生提交的纠错反馈进入教师待处理队列；答题数据不逐条推送，教师端按需查询聚合结果（避免把学生端的写压力放大到教师端）。

V3 的实现要点：管理员的发布动作是「内容可见性开关」，不是「给学生发消息」。学生端通过拉取 + WS 通知感知变化。

### 4.2 三设备实时通道

复用既有 WebSocket 能力，**不新建服务**。`backend/app/api/v1/websocket.py` 现有 4 个端点：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/ws/online_users` | 查询在线用户 |
| GET | `/ws/room/{room_name}` | 房间式连接（论坛房间等） |
| POST | `/ws/notify/{user_id}` | 向指定用户推送 |
| POST | `/ws/broadcast` | 广播 |

三设备同步使用 `POST /ws/notify/{user_id}`：同一个 `user_id` 在 PC、平板、手机各保持一条连接，服务端向该用户推送时，三端同时收到 `data-changed` 消息。消息体只携带「哪个域、什么类型变了、关联 id」，不携带完整业务数据；各端收到后调用自己的 API 拉取。

无 WS 时的降级路径：

1. 页面 `onMounted` 主动拉取（所有页面强制）；
2. 页面重新获得焦点（`visibilitychange` / 路由激活）时再拉一次；
3. 下拉刷新（移动端）/ 手动刷新（PC）。

这三条路径保证「WS 不可用」只会让实时性下降，不会让数据错误。

### 4.3 一致性的铁律

**任何跨设备、跨角色的状态必须持久化到后端；后端是唯一事实来源。** `localStorage` 只允许保存 UI 偏好（主题、字号、列表密度、上次选中的筛选标签），禁止保存业务状态（金币余额、错题列表、成就进度、签到状态）。原因很直接：业务状态一旦进入本地存储，就会出现「手机上签到成功、PC 上还能再签」的双写漏洞。

### 4.4 示例：试卷发布链路

以「教师 PC 建卷 → 管理员审批 → 学生三端可见」为例：

1. **教师建卷。** 教师在 PC 端 `smart_exam` 页面组卷，保存为 `draft`。此时学生端任何设备都查不到这份试卷（后端查询强制过滤 `published`）。
2. **提交审批。** 教师点击提交，状态变为 `pending`，进入管理员待审列表。教师端不再可编辑（或编辑需先撤回为 `draft`）。
3. **管理员审批。** 管理员在管理端审核题目与答案，点击通过，状态变为 `published`，记录审批人与时间。
4. **事件发布。** 后端在状态变更事务提交后发布事件（复用 `events.py` 的发布能力，由 `event_consumer.py` 消费）。
5. **WS 推送。** 消费者向「该试卷目标学生群体」的每个 `user_id` 调用 `POST /ws/notify/{user_id}`，消息体为 `data-changed`，域为 `exam`，类型为 `paper.published`，附带试卷 id。
6. **三端接收。** 学生 PC、平板、手机若在线，三端同时收到通知；若某端正在试卷列表页，则触发一次列表拉取；若不在该页，只更新未读数/红点，等用户进入时再拉。
7. **离线兜底。** 学生手机当时离线，稍后打开 App，进入历年试卷页，`onMounted` 拉取 `/api/v1/...` 试卷列表，看到的是同一份已发布试卷。三端最终展示完全一致。

这个链路的三个关键决策：状态先落库再推送（不推未提交的状态）、推送只推「变了」不推「全量」（避免大 payload 与版本错乱）、每端以拉取为准（避免推送乱序导致的状态倒退）。

### 4.5 不新增后端服务的论证

| 需求 | 既有能力 | 结论 |
|---|---|---|
| 事件发布/消费 | `events.py` + `event_consumer.py` | 直接复用，不新建消息队列 |
| 契约冻结 | `api_surface.json`（343 端点） | 新增端点走契约增量登记，不改既有路径 |
| 实时推送 | `websocket.py` 4 个端点 | 直接复用，不新建推送服务 |
| 用户行为记录 | `record_user_action()`，19 处调用点 | 直接复用，只补调用点与统一命名 |
| 定时任务（签到日切） | `badge_task` 的 `t_type=daily` | 复用任务表，不新建调度器 |

因此本方案的后端改动只有三类：补齐 `record_user_action()` 调用点、新增签到端点、在既有端点上增加「变更后推送」的调用。**没有新服务、没有新表、没有路径变更。**

说明：

- **`.vtj/` 原地不动。** 页面文件不迁入 `src/modules/`。模块外壳只承载逻辑（store / api / events / 文档），页面通过 `import` 使用外壳。
- **`src/views/` 不新增学生端页面。** 学生端页面全部在 `.vtj/vue/`，`src/views/` 保持现状。
- **`src/services/api/` 是「激活」而非「新建」。** 目录已存在，当前未统一使用；本方案要求 14 个模块全部改用同一 axios 实例，禁止各自 `axios.create`。
- **`src/modules/<域>/` 命名使用英文短名**，与后端域、分支名一一对应，便于脚本校验。

### 5.2 模块外壳四件套

每个模块必须且只能包含以下四类文件（可按需增加 `components/`、`__tests__/`）：

| 文件 | 职责 | 允许依赖 |
|---|---|---|
| `store.ts` | 域内状态、派生状态、加载动作 | 自身 `api.ts`、全局 `stores/auth.ts`、`event-bus.ts` |
| `api.ts` | 本域端点的类型化封装 | `services/api/client.ts` |
| `events.ts` | 本域发布的事件名、订阅的事件名、payload 类型 | `event-bus.ts` 常量 |
| `README.md` | 域卡：页面清单、端点清单、状态契约、事件进出、测试位置、三端验收清单 | 无（文档） |

硬约束：

- 域与域之间**禁止互相 import 外壳**。`src/modules/practice/` 不得 `import` `src/modules/wrongbook/`。
- 跨域只允许两种方式：**读共享 store**（`stores/auth.ts`、`stores/user-profile.ts`）与**经事件总线通知**。
- 若确需跨域读数据，提升为全局 store 并在 `event-bus.ts` 登记事件，不得私下建立模块间依赖。

### 5.3 状态三层模型

| 层 | 位置 | 存放内容 | 生命周期 | 示例 |
|---|---|---|---|---|
| 全局契约层 | `src/stores/` | 所有模块都需要的、稳定的、只读为主的状态 | 应用级 | 当前用户、角色、设备类型、金币余额快照 |
| 域状态层 | `src/modules/<域>/store.ts` | 单模块业务状态 | 模块级（可缓存，可丢弃） | 错题列表、筛选条件、分页游标 |
| 组件局部层 | 页面 `<script>` 内的 `ref` / `reactive` | 纯 UI 状态 | 组件级 | 弹窗开关、输入框草稿、当前选中 tab |

### 5.4 状态归属判定规则

1. **单域使用 → 域状态。** 只有本模块页面读写的状态，一律放域 store，不上提。
2. **≥ 2 个域读 → 提升为全局，并登记事件。** 例如金币余额被 ①「我的」、⑬ 商城、⑭ 签到同时读取，提升到全局 store，并在 `event-bus.ts` 登记 `reward:coins-changed`。
3. **跨域写 → 禁止。** A 域不得直接修改 B 域的 store 或直接调用 B 域的写接口。正确做法：A 调自己的写接口，后端落库后通知，B 收到事件或下次拉取时自行更新。
4. **能从后端推导的状态不落前端。** 例如「今日是否已签到」不在前端存布尔值，每次进入页面向后端查询。

第 3 条是最容易被违反的一条，也是最容易造成「两个模块互相改状态、出现幽灵数据」的根源。域卡评审时必查。

### 6.2 设计器单实例

设计器统一在 `D:\砺安题库\砺安题库\vtj-mcp-server` 启动，访问地址 `http://localhost:9527/__vtj__/`。约定：

- 需要并行编辑时，各自在本地启动设计器，但只打开**自己域内的页面**；
- 设计器启动前先 `git pull`，关闭前确认已保存并提交。

### 6.3 页面隔离与零冲突

VTJ 的页面以 page id 为键，不同页面写不同的 `.vtj/files/<id>.json` 与 `.vtj/vue/<id>.vue`。因此：

- 甲负责 ⑥ 错题集，只打开错题相关页面；乙负责 ⑨ 论坛，只打开论坛页面。两人的改动落在不同文件，合并天然无冲突。
- **共享页面**（三端 `home`、`login`、「我的」）由 ① 域独占。其他模块不得直接改这些页面；需要首页展示自己模块的内容时，通过共享 store 提供数据，由 ① 域统一渲染。

### 6.4 双人改同一页面的冲突处置

极端情况下两人改了同一页面（例如联调期）：

1. 以 `.vtj/files/<id>.json` 中的 `__VERSION__` 较大者为准；
2. 版本号相同则视为冲突，必须人工比对 `nodes` 差异，由该页面所有者裁决；
3. 裁决后重新在设计器保存一次，使 `.vue` 与 DSL 版本号一致；
4. 禁止用「保留双方」的方式手工拼接 JSON，会造成节点树损坏。

### 6.5 AI 编辑脚本的约束

- AI 只允许改 `<script>`，禁止改 `<template>`（R3）。
- 改前必须 `dryRun: true` 预览，确认后再落盘。
- `raw: true` 的页面禁止调用 `vtj_sync_vue_to_dsl`（同步器提取不到手写方法，会丢代码）。
- 改完必须跑 `vtj_check_consistency`，确认 `.vue` 与 DSL 的版本号、方法签名、状态字段一致。

## 七、分支协作规范与《分支使用说明书》

### 7.1 分支模型

| 分支 | 用途 | 保护 |
|---|---|---|
| `main`（或团队约定的基线分支） | 可发布基线 | 保护分支，禁止直推，只接受 PR 合并 |
| `feat/<域>/<任务>` | 个人开发分支 | 一人一条，生命周期为单个任务 |
| `fix/<域>/<问题>` | 缺陷修复 | 同上 |

命名示例：`feat/wrongbook/review-flow`、`feat/growth/checkin-task`、`fix/community/quote-pagination`。

规则：

- 一人同时只保留一条活跃功能分支，避免自己和自己冲突；
- 分支从最新基线切出，切出后尽快合并，生命周期建议不超过 5 个工作日；
- 合并前必须 rebase 或 merge 基线，禁止把落后很多的分支直接提 PR。

### 7.2 合并门禁

| 门禁 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 全量门禁 | `backend/scripts/gate_all.py` | 8 项中至少 7 项通过（L2 存在已知的 harness 正则误报，见 8.3） |
| 前端构建 | `vite build` | 构建成功，无新增告警 |
| 设计器一致性 | `vtj_check_consistency` | 本域页面全部一致；共享页面由 ① 域确认 |
| 域依赖检查 | 扫描 `src/modules/<域>/**` 的 import | 不出现其他域的 `@/modules/<域>` |
| 单测 | 本域 Vitest + 相关 pytest | 全部通过；不引入新的失败用例 |

门禁未过不得合并。允许「先合并基础设施、后补业务」的两段式提交，但基础设施 PR 也必须过门禁。

### 7.3 《分支使用说明书》章节结构

说明书是 Phase 1 的交付物，7 章，面向新加入的开发者：

| 章 | 标题 | 内容要点 |
|---|---|---|
| 1 | 环境准备 | Node / Python 版本，`npm install`，`vtj-mcp-server` 启动，`http://localhost:9527/__vtj__/` 访问，后端 `uvicorn` 启动，SQLite 文件位置，常见环境错误 |
| 2 | 拉取与分支 | 克隆、切基线、拉最新、建 `feat/<域>/<任务>`、提交信息规范、推送、开 PR |
| 3 | 所有权映射表 | 14 模块 × 页面 × 端点的完整映射，以及「我该改哪些文件」的查表方法 |
| 4 | 域卡模板 | 域卡的 7 个字段与填写示例（见 7.4） |
| 5 | 跨域通信规则 | 禁止互相 import；共享 store 读；事件总线通知；`record_user_action()` 的使用方式 |
| 6 | 合并验收 | 门禁命令、检查清单、PR 描述模板、评审人职责 |
| 7 | 冲突处置 | 代码冲突、`.vtj/files` 冲突、`__VERSION__` 裁决、lock 文件冲突、回滚方式 |

### 7.4 域卡模板（`src/modules/<域>/README.md`）

域卡是模块的「身份证」，7 个字段缺一不可：

| 字段 | 填写要求 | 示例（⑥ 错题集） |
|---|---|---|
| 负责页面清单 | 页面 id + 文件路径 + 设备端 | `wrong_questions`（PC/平板/手机）、`wrong_review`（三端） |
| 后端端点清单 | 方法 + 路径 + 归属（拥有/只读） | `GET /api/v1/wrong-questions`（拥有）、`POST /api/v1/wrong-questions/{id}/review`（拥有） |
| store 状态契约 | 状态字段、类型、是否持久化 | `list: WrongQuestion[]`、`filters: {...}`、`cursor: string`，均不持久化 |
| 发布事件清单 | 前端事件常量 + 后端 `trigger_type` | `wrong-questions:changed`、`wrong.reviewed` |
| 订阅事件清单 | 前端事件常量 + 处理动作 | `wrong-questions:changed` → 增量拉取 |
| 测试文件位置 | 单测与后端测试路径 | `src/modules/wrongbook/__tests__/`、`backend/tests/test_wrong_questions.py` |
| 三端手工验收清单 | PC / 平板 / 手机各 3..5 条可勾选动作 | 见下方示例 |

三端手工验收清单示例（⑥ 错题集）：

- PC：进入错题集，筛选「未掌握」，列表与计数一致；点击重练进入答题页；重练后返回列表，该题状态已更新。
- 平板：横竖屏切换后列表不丢筛选条件；分屏状态下在答题页答错，返回错题集能看到新错题（事件 + 拉取双路径）。
- 手机：下拉刷新可用；弱网（限速）下先显示骨架屏再出数据；退出重进后状态与后端一致。

### 7.5 提交与评审规范

- 提交信息：`<域>: <动词> <对象>`，例如 `wrongbook: add review-state filter`；中文描述可用，但域前缀必须是英文短名。
- 一个 PR 只做一件事；基础设施改动与业务改动分开提。
- PR 描述必须包含：改了哪些页面 id、哪些端点、发布/订阅了哪些事件、门禁结果、三端验收勾选。
- 评审人优先看三处：域边界是否被越过（跨域 import）、写操作是否走后端、事件是否只做加速。

## 八、测试与验收

### 8.1 前端测试

位置：`src/modules/<域>/__tests__/`。

覆盖要求（按模块复杂度分档）：

| 模块类型 | 必测内容 |
|---|---|
| 有状态流转（③④⑤⑥⑫⑬⑭） | store 的加载、错误、空态、状态流转；事件订阅后的增量更新；重复事件的幂等 |
| 以展示为主（②⑩⑪） | 列表分页、筛选参数拼装、空态与错误态渲染 |
| 表单为主（①⑦⑨） | 校验规则、提交成功/失败、重复提交防护 |
| 枢纽（⑫） | 事件消费的判据计算、去重、奖励发放幂等、历史回放 |

测试原则：测 store 与 api 封装，不测 VTJ 生成的模板结构（模板由设计器负责，测试模板结构会因设计器重排而脆弱）。

### 8.2 后端测试

按域组织 pytest，沿用既有目录风格。基线（实测）：

| 指标 | 基线值 |
|---|---|
| 通过 | 278 |
| 失败 | 17（均为既有失败，与模块化无关） |
| xfailed | 3 |

要求：

- 新模块的测试**必须全绿**；
- 不得把既有 17 个失败「顺手修掉」混入模块 PR（避免扩大评审面）；如需修复，单独开 PR；
- 不得新增失败用例；若确实因环境导致，须在 PR 中说明并附复现命令。

后端测试重点：

- ③ 的判分 + 记录 + 错题写入是否同事务（构造中途异常，验证回滚）；
- ⑫ 的判据计算与奖励发放是否幂等（同一事件重复投递）；
- ⑭ 的签到是否「一天一次」（并发两次请求只成功一次）；
- 权限：学生不能看到 `draft` / `pending` 试卷；非管理员不能审批。

### 8.3 门禁基线

`backend/scripts/gate_all.py` 编排 8 个脚本（L0 / L1-G / L1 / L1-H / L2 / L3 / L4 / L5）。当前基线为 **7/8 通过**，L2 存在已知的 harness 正则误报（非真实缺陷）。

处理方式：

- L2 的误报在门禁报告中显式标注，不作为阻塞项；
- 其余 7 项必须通过；
- 若某次改动导致第 8 项从「已知误报」变成「真实失败」，必须定位原因，不得笼统归因于 L2。

### 8.4 三端手工验收

每个域卡自带三端清单（见 7.4 示例）。验收在真实设备或浏览器设备模拟下完成，重点验证：

1. **一致性**：同一账号在三端看到的数据一致（金币、签到、错题数、成就进度）。
2. **实时性**：一端产生变更，另一端在线时秒级刷新；离线端重新进入时数据正确。
3. **降级**：断开 WS 后，页面仍能通过拉取拿到正确数据。
4. **设备适配**：`meta.platform` 分支正确，平板不出现手机布局、手机不出现 PC 表格溢出。

### 8.5 验收责任

| 角色 | 责任 |
|---|---|
| 模块负责人 | 自测：单测 + 本域三端清单 + 门禁 |
| 评审人 | 边界检查（跨域 import、跨域写、事件滥用）+ 抽查三端 |
| 集成负责人 | 合并后跑一次全量门禁 + 跨模块链路（E11/E12/E13、试卷发布链路） |

## 九、实施节奏

### 9.1 三阶段

| 阶段 | 名称 | 交付物 | 退出标准 |
|---|---|---|---|
| Phase 1 | 基础设施 | `stores/auth.ts`、`stores/user-profile.ts`、`stores/event-bus.ts` 三件套；`services/api/` 统一客户端；14 个模块外壳（store/api/events/README 四件套，允许方法体为空实现但签名完整）；《分支使用说明书》v1；域依赖检查脚本 | 14 个外壳可编译；依赖检查脚本可运行；说明书 7 章齐备；门禁 7/8 |
| Phase 2 | 逐域实现 | 按模块顺序把页面逻辑迁入外壳、补齐 `record_user_action()` 调用点、实现域内 store 与 api；**优先完成 10 个成就发布点** | 10 条入边事件全部可观测（来源模块调用 → 成就模块收到）；3 条非成就边有测试覆盖 |

### 9.2 Phase 2 的模块顺序

先做「事件发布点」，再做「消费与展示」，理由是先打通数据流，后续模块可以边开发边看到成就联动效果。

1. ③ 答题练习（E1 + E11 + E12，是全系统最复杂的写入方，先做可暴露事务与事件问题）
2. ④ 练习记录（E2，验证 ③ 的写入）
3. ⑥ 错题集（E4，验证 E12 的落库与拉取）
4. ⑤ 智能组卷 + 历年试卷（E3 + 试卷发布链路）
5. ⑦ 笔记 + 收藏（E5）
6. ⑨ 论坛社区（E6）
7. ⑩ 资讯中心（E7）
8. ⑪ 备考资料（E8）
9. ⑬ 金币商城（E9 + `reward:coins-changed`）
10. ⑭ 每日签到（E10，依赖 `badge_task` 与 ⑬ 的金币展示）
11. ⑫ 成就成长（消费 10 条入边，做判据与奖励）
12. ⑧ 成绩分析（E13 的发起方）
13. ② 题库浏览（读为主，最后收口）
14. ① 认证 + 个人中心（共享页面最多，放在最后避免早期频繁改动共享文件）

### 9.3 三条「零变更」承诺

| 承诺 | 含义 | 验证方式 |
|---|---|---|
| 零 `.vtj/` 迁移 | 不移动、不改名、不删除任何 `.vtj/` 文件与目录 | `git status` 中无 `.vtj/` 的 rename/delete；92 处 import 全部可解析 |
| 零 VTJ 版本变更 | 8 个包版本保持 0.16.35 / 0.12.19 | `package.json` diff 为空 |
| 零后端目录迁移 | `backend/app/api/v1/` 文件不搬家 | `git status` 中无 `backend/app/api/v1/` 的 rename；`api_surface.json` 比对 343 端点一致 |

这三条是本方案能落地的根本原因：模块化靠「所有权 + 外壳 + 事件」实现，不靠「搬文件」。搬文件会同时触发 VTJ 硬绑定、路由 404、端点路径变更三类风险，收益远小于成本。

## 十、风险与应对

| 风险 | 触发条件 | 影响 | 应对 |
|---|---|---|---|
| 跨域 import 悄悄出现 | 开发者图省事直接 import 别的域 store | 模块边界腐化，最终回到单体前端 | 依赖检查脚本纳入门禁；评审重点看 import |
| 事件被当作正确性来源 | 页面不拉取，只等事件 | 事件丢失时页面长期空白或陈旧 | 强制 `onMounted` 拉取；评审检查每个页面的初始加载 |
| 两人改同一 VTJ 页面 | 共享页面被非 ① 域修改 | DSL 冲突、节点树损坏 | 共享页面单一主人；`__VERSION__` 裁决；禁止手工拼 JSON |
| 端点被「顺手改路径」 | 新增能力时改既有路径 | 343 端点契约破裂，前端 404 | 契约比对纳入门禁；只允许新增端点 |
| 签到做成新表 | 未查证现状就建表 | 多一套表与迁移，违背零新表承诺 | 明确复用 `badge_task` 的 `t_type=daily`；实现前先读表结构 |
| 事务边界不清 | 判分成功但错题未写 | 数据不一致，用户投诉 | E11/E12 与判分同事务；构造异常测试回滚 |
| WS 推送乱序 | 多端同时收到旧状态 | 界面状态倒退 | 推送只带「变了」；各端拉取为准 |
| 版本被动升级 | 安装依赖时 lock 漂移 | 设计器行为变化，页面渲染异常 | 版本锁定 + 门禁检查 lock；升级单独提案 |
| 门禁 L2 误报被忽视 | 习惯性认为 L2 永远误报 | 真实缺陷被放过 | 每次确认失败原因；从「已知误报」变为「真实失败」必须定位 |
