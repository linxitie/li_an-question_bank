# 文件上传提速 方案 v1（待批准）

> 日期：2026-11-12　｜　分支：`feat/material-multi-format-import`（**不动 main**）
> 你的问题：「现在文件上传速度有点慢，不是扫描件的 PDF 也要约 10 秒/个，能否尽量加快所有类型文件上传」
> 本文是**方案**，按全局规则：**未获批不动代码**。所有数字都是本机实测（2026-11-12/13）。

---

## 0. 一句话结论

**慢的只有 PDF，而且是"同一份文件被解析了两遍"造成的**：
`detect_scanned` 用 **pdfplumber** 把全文抽一遍（3.1s/17 页）→ 再让 `parse_pdf_text` 用 **pymupdf** 抽一遍（0.9s/17 页）。
**改成"一遍 pymupdf 同时完成判定 + 抽取"，这份文件 4.1s → 约 0.9s（−78%）**；页数越多差距越大（90 页约 16s → 4.6s）。
docx 本来就快（实测 **0.39s**），xlsx 更快；扫描件的额外等待主要是 **OCR 进程每次启动要加载模型 ≈20–25s**，改成常驻 worker 可把这 20 多秒摊掉。

---

## 1. 实测（本机，2026-11-12/13）

### 1.1 API 端到端（`POST /api/materials/admin/import/upload`，每份跑 2 次取中位）

| 文件 | 大小 | 端到端耗时 |
|---|---|---|
| 文字版 PDF（17 页） | 0.44 MB | **4,132 ms** |
| docx（297 段） | 0.69 MB | **391 ms** |
| docx（大） | 1.40 MB | **340 ms** |

> 结论：**docx/xlsx 不慢**（几百毫秒）。你感觉"每个都要 10 秒"，基本都发生在 PDF 上（尤其是几十页的真题/解析 PDF）。

### 1.2 PDF 内部拆解（`_run/profile_upload.py`）

| 步骤 | 实现 | 17 页实测 | 说明 |
|---|---|---|---|
| `detect_scanned` | **pdfplumber** 逐页 `extract_text` | **3,102 ms** | 只为算"平均每页字符数 < 100"这一个布尔值 |
| `parse_pdf_text`（后定义覆盖前定义） | **pymupdf** 逐页取文本 + 字号聚类 | **911 ms** | 真正的解析 |
| 合计 | 两次全量解析 | **≈4.0 s** | 页数线性增长：90 页 ≈ 16 s + 4.8 s |

### 1.3 扫描件的额外等待（P2 实测）

- 24 页扫描件：**272 s 完成（11.3 s/页）**，但**第一条进度出现在第 25 秒** —— 前面 25 秒是 OCR 进程启动 + RapidOCR 模型加载；
- 3 页扫描件：**约 50–90s**（其中 25s 仍是启动开销）→ 小文件被"固定开销"支配。

## 2. 根因清单

| # | 根因 | 证据 | 影响面 |
|---|---|---|---|
| **R1** | **PDF 被解析两遍**（pdfplumber 判定 + pymupdf 抽取） | §1.2 实测 3.1s + 0.9s | 所有文字版 PDF，占其耗时 **75%** |
| **R2** | **pdfplumber 比 pymupdf 慢一个数量级** | 同文件 3.1s vs 0.9s | R1 的放大器 |
| **R3** | **扫描件判定也要全量解析** | `detect_scanned` 读完所有页才给结论 | 扫描件"开始 OCR"前先白等 3–16s |
| **R4** | **每次 OCR 都新起进程、重新加载模型** | 首条进度固定晚 20–25s | 每篇扫描件白等 20–25s；批量 9 篇 ≈ 多等 3–4 分钟 |
| **R5** | 批量上传**逐条串行**（前端 for 循环） | `ArticleBatchUpload.start()` | 批量总时长 = 各篇之和 |

## 3. 优化项（按性价比排序，全部可单独回滚）

### O1 单遍解析：`parse_pdf_once()`（推荐，先做）

- **做法**：新增 `material_parser.parse_pdf_once(path, scan_threshold=100)` —— 用 **pymupdf** 打开一次，逐页取文本（`page.get_text()`），顺路算出"平均每页字符数"：
  - `< 100` → 返回 `{"scanned": True, "pages": N}`（路由到 OCR，不再二次解析）；
  - `>= 100` → 接着用**同一批页文本**走现有字号聚类/HTML 构建，返回 `{scanned: False, html, word_count, chapters}`。
- **改动面**：`material_parser.py`（新增函数，不动旧的两个导出）、`materials.py` 上传分支（把 `detect_scanned` + `parse_pdf_text` 换成一次调用）。
- **预期收益（本机）**：17 页 **4.13s → ≈0.9s（−78%）**；90 页 ≈ **16s → ≈4.6s**；扫描件"进入 OCR"从 3–16s 降到 **0.1–0.3s**。
- **风险**：中低 —— 判定阈值与 HTML 构建规则保持**完全同口径**（阈值 100、同一套聚类），并用真实语料回归；`detect_scanned`／`parse_pdf_text` 原样保留，出问题一行切回。
- **估时**：**0.5 天**（含 6 例单测 + 真机对照）。

### O2 扫描件判定只采样前 3 页（并入 O1）

- **做法**：`parse_pdf_once` 的判定改用前 3 页平均字符数（无文字层的前几页就足以判定；现有 `threshold=100` 不变）。
- **收益**：扫描件判定 3.1s → **≈0.2s**（O1 已覆盖大部分，这一条让超长扫描件也快）。
- **风险**：低 —— 若"前 3 页是封面/图片、后面是文字"，会被判成扫描件 → 仍能 OCR 出文本，只是慢一点（可接受，且可在 `_ocr` 里标 `sampled=true` 便于排查）。
- **估时**：并入 O1。

### O3 OCR 常驻 worker（省掉每篇 20–25s 模型加载）

- **做法**：把 `rapidocr_worker.py` 从"一次一个 PDF、跑完退出"改成**常驻进程 + 简单行协议**（`OCR <path>` → 逐页回事件），主进程用一个轻量池（1 个实例，串行复用）；模型只加载一次，页面仍逐页释放。
- **收益**：每篇扫描件固定开销 **25s → ~1s**；3 页小文件 **50–90s → ~25–60s**；批量 9 篇 **≈3–4 分钟**。
- **风险**：中 —— 常驻进程要处理"卡死/崩溃重启/超时回收"（这些 P1 已有超时与杀进程逻辑，可复用）；`OCR_ENGINE=sidecar` 仍保留一次性模式兜底。
- **估时**：**0.8 天**（含看门狗与 4 例测试）。

### O4 批量上传并发 2 路

- **做法**：`ArticleBatchUpload` / `MaterialBatchUpload` 的串行 `for` 改"最多 2 个在飞"（`Promise` 池），每行进度互不干扰。
- **收益**：docx 批量 9 篇 **3.5s → ≈2s**；PDF 批量近似减半（CPU 双核以上）。
- **风险**：中低 —— 并发下"重复文件 409"与"同内容合并"已经按行处理；后端 OCR 仍串行（O3 的池大小=1），不会 CPU 打满。
- **估时**：**0.3 天**。

### O5 上传即返回、解析转后台（最大改造，建议单独立项）

- **做法**：上传只做"落盘 + 建记录"，解析全部转后台（现在 docx/xlsx/文字 PDF 都在请求内同步解析）。
- **收益**：**首字节 < 300ms**（用户点完就返回），进度条接管等待。
- **代价**：要处理"上传成功但解析失败"的状态、前端全链路轮询、重复上传拦截时机变化；估 **2 天**，且会让 `import/upload` 的语义变化（`parse_status` 从 success 变 processing）。
- **建议**：**先不做**，等 O1–O4 落地后再看体感。

## 5. 验收（S-A/S-B/S-C 共同）

- 同一批真实文件（17 页文字 PDF / 40MB 大 PDF / docx / 24 页扫描件）跑 **前/后对照表**，写进交付记录；
- `pytest`：O1 新增 ≥6 例（判定阈值、同口径 HTML、页数边界）、O3 新增 ≥4 例（常驻协议、崩溃重启）；
- `gate_all` 仍 **9/10**（唯一红=既有 L1-G）；`vue-tsc` 0；`vitest` 全绿；
- 解析结果**逐字节兼容**：同一文件在优化前后 `html` 与 `word_count` 一致（用 3 份语料做快照比对）。

## 6. 风险与回滚

| 风险 | 评估 | 处置 |
|---|---|---|
| O1 判定口径漂移 → 文字版被当扫描件 | 中 | 阈值/采样口径与现网一致 + 3 份语料快照对比 + 保留旧函数一行切回 |
| pymupdf 对个别字体取不到字（历史坑） | 中 | 现状 `parse_pdf_text` 本来就是 pymupdf（2026-10-30 修过），O1 只是复用同一实现 |
| O3 常驻进程卡死 | 中 | 复用心跳/页超时 + 空闲回收 + 崩溃自动重启；`OCR_ENGINE=oneshot` 兜底 |
| O4 并发导致进度串行混乱 | 低 | 按行更新、池上限 2；后端 OCR 池仍为 1 |
| 回滚 | — | 每项独立提交、独立开关（`PDF_PARSE_MODE`、`OCR_ENGINE`、`UPLOAD_CONCURRENCY`） |
