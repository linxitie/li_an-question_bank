## 0. 一句话结论

**可以，而且这正是把「我传了两套卷、统计还是 0」这类问题一次性根治的做法。**
做法：试卷只作为**一条资料**存在（`study_material.type='paper'`），上传/管理/审批**只在资料管理页**；状态只留**两态**（未上架 / 已上架），**「上架」这一个动作 = 审批通过**；独立「试卷审批」页与菜单项下线；`exam_paper` 退为「可作答卷」的**投影**（上架→`PUBLISHED`，下架→`DRAFT`），不再对外暴露审批入口。

## 2. 目标模型

### 2.1 一份试卷 = 一条资料

| 维度 | 落点 |
|---|---|
| 主体 | `study_material`（`type='paper'`），主键 `material_id` |
| 原件 | `material_file`（pdf + docx 配对，B 批；docx 为主、pdf 副本） |
| 元数据 | 科目 / 年份 / 地区 / 题本·答案 / 题量 / 满分 / 卷别（D32 文件名解析 + 列表内「改信息」） |
| 编号 | `paper_code` 人读码（D24，如 `GZ-2019-BJ-T`） |
| 可作答卷（可选） | `exam_paper` 通过 `paper_code` 一对一关联 |

### 2.2 两态 + 一个动作

| 状态 | `status` | 含义 | 谁能改 |
|---|---|---|---|
| **未上架** | 0 | **未通过**（含草稿/待处理），学生不可见 | 上传者保存、管理员驳回时回退 |
| **已上架** | 1 | **审批通过**，学生可见、考试可用 | 管理员点「上架」 |
| （删除） | -1 | 软删除，不参与列表与统计 | 管理员删除 |

> ⚠️ **实测偏差（2026-11-07 复核，待裁定）**：本表「管理员删除 → `status=-1`」**与当前代码不符**。
> 实测 `backend/app/api/v1/library/materials.py`：
> - `DELETE /admin/{id}`（L1645 起）→ `db.delete(m)` **物理删除**，并连带删除该资料的 `UserMaterialProgress`；
> - `DELETE /admin/batch`（L1766 起）→ 同样是物理删除；
> - 只有学生端 `DELETE /my/{id}`（L551 起）才是 `m.status = -1` 软删除。
>
> 因此 `admin_stats.by_status.deleted` 的 **5 条**（16/20/25/46/47）**全部来自学生端软删**，管理员删除不会让它增加。
> 处置二选一（需你裁定后我再改代码，不擅自动数据语义）：
> **A** 维持物理删除 → 管理页确认文案写「永久删除，不可恢复」（**已先按此改文案，保证不误导用户**），C 批不做回收站；
> **B** 改为软删除 `status=-1` → 与本表一致，C 批回收站可「恢复/彻底删除」，但需处理学生端可见性与重复占用（同内容再上传会撞唯一性/重复检测）。

- **没有单独的「通过 / 驳回」按钮**：上架 = 通过；下架 = 回到未通过（可不填理由）。
- 教师将来能上传时，只能落 `status=0`，管理员上架才可见 → **审批语义自然成立，不需要第二套流程**。

### 2.3 可作答卷降为投影（关键机制）

- 上架：`study_material.status → 1` 时，若存在关联 `exam_paper`，同步 `paper_type → PUBLISHED`；
- 下架：`status → 0` 时同步 `paper_type → DRAFT`；
- **反向不再驱动**：`paper_type` 变了不改资料状态（唯一真源 = `study_material.status`）；
- 学生考试链路依赖 `paper_type='PUBLISHED'`（`exams.py:46/104/141` 三处过滤）→ 联动必须做对，否则"资料下架了但学生还能考"。

### 2.4 与「拆题」的关系（不变）

拆题仍是 P2：把原卷 PDF/Word 拆成 `question_bank` 题目，挂到关联的 `exam_paper`。
**资料（可看原卷）与题目（可练）通过 `paper_code` 双向可达**——这是 D23/D27 已批准的形态，本方案不动它，只是把"建资料"这一步收敛到一页。
