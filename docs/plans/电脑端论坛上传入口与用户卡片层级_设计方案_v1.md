# 电脑端论坛：上传入口可见性与用户卡片层级 — 设计方案 v1

> 状态：**待批准**，本文只做设计，不含代码改动。
> 日期：2026-10-25
> 分支：`feature/forum-personalization`（HEAD `b758f82`）
> 涉及页面：`.vtj/vue/forum.vue`（PC 论坛，**raw: true**）

---

## 0. 结论先行

1. **上传能力不是缺失，是被埋在弹窗底部**。前端 `FileUploader` 已经在评论输入区（`forum.vue:435`）和发帖区（`forum.vue:180`），后端 `/api/forum/upload` 与 `/api/media/image` 都在，白名单与前端 `accept` 完全对齐。实测评论上传入口位于 `y≈2154`，而弹窗可视高度只有 `765`、内容总高 `2388` —— 要往下滚约 1400px 才看得到。
2. **修法一（推荐）**：把 `.comment-input-area` 从 `position: relative` 改成 `position: sticky; bottom: 0`。**纯 CSS，不碰 template**，符合 R3。改完后「表情 / 图片文件 / 输入框 / 发表评论」常驻弹窗底部。
3. **用户卡片被盖是 z-index 相同 + DOM 顺序决定**。两个 `.modal-overlay` 都是 `z-index: 2000`，用户卡片在 DOM 里更早，于是帖子详情盖住它。实测 `elementFromPoint` 在用户卡片中心命中的是 `.post-detail-card`。
4. **修法二（推荐）**：`.modal-overlay:has(.profile-card) { z-index: 2100 }`。同样纯 CSS，不碰 template。

## 1. 现状证据（本轮实测）

### 1.1 上传能力已具备（前后端对照）

| 环节 | 证据 |
|---|---|
| 评论上传入口存在 | `forum.vue:434-436` → `<div class="comment-image-upload"><FileUploader v-model="state.newCommentImages" :max-docs="3" /></div>` |
| 发帖上传入口存在 | `forum.vue:180` → `<FileUploader v-model="state.newPost.images" :max-docs="10" />` |
| 组件已注册 | `forum.vue:526-527, 544-545` |

| 后端文档白名单 | `forum.py:1052-1055`：`.doc .docx .pdf .xls .xlsx .ppt .pptx .txt .csv .zip .rar .7z` —— **与前端逐项一致** |

**结论：后端字段、路由、接口都完整，不需要后端改动。**

### 1.2 为什么"看不到"

Playwright 实测（1440×900，`http://10.201.3.21:5173/#/forum`，打开帖子详情）：

```
.post-detail-card 可视高度   765   （max-height: 90vh）
.post-detail-card 内容总高   2388
.file-uploader（评论）数量   1
.fu-add 文案                "+ 图片 / 文件"
.fu-add 位置 top            2154  ← 距可视区下沿 1389px
```

即：输入框、表情按钮、上传入口、发表按钮**全部在弹窗内容的最末尾**，用户打开详情后看到的是帖子和评论，不往下滚三段就永远看不到它们。

### 1.3 弹窗层级实测

打开帖子详情 → 点评论头像 → 用户卡片出现：

```
.modal-overlay #0  z=2000  contains .profile-card
.modal-overlay #1  z=2000  contains .post-detail-card
elementFromPoint(用户卡片中心) → .post-detail-card
profileIsOnTop = false
```

两个遮罩 z-index 完全相同（`forum.vue:1546` 唯一一处 `z-index: 2000`），由 DOM 顺序决定谁在上；用户卡片在 `forum.vue:209-247`，帖子详情在 `forum.vue:249`，所以详情压住卡片。

## 2. 目标与非目标

### 2.1 目标

1. 打开帖子详情后，**不用滚动**就能看到并使用：表情、图片/文件上传、输入框、发表按钮。
2. 发帖弹窗内的上传入口同样可见（登录后可验证）。
3. 点评论作者头像弹出的用户卡片**显示在帖子详情之上**，关闭卡片后详情仍在。
4. 不改表结构、不改接口、不改后端。
5. 遵守 R2（raw 页禁止 `vtj_sync_vue_to_dsl`）与 R3（template 不手改）。

### 2.2 非目标

- 不做图片/文档的在线预览（仍为下载）。
- 不改手机端、平板端页面。
- 不调整 PC 论坛的三栏布局。
- 不动上传大小限制与白名单（已对齐）。

## 3. 方案

### 3.1 问题一：评论输入区常驻

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 输入区 sticky（推荐）** | `.comment-input-area` 改 `position: sticky; bottom: 0`，白底 + 顶部阴影 | **选中**：纯 CSS，不动 template，R3 零风险 |
| B. 顶部加「写评论」锚点 | 评论标题右侧加按钮，点击滚到底并聚焦 | 弃：需改 template；且仍要滚到底，只是省一次手动滚动 |
| C. 输入区独立成小弹窗 | 「写评论」打开独立 composer | 弃：需改 template + 新增交互状态，改动面大，收益低于 A |

**为什么 A 可行**：`.comment-input-area`（`forum.vue:415`）的直接滚动祖先是 `.post-detail-card`（`overflow-y: auto`，`forum.vue:1548-1557`），中间没有其它 `overflow` 容器，`sticky bottom: 0` 会贴住弹窗可视底边。这一点在实施时用 Playwright 断言验证（见 §6）。

### 3.2 问题二：用户卡片压过帖子详情

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. `:has()` 提层（推荐）** | `.modal-overlay:has(.profile-card) { z-index: 2100 }` | **选中**：纯 CSS，不动 template；Chrome 105+/Safari 15.4+ 支持 |
| B. 加修饰类 | template 加 `class="modal-overlay profile-overlay"` | 弃（本期）：需改 template，触发 R3 授权流程 |
| C. 调 DOM 顺序 | 把用户卡片节点移到帖子详情之后 | 弃：template 大改 + 影响 `v-if` 与点击穿透逻辑 |

**为什么 A 够用**：本项目 PC/平板/手机均为现代 Chrome/Safari 内核；`@supports` 兜底见 §4.2。若日后发现老内核，再切到方案 B（只需一行 class + 一条 CSS）。

## 4. 详细设计

### 4.1 改动点一：`forum.vue:1971` `.comment-input-area`

```css
.comment-input-area {
  margin-top: 16px;
  padding-top: 12px;
  border-top: 1px solid #f0f2f5;
  position: sticky;        /* 原为 relative */
  bottom: 0;
  background: #ffffff;     /* 遮挡滚动内容 */
  z-index: 5;
  padding-bottom: 4px;
  box-shadow: 0 -8px 16px rgba(26, 54, 93, 0.05);
}
```

配套：`.post-detail-card` 底部内边距 +8px（可选，避免最后一条评论贴着输入区上沿）。

### 4.2 改动点二：`forum.vue` 新增两条 CSS

```css
/* 用户信息卡片必须盖在帖子详情之上（两者默认都是 2000） */
@supports selector(:has(*)) {
  .modal-overlay:has(.profile-card) {
    z-index: 2100;
  }
}
```

用 `@supports` 包住：不支持 `:has()` 的浏览器保持今天的行为（卡片仍被盖），不会出现半吊子状态。

### 4.3 改动点三（待定，需你拍板）

发帖弹窗（`forum.vue:180`）的上传入口本轮**未能验证**——匿名会话点「发布新帖」被 `openNewPost` 的登录校验拦住。登录后若同样需要吸底，做法同 §4.1（把 `.new-post-form` 里的上传区贴底）。**默认不做**，等验收结果。

### 4.4 不做的事

- 不执行 `vtj_sync_vue_to_dsl`（raw 页，R2）。
- 不改 `<template>`（R3）。
- 不改后端任何文件。

## 7. 风险

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | sticky 未生效（祖先链里出现新的 overflow 容器） | 输入区仍埋在底部 | 实施第一步就用 Playwright 断言 §6-1；失败则退回「方案 B 锚点」（需 R3 授权） |
| 2 | `:has()` 在老内核不支持 | 卡片仍被盖 | `@supports` 包裹，行为与今天一致；需要时切方案 B |
| 3 | sticky 遮挡最后一条评论 | 读不到末尾内容 | `.post-detail-card` 底部加内边距，§6-4 断言 |
| 4 | 弹窗内 emoji 面板被挡 | 选表情时看不全 | emoji 面板为 `absolute` 且 `bottom: 100%`，会浮在输入区上方；§6 加一条目视确认 |

## 8. 需要你拍板的三件事

1. **是否接受纯 CSS 方案**（sticky + `:has()`）——好处是完全不碰 template，R3 零风险；代价是 `:has()` 依赖浏览器支持（Chrome 105+）。
2. **发帖弹窗的上传区要不要一起吸底**——默认不做，等你登录看一眼再说。
3. **是否顺带把评论区顶部加一个「写评论」入口**——默认不做（属方案 B，需改 template）。
