## 一、总体愿景

| 现状 | v2 目标 |
| :--- | :--- |
| 模块4：一次性生成静态计划 | **可训练、可推演、可干预的规划智能体**：基于用户画像持续推演、按日动态演化 |

## 二、模块 4 v2：动态规划智能体（PlanAgent）

### 2.1 用户画像系统（注册页改造）

**询问维度**（按用户建议的六维 + 扩展项）：

| 维度 | 字段 | 采集方式 |
| :--- | :--- | :--- |
| 年级 | grade（大一~大四/应届） | 单选 |
| 目标分数 | target_score（总分/行测/申论/公专） | 数字输入 + 滑杆 |
| 当前水平自评 | self_level（零基础/入门/有基础/冲刺） | 单选 + 自评题（3 题小测） |
| 可用每日时长 | daily_hours | 滑杆（1-8h） |
| 学科强弱项 | subject_strengths / subject_weaknesses | 多选 + 可选自述 |
| 备考截止日期 | exam_date | 日期选择 |
| 扩展 | target_region / target_post（岗位意向） | 关联选岗 Agent（v2.1 打通） |

**询问交互设计**（登录页/注册页建议）：
- **引导式**：分步向导（Step 1 基本信息 → Step 2 目标 → Step 3 自评 → Step 4 生成预览），进度条 + 每步可回退
- **多样本输出**：3 套问卷模板（极简卡式 / 沉浸问答式 / 专业诊断式）随机或用户自选，样式轮换
- **交互式**：自评采用微型测验（3 题快测估算当前水平），而非纯主观选择

**数据模型（新增）**：`user_profile`（user_id 1:1，全维度字段 + `profile_status` 完成度 + `updated_at`）
**端点（登记台账）**：`POST /api/profile/upsert`、`GET /api/profile`、`GET /api/profile/questions`（问卷模板）

### 2.2 规划智能体（PlanAgent）推理链路

```
画像数据 ──→ ① 认知推理（多维度评估）
                 ├ 时间资源评估（距离考试天数 × 每日时长 = 可用总学时）
                 ├ 科目差距评估（目标分数 - 自评基线 → 各科缺口权重）
                 └ 学习习惯评估（水平自评 + 快测结果 → 学习节奏建议）
        ──→ ② 方案生成（并行生成 2~3 套差异化方案：均衡型/强化突击型/稳扎稳打型）
        ──→ ③ 方案评分筛选（学时约束、科目权重、可行性 → 排序）
        ──→ ④ 输出最优方案（总计划 + 阶段 + 首周每日任务）
```

- **动态推演**：计划不是一次性快照。`plan` 状态机：`生成 → 执行中 → 局部调整 → 完成/失效`；每日任务按 `sort_order + 日期` 滚动生成，执行后回流反馈
- **干预机制**：用户反馈（"今天太累""某科需要加码""时间变更"）→ **局部重推演**（只重算受影响阶段/任务，不整表重生成），全程记录 `plan_adjustment` 干预日志

**数据模型（新增/改造）**：
- `study_plan`（计划主表：画像快照、状态、exam_date、生成策略）
- `plan_task`（每日任务：date、task、duration、coins、status、completed_time）——替换现有 StudyGoal 平铺结构
- `plan_adjustment`（干预记录：类型、原因、影响范围、前后对比）
- 现有 `StudyGoal` 保留兼容（错题/目标关联不破坏）

**端点（登记台账）**：`POST /api/plan/generate`（改造：走画像+推理）、`POST /api/plan/{plan_id}/adjust`（干预）、`GET /api/plan/{plan_id}/tasks?date=`（按日取任务）

### 2.3 每日任务闭环（"个人小目标" → "每日任务"展示栏）

- **展示栏**：首页小目标模块升级为"今日任务"面板：今日任务列表 + 对应**金币奖励** + "完成才可领取"按钮（沿用现有金币/coin 体系 `total_coins`）
- **任务领取逻辑**：任务完成（勾选）→ 金币解锁 → 领取入账；跨日未完成 → 任务作废不补金币
- **消息推送服务**：站内消息（复用现有消息/通知表）+ 定时任务（每日 20:00 检查今日未完成任务 → 站内提醒）；后续可扩展短信/微信模板消息
- **端点（登记台账）**：`POST /api/plan/task/{task_id}/claim`（领取金币）、`GET /api/plan/today`（今日面板）、`POST /api/notify/task-remind`（推送触发）

## 三、模块 7 v2：多 Agent 备考陪伴系统

### 3.1 Agent 矩阵与调度

| Agent | 职责 | 触发场景 |
| :--- | :--- | :--- |
| `router`（调度器） | 意图识别与路由 | 所有入口消息（LLM 分类 + 关键词规则双保险） |
| `选岗 Agent` | 岗位匹配：画像/地区/专业 → 岗位推荐与竞争分析 | "我能报哪些岗""选岗建议" |
| `面试 Agent` | 结构化面试题 + 答题框架 + 模拟追问 | "面试怎么准备""帮我练一道面试题" |
| `心理辅导 Agent` | 情绪疏导（现有 psychological 场景升级） | 焦虑/压力/心态类 |
| `申论 Agent` | 申论范文拆解、概括/对策/作文批改思路 | 申论类问题 |
| `行测 Agent` | 行测五大模块解题技巧与考点解析 | 行测类问题 |
| `公专 Agent` | 公安专业知识、法条应用、情景题 | 公专类问题 |

- **编排**：`router` 输出 `{agent, 置信度, 提炼后的任务}` → 对应 Agent 用**专业 system prompt + 知识库检索**作答；路由置信度低时走兜底（通用 qa）
- 复用现有 `llm_client`：按 Agent 维护 system prompt 模板表（`agent_prompts` 配置），不做多进程 Agent，单会话内按意图切换

### 3.2 记忆与长期陪伴

**三层记忆**：
1. **画像记忆**：直接读取模块 4 的 `user_profile`（共享，一次采集两模块受益）
2. **会话记忆**：现有 ChatSession/ChatMessage（消息上限 2000、历史 10 条上下文）
3. **长期记忆**：`user_memory` 表（关键事实抽取：目标分数、弱项科目、承诺的行动、情绪波动事件、里程碑达成）——每条带 `memory_type`、`expire_at`（可选）、`source`（哪个 Agent 记录的）

**档案感知对话**（"带着档案来对话"）：
- 对话启动时装配**档案上下文**：`user_profile` + 模块 4 当前计划摘要 + 学情报告（做题量/正确率/错题分布）+ 最近错题 Top N
- 实现：`GET /api/context/assemble`（路由层拼装档案上下文注入 system prompt，控制 token 用量：只取摘要与统计，不塞原文）

### 3.3 对话 / 工作双模式

- **对话模式**（现有聊天 UI）：自由问答，Agent 自动路由
- **工作模式**（新增面板）：左侧任务类型列表（"生成一周申论计划""行测错题诊断""模拟一场面试"…），点选后进入**结构化向导**（表单收集参数 → 调对应 Agent → 结果以卡片/清单呈现，可一键"写入计划"或"加入今日任务"——与模块 4 联动）

**端点（登记台账）**：`POST /api/agent/route`（内部调度，可选）、`GET /api/agent/tasks`（工作模式任务清单）、`POST /api/agent/run`（执行工作模式任务）

## 四、自生长多模态知识库（模块 4/7 共用底座）

### 4.1 知识库分层

| 库 | 内容 | 来源 | 服务对象 |
| :--- | :--- | :--- | :--- |
| 法条库 | 公安执法相关法律/法规/条例条文 | Obsidian vault（官方源抓取/人工校对） | 公专 Agent、选岗 Agent（资格条件） |
| 报考信息库 | 公告、岗位表、历年分数线、政策 | Obsidian + 团队维护 | 选岗 Agent |
| 考点知识库 | 科目-考点-题型-题目结构 | 现有题库 + 人工整理 | 全部 Agent、组卷、图谱 |
| 错题库 | 用户错题（结构已有） | 系统自动 | 档案感知、学情推理 |

### 4.2 知识图谱框架

- **实体**：科目、考点、题型、题目、法条、岗位、地区
- **关系**：`包含`（科目→考点）、`关联`（考点↔题型）、`前置`（考点A→考点B）、`依据`（题目→法条）、`匹配`（岗位→专业/学历/地区）
- **存储**：`knowledge_node`（实体）+ `knowledge_relation`（边）两张表（轻量图存储，不引入 Neo4j）
- **可视化**：前端"知识图谱"页（ECharts graph：按科目/考点聚合展示，支持展开、检索、点选进入题目/法条）
- **应用**：学情推理（弱项考点→关联前置考点→自动补强计划）、组卷、Agent 回答附来源

### 4.3 Obsidian 自生长工作流（半自动，省人力）

```
官方数据源（公安部/招警平台等）──(定时/人工粘贴)──▶ Obsidian Vault
    │                                                    │
    │  markdown 规范：YAML 头（type/title/source/date/status）+ 正文
    ▼                                                    ▼
系统侧同步器（scripts/obsidian_sync.py）──▶ 解析为候选知识节点
    │
    ▼
审批界面（管理端"知识库审批"页：预览卡片 + 差异对比 + 通过/驳回）
    │
    ▼
审批通过 → 入库（knowledge_node，标记 source_vault_path）→ 图谱与检索生效
```

- **新增**：`scripts/obsidian_sync.py`（扫描 vault → 解析 → 生成候选 diff）、管理端审批页（`.vtj/vue` 新页面）、`knowledge_base.py` 服务（检索：关键词 + 结构化过滤，向量检索列为 v3 可选项）

### 4.4 检索增强（RAG 轻量版）

- v2 落地：**结构化检索**（法条按标题/条文号过滤 + 关键词 LIKE）+ 检索结果以"参考资料"注入 Agent 上下文，回答附**来源标注**（"依据《人民警察法》第X条"）
- v3 可选项：向量化（本地 embedding + 向量表），看实际效果再定，不预设

## 六、实施阶段规划（建议顺序）

| 阶段 | 内容 | 预估工作量 | 前置依赖 |
| :--- | :--- | :--- | :--- |
| **Phase 1 画像与动态计划内核** | 画像问卷（3 模板）+ user_profile + PlanAgent 推理生成 + 每日任务栏（金币领取）+ 站内提醒 | 大（跨前后端） | 无 |
| **Phase 2 多 Agent 与档案感知** | router 调度 + 6 Agent prompt 体系 + user_memory + 档案上下文装配 + 对话/工作双模式 | 大 | Phase 1（画像共享） |
| **Phase 3 知识库与图谱** | Obsidian vault 接入 + 法条/报考库 + 审批界面 + 知识图谱页 + Agent 检索增强 | 中大 | Phase 2（Agent 消费知识库） |

> 建议：Phase 1 与 Phase 2 可并行启动（不同子分支），Phase 3 依赖前两者产生的内容消费场景。每阶段内部走"设计→审核→开发→测试→合并"闭环。

## 七、待确认事项（需用户拍板）

1. **知识库数据源清单**：法条优先收录哪些（人民警察法、行政处罚法、刑事诉讼法…？按公安联考大纲圈定）；报考信息源（各省招警公告/分数线）由谁维护
2. **Obsidian vault 位置与目录规范**：确认 vault 路径（建议 `docs/knowledge-vault/`，与仓库同管）、法条抓取自动化程度（官方源是否有稳定可爬入口，还是以人工粘贴校对为主）
3. **金币数值体系**：每日任务金币单价（建议 10-50/任务，与现有签到/做题奖励一致）、连续完成加成
4. **推送渠道**：先站内信（可立即做）；短信/微信模板是否要在本迭代做（涉及第三方服务）
5. **选岗 Agent 数据边界**：岗位表数据来源（历年公告人工维护 vs 实时抓取）——决定选岗回答的准确度承诺
6. **阶段优先级**：若资源有限，先做哪条线（建议先 Phase 1 画像+动态计划，收益最直观）
