## 0 结论摘要（先看这 10 条）

1. **这不是一个模块，是一个包含 6 条工作流的项目群**：图谱底座、Obsidian 协同、审核智能体、金句分类、新闻分类/搜索、招考附件/关注/提醒。一次全上就是大爆炸，必须按 R0→R4 分阶段。
2. **图谱先定形**：v1 冻结 **8 类节点 + 10 类关系**，用一张 `kg_edge` 薄图挂接现有 `knowledge_point`、金句、新闻、招考、来源、机构、事件、证据；**不复制正文、不另起一套分类**。
3. **现有系统已经有图谱骨架**：`knowledge_point`（94 条）+ `question_knowledge`（题目↔考点）已在用；新图谱应**复用**它，而不是再造一个 Neo4j。
4. **Obsidian 是"投影 + 审核收件箱"，不是第二事实源**：SQLite 仍是唯一事实源；服务器把待审/已发布内容导出为 Markdown，人在 Obsidian 改 `status/topics/review_note`，同步器校验后回写。正文只读，避免双写冲突。
5. **"全自动审核"用两段式落地**：先 **影子模式**（智能体给建议、人决定）→ 再 **辅助模式**（预填建议）→ 最后 **白名单自动**（仅官方来源金句，置信度≥阈值）。新闻/招考本期不自动发布。
6. **智能体分工就是您说的两个**：**Scout** 负责去相关网站取证（标题/作者/日期/原文快照），**Curator** 负责判断与打分；可选 **Linker** 负责图谱连边，**Auditor** 负责抽样审计。
7. **招考"超文本"当前是断的**：前端 `sanitizeHtml` 的 `ALLOWED_TAGS` **不含 `<a>`**，实测 788 条招考里有 **206 条含 `<a href>`**，链接被降级成纯文本，用户点不了。这是本期必须修的第一处。
8. **招考附件有真实存量**：788 条中 168 条含 `.xls/.xlsx` 字样、124 条含 `.doc/.docx`、21 条含 `.pdf`、51 条含 `<table>`、72 条含 `<img>`。附件抽取/下载/表格导出有数据基础，不是空想。
9. **新闻分类与搜索要换底座**：现在只有 `理论/党史/公安报` 三类硬编码（实际只有理论 5 条、党史 3 条），列表无分页、无搜索、每条都带回全文。改为 `news_category` 字典 + `category_code` + FTS5 **trigram**（已实测可用）+ 分页。
10. **总工期诚实估计**：单人 **9.5–11.5 工程师周**；两人并行约 **6 周**。R0 底座 2 周必须先做，否则后面五条工作流都会返工。

## 1 目标与度量

### 1.1 业务目标

| 目标 | 可验收的定义 |
|---|---|
| 一个图谱统摄三类内容 | 金句/新闻/招考发布时 **100%** 至少连 1 个主题；孤儿内容为 0 |
| 分类清楚、边界明确 | 课程考点（knowledge_point）与主题（topic）分层；内容表不新增自由文本分类 |
| Obsidian 可审、可看、可搜 | 待审、新闻总览、招考总览、主题地图、图谱视图、搜索五类界面可用 |
| 审核自动化 | 白名单官方来源金句自动通过；低置信度/风险项 100% 转人工 |
| 金句可按需筛选 | 分类栏切换后 p95 ≤300ms；筛选结果与图谱主题一致 |
| 新闻可按类/模糊搜 | 20 条黄金查询召回 ≥90%；搜索 p95 ≤300ms |
| 招考可下载、可关注、可提醒 | 附件抽取覆盖率 ≥90%；关注后日历可见；提醒到达率 ≥99% |

### 1.2 技术指标

| 指标 | 目标 |
|---|---|
| 图谱查询（2 跳子图） | ≤150ms（1 万节点/5 万边内） |
| Obsidian 导出/回写延迟 | ≤5 分钟（定时扫描） |
| 审核智能体影子一致率 | ≥90% 后才允许进入辅助模式 |
| 自动通过精确率 | 抽样 ≥98%；低于则自动降级为人工 |
| 新闻 FTS 查询 | p95 ≤300ms |
| 招考附件下载 | 成功率 ≥99%；单文件 ≤20MB |
| 提醒任务 | 每日 08:00 执行；重复提醒 0 |

### 1.3 失败判据

同一内容在 Obsidian 与网页状态不一致超过 10 分钟；图谱出现第二套主题字典；自动通过内容被抽检出错误且无审计链；招考链接仍不可点；提醒重复轰炸；任一工作流绕过 R0 底座直接改内容表。

## 2 范围与非目标

### 2.1 本期范围

- **A Quote 基础**（继承 v2.0）：SQLite 事实源、Obsidian 导入、daily 预生成、收藏兼容。
- **B 图谱底座**：`topic` + `kg_edge` + 关系注册表 + 三类内容回填 + 图谱 API。
- **C Obsidian 协同**：目录规范、导出、审核回写、Dataview 看板、图谱视图。
- **D 新闻**：分类字典、`category_code`、FTS5 trigram 搜索、分页、前端筛选/搜索。
- **E 招考**：`<a>` 白名单修复、附件抽取/下载、表格导出（V1）、关注、加入日历、提醒、通知中心。
- **F 审核智能体**：Scout/Curator/Linker/Auditor；影子→辅助→白名单自动。

### 2.2 非目标

- 不引入 Neo4j / MongoDB / Milvus / MinIO / 端侧模型。
- 不做新闻/招考的自动发布；不做全网爬虫扩张。
- 不做音视频证据（V2 再评估）；不做二维码解码（先存图）。
- 不做 Obsidian 自定义插件开发；不要求 Meta Bind 等第三方插件。
- 不做正文双向编辑；Obsidian 只改白名单字段。
- 不修改既有 API 路径/方法/响应外壳；不重写三端页面模板（模板由设计器改）。

### 2.3 反目标

- 为了"图谱"把正文复制进图数据库，制造双份事实。
- 为了"自动"让 LLM 直接发布新闻/招考。
- 为了"Obsidian 自生长"让脚本随意新建主题，导致分类爆炸。
- 六个工作流并行开工，互相等接口。

## 5 知识图谱定形（先定形，后拓展）

### 5.1 分层与边界（最重要）

| 层 | 节点/职责 | 权威归属 | 不做什么 |
|---|---|---|---|
| 课程层 | `subject` → `sub_category` → `knowledge_point` | 题库域（已有表） | 不承载新闻/招考分类 |
| 主题层 | `topic`（忠诚教育/执法素养/心理韧性…） | 内容域（新增） | 不用于判分、不替代考点 |
| 内容层 | `quote` / `news` / `recruitment` | 各自模块 | 不自建分类字符串 |
| 来源层 | `content_source`（URL/文件/投稿） | 内容域 | 不存正文 |
| 事件层 | `event`（考试/报名截止/会议） | 日历/招考 | 不存内容正文 |
| 证据层 | `content_evidence`（图片/PDF/二维码） | 内容域 | 不重复存正文 |

**边界铁律**：
1. 内容表里的 `category`/`source` 只作**兼容展示**，新逻辑一律走 `kg_edge`。
2. 课程考点由题库域维护；内容只能"引用"，不能新建考点。
3. 主题由内容域维护；新增主题必须走"建议→审核→合并"，禁止脚本自建。
4. 图只存 `(type,id)` 指针，不复制标题/正文；展示时按类型解析。

### 5.2 节点类型（v1 冻结 8 类）

| 类型 | ID 来源 | 说明 |
|---|---|---|
| `subject` | `question_subject.subject_id` | 行测/申论/公专 |
| `knowledge_point` | `knowledge_point.point_id` | 考点（复用现有 94 条） |
| `topic` | `topic.topic_id` | 主题/场景标签 |
| `quote` | `essay_quote.quote_id` | 金句 |
| `news` | `news_article.news_id` | 新闻 |
| `recruitment` | `recruitment_info.recruitment_id` | 招考 |
| `source` | `content_source.source_id` | 来源 |
| `event` | `exam_calendar.event_id` / 招考节点 | 考试/截止/会议 |

`organization`、`media` 在 v1 先作为**属性/证据**，不单独建节点；V2 如出现"机构主页/多内容关联"再升级为节点（扩展路径写明）。

### 5.3 关系类型（v1 冻结 10 类）

| 关系 | 方向 | 允许的端点 | 用途 |
|---|---|---|---|
| `covers` | 内容 → 考点 | quote/news/recruitment → knowledge_point | 备考关联 |
| `has_topic` | 内容 → 主题 | 任意内容 → topic | 主分类 |
| `mentions` | 内容 → 机构/人 | news/recruitment → topic（机构暂存属性） | 实体提及 |
| `derived_from` | 内容 → 来源 | 任意内容 → source | 溯源 |
| `related_to` | 内容 ↔ 内容 | quote↔quote/news↔news | 相似/互补 |
| `opposite_to` | 内容 ↔ 内容 | quote↔quote | 对立观点 |
| `scheduled_as` | 招考 → 事件 | recruitment → event | 报名/考试时间 |
| `prerequisite_of` | 考点 → 考点 | knowledge_point → knowledge_point | 先修关系 |
| `broader_than` | 主题 → 主题 | topic → topic | 主题树 |
| `has_evidence` | 内容 → 证据 | 任意内容 → media | 图片/PDF/二维码 |

### 5.4 存储

```sql
CREATE TABLE topic (
  topic_id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  slug TEXT NOT NULL UNIQUE,
  parent_id INTEGER,
  description TEXT,
  aliases TEXT,              -- JSON
  status INTEGER DEFAULT 1,
  sort_order INTEGER DEFAULT 1
);

CREATE TABLE kg_edge (
  edge_id INTEGER PRIMARY KEY AUTOINCREMENT,
  src_type TEXT NOT NULL,
  src_id INTEGER NOT NULL,
  dst_type TEXT NOT NULL,
  dst_id INTEGER NOT NULL,
  relation TEXT NOT NULL,
  weight REAL DEFAULT 1.0,
  confidence REAL DEFAULT 1.0,
  origin TEXT DEFAULT 'rule', -- rule/llm/human
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (src_type, src_id, dst_type, dst_id, relation)
);
CREATE INDEX ix_kg_src ON kg_edge(src_type, src_id, relation);
CREATE INDEX ix_kg_dst ON kg_edge(dst_type, dst_id, relation);

CREATE TABLE kg_relation_type (
  relation TEXT PRIMARY KEY,
  description TEXT,
  directed INTEGER DEFAULT 1,
  src_types TEXT,            -- JSON array
  dst_types TEXT
);
```

**为什么不用通用 `kg_node` 表**：会复制 94 个考点 + 788 条招考 + 10 条金句的标题，产生第二事实源；薄边表 + 类型解析足够。**为什么不上 Neo4j**：1 万节点内递归 CTE 2 跳 ≤150ms；Neo4j 的运维成本与当前单机 SQLite 不匹配。

### 5.5 扩展规则（"后拓展"的唯一入口）

- 新增**关系**：向 `kg_relation_type` 加一行 + 代码白名单 + 测试，不改表结构。
- 新增**节点类型**：必须提供 `resolve_node(type,id) -> {label,url}` 解析器 + 回填脚本 + 文档；否则禁止入库。
- 新增**主题**：`topic` 插入 + 别名 + 父主题；合并走 `merge` 接口（保留 canonical，重指边）。
- 主题最大深度 2；同义主题必须合并，不允许"忠诚教育/忠诚铸魂"并存。

### 5.6 图谱 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/kg/topics?tree=1` | 主题树 + 内容计数 |
| GET | `/api/kg/nodes/{type}/{id}` | 节点 + 一跳邻居 |
| GET | `/api/kg/subgraph?type=&id=&depth=2&relations=` | 子图（递归 CTE） |
| GET | `/api/kg/search?q=&type=` | 节点检索 |
| POST | `/api/admin/kg/edges` | 增/改边（含 provenance） |
| DELETE | `/api/admin/kg/edges/{id}` | 删边（软删/审计） |
| POST | `/api/admin/kg/topics/merge` | 合并主题 |

### 6.3 迁移与回填

1. `sqlite3.backup()` 备份；记录行数/哈希。
2. 建表/加列；建 FTS；建索引。
3. 主题种子（见附录 B）导入；金句 10 条按 `category` 映射；新闻 8 条按 `category` + 关键词映射；招考 788 条按 `category/region/organization` 映射。
4. 生成 `content_source`：金句（Obsidian 文件名）、新闻（url）、招考（url）。
5. 考点 94 条建 `knowledge_point` 节点；因 `question_subject` 为空，先补科目字典或允许 `covers` 只用考点（需确认）。
6. 对账：每类内容 `has_topic` 覆盖率 100%；孤儿 0；重复主题 0。
7. 回滚：开关 `CONTENT_HUB_ENABLED=false` + 恢复备份；不删旧列，直到 R1 验收。

## 9 Obsidian 协同设计

### 9.1 定位

Obsidian = **只读投影 + 审核收件箱 + 可视化台**。SQLite 是唯一事实源；Obsidian 不直接连数据库，不同步正文。

### 9.2 目录规范

```
每日金句知识库/
├── 00-收件箱/            # 智能体写入的待审候选
│   ├── 金句/
│   ├── 主题建议/
│   └── 冲突/
├── 01-金句/              # 已发布金句（按主题/日期）
├── 02-新闻/              # 新闻索引页（按日/分类）
├── 03-招考/              # 招考索引页（按分类/截止日）
├── 04-主题地图/          # topic hub（MOC）
├── 05-考点地图/          # knowledge_point hub
├── 06-看板/              # Dataview：待审/新闻/招考/统计
├── 07-归档/
└── 99-系统/              # 模板、导出清单、同步日志
```

### 9.3 笔记 schema

```yaml
---
uid: q_7f3a9c2e
type: quote            # quote/news/recruitment
status: pending        # pending/published/rejected
topics: [忠诚教育, 心理韧性]
knowledge_points: []
source: "人民日报"
source_url: "https://..."
quality: 82
review_rev: 3
exported_at: 2026-10-29T10:00:00+08:00
---
正文（只读）
```

`[[主题-忠诚教育]]`、`[[考点-...]]`、`[[来源-...]]` 由导出器按 `kg_edge` 生成。

### 9.4 导出与回写

**导出**：DB → Markdown，临时文件 + 原子 rename；记录 `exported_at/hash`；同一内容重复导出幂等。

**回写**（审核）：扫描 `00-收件箱` 变更文件 → 只允许改 `status/topics/review_note` → 校验 YAML（safe_load、大小限制）→ 调服务层写 `quote_review` + `kg_edge` → 生成新投影 → 旧文件归档。

**冲突**：文件 `review_rev` 小于库中版本 → 不覆盖，写 `00-收件箱/冲突/` 并保留双方；人工处理。

**正文只读**：Obsidian 中改正文不生效；如需改稿，走网页/API 生成新修订并重新审核。

### 9.5 看板（Dataview 示例）

```dataview
TABLE status, quality, source
FROM "00-收件箱/金句"
WHERE status = "pending"
SORT quality DESC
```

新闻总览：按 `type=news` + `publish_date` 分组；招考总览：按 `deadline` 倒计时；主题地图：按 `topics` 统计。

### 9.6 自生长

- 主题 hub 页由边自动生成；新增主题只从 `00-收件箱/主题建议/` 进入，人工批准后合并。
- 不改用第三方插件；如需要按钮，可选 Meta Bind，但不作为依赖。

## 10 审核智能体设计

### 10.1 角色与工具

| 角色 | 职责 | 工具 | 不做什么 |
|---|---|---|---|
| **Scout** | 去来源站取证：标题/作者/日期/原文快照、链接可达性 | `fetch_source(url)`（域名白名单、robots、超时、缓存） | 不抓登录墙、不绕验证码、不无限翻页 |
| **Curator** | 判断是否金句、质量分、主题、风险、重复 | `lookup_duplicate`、`classify`（LLM JSON Schema）、规则库 | 不直接发布；只给决策建议 |
| **Linker** | 连主题/考点/相似句 | `suggest_edges` | 不自建主题；只提建议 |
| **Auditor** | 抽样复核自动通过项 | 抽样查询 + 人工 | 不改内容 |

### 10.2 流水线

```
候选 → Scout 取证 → Curator 打分 → 门控
  ├─ score≥0.85 且 source_trust≥80 且无风险 且 来源在白名单 → auto_publish
  ├─ 0.60–0.85 或任一不满足 → 人工队列（Obsidian 00-收件箱）
  └─ <0.60 或命中风险 → 隔离/拒绝
→ Linker 连边 → 导出 Obsidian → Auditor 抽样 10%
```

### 10.3 置信度

```
score = 0.35*source_trust + 0.25*source_verified
      + 0.20*text_quality + 0.20*classify_confidence
      - risk_penalty
```

默认阈值可配置；**白名单只限官方来源**（公安部、人社部、省级政府/人社厅、官方媒体）；个人投稿永不自动通过。

### 10.4 三阶段启用

| 阶段 | 行为 | 放行条件 |
|---|---|---|
| 影子 | 智能体只写建议，人全审 | 一致率 ≥90%，连续 2 周 |
| 辅助 | 预填建议，人确认 | 建议采纳率 ≥80% |
| 白名单自动 | 官方来源 + 高置信度自动通过 | 抽样精确率 ≥98%，无高危事故 |

### 10.5 护栏

- `AUTO_REVIEW_ENABLED` 总开关；按来源白名单；日自动通过上限（如 50 条）。
- 成本上限：每次取证 ≤3 次请求；每日 token 上限；超限转人工。
- 提示注入：抓取内容加分隔符、声明"仅数据"，禁止工具调用；输出必须过 Schema。
- 审计：每次决策写 `llm_call_log` + `quote_review`（agent 版本、prompt 版本、证据快照哈希）。
- 一键降级：关闭自动，队列转人工。

## 12 安全设计

| 风险 | 控制 |
|---|---|
| `<a>` 白名单引入 XSS | 仅允许 `http/https`；`rel=noopener noreferrer`；`target=_blank`；禁 `javascript:/data:`；前后端同一套测试 |
| SSRF（Scout/附件） | 域名白名单；禁私网/环回/元数据地址；禁重定向到内网；超时/大小限制 |
| 附件恶意文件 | 类型白名单（pdf/doc/xls/zip/图片）；MIME 嗅探；禁可执行；≤20MB；sha256 去重；可选 ClamAV |
| YAML 注入 | `safe_load`；字段白名单；大小/深度限制；不执行标签 |
| 自动发布风险 | 白名单 + 阈值 + 抽样 + 总开关；新闻/招考不自动 |
| 提示注入 | 内容分隔、无工具、Schema 校验、来源可信度 |
| 越权 | 审核/图谱管理 `role_level≥2`；服务端二次校验 |
| 版权 | 附件仅镜像公开官方文件；保留来源/下架流程 |
| 隐私 | 投稿人信息最小化；不公开手机号 |
| 通知滥用 | 每用户每日上限；免打扰时段 |
| 读接口写库 | 修掉 `view_count` 在 GET 中自增；改为异步/批量 |

## 15 风险与回滚

| 风险 | 影响 | 缓解 |
