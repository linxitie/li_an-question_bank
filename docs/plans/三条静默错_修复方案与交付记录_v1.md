# 三条「静默错」修复方案与交付记录 v1

> 日期：2026-11-12　｜　分支：`feat/material-multi-format-import`（**main 未动**）
> 来源：`11月5日以来工作盘点与缺陷复核_v1.md` §3-3 / §3-4 / §3-6 与 §4-N1/N2/N3（你指示「先修这 3 条」）
> 定性：三条都是**不报错、界面看着正常、但数据没落对**的静默错——比崩溃更难发现，也最容易在验收时被判"功能没做"。

---

## 0. 三条一览

| # | 问题 | 用户能感知到什么 | 根因一句话 |
|---|---|---|---|
| 1 | **模考错题不进错题本** | 考完去「错题本」是空的 | `session` 是 `autoflush=False`，交卷代码在 `commit` 前重新 `query` 刚 `add` 的明细 → 永远 `None` |
| 2 | **老资料去重失效** | 同一份老讲义重传，又生成一条 | 去重只比 `content_hash` 列，而 W2 之前入库的 **98 条该列为 NULL** |
| 3 | **文章批量没有「立即上架」** | 一批 20 篇要手点 20 次上架 | 后端 `import_confirm` 的文档分支**硬编码 `status=0`**（`publish` 只对 xlsx 卡片生效），前端也没这个开关 |

## 1. 模考错题本（`exam/exams.py` 交卷链路）

### 1.1 证据链

- 库：`wrong_question_personal` **0 行**；`exam_answer_detail` **388 行**，其中 `is_correct=0` 且**有作答**的至少 6 条（#2/#3/#4 各 2 条）。
- 代码：交卷端点里本来**有**错题钩子（`exams.py:448-459`）：

```python
for question_id, student_answer in answers.items():
    detail = db.query(ExamAnswerDetail).filter(
        ExamAnswerDetail.record_id == record_id,
        ExamAnswerDetail.question_id == question_id).first()
    if detail and not detail.is_correct:
        _auto_record_wrong(...)
```

- 但 `backend/app/core/database.py:45` 是 `sessionmaker(..., autoflush=False)`：上面 `db.add(answer_detail)` 的明细**还没 flush**，`query()` 只查数据库 → `detail` 恒 `None` → 整段是**死代码**。
- 另有一处口径错：`not detail.is_correct` 对空白题（`is_correct=0`、答案空串）也为真 —— 即使修好查询，**未作答也会被当错题收录**，与结果页"未答≠错"的口径冲突。

### 1.2 修法

1. 不再重新查询：直接用内存里的 `created_details`（本轮 `db.add()` 的那批）；
2. 只收 **`is_correct == 0` 且 `student_answer` 非空**的题（空白 = 未作答，不进错题本）；
3. 复用既有 `_auto_record_wrong()`（内部走 `practice_grading.upsert_wrong_question`，同事务、同表、同 `collection_type='WRONG'`）；
4. 写日志 `错题入库 N 条`，便于以后核对；异常仍由 `_auto_record_wrong` 吞掉，不影响交卷。

### 1.3 预期效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 答对 1 / 答错 1 / 空 1 | 错题本 0 条 | **只收答错那 1 条**，`user_answer` = 学生选项 |
| 同一题第二次考又错 | — | 同一行 `error_count` +1（`upsert` 幂等） |
| 全对 / 全空 | 0 条 | 0 条 |

### 1.4 测试（`backend/tests/test_exam_wrong_book.py`）

- 交卷后 `wrong_question_personal` 恰好 1 行且是"答错且作答"的那题；
- 空答题、答对题都不在里面；
- 重复交卷 400，错题本行数不变；
- 同一题第二次考错 → `error_count=2`（不是两行）。

## 2. 老资料 hash 回填 + 去重兜底

### 2.1 证据链

- 库：`content_hash IS NULL` **98 条**（卡片/文章/讲义里 W2 之前入库的都在内）；
- `_find_duplicate_material_id()`（`materials.py:3249`）只做 `StudyMaterial.content_hash == hash`，NULL 永不命中 → 重传同内容老资料不会被拦；
- 新建入口算哈希用的是 `_material_content_hash(data)`：卡片 = 正面+背面；其它 = 正文，正文为空退化为 标题+摘要。

### 2.2 修法（两层，回填治存量、兜底防再犯）

| 层 | 内容 |
|---|---|
| 存量 | 新增 `backend/scripts/migrate/backfill_material_content_hash.py`：只填 `content_hash IS NULL` 的行，口径与 `_material_content_hash` 完全一致；默认 dry-run，`--apply` 才写；写前 `sqlite3.backup()`（R10）、写后 `integrity_check`；算不出（全空）的行**保持 NULL** 并单独报数 |
| 代码 | `materials.py` 新增 `_row_content_hash(m)`（按已入库行重算，同口径）；`_find_duplicate_material_id` 在"列匹配"未命中时，**只扫 `content_hash IS NULL` 的未删除行**逐行重算比对（回填后是空集，成本≈0；上限 500 行防意外） |

> 为什么不只做回填：以后若再有 raw SQL / 老脚本插入不带 hash 的行，兜底仍然能拦住；两层都做才叫"修好"。

### 2.3 数据操作（需授权，你已在指令里给出）

```powershell
python backend/scripts/migrate/backfill_material_content_hash.py            # dry-run：只看会改哪些
python backend/scripts/migrate/backfill_material_content_hash.py --apply    # 备份后写入
```

预期：98 条中能算出正文的会被填上（卡片按正反面、文章/讲义按正文），全空的（如无正文的试卷行）保持 NULL 并在报告里列出条数。

### 2.4 测试（`backend/tests/test_materials_dedupe_legacy.py`）

- 造一条"老资料"（`content_hash=None`，有正反面）→ 用同内容 POST `/admin` → **409 + 回老 id**；
- 不同内容 → 正常创建（不误杀）；
- `_row_content_hash(老行)` 与 `_material_content_hash(同等 dict)` **同值**（口径一致性）；
- 回填脚本的纯函数在"全空行"上返回空串（不会被写成非空 hash）。

## 3. 文章批量「立即上架」

### 3.1 证据链

- 前端 `ArticleBatchUpload.vue:288` 调 `confirmMaterialImport` 只传 `subject/type/title`，没有 `publish`；
- 后端 `import_confirm` 顶部读了 `publish = bool(body.get("publish"))`，但**只用在 xlsx 卡片分支**（`status=(1 if publish else 0)`）；文档分支 `materials.py:3686` 写死 `status=0`，且回包里还回 `"published": publish`（如果传了 publish=true 会**谎报已上架**）。

### 3.2 修法

1. 后端文档分支：`status=(1 if publish else 0)`，并把实际状态回传（`published` 用真实值）；
2. 前端 `ArticleBatchUpload.vue`：入库参数区加「立即上架」勾选（默认不勾，文案说明"默认不上架，学生看不见"），confirm 时带 `publish`；
3. 成功提示按实际状态区分（`已创建 N 篇（未上架）` / `已创建并上架 N 篇`）。

### 3.3 预期效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 不勾选 | 全部 `status=0` | 不变（默认安全） |
| 勾选后导入 3 篇 | 仍 `status=0`，要手点 3 次 | **3 篇直接 `status=1`**，学生端立即可见 |
| 回包 | `published: true` 但库里 0（谎报） | `published` 与实际一致 |

### 3.4 测试（`backend/tests/test_article_batch_publish.py`）

- docx 上传 → confirm `{type:'article'}` 不传 publish → `status=0`（回归）；
- 同链路传 `publish=true` → `status=1`，且回包 `published=true`；
- 讲义 `type:'lecture'` 同样支持（共用分支）。

## 4. 风险与回滚

| 风险 | 处置 |
|---|---|
| 错题本写入拖慢交卷 | 只对"答错且有作答"的题写，单场最多 N 题、每行一次 upsert；异常被吞不影响交卷 |
| 回填把空正文行算出"标题 hash" | 脚本对"正文与正反面都为空"的行**保持 NULL**（不写标题兜底），避免同标题互相误判 |
| 去重兜底误杀 | 只在列匹配未命中时扫 NULL 行；单测覆盖"不同内容不误杀" |
| 文章勾选上架后内容有问题 | 默认不勾；勾选文案提示先预览；上架/下架仍可一键回退 |
| 回滚 | 三条互不影响：`git revert` 本次提交即可；回填的数据可用脚本自动备份顶回 |

### 6.4 老实说

- **错题本**这次只做了单元/接口级验证（3 例在一个干净的考试库里跑通）；没有拿线上卷 #5 再考一次——验收账号在那个卷只剩 1 次机会（`4/5`），不想为验证把它用掉。要看真机效果，等你下次做一套卷，交卷后去错题本看是否出现"答错且作答"的那几题。
- **文章上架**真机只验到"勾选 + 文案 + 请求带 `publish`"（截图）；真的上传一批并上架需要挑真实文章，我没往库里塞测试文章。
- hash 归一改的是**派生字段**，不动正文；7 条历史哈希被重算（有备份），若你发现某条老资料"应该能重复建却被拦"，大概率是它原本就与另一条同内容。
