## 0. 一句话结论

**后端其实已经支持 docx / xlsx / 文字型 PDF，甚至给扫描件留了 MinerU 异步通道**——但**前端只有一个学生页、只接受 `.xlsx/.csv`**，且 MinerU 运行环境（`C:\mineru_env`）**根本不存在**，导入记录表**没有进度字段**。
所以这一轮不是"从零做导入"，而是：**把已有后端能力接到三端 UI + 补批量队列 + 补进度模型 + 把 MinerU 通道真正点亮**。

## 4. 方案

### 4.1 总体流程（三段式进度）

```text
① 选择/拖入（多文件、文件夹、zip）
      │  上传进度（浏览器 XHR progress，0-100%）
      ▼
② 入队（batch_id 一批 N 个文件）→ 串行/并发 2 解析
      │  解析进度（服务端：当前文件 p/N + 文件内页级进度）
      ▼
③ 预览确认（逐文件）→ 入库（status=0 下架态）→ 完成
```

**进度语义（每文件 0–100）**：
| 阶段 `current_phase` | 占比 | 说明 |
|---|---|---|
| `uploading` | 0–10 | 浏览器侧 XHR 上传 |
| `queued` | 10 | 排队中（显示"第 k 位"） |
| `parsing` | 10–70 | 解析：PDF 按页、docx 按段、xlsx 按行 |
| `ocr` | 10–70 | 扫描件走 MinerU（按页回调） |
| `extracting` | 70–90 | 结构化（章节/卡片/图片） |
| `preview_ready` | 90 | 待人工确认 |
| `committing` → `done` | 90–100 | 入库 |
| `failed` | — | 带 `error_message` + 可重试 |

### 4.2 格式 → 解析器映射（G6）

| 输入 | 判定 | 解析器 | 产物 | 优先级 |
|---|---|---|---|---|
| `.xlsx/.csv` | 表头含 `正面/背面` | 现有 `parse_xlsx` + `validate_rows` | 卡片（`type=card`） | P0 |
| `.docx` | `tables=0` 且段落含星级/标题 | 现有 `parse_docx` | 文章（`type=article`）+ 章节 | P0 |
| `.pdf` 有文字层 | 前 3 页字符 > 200 | 现有 `parse_pdf_text` | 文章 + 章节 | P0 |
| `.pdf` 无文字层 | 前 3 页字符 < 50 | **MinerU**（`run_mineru`） | 消毒 HTML + 图片（现有 `material_sanitizer`） | P1 |
| `.doc`（老格式） | 扩展名 | 先提示"另存为 .docx"；后续可用 LibreOffice 转换 | 文章 | P2 |
| `.md/.txt` | 扩展名 | 新增轻量解析（标题 `#`→章节） | 文章 | P1 |
| `.pptx` | 扩展名 | 新增（python-pptx 已在环境里） | 讲稿/文章 | P2 |
| 图片 `.jpg/.png` | 扩展名 | 走 `admin/upload/image`（已有）挂到文章/卡片 | 配图 | P1 |

### 4.3 三端上传矩阵（权限与范围）

| 端 | 入口 | 允许格式 | 上限 | 审核 |
|---|---|---|---|---|
| 管理员 | 新页 `src/views/admin/material_import.vue`（手写页，**不改 `.vtj` 模板**） | 全部（含 PDF/zip/多选） | 单 250 MB / 批 50 个 | 直接入库（`status=0`） |
| 教师 | 同组件，独立薄壳页 `src/views/teacher/material_import.vue` | docx/xlsx/文字型 pdf | 单 50 MB / 批 10 个 | 待审 `status=0` |
| 学生 | 现有 `material_upload.vue` 扩展 Tab | xlsx/csv + 图片 | 单 5 MB / ≤200 行 | 待审（保持现状） |

**"同一个页面"到底指什么（IMP-5 澄清）**：`同页 ≠ 同布局、≠ 同功能`。三种实现方式与代价：

| 方案 | 页面文件 | 路由/页面计数 | 布局 | 权限隔离 | 适用 |
|---|---|---|---|---|---|
| **A 完全同页** | 1 个 | 104→**105** | 同一套布局，按角色 `v-if` 显隐（管理员多出"全量队列/批量/他人记录"） | 靠页面内条件 + 后端校验，**前端易漏判** | 教师只需要"能传" |
| **B 共享组件 + 两个薄壳**（推荐） | 1 个组件 `components/MaterialImporter.vue` + 2 个薄壳页 | 104→**106** | 各按角色组织：管理员双列（队列+详情）、教师单列（上传+我的记录） | **路由级** `meta.roles` 各自收敛，天然隔离 | 教学/管理信息架构不同 |
| **C redirect** | 1 个 + 1 条 redirect | 104→**105**（redirect 不计页） | 同 A | 同 A | 只是想让教师"能用入口"、不求独立观感 |

> 无论选哪个，**权限必须由后端兜底**：现状是 `_require_admin` 硬校验；放开教师需新增 `_require_staff`（admin+teacher）并按 `uploader_id` 过滤"我的记录"，前端隐藏只是体验，不是安全边界。

> 学生端是否开放 PDF/Word 上传 = **D3**（默认不开放，避免滥用与 OCR 成本）。

### 4.7 MinerU 部署选型（G7）

| 方案 | 内容 | 优点 | 缺点 | 成本 |
|---|---|---|---|---|
| **A 本地 venv**（代码已按此写） | `C:\mineru_env`（Python 3.11 纯 ASCII 路径）+ `mineru 4.1.7`（pypi 可达）+ 模型走 `modelscope`（302 可达） | 离线、无 key、数据不出本机、与现有 `mineru_material_service.py` 完全兼容 | 依赖约 3–5 GB（torch 等）+ 模型约 1–2 GB；CPU 单页约 70s（代码注释实测） | 装 30–60 分钟；90 页扫描件约 **1.5–2 小时** |
| **B 在线 API** | `mineru.net` 200 可达，官方 API + token | 不占本机资源、GPU 侧更快 | 需注册 key、按量计费、**要把资料上传第三方**（与资料可能含版权内容冲突） | 10 分钟接入 |
| **C 不行就用现成 OCR** | 本机已有 `pytesseract` / `easyocr` 库 | 无新增依赖 | 只出纯文本，**版面/表格/公式还原不了**，讲义会变成一坨文字 | 低 |

**建议：A 为主，B 作为"急用/大件"备选；C 兜底。** 理由：代码已经按 A 写好（连 ASCII 路径坑都记了），换成 B 要改服务层；且 90 页扫描件本地跑一晚即可，不需要长期在线。

### 4.8 远端能否用（你问的"上传远端"）——能，但现在是"半接线"

**先给结论**

| 部署形态 | 扫描件导入能不能跑 | 说明 |
|---|---|---|
| 本机（Windows + `C:\mineru_env`） | ✅ 能（装好 MinerU 后） | 现有代码路径就是本机子进程 |
| 远端 Docker **CPU**（compose `--profile ocr`） | ✅ 能，但需接线 + 调参 | 代码里**已经有** parser sidecar 与 compose 服务，只差把 `PARSER_URL` 接上；90 页 CPU 约 **1.8 小时/件** |
| 远端 Docker **有 GPU** | ✅ 能，快 5–10× | 需镜像换 cu124 torch + compose 加 GPU reservation（当前 compose 无 GPU 声明） |
| 纯静态托管 / 无 Docker 的共享空间 | ❌ 不能 | 起不了常驻解析服务 |

**已就绪的部分（不用重写）**

| 资产 | 位置 | 说明 |
|---|---|---|
| 解析微服务 | `backend/parser/app.py` | `POST /parse`（PDF→Markdown+base64 图）、`GET /health`、`Semaphore(1)` 串行防 OOM、413/502/504 明确错误码 |
| 镜像 | `backend/parser/Dockerfile` | `python:3.11-slim` + ffmpeg/libgl + 非 root 用户 + 模型缓存卷 + `MINERU_MODEL_SOURCE=modelscope` |
| 编排 | `deploy/docker-compose.yml` 的 `parser` 服务（`profiles: ["ocr"]`） | 内网 `expose 8080`、2 CPU / 4G、`/tmp` 4G tmpfs、健康检查 180s 启动期 |
| 配置项 | `backend/app/core/config.py` | `PARSER_URL`（注释写明"留空走本地子进程，配置了优先走 HTTP，失败回落"） |

**5 个卡点（必须补，否则远端跑不了）**

| # | 卡点 | 证据 | 修法 |
|---|---|---|---|
| 1 | **`PARSER_URL` 没有任何消费方** | 全仓检索只在 `config.py:104` 定义，业务代码 0 处引用 → 远端仍会去找 `C:\mineru_env\Scripts\mineru.exe` | 抽 `OcrProvider` 接口：`HttpSidecar`（`PARSER_URL`）/ `LocalCli`（`MINERU_EXE`），HTTP 优先、失败回落（按原设计注释语义） |
| 2 | **20 MB 上限** | `DOC_SIZE_LIMIT = 20 * 1024 * 1024`（`materials.py:1678`） | 你的 `三色笔记-申论.pdf` 是 **204 MB**，现在**连 MinerU 都到不了**就被拒。需分级上限（PDF 250 MB）+ 改流式落盘（`_save_tmp` 现在 `file.file.read()` 全量进内存） |
| 3 | **长任务无队列、重启即丢** | 走 `BackgroundTasks + run_in_threadpool`；`requirements.txt` 里 celery 被注释、无 worker | 最小方案：DB 状态机 + 单线程 worker（`processing` 超时自动重置可重试）；不必引入 celery |
| 4 | **超时写死 600s** | `mineru_material_service.py:26` `TIMEOUT_SECONDS=600`（未用 `MINERU_SECONDS_PER_PAGE`） | 90 页 × 71.2s ≈ 6410s → 必超时。改成 `max(600, 120 + 75×页数)`，与 `config.py` 已有算法一致 |
| 5 | **结果图 base64 回传** | sidecar 单图 8 MB、最多 200 张 → 响应体可达数百 MB | 改为 sidecar 落共享卷/ObjectStore 并只回 URL（复用 F3 `media_assets` 机制） |

**资源与时间（按实测 71.2 s/页 CPU）**

| 文件 | 页数 | CPU 预估 | 有 GPU（约 8×） |
|---|---|---|---|
| `三色笔记-申论.pdf` | 90 | **≈ 1.8 小时** | ≈ 13 分钟 |
