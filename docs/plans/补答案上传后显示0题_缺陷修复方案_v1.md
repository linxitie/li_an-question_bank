## 0. 一句话结论

**上传接口的回包里没有 `items`，而前端只读回包里的 `items`。**
关掉抽屉再打开就走另一个接口（`/answers/latest`），那个接口带 `items` —— 所以"关掉重开"能看到 97 行。

---

## 1. 证据链（三条，都可复跑）

### 1.1 解析其实完全成功（库里 97 条明细齐全）

今天你三次上传（19:45:40 / 19:46:02 / 19:46:23），每次都把上一份 pending 草稿作废，最后留下 **draft #7**：

```
paper_answer_draft #7  paper_id=5  status=pending  item_count=97
items: 97 条，answer 全部非空；current（库里现有答案）与 answer 相同：97/97
```

→ 说明这份 PDF 的题号、答案、解析都抽对了，且**和 11-09 已写入的 97 题完全一致**。

### 1.2 上传回包缺 `items`（根因）

| 接口 | 是否带 `items` | 代码 |
|---|---|---|
| `POST /admin/papers/{id}/answers/parse`（上传） | ❌ **不带** | `materials.py:2313` → `draft_payload(db, draft)`，`with_items` 默认 `False` |
| `GET /admin/papers/{id}/answers/latest`（打开抽屉续草稿） | ✅ 带 | `materials.py:2333` → `with_items=True` |
| `GET /admin/answers/drafts/{id}`（明细） | ✅ 带 | `materials.py:2352` |

前端 `AnswerDraftDrawer.vue` 的 `upload()`：

```ts
const data = await parseAnswerFile(props.paperId, file, ...);
items.value = (data.items || []).map(...);   // 回包没有 items → []
ElMessage.success(`已解析 ${data.item_count} 题`);  // 97（来自 metadata）
```

→ 出现"提示 97 题、表格 0 行"的矛盾画面。

### 1.3 关掉重开就正常（真机实测）

CDP 实测（同一张卷、不重新上传，只重新打开抽屉）：


## 2. 还有一个次要缺陷：按钮数字不是"会写入的题数"

`filledCount = items.filter(i => i.answer).length` → 显示「确认写入 **97** 题」。
但 `apply_draft` 的口径是：**只填空位**；库里已有且一致的算 `kept`。

你这张卷 `current == answer` 97/97，所以真点下去的结果是：

```
已写入 0 题、保留原有 97 题
```

→ 按钮写 97、结果 0，虽然不是数据错误，但会让人以为"没写进去"。

---

## 3. 修法（两处，都很小）

### 3.1 主缺陷：让"上传"和"续草稿"回同一份数据

| 层 | 改动 |
|---|---|
| 后端（首选） | `parse` 端点改为 `draft_payload(db, draft, with_items=True)`，并回 `can_edit=True` —— 与 `/latest`、`/drafts/{id}` 完全同形 |
| 前端（兜底） | `upload()` 里若 `!data.items?.length && data.draft_id`，再调 `fetchAnswerDraft(data.draft_id)` 取一次明细（后端以后若再裁剪回包也不至于空屏） |
| 文案 | 上传成功提示改为：`已解析 97 题（与现有答案一致 97 题）` / `已解析 97 题（其中 3 题与现有答案不同）`，不再只报总数 |

### 3.2 次要缺陷：把"识别题数"与"将写入题数"分开

- 新增 `writableCount`：`answer` 非空 **且**（无 `current` **或** `current !== answer` **或** 勾了覆盖）；
- 按钮：`确认写入 ${writableCount} 题`；为 0 时**禁用**，旁边一句「97 题与现有答案一致；要覆盖请勾选下方开关」；
- 空表文案从「没有需要确认的题」改为「这份草稿没有可显示的题（请重新上传）」（区分"没有待确认"与"根本没加载"）。

## 4. 预期效果（修复后同一串操作）

| 步骤 | 修复前 | 修复后 |
|---|---|---|

| 真的有空的答案 | 上传后看不到 | 行内可编辑，按钮按实际可写数显示 |

## 6. 风险与回滚

| 风险 | 处置 |
|---|---|
| 回包变大（97 行 × 每行 ~400B ≈ 40KB） | 可接受；与 `/latest` 本来一致（抽屉打开时已经传过同样大小） |
| 前端兜底导致重复请求 | 只在 `items` 为空时补一次，且用 `draft_id` 判空 |
| 按钮禁用被误读为"坏了" | 禁用时给一句原因（"与现有答案一致，勾选覆盖可重写"） |
| 回滚 | 单提交 revert（后端 1 处 + 前端 2 处 + 2 个测试文件） |

**工期**：后端 0.2h + 前端 0.4h + 测试 0.4h + 真机复核 0.2h ≈ **1.2 小时**。

- 不做"按文件名自动匹配卷"（Q4）；
