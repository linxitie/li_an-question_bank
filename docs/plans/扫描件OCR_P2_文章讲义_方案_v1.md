## 0. 一句话结论

**能补，而且和 P1 共用同一个 sidecar（不用再装任何东西）**；真正的工作量不在 OCR 本身，而在四件配套事：
**① 段落重排**（OCR 是硬换行，直接入库会变成一堆碎行）、**② 进度回传**（一篇 24 页要 3–7 分钟，前端现在 3 分钟就判超时）、**③ 超时/页数边界**、**④ 失败语义**（哪一页失败、能不能部分成文）。

实测（本次 PoC，同一台机器同一个 sidecar）：**2 页 35.3 秒（16.5s/页）→ 3542 字 → 64 个段落**，段落可读性达标；24 页 ≈ 3.4–6.6 分钟。

## 1. 现状审计（全部实测，附代码位置）

### 1.1 扫描件现在走的哪条路

| 环节 | 位置 | 现状 |
|---|---|---|
| 上传入口 | `POST /api/materials/admin/import/upload`（`materials.py:3381`） | 管理员 / 批量上传文章 / 智能导入共用 |
| 扫描判定 | `material_parser.detect_scanned`（pdfplumber，**平均每页可提取字符 < 100** 判为扫描件） | 整份文件一刀切（混合版式按"扫描"处理） |
| 扫描分支 | `materials.py:3460-3504` | `parse_mode="async(mineru)"`、`parse_status="processing"`，后台线程调 `run_mineru` |
| OCR 引擎 | `services/mineru_material_service.py`（`MINERU_EXE=C:\mineru_env\Scripts\mineru.exe`） | **该 exe 不存在** → 直接 400「该 PDF 为扫描图片版且系统 OCR 组件未就绪」；即使装上 CPU 实测 **71.2s/页** |
| 进度 | `MaterialImportRecord` **11 列**（import_id/file_name/file_type/file_size/parse_mode/parse_status/parse_result/error_message/uploader_id/create_time/update_time） | **没有任何进度列**；只有 `parse_status` 四态 |
| 前端等待 | `src/components/admin/ArticleBatchUpload.vue:223-239` | 轮询 `status`，**最多 72 次 × 2.5s = 180 秒**，超时文案「解析超时（>3 分钟）」 |
| 前端展示 | 同上，行状态只有 `waiting/uploading/parsing/confirming/ok/duplicate/failed` | 解析中只有两个字「解析中」，**没有页数/进度/预计时间** |
| 入库 | `POST /import/{id}/confirm`（`materials.py:3573+`） | 用 `result["html"]` 落 `content`、`result["images"]` 迁移图片、`word_count` 算 read_time |

### 1.2 三个会让 P2 "做了也白做"的硬点

| # | 硬点 | 证据 | 不解决的后果 |
|---|---|---|---|
| **H1** | **前端 180s 就放弃** | `ArticleBatchUpload.vue:226`：`for (let i = 0; i < 72; i += 1)`，每次 `sleep(2500)` | 24 页扫描件 3.4–6.6 分钟 → 界面先报"超时"，后台其实还在跑 → 用户以为失败、重复上传（同 sha256 又会被 409 拦），体验最差 |
| **H2** | **没有进度可显示** | 表里无进度列；`import_status` 只回 `parse_status/elapsed_seconds/error_message`（`materials.py:3547`） | 一篇 6 分钟全程只有"解析中"，用户不知道是 10% 还是 90% |
| **H3** | **OCR 文本是硬换行** | 见 §5 PoC：一行 40±2 字，按栏宽切 | 直接 `"\n".join` 入库 → 正文是一堆碎行，阅读体验比"传不上去"更差 |

### 1.3 其它已确认的边界（读代码，非推测）

- `detect_scanned` 是**整份文件**判定：混合版式（前几页文字、后面扫描）会整份 OCR，文字页的白白 OCR 一遍（P2 接受，P4 再优化逐页判定）。
- `_migrate_images` 对 `images=[]` 安全（`result.get("images") or []`），P2 不做图片不会炸确认链路。
- `parse_result` 是 JSON 文本列，已经塞了 `_tmp / _sha256 / _seconds / validation` 等内部键（`_stash_fingerprint`），**再塞 `_ocr` 进度是同一套做法，零迁移**。
- 重复上传拦截只看 `parse_status == "consumed"`（`_IMPORT_DONE_STATUS`），所以"卡在 processing 的僵尸记录"**不会挡住重传**，但会永久占着一条状态（D6 处理）。
- 批量是**串行** `for` 循环：9 篇 × 4 分钟 ≈ 36 分钟；OCR 进程单实例，串行天然避免 CPU 打满。

## 3. 设计

### 3.1 复用 P1 的 sidecar（不新增运行环境、不新增依赖）

```python
# services/ocr_sidecar.py 已具备（P1 交付）
text, meta = read_pdf_text(path, max_pages=60, dpi=200,
                           page_timeout=60, total_timeout=1800,
                           progress=lambda done, total: ...)   # 逐页回调已存在
```

- 主进程只用 stdlib + 现有依赖；OCR 仍在 `C:\ocr-env`（287MB，仓库外）。
- 页级/总级超时、失败页号、`truncated` 标记全部复用。
- **新增执行开关**：`OCR_ENGINE=sidecar|mineru`（默认 `sidecar`），MinerU 分支原样保留 —— 万一本机将来装了 MinerU，可一键切回。

### 3.2 文本 → 段落 HTML：新模块 `services/ocr_html.py`（纯函数，可单测）

| 函数 | 职责 | 规则（可配置常量） |
|---|---|---|
| `drop_noise(lines)` | 去页眉/页脚/导流 | 正则表：`获取试卷更新`、`公众号`、`来源：`、`整理：`、`微信：`、`第 N 页`、`N/M`；（实测每页首行是同一条公众号导流） |
| `reflow(lines)` | 断行合并 + 断段 | 合并：上一行不以 `。！？；：…` 结尾且下一行不是新块起始 → 直接拼接（中文不加空格）；断段：遇到**新块起始**（`1、` `一、` `（一）` `A、` `第X章/节/条` `【`）或句末标点 |
| `to_html(paras)` | 段落 → HTML | `html.escape` 转义；空段丢弃；单段 > 1000 字按句再切；输出 `<p>…</p>` 拼接 |
| `stats(paras, seconds)` | 元信息 | `chars / paragraphs / seconds / failed_pages` |

> **为什么不用 `<br>` 或纯文本**：confirm 落的是 `content`（HTML），详情页按 HTML 渲染；用 `<p>` 才有正常段距，和 MinerU/docx 链路一致。

### 3.3 进度：零迁移（沿用 `parse_result` 内部键）

```json
// parse_result 里新增一个内部键（每 2 页或每 3 秒写一次，避免频繁写库）
"_ocr": {"done": 12, "total": 24, "phase": "ocr", "seconds": 96.5,
         "truncated": false, "failed_pages": [7]}
```

`GET /admin/import/{id}/status` 回包**加字段**（路径不变，守 R11）：

```json
{"parse_status":"processing","elapsed_seconds":96,
 "progress":{"done":12,"total":24,"percent":50,"phase":"ocr","failed_pages":[7]}}
```

### 3.4 失败语义（建议 D4=A：有成功页即成文）

| 情形 | 处理 |
|---|---|
| 全部页失败 / 0 字 | `failed`，`error_message`=「OCR 没有识别出任何文字（失败 N 页），首条：第 X 页 …」→ **不建空文章** |
| 部分页失败（≥1 页成功） | `success`，`_ocr.failed_pages=[…]`；前端成功行写「已 OCR 22/24 页（2 页未识别）」 |
| 超过 60 页 | 只识别前 60 页，`_ocr.truncated=true`；前端提示「仅识别前 60 页，后续内容请拆分上传」 |
| OCR 组件缺失 | `failed` +「OCR 运行时没装：找不到 …（见方案 §9.1）」 |

### 3.5 前端（`ArticleBatchUpload.vue`）

| 改动 | 现在 | 改后 |
|---|---|---|
| 等待上限 | 180s（72×2.5s） | **30 分钟**（720×2.5s），与后端 1800s 上限对齐 |
| 行状态 | 只有「解析中」 | 「OCR 12/24 页 · 已用 1:36」（读 `progress`） |
| 总进度 | 「x/y 处理完」 | 追加「1 篇 OCR 中 · 预计还需 22 分钟」（按已完成篇均值估算） |
| 说明文案 | 「扫描版 PDF 需要 OCR，未就绪会明确失败」 | 「扫描版 PDF 自动 OCR（约 10–20 秒/页，长文请耐心等）」 |
| 成功行 | 只有「已入库」 | 追加「已 OCR 24 页 / 31,542 字」；部分失败追加「2 页未识别」 |
| 失败行 | 后端一句话 | 保留后端具体页号文案 |

### 3.6 卡死兜底（D6=A，惰性判定）

`import_status` 里：若 `parse_status=="processing"` 且 `elapsed > 40 分钟` → 顺带置 `failed`，消息「OCR 超时中断（>40 分钟），请重试或拆分文件」。**不加启动钩子、不加迁移**。

## 5. PoC 实测（本次已做，不写业务代码）

样本：`题库/答案解析（不用打印）/2016年河南省公务员考试《公安基础知识》专业考试真题答案及解析.pdf`（17 页，扫描版），取前 2 页：

| 指标 | 实测 |
|---|---|
| 耗时 | **35.3s / 2 页 = 16.5s/页**（比 2017 那份 8.6s/页 慢一倍，版面更密） |
| 文本量 | 3542 字 |
| 段落 | **64 段**，平均 55.3 字/段 |
| 噪声行 | 2 页共丢弃 3 行（每页首行的公众号导流 + 页码） |
| 外推 | 17 页 ≈ **4.7 分钟**；24 页 ≈ 6.6 分钟；60 页 ≈ 16.5 分钟 |

重排后的真实段落（节选，未经人工修饰）：

```
[1] (31字) 2016年河南省公务员考试《公安基础知识》专业考试真题（解析）
[2] (13字) 1、本题考查公安基础知识。
[3] (71字) 社会主义法治理念是中国特色社会主义理论在法治建设上的体现。其深刻内涵可以概括为
           依法治国、执法为民、公平正义、服务大局、党的领导五大方面的内容。
[4] (89字) A项错误，依法治国是广大人民群众在党的领导下，依照宪法和法律规定，通过各种途径
           和形式管理国家事务等，逐步实现社会主义民主政治的规范化、程序化和法制化……
[7] (8字)  故正确答案为C。
```

> 已知质量边界（与 P1 同源）：错字（`着眼/耍`类）、`c项错误` 小写、**表格/双栏会按阅读顺序拆散**、公式与手写批注乱码。文章链路只存段落文本，**不做版式承诺**。

## 8. 风险与回滚

| 风险 | 评估 | 处置 |
|---|---|---|
| OCR 期间 CPU 打满拖慢其它接口 | **中** | 串行（D5=A）+ 单页超时；批量本来就是逐条 |
| 时长超预期（16.5s/页） | 中 | 上限 60 页；前端给区间「10–20 秒/页」；进度条兜住体感 |
| 错字/表格错序 → 文章内容不可信 | **中高** | 入库为**未上架**，必须人工预览后再上架；界面写明"OCR 文本请校对" |
| 卡在 processing 的僵尸记录 | 低 | D6 惰性超时置 failed |
| 大文件内存 | 低 | sidecar 逐页渲染、逐页释放；页数上限 |
| 回滚 | — | 把 `OCR_ENGINE` 设回 `mineru`（或 revert T2 提交），P1 与文字版链路完全不受影响 |
