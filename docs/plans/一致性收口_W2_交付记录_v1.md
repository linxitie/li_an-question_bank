## 1. 一句话结论

把"资料怎么进库"这条链上**四处各说各话**的口径收成一处：

| # | 原来 | 现在 |
|---|---|---|
| 1 | `POST /admin` 建资料**默认就是已上架**（模型默认 `status=1`）→ 建好即等于审批通过 | **默认未上架**（`status=0`），要上线必须显式传 `status=1` 或点「上架」 |
| 2 | `POST /admin/batch` 同病 | 同口径；**同内容跳过**并回报 `skipped_duplicates`（批量里"跳过"比"整批回滚"有用） |
| 3 | 上传只有"落未上架"一条路，想直接上架得再点一次 | 新增「**立即上架**」开关（`publish=1`）：上传即 `status=1`，且**必走 P5 联动**把卷同步成 PUBLISHED |
| 4 | `POST /admin` / 批量建**不写 `content_hash`、不去重** | 与建卡/文章入库同口径算 `content_hash`：单条同内容 **409**（回已有 id）、批量 **skip** |
| 5 | 教师**看不到未上架**资料（详情硬过滤 `status==1`，而管理端预览要管理员） | 教师（`user_type=teacher`）可看未上架详情；学生/游客仍 404；回收站（-1）谁都看不到 |

---

## 2. 为什么第 5 条要用 `user_type` 而不是 `role_level`

实测口径：`sys_user` 里 **student=0 / teacher=1 / admin=3**（DB 实测 28/1/1）。
教师与部分测试学生的 `role_level` 都是 **1**，按 level 判会把教师一起挡掉 ——
`conftest.test_user` 正是 `user_type=student, role_level=1` 的"陷阱账号"，所以这里必须看 `user_type`。

## 3. 接口变化（对外语义）

| 端点 | 变化 | 兼容性 |
|---|---|---|
| `POST /api/materials/admin` | 回包多 `status` / `duplicate` / `content_hash`；**默认 status 从 1 变 0**；同内容 409 | ⚠️ 行为变化（有意）：调用方若依赖"建完即上架"需显式传 `status=1` |
| `POST /api/materials/admin/batch` | 回包多 `skipped_duplicates`；默认 status 0 | 同上 |
| `POST /api/materials/admin/files/upload` | 新增表单字段 `publish`（默认 0）；回包多 `published` / `status` | 向后兼容（不传=旧行为"未上架"） |
| `GET /api/materials/{id}` | 教师/管理员可看 `status=0`；学生/游客规则不变 | 只放宽 staff，学生侧零变化 |

## 7. 已知边界

1. **去重只看"内容哈希"**：标题不同但正文相同的也会被判重复（这是有意的）；要强制再建一份，
   目前没有 `force` 参数 —— 需要时再加（批量场景已经是"跳过 + 回报 id"）。
2. **文章批量上传**（`ArticleBatchUpload` → `import/confirm`）那条链路的"立即上架"没做：
   它本来就固定落未上架，语义正确。
3. 教师可看未上架之后，**教师端页面还没有"未上架"标识** —— 目前只是能打开详情；
   要显示"这是待审稿"需要在教师端列表加标记（下一批）。
