# 警考雷达——招考信息模块优化设计方案 v2.0

> 文档状态：待用户审批，未实施  
> 编制日期：2026-11-11  
> 方案范围：砺安题库系统「招考信息」模块  
> 对标方案：用户提交的《警校备考系统：招考信息模块（警考雷达）设计方案》  
> 目标：从“分类公告看板”升级为“公告 + 职位库 + 资格卡 + 智能匹配”的招考雷达

---

## 0. 结论先行

用户原始方向正确：招考模块不能只停留在公告列表，而应把长公告拆成可比较的职位条件，再结合考生资格卡进行匹配。

但原方案有三处需要在实施前修正：

1. **不要新建重复的 `job_posts` / `user_profiles` 表**
   - 系统已经有 `recruitment_info`（公告）、`police_post`（公安联考岗位库）、`user_profile`（用户备考画像）。
   - 本方案应在现有模型上扩展，避免第三套招考和用户数据。

2. **公告与职位必须分层**
   - 一条公告可能包含多个职位；
   - 一个职位可能来自公告正文，也可能来自附件表格；
   - 公告状态和职位报考条件不能混在同一行。

3. **匹配结果必须可解释，不能只给红黄绿**
   - 红色不可报、黄色需核实、绿色匹配都要有具体依据；
   - “专业相近”“条件未知”不能静默判定为不可报；
   - 所有硬性条件必须保留原文证据和公告链接。

此外，当前招考数据存在一个紧急前置问题：

```text
现有招募记录：790 条
最新源站发布日期：2026-05-15
当前日期：2026-11-11
旧采集源 rszk.net 的六个分类入口均出现 HTTP 404
```

因此，P0 的第一件事不是做页面，而是**确认新的、允许采集的官方招考来源 URL**。

## 2. 产品目标与边界

### 2.1 产品目标

| 目标 | 衡量方式 |
|---|---|
| 不漏关键条件 | 公告/职位结构化字段覆盖率 ≥ 90% |
| 不误导考生 | 每条匹配结论都有条件证据和“需核实”提示 |
| 能快速筛选 | 省份、学历、专业、政治面貌、状态筛选后 1 秒内返回 |
| 能持续更新 | 每日增量采集，失败保留旧数据 |
| 能人工纠错 | 管理端可修改解析结果、重新匹配 |

### 2.2 本期边界

本期做：

- 公告分类看板保留；
- 新增“警考雷达”页面；
- 职位库与资格卡；
- 规则匹配引擎；
- LLM 公告解析；
- 管理端解析复核；
- 桌面和移动端展示。

本期不做：

- 不做报名代报、缴费、准考证等交易功能；
- 不做自动判断“政审一定通过”；
- 不做未经授权网站的大规模爬取；
- 不把 LLM 结果直接当官方结论；
- 不做实时爬取（每日增量即可）。

## 3. 总体架构

```text
官方公告来源
   ↓
采集器（列表/详情/附件）
   ↓
recruitment_info（公告）
   ↓
LLM 解析 job_parser.py
   ↓
职位条件（police_post 扩展）
   ↓
资格卡（user_profile 扩展）
   ↓
匹配引擎（纯 Python 规则）
   ↓
警考雷达 API
   ↓
PC / 移动端雷达页 + 管理端复核
```

### 3.1 分层原则

1. **公告层**：一条公告一条 `recruitment_info`。
2. **职位层**：公告下的一个岗位一条 `police_post`。
3. **条件层**：职位条件以结构化字段 + JSON 证据保存。
4. **用户层**：资格卡字段存 `user_profile`，仅本人可见。
5. **结论层**：匹配结果实时计算，不直接写成官方结论；可缓存但不作为事实源。

## 5. LLM 解析设计

### 5.1 输入

- 公告标题、正文；
- 公告附件中的 PDF/Excel 职位表；
- 来源 URL、发布单位、发布日期。

### 5.2 输出 JSON 契约

```json
{
  "announcement": {
    "title": "",
    "organization": "",
    "category": "",
    "province": "",
    "city": "",
    "registration_start": "",
    "registration_end": "",
    "exam_date": ""
  },
  "positions": [
    {
      "job_code": "",
      "job_name": "",
      "employer": "",
      "province": "",
      "city": "",
      "education_req": "",
      "major_req": "",
      "major_categories": [],
      "political_req": "",
      "fresh_grad_req": "",
      "grassroots_years": 0,
      "age_req": "",
      "gender_req": "",
      "physical_req": "",
      "other_req": "",
      "evidence": {
        "education_req": "原文片段",
        "major_req": "原文片段"
      },
      "confidence": 0
    }
  ]
}
```

### 5.3 解析规则

- 没有写要求时，输出“不限”，不得凭空补条件；
- 无法确认时输出 `unknown`，不要猜测；
- 每个硬性条件保留 `evidence` 原文；
- 附件表格优先于正文概括；
- JSON 解析失败自动重试一次，仍失败进入 `needs_review`；
- 不直接发布解析结果，先进入管理端抽检。

### 5.4 解析任务

```text
公告采集
→ parse_status=pending
→ 02:10 LLM 解析队列
→ 结构化入库
→ 管理端抽检
→ 雷达可见
```

## 6. 匹配引擎设计

### 6.1 输入

- `user_profile` 资格卡；
- `police_post` 结构化条件；
- 公告/职位状态。

### 6.2 输出

```json
{
  "level": "green|yellow|red",
  "score": 0,
  "reasons": [
    {"field": "education", "result": "pass", "message": "本科满足本科及以上"},
    {"field": "major", "result": "risk", "message": "岗位要求法学类，你为公安学类，建议核实专业目录"},
    {"field": "political", "result": "fail", "message": "岗位要求中共党员，你为共青团员"}
  ],
  "evidence": [],
  "disclaimer": "以招录单位审核为准"
}
```

### 6.3 状态定义

| 状态 | 条件 |
|---|---|
| 🟢 完美匹配 | 所有硬性条件明确满足，且无高风险未知项 |
| 🟡 风险提示 | 存在专业相近、条件未知、基层/体能等待核实项 |
| 🔴 不可报考 | 学历、政治面貌、应届身份、性别等明确硬性不符 |

### 6.4 规则优先级

```text
硬性不符（red）：学历层次不足、政治面貌不符、应届身份不符、性别限制不符
软性风险（yellow）：专业相近、基层年限不确定、体能未自评、年龄边界
明确满足（green）：全部硬性条件通过
```

### 6.5 专业匹配

- 先匹配专业全称；
- 再匹配专业大类；
- 再匹配专业目录别名；
- 无法匹配时标黄，提示查阅《专业目录》并联系招录单位；
- 不把“相似专业”直接判为通过。

### 6.6 学历匹配

```text
博士 > 硕士 > 本科 > 大专
```

岗位写“本科及以上”时，硕士/博士可以通过；岗位写“仅本科”时严格匹配。  
“全日制”“双一流”“公安院校”等特殊要求单独作为风险项。

### 6.7 结论免责声明

雷达结论只是资格预筛，不是官方资格审核。最终以招录单位审核为准。

## 9. 来源与定时任务

### 9.1 来源前置

当前 `rszk.net` 六分类入口均 404，不能继续依赖。

需要用户提供或确认：

```text
国家公务员局/国家公务员考试专题
各省人社厅/人事考试网
各省公安厅招录栏目
公安联考/选调生/三支一扶官方栏目
```

每个来源需要记录：

```text
来源名称
列表 URL
文章 URL 规律
允许采集说明
目标分类
更新频率
```

### 9.2 调度

建议：

```text
02:00  招考公告采集
02:10  LLM 解析队列
02:30  匹配预计算/缓存（可选）
```

现有 00:05 招考任务迁移到 02:00，或停用旧任务后新增新任务，避免重复采集。

### 9.3 失败保护

- 单来源失败不影响其他来源；
- 采集失败保留旧数据；
- 解析失败进入 `needs_review`，不进入雷达；
- 来源连续失败触发告警日志。

## 10. 权限、隐私与合规

- 资格卡是敏感个人信息，仅本人和管理员可读；
- 雷达结论不作为官方资格审核；
- 公告和职位保留原文链接和证据片段；
- LLM 不编造条件，未知输出 unknown；
- 采集遵守来源 robots、服务条款和引用规范；
- 不绕过登录、验证码、反爬；
- 管理员操作写入审计日志。

## 12. 验收标准

### 数据

- 每条雷达职位必须关联公告；
- 学历、专业、政治面貌等硬性字段覆盖率 ≥ 90%；
- 每条结论有至少一条原因；
- 未知条件不得伪装成“不限”。

### 匹配

- 学历、政治面貌、应届、性别等硬性规则单元测试通过；
- 专业相近必须黄灯；
- 明确不符合必须红灯；
- 任何红色/黄色均展示原因和免责声明。
