## 3. 流程（v2）

```text
管理员进入「资料批量导入」页
  → 选择/拖入多文件（≤50 个，单文件按类型限 250/50/10 MB）
  → 前端预检（格式/命名/体积/表头）→ 有问题先提示，不浪费上传时间
  → 上传（浏览器 XHR 进度 0-10%）→ 服务端流式落盘
  → 队列解析（10-70%：xlsx 行 / docx 段 / pdf 页 / 扫描件 OCR 页）
  → 结构化（70-90%）→ 预览（90%）→ 确认入库（90-100%，status=1 全员可见）
  → 学生端列表立即可见（无需任何学生端改动）
```

## 4. 你问的第二件事：统一格式 / 传输流畅性 / 数据稳定储存——现状审计与补法

> 结论：**统一格式有规划（T0，但要落成代码）；传输与存储只规划了一半，下面 7 个缺口必须补，否则"能传"会变成"传得慢、传一半断、存得不稳"。**

### 4.1 统一格式上传（有规划，待落地）

| 项 | 现状 | 本期动作 |
|---|---|---|
| 三类资源格式规范 | ✅ 已起草 `资料内容格式与分类规范_v2.md`（卡片/讲义/试卷，含 E/W 错误码） | T0.1 冻结 |
| 机检 | 🟡 只有卡片校验器（E001–E010，ROW_LIMIT=200） | T0.3 扩到三类 + 预检接口 |
| 模板 | ❌ 只有 `_模板` 目录 3 个历史 xlsx | T0.2 出 3 个正式模板 |
| 上传前预检 | ❌ 无 | T0.3 `POST /admin/import/precheck` + 前端先检后传 |

### 4.2 传输流畅性（**3 个缺口，必须补**）

| # | 缺口 | 证据 | 补法（本期） | 不做的代价 |
|---|---|---|---|---|
| **S1** | **nginx 上限 200m < 业务上限 250MB** | `deploy/nginx.conf:28`、`nginx.tls.conf:37` 都是 `client_max_body_size 200m` | 改 **300m**（两个 nginx 配置 + 文档），并加一条"两处必须同步"的注释 | 204 MB 扫描件在网关就被 413，应用层放宽也没用 |
| **S2** | **单请求上传 250 MB、无断点续传** | 前端 `material_upload.vue` 用 `fetch + FormData`，**无 progress 回调**；后端现为整读内存 | ①前端改 XHR 带 `onUploadProgress`（0–10% 段）②后端流式落盘（64 KB 块 + fsync）③失败**整文件重试**（不做分片）④40 MB 以上文件提示"请保持页面在前台" | 老师传 204 MB 中途断网 → 从 0 重来；无进度用户以为卡死 |
| **S3** | **解析队列串行，大文件会堵住小文件** | 计划里 worker 并发=1 | 分成 **2 条队列**：`fast`（xlsx/docx/文字 pdf，秒级）与 `slow`（扫描件 OCR，分钟级）；fast 优先、slow 单飞 | 一个 90 页扫描件跑 1.8 小时，后面 30 个 xlsx 全在排队 |

> 另有两条本期明确**不做**：分片/断点续传（P2）、局域网直传/对象存储直传（P2，需要前端签名与 OSS/MinIO）。

### 4.3 数据稳定储存（**4 个缺口，必须补**）

| # | 缺口 | 证据 | 补法（本期） |
|---|---|---|---|
| **D-S1** | **临时文件生命周期未定义** | `UPLOAD_TMP_DIR = uploads/materials/tmp`，无清理逻辑（全仓无 tmp 清理任务） | ①确认入库后**立即删除**原文件与中间产物；②未确认的按 **24 小时 TTL** 定时清理（启动时扫一次 + 每小时）；③清理前写审计 |
| **D-S2** | **磁盘水位未检查** | 无任何 `disk_usage` 判断 | 上传前检查剩余空间：< 5 GB 拒绝并提示；解析中间产物目录也纳入检查 |
| **D-S3** | **写盘非原子** | 现在是 `write_bytes`（整读内存后一次写） | 流式写入 `xxx.part` → `fsync` → `os.replace()` 原子改名；记录 `sha256` 用于去重与完整性校验 |
| **D-S4** | **批量入库可能长事务锁库** | 一次确认 30 个文件 × 1277 行，若单事务提交 | 每 100 条提交一次；`content_hash` 唯一约束保证重跑幂等；失败回滚到"已提交批次"的边界并记录 |

### 4.4 已就绪的部分（不用再补）

| 项 | 现状 |
|---|---|
| 文件类型/魔数校验 | `MAGIC_BYTES` 已有；扩展名白名单 `ALLOWED_DOC_EXT` |
| 存储位置 | `uploads/` 是宿主 bind mount（compose 里 `/app/uploads` → `UPLOAD_ROOT`），不在容器可写层，重启不丢 |
| 数据库 | SQLite WAL + 迁移脚本；素材入库走 `study_material` 既有表 |
| 图片 | 卡片配图走 `_safe_image_upload`（扩展名/魔数/≤5MB）；Word 内嵌图迁移到正式目录（已有 confirm 迁移逻辑，T2 补验证） |
| 去重 | `study_material.content_hash` 已存在 |
| 备份 | R8/R10：`sqlite3.backup()` API，上传不影响备份链路 |

## 8. 验收（v2 DoD）

1. 管理员一次选 **30 个 xlsx** → 总进度到 100%，入库 1277 卡，**学生端列表立刻可见**（学生端 0 改动）；
2. 一次选 **24 个文字型 PDF（1594 页）** → 页级进度递增；失败可重试；fast 队列不被 OCR 阻塞；
3. **1 个 docx（297 段）** → 文章 + 章节；内嵌图片入库后仍可访问（F6）；
4. **204 MB 扫描件**：P0 阶段返回明确"OCR 组件未就绪"（不静默失败），P1 点亮后可解析；
5. 传 260 MB 文件 → 网关与业务层都给出 413 且提示上限（S1 生效）；
6. 传 600 行 Excel → 自动拆 2 份（D17）；
7. 磁盘剩余 <5 GB → 上传前被拒绝并提示（D-S2）；
8. 服务重启 → 未完成任务续跑；临时文件 24h 后自动清理（D-S1）；
9. `gate_all 10/10`、`vitest` 全绿、`vue-tsc` 0、`vtj_version_sync --check` 69/0；三端 0 溢出、触控 ≥44px。
