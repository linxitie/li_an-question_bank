## 1. 先纠正一个语义坑（我自己第一次统计时也踩了）

`git rev-list --left-right --count main...branch` 输出的是 **`<main 独有> <branch 独有>`**：

| 概念 | 正确算法 | 我第一次的错误算法 |
|---|---|---|
| 分支是否已并入 main | `main..branch` 的提交数 **= 0**（即 ahead=0） | 用 behind=0 判断 → 会得出「全部已合并」的错误结论 |

按正确语义重算后：**31 个本地分支里只有 4 个在 main 里**，备考资料模块的 27 个功能分支**一个都没进 main**。

## 5. 建议的合并路径（**待你批准后执行**）

```powershell
# 0) 先在 main 上打备份分支 + tag（可回退，不动历史）
git branch backup/main-pre-r4 main
git tag pre-r4-merge main

# 1) 把 r4 合到模块父分支（保持 main → feat/<模块> → r2 → r3 → r4 的拓扑）
git checkout feat/Study-Material-Management
git merge --ff-only feat/Study-Material-Management-r4      # r4 包含父分支，可 FF

# 2) 再合进 main（main 是 r4 祖先，可 FF，不产生 merge commit）
git checkout main
git merge --ff-only feat/Study-Material-Management

# 3) 合后立即验证
cd backend; python scripts/gates/gate_all.py            # 期望 10/10
cd ..; npx vitest run; npx vue-tsc --noEmit

# 4) 推送（如果确实要推到远端，需你再次确认）
# git push origin main
```

**为什么用 `--ff-only`**：三条链是线性包含关系（main ⊂ 父分支 ⊂ r2 ⊂ r3 ⊂ r4），FF 合并不会产生额外 merge commit，历史最干净，也能一眼看出「模块 → main」的推进点。若你更希望留一条 `merge: 备考资料模块合入 main` 记录，把最后一步换成 `git merge --no-ff`。

| 步骤 | 命令 | 结果 |
|---|---|---|

| 备份 tag | `git tag pre-r4-merge main` | `pre-r4-merge = da218d1` |
| 祖先校验 | `git merge-base --is-ancestor main e3e2e54` / `… feat/Study-Material-Management e3e2e54` | 两条均 exit 0 → 可 fast-forward |
| 父分支推进 | `git branch -f feat/Study-Material-Management e3e2e54` | `ce19649 → e3e2e54` |

| 检出 | `git switch main` | 工作区文件零变更（main 与 r4 树相同），`git status` clean |

**为什么用 `git branch -f` 而不是 `git merge --ff-only`**：两者在「目标分支是祖先」时结果完全等价——都只是把分支指针移到同一个 commit，**不产生 merge commit、不重放提交、不改任何文件**。区别在于 `git merge` 要求先检出目标分支：本机前端 9527 / 后端 8010 正在运行，先检出 `main`（缺 385 个文件）再合并会让 dev server 经历一次「整模块消失又恢复」的窗口。先做祖先校验再移指针，得到同样的历史且工作区零抖动。**如果没有「目标为祖先」这个前提，`branch -f` 会丢失提交——所以第 3 步的校验是必需的，不能省。
