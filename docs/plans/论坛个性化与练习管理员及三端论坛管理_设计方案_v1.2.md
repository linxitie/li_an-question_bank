| # | 决策 | 结论 |

| 8 | 评论图片 | **P1 就支持，三端都允许；单条 ≥3 张自动折叠，点击展开看全部** |
| 9 | 论坛分类 | **固定分类够用**；P1 只加 `FEEDBACK`，暂不做动态分类 |
| 10 | 通知渠道 | **只做站内信** |
| 11 | 教师/管理员管理页 | 采用**手写 SFC**（`.vue` 单文件组件），不进 VTJ 设计器 |
| 12 | SLA | **首次响应 24h、解决 72h，超时升级给管理员**（已确认） |

### 名词解释

- **SLA（Service Level Agreement，服务时限）**：对「多久必须有人处理」的承诺。本方案用它约束反馈工单：超过首次响应时限标红提醒，超过解决时限升级给管理员。
- **SFC（Single File Component，单文件组件）**：普通手写的 `.vue` 文件（template + script + style 写在一起），可以直接用代码修改、不依赖 VTJ 设计器；与 `.vtj/vue/` 下由设计器管理的页面相对。

## 0. 结论先行

1. **个性化的大部分底座已经存在，缺的是「展示层」和「编辑入口」。**
   `sys_user` 已有 `nickname / signature / avatar / avatar_frame / growth_points`；论坛序列化已返回 `nickname / avatar / avatarFrame / signature`；头像上传与昵称签名编辑接口已存在。真正缺的是：统一的用户卡片、手机端昵称/签名编辑、头像框资产、评论区的结构化展示。
2. **「练习管理员」不建议新增 `user_type`，建议做「按用户授予的能力包」。**
   现有权限是**按角色**写死的（`ROLE_PERMISSIONS`），没有按用户授权的能力；新增角色会牵动登录、路由、权限三处。用 `user_capability` 授权表 + 现有 `Permission` 枚举：**教师由管理员任命**，**学生骨干由教师任命（默认本班）**，可随时撤销。
3. **教师端、管理员端论坛是「管理 + 参与」两件事，不建议复制一套论坛。**
   管理动作做独立管理页，浏览/回复复用现有论坛；否则会形成三套内容与三套审核逻辑。
4. **分类不做「动态分类表」。**
   当前分类是硬编码枚举（`EXPERIENCE/RESOURCE/DISCUSSION/FEELING/QUESTION`）。已确认：固定分类够用，P1 只加系统分类 `FEEDBACK`，**不做管理员动态增删分类**。
5. **反馈与论坛必须是两条通道、一个闭环。**
   具体题目错误走工单（可统计、可追踪）；公开讨论走论坛；论坛「问题反馈」帖可一键转工单。不要做成两套互不相通的系统。
6. **个性化文字必须坚持「存纯文本、渲染白名单」。**
   直接放开 HTML 会引入 XSS；彩色标题只允许从固定色板选 token，不允许任意 CSS。

## 2. 目标与非目标

### 2.1 目标

1. **身份个性化**：头像、头像框、昵称、签名、等级/身份徽章在论坛三端一致展示。
2. **文字发布个性化**：话题标签、@提及、emoji/表情包、可选标题色板、图片；评论同样支持。
3. **评论区多样化**：楼中楼、热度/最新排序、表情反应、楼主/教师/练习管理员徽章、作者置顶、举报。
4. **练习管理员**：可任命的受限角色。教师练习管理员处理本科目反馈与全校论坛巡版；学生骨干只处理本班反馈，**不参与论坛举报处理**。
5. **学生反馈闭环**：做题页一键报错 → 工单 → 练习管理员处理 → 学生收到通知 → 可评价。
6. **教师端论坛模块**：全校浏览/答疑、内容管理（限教师练习管理员）、本科目反馈处理、任命本班学生骨干。
7. **管理员端论坛模块**：全站内容管理、举报中心、分类/标签、用户处置、练习管理员全局管理、数据看板。
8. **三端一致**：学生端（PC/平板/手机）、教师端（PC）、管理端（PC）使用同一套数据契约。

### 2.2 非目标

- 不做即时聊天/私信（本次只做评论与通知）。
- 不做匿名发帖/匿名评论。
- 不做语音评论。
- 不做完整富文本编辑器（P5 之前只做 Markdown 子集）。
- 不做动态分类表（已确认固定分类够用）。
- 不做新的用户主角色枚举。
- 不改变 `/api/v1/...` 既有路径（R11）；只新增端点或新增可选参数。

## 3. 关键决策（请审核时重点看）

### D1 练习管理员的身份模型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 按用户授予「能力包」（`user_capability` + 现有 Permission） | 管理员可任命教师、教师可任命本班学生；可撤销；不动登录与主角色；学生骨干手机端可用 | 需要新增一张表与权限合并逻辑 | **已确认采用** |
| B. 新增 `user_type = practice_admin` | 语义直观 | 牵动登录、路由、权限、历史数据；手机端登录规则要改 | 不推荐 |
| C. 复用 `role_level = 2` | 零新表 | 等同于管理员，权限过大，违背最小权限 | 禁止 |

**已确认的落地方式**：
- 新表 `user_capability(user_id, capability_code, scope_type, scope_id, status, granted_by, granted_at, revoked_at)`。
- `capability_code='practice_admin'`；`scope_type ∈ global/subject/class`。
- **授权链**：
  - 管理员 → 任命教师为练习管理员（`scope_type=global|subject`）。
  - 教师（练习管理员）→ 任命**本班学生骨干**为练习管理员（`scope_type=class`，`scope_id=班级`）。
  - 学生骨干不能再向下授权。
  - 只有被任命的教师拥有 `feedback:handle` / `forum:moderate`；未任命的普通教师只能浏览与回复。
- 有效权限 = 角色权限 ∪ 能力包映射权限。
- 前端路由守卫增加 `meta.permissions` 判断；`permissions` 已由登录接口返回。
- 防提权：授权接口校验「授予人的 scope 必须覆盖被授予人的 scope」，且学生不能授予任何人。

### D2 论坛分类

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 固定 6 类，新增 `FEEDBACK` | 改动小；与现有前端常量一致 | 管理员不能自定义 | **已确认采用** |
| B. 动态分类表 | 运营灵活 | 要改三端、迁移历史、处理排序/停用 | **不做** |
| C. 固定类 + 管理员可加子标签 | 折中 | 仍需标签管理页 | 不做 |

### D3 教师端/管理员端论坛形态

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 独立管理页 + 复用论坛浏览/回复 | 一套内容、一套审核；管理动作集中 | 需要新增 4 个页面 | **已确认采用（手写 SFC）** |
| B. 完全独立的管理端论坛 | 权限清晰 | 两套论坛、两套评论、两套举报 | 不推荐 |
| C. 只在现有论坛塞管理按钮 | 改动小 | 教师/管理员没有工作台，效率低 | 只能作为过渡 |

### D4 个性化文字的能力边界

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 纯文本 + emoji + 表情包 + `#话题#` + `@昵称` + 固定色板标题 | 零 XSS；实现快 | 表达力有限 | **P1 采用** |
| B. Markdown 子集 + 白名单渲染 | 表达力与安全平衡 | 需要渲染器与测试 | **P3 采用** |
| C. 富文本 HTML | 最强 | XSS、审核、包体积、VTJ 兼容都差 | 禁止 |

标题颜色只存 token：`default / red / gold / blue / green / purple`，前端映射为固定 CSS 变量，**不存任意色值**。

### D5 反馈与论坛的关系

**推荐**：工单为主，论坛为公开讨论；论坛「问题反馈」分类的帖子可一键转工单，工单解决后可在帖子下自动回一条「已修复」。

### D6 通知

**推荐**：新建统一 `user_notification` 表（站内信），学生/教师/管理员共用；不继续扩展 `teacher_message`（该表是运行时裸 SQL 建的，见 `teacher.py:1808-1826`）。

### D7 图片张数与折叠

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 发帖/评论都不限张数，评论 ≥3 张折叠 | 符合用户预期；阅读体验可控 | 需要上传队列、缩略图、灯箱 | **已确认采用** |
| B. 发帖 3 张、评论 1 张 | 实现简单 | 表达受限；用户明确要求去掉 | 不采用 |
| C. 全都不限且不折叠 | 最简单 | 评论区会被图片撑爆 | 不采用 |

> 关键取舍：**业务不限制 ≠ 完全不设防**。张数放开后，风险从「数量」转移到「体积、频率、存储」。因此保留单图大小、单次上传数、每人每日配额、总附件体积四道安全阈值，但不把它们做成用户可见的「最多 N 张」。

### 3.1 设计取舍与反直觉点（brainstorm 记录）

1. **教师论坛全校可见，但反馈只按科目**：可见性与处理权是两件事。全校可见能形成答疑氛围；处理权按科目才能避免「数学老师改语文题」的误判。
2. **学生骨干不给论坛举报权**：举报处理涉及删帖/封号判断，需要更强的责任能力；学生骨干只做「本班反馈的 first responder」，权限最小化。
3. **折叠阈值定在 3 张**：1-2 张平铺不会破坏信息流；3 张开始高度明显膨胀，折叠收益最大。阈值放配置里，后续可调。
4. **不做动态分类**：分类是内容契约，三端、统计、反馈路由都依赖它；固定枚举更稳。真需要运营灵活性，优先加「标签」而不是改分类。
5. **不做新角色**：角色会牵动登录、路由、权限、历史数据；能力包只加一张表，撤销即失效。
6. **不直接上富文本**：富文本的 XSS 攻击面、审核成本、VTJ 兼容性都远高于「纯文本 + token」。先把表达力用 token 补齐，再评估 Markdown。
7. **管理页手写 SFC**：VTJ 页面受 R3 限制，改模板要设计器；管理页交互复杂、迭代频繁，手写 SFC 更快也更可控。
8. **图片不限张数但保留安全阈值**：用户要的是「不要因为张数被拦住」，不是「允许无限流量攻击」。两者可以同时满足。

## 4. 身份、权限与角色矩阵

### 4.1 新增权限码

| 权限 | 说明 | 默认授予 |
|---|---|---|
| `feedback:read` | 查看反馈工单 | 管理员、**被任命的练习管理员** |
| `feedback:handle` | 认领/回复/关闭工单 | 管理员、**被任命的练习管理员** |
| `feedback:stats` | 查看处理统计 | 管理员、**被任命的练习管理员** |
| `forum:moderate` | 置顶/加精/关闭评论/隐藏 | 管理员、**被任命的教师练习管理员**（全校） |
| `forum:report_handle` | 处理举报 | 管理员、被任命的教师练习管理员 |
| `practice_admin:grant_teacher` | 任命教师为练习管理员 | 管理员 |
| `practice_admin:grant_student` | 任命本班学生骨干 | 被任命的教师练习管理员 |
| `forum:category_manage` | 分类管理 | 不做（已确认固定分类） |

> 现有 `forum:manage` 保留，作为 `forum:moderate` 的兼容别名，避免改历史配置。
> **未任命的普通教师**只有浏览与回复权限，没有工单处理与内容管理权限。

### 4.2 能力包与范围

| 授予人 | 被授予人 | 默认 scope | 可授予范围 |
|---|---|---|---|
| 管理员 | 教师 | **`subject`（按科目）** | 一个或多个 `subject`；不建议直接给 global |
| 教师练习管理员 | 本班学生骨干 | `class`（本班学生反馈） | 仅本班 `class` |
| 学生骨干练习管理员 | — | — | **不能再授予任何人** |

> 教师练习管理员如果负责多个科目，`user_capability` 允许多行（每个科目一行），不是一条记录塞多个 ID。
> 论坛浏览/回复仍为全校（见决策 3）；**只有反馈处理按科目限制**。

**边界（硬约束）**：
- 不能改题库、不能改用户资料、不能发金币、不能看完整手机号/身份证。
- 不能物理删除，只能隐藏/软删除。

## 5. 论坛个性化设计

### 5.1 头像与身份展示

**目标**：三端在任何出现用户的地方，展示同一套身份信息，而不是「有时首字、有时图标、有时没有」。

**统一组件 `UserBadge`（列表/评论用）**
- 结构：头像（含头像框）→ 昵称 → 身份徽章 → 等级。
- 徽章来源（按优先级，最多显示 2 个）：
  1. 楼主（当前帖子作者）
  2. 教师 / 练习管理员 / 管理员（来自 `userType` + 能力包）
  3. 等级（`growth_points` 映射 L1-L10）
  4. 活跃/成就徽章（复用 `BadgeTask`/`UserAchievement`，P5）
- 头像回退：真实头像 → `avatarInitial`（中文优先、纯数字→「友」）→ 渐变底色。

**统一组件 `UserCard`（点击头像/昵称弹出）**
- 大头像 + 头像框 + 昵称 + 签名 + 等级 + 学校/班级（可选）+ 发帖数/获赞数 + 「Ta 的帖子」入口。
- PC/平板用弹窗，手机用底部抽屉。
- 签名最多 2 行，超出省略。

**头像框**
- `avatar_frame` 字段已存在，商城发放逻辑已有（`deliverable_service.py:61-68`）。
- 需要补：头像框资产目录（`public/frames/*.png` 或 CSS 边框）+ 前端映射表 `frame_code -> 样式`。
- 头像框只做装饰，不影响权限与等级。

**头像上传增强**
- 现有：≤2MB、扩展名白名单。
- 增加：最小 128×128、前端 1:1 裁剪、服务端重编码去 EXIF、旧头像保留 7 天后由调度器清理。
- 头像审核：不做全量机审；提供「举报头像」入口，管理员可下架并回退默认头像。

**昵称/签名**
- PC/平板已有编辑入口；**手机端补齐**（`mobile_profile.vue` 增加昵称/签名编辑，复用 `/api/auth/profile`）。
- 昵称 2-20 字、签名 ≤60 字，均走敏感词；签名禁止 URL、手机号、微信号。
- 昵称不做全局唯一（避免抢注），但禁止与官方身份同名（如「管理员」）。

### 5.2 个性化文字发布

**发帖输入（P1）**
- 标题：≤200；可选 `title_color` token（默认/红/金/蓝/绿/紫）。
- 正文：≤10000；支持：
  - emoji（Unicode）
  - 自定义表情包 `[[sticker:url]]`（已有）
  - 话题 `#话题#` → 解析写入 `tags`
  - @提及 `@昵称` → 写入 `forum_mention` 并通知
  - 图片：**不限制张数**（新增 `/api/media/image`）
- 发布预览：显示渲染后的效果（表情包、话题、@、图片）。

**图片策略（已确认）**
- **业务层不限制张数**：发帖、评论都不再设置「最多 3 张 / 1 张」的业务上限。
- **安全阈值保留**（不是业务限制，是防滥用）：
  - 单张图片 ≤5MB；仅 jpg/jpeg/png/gif/webp；服务端重编码去 EXIF。
  - 单次上传请求 ≤20 张（超过分批上传，前端自动拆分）。
  - 同一用户每分钟 ≤30 张、每天 ≤500 张；超出返回 429。
  - 单帖/单评论总附件体积 ≤200MB（防止误传超大文件）。
- 超过阈值时给出明确提示，不静默失败。

**发帖图片展示**
- 1 张：大图；2-4 张：两列；5-9 张：三列九宫格。
- 超过 9 张：先展示前 9 张，第 9 张覆盖「+N」，点击进入图集/灯箱查看全部。
- 这是**展示折叠**，不是上传限制。

**评论输入（P1）**
- 与发帖同一套 token 语法；≤2000 字；图片不限制张数。
- 支持「回复 @某人」，插入 `reply_to_user_id`。
- **评论图片折叠规则（已确认）**：
  - 单条评论图片 **≥3 张** 时进入折叠态：
    - 折叠态：只显示首张缩略图 + 「共 N 张」角标；
    - 点击缩略图或角标 → 展开为三列网格；再点单张 → 灯箱全屏；
    - 折叠/展开状态只影响当前浏览者，不写回数据库。
  - 1-2 张：直接平铺，不折叠。
  - 三端（PC/平板/手机）使用同一规则与同一组件。

**渲染规则（安全核心）**
- 数据库只存纯文本 + 受控 token，**不存 HTML**。
- 前端用 `ForumContent` 统一渲染：
  1. 先转义 HTML；
  2. 再替换 `[[sticker:...]]` 为白名单域内的图片；
  3. 再解析 `@昵称` 为站内链接；
  4. 再解析 `#话题#` 为可点击 chip；
  5. 图片走白名单 URL。
- 标题颜色：只接受 token，不接受 `#fff`/`rgb()`/`style`。

**编辑与删除**
- 作者可在发帖 30 分钟内编辑；编辑后显示「已编辑」+ 时间。
- 删除为软删除（`status=DELETED`），前台显示「该内容已删除」占位。
- 管理员的隐藏为 `status=BLOCKED`，前台不显示，作者可见「已被管理员隐藏」。

### 5.3 评论区多样化

**结构层（P1）**
- 真正渲染两层楼中楼（数据层已有 `parent_comment_id`）。
- 父评论删除时子评论保留，显示「原评论已删除」。
- 评论分页：默认 20 条/页；热门排序下取前 50 条计算。

**排序层（P1）**
- 默认「热度」：`like*2 + reply*3 + 时间衰减`。
- 可切换「最新」。
- 楼主评论、教师/练习管理员回复优先展示并打标。

**表达层（P1）**
- 评论支持 emoji、表情包、@、图片（**P1 就支持，三端都允许**）。
- 评论图片 ≥3 张自动折叠，点击展开看全部（见 5.2）。

- 评论可被楼主/教师/管理员「置顶」（每条帖子最多 3 条）。

**身份层（P2）**

- 「楼主」「教师」「练习管理员」「管理员」由服务端计算并返回，前端不猜。

**审核层（P3）**

- 管理员/练习管理员可隐藏单条评论。

### 6.1 学生反馈入口

| 入口 | 位置 | 自动带入 |
|---|---|---|
| 做题页「报错」 | 题目卡片底部 / 解析区 | `question_id`、当前选项、`practice_record_id` |
| 练习记录「反馈这次练习」 | 练习记录详情 | `practice_record_id`、题目列表 |

| 我的-意见反馈 | 现有页面 | 无（通用反馈） |

**表单字段**
- 类型：题目内容错误 / 答案错误 / 解析错误 / 功能异常 / 其他
- 描述：≤500 字
- 图片：≤5 张（反馈是工单凭证，保留上限便于处理；论坛发帖/评论不限制张数），单张 ≤5MB
- 关联：题目 ID、练习记录 ID（自动，前端可隐藏）
- 联系方式：默认取账号，不额外收集

**提交后**
- 返回 `ticket_no`（如 `FB20261023-0001`）。
- 学生可在「我的反馈」看到状态时间线与管理员回复。
- 可追加回复、可对结果评价（解决/未解决）。

### 6.2 状态机与 SLA

```
pending → claimed → replied → resolved
                  ↘ rejected
pending/claimed → merged（重复反馈合并）
```

- 认领：同一工单只能一个处理人；`claimed` 用条件更新防并发。
- **SLA（服务时限）**：指「多久必须有人处理」的承诺。本方案默认：
  - **首次响应 ≤ 24 小时**：学生提交后 24h 内必须有人认领或回复，否则工单标红并提醒练习管理员。
  - **解决 ≤ 72 小时**：从提交到 `resolved/rejected` 不超过 72h；超时自动升级给管理员。
  - 所有时限可按类型配置（如「功能异常」可放宽到 7 天）。
- 重复合并：同一 `question_id` + 同类型，7 天内 ≥3 条 → 合并为一条主工单，其余标记 `merged` 并关联主工单。
- 通知：状态变化推送站内信；学生提交后通知范围内练习管理员。

### 6.3 练习管理员工作台

**PC（教师练习管理员主入口）**
- `/practice-admin/feedback`：待处理 / 我处理的 / 已解决 / 已驳回；按类型、科目、时间筛选。
- 工单详情：题目原文 + 学生描述 + 截图 + 快捷操作（认领/回复/转交/解决/驳回）。
- 回复模板：常用 5 条（已收到/已复现/已修复/请补充截图/非题目问题）。
- `/practice-admin/forum`：举报队列 + 隐藏/忽略 + 跳转原帖。
- `/practice-admin/stats`：响应时长、解决率、高频错题。

**手机端（轻量，学生骨干练习管理员主入口）**
- `/mobile/practice-admin`：待处理列表 + 快捷回复；**不含论坛举报处理**；不做批量与复杂筛选。
- 入口在「我的」页，仅 `hasPermission('feedback:handle')` 可见。
- 因为登录限制只允许 student 进入手机端，**学生骨干练习管理员可在手机处理本班反馈**；教师练习管理员只能在 PC 处理（如需教师手机端，需单独调整登录规则，不在本方案内）。

### 6.4 与论坛的打通

- 新增论坛分类 `FEEDBACK`（问题反馈）。
- 发帖时可关联题目；帖子详情显示「关联题目」卡片。
- 练习管理员/管理员可「转为工单」；工单解决后自动在帖子下回复「已修复」并通知作者。
- 举报帖子与反馈工单分开统计，但在同一个工作台可切换。

## 11. 安全、性能、运维

### 11.1 安全

| 风险 | 处置 |
|---|---|
| XSS | 只存纯文本 + token；渲染先转义；白名单 URL；禁止任意 HTML |
| 越权 | 所有管理接口用 `require_permission`；范围过滤在 SQL 层；不信任前端 |
| 权限提升 | 能力包只能由 `practice_admin:grant` 授予；授予/撤销写审计 |
| 头像/图片 | MIME 白名单、大小限制、随机文件名、重编码去 EXIF、禁止 svg |
| 刷屏 | 发帖 60 秒 1 条、评论 10 秒 3 条、反馈 10 分钟 5 条 |
| 举报滥用 | 每人每目标只能举报一次；恶意举报记录在案 |
| 隐私 | 练习管理员列表脱敏手机号；日志不记录正文全文 |
| 软删除 | 所有管理删除为软删除 + 审计，不做物理删除 |

### 11.2 性能

- 列表批量查用户（现有 `user_map` 模式），避免 N+1。
- 评论/帖子计数冗余字段已有（`comment_count`/`like_count`），写入时更新。
- 热度排序先用 `last_activity_time` + 计数，避免每次全表计算。
- 图片统一走 `/uploads`，前端懒加载 + 固定宽高防抖动。
- 通知列表分页 + 未读数缓存。

### 11.3 运维

- 所有新增表纳入 `create_all`；新列纳入 `main.py` 自动迁移清单。
- 迁移前 `sqlite3.backup()`；回滚同时删 `-wal`/`-shm`（R10）。
- 新增权限码写进 `admin_permissions.vue` 的可配置项。
- 管理动作统一 `SysOperationLog`，module 用 `forum`/`feedback`。
- 提供 `backend/scripts/verify/verify_forum_permissions.py`（P0）校验权限矩阵。

## 12. 分期路线与验收

### P0 底座（1 周）

- `user_capability`、`feedback` 扩展、`forum_report`、`user_notification`、`forum_mention`。
- 权限码与 `require_permission`；能力包合并逻辑。

- 测试：权限矩阵、越权、工单状态流转、举报唯一约束。

**验收**：`pytest` 新增用例全绿；`/api/auth/login` 返回的 permissions 含能力包权限；无权限用户访问管理接口返回 403。

### P1 学生个性化 + 反馈入口（1-2 周）

- `UserBadge`/`UserCard` 三端接入。
- 手机昵称/签名编辑。
- 发帖/评论：话题、@、emoji、表情包、**标题颜色色板**、预览。
- **图片：发帖不限张数；评论不限张数；单条评论 ≥3 张自动折叠，可点击展开（三端统一）**。
- 图片安全阈值：单张 ≤5MB、单次 ≤20 张、频率限制；服务端重编码去 EXIF。
- 做题页「报错」入口 + 反馈表单扩展 + 我的工单。
- 论坛分类加 `FEEDBACK`。

**验收**：三端身份展示一致；发帖含话题/@/表情/标题颜色可正确渲染；三端都能发多图；评论 3 张及以上折叠、展开后看全部；报错工单可在「我的反馈」看到状态。

### P2 评论区 + 练习管理员工作台（1-2 周）

- 楼中楼、排序、置顶、身份徽章、举报（图片评论已在 P1 完成）。
- 练习管理员 PC/手机工作台、认领/回复/解决/驳回、统计。
- 通知中心。

**验收**：学生提交 → 练习管理员认领 → 回复 → 学生收到通知 → 评价；举报可处理。

### P3 教师端论坛模块（1 周）

- 教师论坛（全校浏览/回复）、答疑、内容管理、反馈处理、任命本班学生骨干。

**验收**：全部教师可浏览全校论坛；只有被任命的教师练习管理员能执行管理动作；越权返回 403。

### P4 管理员端论坛模块（1-2 周）

## 13. 风险与回滚

| 风险 | 影响 | 处置 |
|---|---|---|
| `.vtj` 模板改动受 R3 限制 | 学生端 UI 可能卡住 | 新管理页走手写 SFC；学生端模板改动需授权 + 备份 + 逐端验证 |

- 代码：按分期提交，单期可 `git revert`。
- 数据：迁移前 `sqlite3.backup()`；新表可直接删除，新列保留（可空不影响旧代码）。
- 前端：`.vtj` 模板备份文件 `*.bak_<日期>` 可直接覆盖。

## 15. 交付顺序建议

```text
P0 权限与数据底座
  → P1 学生个性化 + 反馈入口
  → P2 评论区 + 练习管理员工作台
  → P3 教师端论坛
  → P4 管理员端论坛
  → P5 增强
```

理由：P0 是所有端的共同依赖；P1 能最快让学生感知到「头像/文字/反馈」的变化；P2 打通闭环；P3/P4 是管理能力，放在闭环跑通之后，避免先建空壳后台。
