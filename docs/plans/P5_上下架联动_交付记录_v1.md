## 3. 关键实现（行为契约）

```python
# exam/contract.py
sync_paper_visibility(db, paper_code, *, visible) -> {
    "paper_id", "paper_code", "before", "after", "changed",
    "skipped": None | "empty_code" | "no_paper" | "ended" | "not_flippable",
}
# visible=True  : DRAFT/PENDING/APPROVED → PUBLISHED（首次置 publish_time）
# visible=False : PUBLISHED → DRAFT（PENDING/APPROVED 也回 DRAFT）
# ENDED         : 一律不改写
```

```python
# services/material_paper_sync.py
sync_material(db, material) -> 契约结果 + {"enabled", "note"}
# visible = (material.status == 1) or 同编号还有其它 status=1 的资料
# note    = "可作答卷 GZ-2019-BJ-T PUBLISHED→DRAFT" / "无可作答卷（…）" / "可作答卷已在回收站，未改动"
```

**事务边界**：`m.status = st` → `sync_material()` → `_audit()` → `db.commit()`。
半成功不可能：联动抛异常时整条请求回滚（T9 用 monkeypatch 验证）。

**回包示例**（`PUT /api/materials/admin/125/status {status:0}`，线上实测）：

```json
{"ok": true, "paper_sync": {"paper_id": 2, "paper_code": "GZ-2019-BJ-T",
 "before": "PUBLISHED", "after": "DRAFT", "changed": true, "skipped": null}}
```

## 4. 与方案的偏差（3 条，全部如实记录）

| # | 偏差 | 原因 | 影响 |
|---|---|---|---|
| 1 | **D-P5-5「入库即上架」没有代码路径**：`import_confirm` 的 `status=(1 if publish else 0)` 位于 **card 分支**（文档类分支只允许 `article`/`lecture`，`materials.py:2732-2734`），试卷资料目前只能由「上传（status=0）」「补录（status=1 且卷必然已发布）」产生 | 方案写 D-P5-5 时假设 import_confirm 能建试卷资料，实测不能 | 少一个触发点；**不减少覆盖面**（card 无卷，补录天然一致）。若将来导入支持试卷，需在 `import_confirm` 里补一次 `sync_material` |
| 2 | `DELETE /admin/batch` 从 **1 条 bulk UPDATE** 改为 **逐条置 -1** | bulk update 用 `synchronize_session=False` 后会话里 status 仍是旧值，会让"同编号是否还有上架资料"判错、该下架的卷没下架 | 语义与返回 `deleted` 完全不变；仅多几条 UPDATE（勾选条数量级很小） |
| 3 | 上架会把 `PENDING/APPROVED` 直接推成 `PUBLISHED` | D-P5-2 你的选择（"上架即终审"） | 审批页仍存在（P0–P4 未做）时，两条入口语义重叠；已在遗留项记 R1 |
