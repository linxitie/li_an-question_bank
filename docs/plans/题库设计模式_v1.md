## 0 一页速览

**一句话**：用「角色锁 + 任务卡 + 上下文清单 + Token 账本 + 证据门禁」五件套，把题库模块从“想到哪写到哪”变成“可预算、可验证、可回滚”的流水线。

```
用户目标
  └─ 任务卡（范围/非目标/预算/验收命令）
       └─ 角色锁（ARCH/PM/FE/BE/API/SEC/QA，一次一个）
            └─ 上下文清单（path:lines + 用途，S 级 ≤3 文件）
                 └─ CTC 11 问（答完才动代码）
                      └─ 四张契约（数据/API/前端/事件）
                           └─ 实现（一逻辑一提交）
                                └─ 门禁证据（命令+输出+退出码）
                                     └─ 归档 + 账本（有效率 ≥95%）
```

**三条铁律**
1. **角色锁**：一个回合只做一个角色；跨角色必须交接卡。
2. **上下文清单**：读取先声明路径、行段、用途；禁止整树/整文回显。
3. **证据门禁**：没跑命令，不得说“完成/通过”。

**Token 目标的诚实定义**：100% = **零重复、零返工、零越界**的纪律目标；可审计的验收线是**有效率 ≥95%**（其余 3–5% 是门禁输出、安全审查、格式约束的不可消除开销）。任何“字面 100%”的承诺都不可核对。

## 1 问题与设计目标

| 现状痛点 | 本模式对策 |
|---|---|
| 项目大（75 页 / 343 端点 / 72 模型 / 1965 行 models），AI 容易“先读全项目” | 上下文清单 + 分级预算 + 基线复用 |
| 角色混用：前端改后端、安全靠事后 | 8 角色卡 + 角色锁 + 安全否决权 |
| 方案与实现脱节，返工多 | 四张契约先行 + CTC 11 问 |
| “完成”无证据，反复对话浪费 | 证据三件套 + QA 门禁 |
| 文档数字与代码漂移（92/38/71/`/api/v1` 等） | 实测基线 + 复测脚本 + 测量日期 |
| 分支拓扑与 Git 引用冲突 | 父分支放远端，本地只留子分支 |
| 大资产（题库 497MB / 静态图 46MB） | 只读元数据，禁止入上下文 |

**设计目标**（可验收）：
1. 任意模块任务在 5 分钟内完成“定级 + 选角色 + 出任务卡”。
2. 任意交付都有命令级证据，返工率可统计。
3. 单任务 Token 有效率 ≥95%，超预算 80% 强制重估。
4. 新模块设计包 14 节齐全，结构体检脚本 PASS。

## 2 系统重点分析（实测 2026-10-27）

> 完整数据与复测命令见 `.agents/skills/li-an-design-mode/references/system-baseline.md`。

### 2.1 工具盘点

| 层 | 现状 | 结论 |
|---|---|---|
| MCP | 仅 `vtj`（19 工具 / 3 资源，stdio），页面读写有 `dryRun` 与 `RAW_PAGE_PROTECTED` 护栏 | 前端建模够用；后端/测试**没有** MCP，不要假装有 |
| Skills | 39 个目录（38 个上游通用技能 + 本模式），lock 记录来源与哈希 | 通用工程能力强；项目角色/流程 skill 原缺，本模式补齐 |
| 门禁 | 9 层本地门禁（L0→L6）+ `check_secrets`/`check_module_boundary`，入口 `backend/scripts/gates/gate_all.py` | 强，但**只能本地跑** |
| CI | 仅 `.github/workflows/vtj-version-check.yml` | CI 不跑测试/门禁，本地门禁是唯一闸门 |
| 基线资产 | `api_surface.json`(343)、`model_map.json`、`coupling.json`、`table_usage.json`、`db_tables.json` | 设计前先查，禁止重新盘点 |
| 测试 | 41 个 `test_*.py`，conftest 用内存 SQLite + TestClient | 可安全跑接口测试，不碰生产库 |

### 2.2 六个结论

1. **MCP 偏科**：`vtj` 覆盖前端建模；后端与测试用 pytest + 门禁替代即可，**暂不新建 MCP**（W3 再按实测需求评估）。
2. **门禁强、CI 弱**：本地 `gate_all.py --quick` 是合并前唯一硬闸门，必须贴输出；CI 扩展属 W2 议题。
3. **基线资产强、文档数字弱**：343 端点基线可靠；但 `AGENTS.md` 的 92 处路由引用、38 路由、71 模型、`/api/v1`、292MB DB、4.3GB 静态图均与实测不符（实测 49/39/72、`/api/*`、8.5MB、46MB）。**以基线文件与实测为准。**
4. **角色未固化**：方案提到的 `li-an-workflow`、`completion-verifier`、`scope-guard`、`context-minimal-loader`、`plan-control` 在本仓库不存在；本模式用角色卡 + 任务卡 + 账本 + 门禁落地同样约束。
5. **分支拓扑受 Git 限制**：`feat/x` 与 `feat/x/y` 不能在本共存（`cannot lock ref`），模块父分支放远端。
6. **数据资产不在当前 checkout**：`backend/data/*.bak*` 不存在，DB/静态图/语料远小于文档体量；**先确认再设计**，禁止按文档体量估算。

| 步 | 动作 | 产出 | 通过条件 |

### CTC 11 问（逐条作答，每问 ≤1 行）

1. 为什么这样写？收益？
2. 有无 SQL 注入 / XSS / 越权？
3. 运维是否方便（日志、回滚、配置）？
4. 文件位置是否符合分层？
5. 前端能否正常显示（状态、响应式、三端）？
6. 字段是否完善？是否需迁移？
7. 路由是否已在 `main.py` 注册？
8. 前端调用是否闭环（请求→状态→渲染→错误）？
9. VTJ 语法是否符合 0.16.35 规范？
10. 是否与既有算法/识别机制冲突（禁止重复造轮子）？
11. 是否有开源实现可复用/借鉴？

## 6 Token 零浪费协议

### 6.1 定义

```
有效率 = 1 − (返工 + 浪费) / 总消耗
```

- **目标 100%**：零重读、零返工、零越界、零冗余。
- **验收 ≥95%**：差额是不可消除的验证/安全/格式开销；低于 95% 必须写明原因。
- 账本五类：必读 / 实现 / 验证 / 返工 / 浪费；返工如实计浪费。

### 6.2 分级预算

| 级别 | 文件数 | 读入上限 | 总预算 | 提交数 |
|---|---|---|---|---|
| S | ≤3 | 8k | 20k | 1 |
| M | 4–8 | 25k | 60k | ≤4 |
| L | 9–20 | 60k | 150k | ≤10 |
| XL | >20 | — | — | 禁止直接开工，先拆 |

### 6.3 十条纪律

1. 一次读取：同一 `path:lines` 不重复读，引用用行号。
2. 三文件上限：超了先拆任务。
3. 不整树：禁止全目录递归；glob/grep 定位。
4. 不整文回显：用 diff/片段，不复述。
5. grep 先行：先搜符号再读段。
6. 大资产只读元数据：`题库/`、`static/`、`*.db` 只取数量/大小/抽样。
7. 输出预算：方案 ≤120 行；结论 ≤3 条 + 证据；日志只留末 10 行。
8. 失败即停：门禁红先修，不带病提交。
9. 复用基线：先查 `api_surface.json`/`model_map.json`/本模式 baseline。
10. 阶段检查点：每阶段 10 行摘要，替代回读历史。

### 6.4 模式路由（DeepInfer / 云端 / PTC）

| 模式 | 场景 | 路由 | 记录字段 |
|---|---|---|---|
| 标准 | 常规 CRUD、重构、文档、测试生成 | 本地 DeepInfer 优先，云端兜底 | `mode/provider/model/fallback_reason` |
| 创造 | 新架构、复杂算法（组卷、判题） | 云端强模型；产出归档 `docs/plans/` 或 `docs/superpowers/specs/` | 同上 + 归档路径 |
| PTC | 大语料清洗、题图索引、压测 | 本地沙箱计算；只回传结果 | `mode=PTC` + 输入路径 + 输出摘要 |

约束：**不把大文件读入模型上下文**；DeepInfer 的端点/模型名以实际配置为准，运行卡必须登记 provider/model，禁止硬编码假设。

### 6.5 子代理经济学

- 派：独立读取 ≥2 区域、广度搜索、对抗审查。
- 不派：单文件小改、结论已明确、交接成本 > 工作本身。
- 契约：输入 ≤300 token，输出 ≤400 token（结论 + 证据 + 未决项）。

## 7 分支与交付协议

### 7.1 拓扑

```
main
 └── feat/<模块名>                 ← 模块域（远端；只收子分支）
      └── feat/<模块名>/<子任务>    ← 本次工作分支（本地）
```

### 7.2 Git 硬限制（实测 git 2.45.1）

`feat/x` 与 `feat/x/y` 不能同时存在于本地，报 `cannot lock ref ... exists`（packed-refs 也不行）。因此：

- 模块父分支放**远端**（`origin/feat/<模块>`），本地只保留子分支。
- 必须本地并存时，子分支用 `feat/<模块>--<子任务>` 兜底。
- 不切换 reftable 引用格式（实验性）。

### 7.3 命令

```powershell
# 开工（父分支在远端）
git fetch origin
git switch -c feat/<模块>/<子任务> origin/feat/<模块>

# 同步父分支
git fetch origin
git rebase origin/feat/<模块>

# 提交（显式路径，禁止 add -A）
git add -- <file1> <file2>
git commit -m "feat: <简述>" -m "<为什么 + 证据 + 归档>"

# 合并回模块域（PR base 必须是 feat/<模块>）
git switch feat/<模块>; git merge --no-ff feat/<模块>/<子任务>
```

### 7.4 提交与合并规则

- 一个逻辑变更一个提交；不混合无关改动。
- 信息格式：`feat|fix|test|refactor: <简述>`；纯文档用 `docs:`（仓库既有约定）。
- PR 目标只能是 `feat/<模块>`，**禁止对 main**；合并顺序 子 → 模块域 → main，不跳层。
- 脏工作区：不 `add -A`、不 `stash` 他人改动、不 `checkout -- .`、不 `clean -fd`。

### 8.3 四张契约（缺一不动工）

- **数据**：表/字段/索引/迁移/回滚；备份必须 `sqlite3.backup()`。
- **API**：与 `api_surface.json` 比对，仅新增或零变更；实际前缀是 `/api/...`，不是 `/api/v1/...`。
- **前端**：路由/页面 id/角色×设备/三态；只改 `<script>`。
- **事件**：事件名/payload/触发/消费/幂等/兜底。

### 8.4 评审门

`ARCH → API → SEC → QA → LEAD`，逐门签署；SEC 高危一票否决；QA 证据缺一不放行。
