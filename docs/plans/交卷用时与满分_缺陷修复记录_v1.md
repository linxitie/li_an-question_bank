# 交卷「用时 0 秒」与「满分 100 但 97 题」· 缺陷修复记录 v1

> 触发：用户 2026-11-09 交卷第 4 套卷（2016 江西 97 题）后，结果页显示 **用时 0秒 / 0 / 100 / 正确 0 · 错误 97**，问"为什么用时为 0 秒，是缺陷吗"
> 结论：**两个是真缺陷（已修）**，第三个（0 分）是**真实结果**，不是缺陷。

## 1. 三件事分开看

| 现象 | 是不是缺陷 | 结论 |
|---|---|---|
| 用时 **0 秒** | ✅ **是缺陷** | 老提交端点把"分钟数"写进了按"秒"解释的列 |
| 满分显示 **/100** 而卷只有 97 题 | ✅ **是缺陷** | `exam_paper.total_score` 没跟着题量/分值同步 |
| 得分 0、正确 0 / 错误 97 | ❌ **不是** | 那次只答了 2 题（第 1 题答 B 正确 D、第 2 题答 A 正确 C），其余 95 题空着；空=错，所以 0 分是真实结果 |

## 2. 缺陷 1：`duration_used` 单位错位（分钟当秒）

**根因**（`app/api/v1/exam/exams.py`，老端点 `POST /api/exams/{record_id}/submit`）：

```python
time_elapsed = (now - exam_record.start_time).total_seconds() / 60   # 分钟
...
exam_record.duration_used = int(time_elapsed)                        # 写进"秒"列
```

而结果页 `formatTime(s)` 是按**秒**拆时/分/秒的：`h=floor(s/3600)…`。
于是：

- 9.3 秒交卷 → 9.3/60 = 0.155 分钟 → `int()` = **0** → 页面「0 秒」；
- 90 分钟的卷 → 记成 **90**，页面显示「1分30秒」（少算 60 倍）。

> 另一条路（`ExamService.submit_exam`）一直是对的（写 `total_seconds()`），
> 只有答题卡页走的老端点错 —— 两条链路两套口径。

**修法**：

```python
elapsed_seconds      = (now - start).total_seconds()      # 落库用（秒）
time_elapsed_minutes = elapsed_seconds / 60               # 超时判定用（与 paper.duration 同单位）
...
exam_record.duration_used = int(max(0, elapsed_seconds))
```

超时/迟交判定仍用分钟（`paper.duration` 就是分钟），语义不变。

**回归用例**（`tests/test_exam_start_submit_regression.py`）：

- `test_submit_records_duration_in_seconds`：开考时间拨到 90 秒前 → 落库 88–120（秒），不是 1、不是 0；
- `test_submit_short_attempt_is_not_zero_seconds`：12 秒前开考 → 落库 10–60，**不再是 0**。

## 3. 缺陷 2：卷满分与题量/分值不一致（97 题却写 100 分）

**根因**：导题入库时只重算 `question_count`，没有同步 `total_score`。
`total_score` 是结果页/成绩单的分母（"得分 X / 满分 Y"），
97 题 × 1 分（上限 97）配满分 100 → 学生看到「0 / 100」，像是被扣了 3 分。

**修法**（`app/services/paper_ingest/service.py` 新增 `sync_total_score`，确认入库时调用）：

```python
total = sum(question_bank.score)  # 与"实际打分用哪一列"同源
if total > 0: paper.total_score = total
```

**为什么取 `question_bank.score` 而不是 `paper_question_relation.question_score`**：
交卷打分用的是 `question.score`；关系表里的分值在历史导入里是**残值**
（实测 #2/#3 的关系表写着每题 5 分 = 500，而题库每题 1 分、卷满分 100）。
我第一次按关系表求和，把 #2/#3 的满分改成了 500 —— 当场发现并回滚重算，
现在以"真正参与打分的那一列"为准。

**数据修正**（`_run/fix_duration_and_score.py`，带备份与守卫）：

```
记录 #1: duration_used 0 → 9 秒（按 end-start 回填）
卷 #2 2019北京: 满分 500 → 100.0（恢复；先被我误改）
卷 #3 2017江苏: 满分 500 → 100.0（同上）
卷 #4 2024国考: 满分 100 已一致，不动
卷 #5 2016江西: 满分 100 → 97.0
integrity: ok
```

## 8. 追加（2026-11-09 晚，你的两条指示）

### 8.1 关系表残值一次性归一

**问题**：#2（2019 北京）、#3（2017 江苏）的 `paper_question_relation.question_score` 写着 **5.0**，
而 `question_bank.score` 是 **1.0**。满分已改成按题库求和（100），关系表却还是 5×100=500 的口径。
虽然当前打分只读 `question_bank.score`，但两张表口径不一致，任何一处将来读关系表都会重新踩坑
（我当天就是这样把 #2/#3 的满分误算成 500 的）。

**做法**（`_run/normalize_relation_score.py`，先备份、只改不一致行、改前打印预览）：

1. `sqlite3.backup()` 备份 → `backend/data/question_bank.db.bak_pre_norm_relation_score_20261109_184333`；
2. 以 `question_bank.score` 为权威值，逐卷比对 `paper_question_relation.question_score`；
3. 只 `UPDATE` 不一致的行，逐卷打印改了多少行；
4. 复核：`total_score` 是否仍等于题库求和、剩余不一致行数、`integrity_check`。

**结果**：

```
卷#2 GZ-2019-BJ-T  关系表 5.0 → 1.0   100 行
卷#3 GZ-2017-JS-T  关系表 5.0 → 1.0   100 行
卷#4 GZ-2024-GK-T  无差异             0 行
卷#5 GZ-2016-JX-T  无差异             0 行
满分复核：#2 100/100  #3 100/100  #4 100/100  #5 97/97  全部 OK
仍不一致的关系行 = 0        integrity_check = ok
```

> 归一后 `sync_total_score` 无论取哪张表，结果都是 100 / 97，两处口径彻底一致。

### 8.2 结果页文案：「0 / 97 分」与「0 / 97 题」

**约束**：`.vtj/vue/paper_result.vue` 的 `<template>` 归设计器维护（R3 红线），AI 不能改。
所以用**纯 CSS 伪元素**加后缀，DOM 结构一行未动 —— 设计器回存不会丢，页面也不存在第二套模板。

```css
.score-max::after            { content: " 分"; }   /* 得分 → 0 / 97 分 */
.score-meta .meta-item:nth-child(3) .meta-value::after { content: " 题"; }  /* 正确/错误 → 0 / 97 题 */
```

**验证**（headless Edge + CDP 读真实 DOM，学生账号交卷后的 `#/paper/result`）：

|---|---|---|
| 得分 | `0 / 97` | **`0 / 97 分`** |
| 正确/错误 | `0 / 97` | **`0 / 97 题`** |
| 正确率 / 用时 | `0%` / `9秒` | 不变 |
