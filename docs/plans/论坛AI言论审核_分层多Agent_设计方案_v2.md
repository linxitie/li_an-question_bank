> 状态：**待用户批准**（本文只做设计，未改代码）

> 核心理念：**审核即研判、研判即知识沉淀**；Obsidian 不是生产数据库，而是人机协同的知识运营与审计界面
> 一句话定位：**评论区实时内容安全的第一道自动化防线 + 舆情态势的持续感知器 + 治理决策的可解释建议者**

## 0. 先对齐现实（实测，不是推测）

v2 规格假设了 PostgreSQL + MongoDB/ES + Qdrant/Weaviate + Neo4j + 对象存储。**本项目当前是 SQLite + 单 FastAPI 单体**：

| 规格里的组件 | 本项目现状 | 实测证据 |
|---|---|---|
| 关系库（PG/MySQL） | SQLite 3.50.4（`DB_TYPE=sqlite`） | `config.py:27,268` |
| 文档库（Mongo/ES） | 无；但 **SQLite FTS5 可用** | 实测 `CREATE VIRTUAL TABLE ... fts5` 成功 |
| 向量库（Qdrant/Weaviate） | 无；有 `numpy`/`cv2`/`redis` 客户端 | 实测 numpy 2.3.5、cv2 4.10.0 |
| 图库（Neo4j） | 无；已有关系型邻接表 `cg_edge`(205 行)、`kg_edge` | 实测表存在 |
| 对象存储 | 本地 `app/static/` | 已有商品图落盘先例 |
| OCR / Whisper / 视觉嵌入 | 无 | 未安装相关依赖 |
| 已有审核底座 | **content_guard M0**：12 张 `cg_*`（policy 11 / term 88 / variant 26 / judgment 1 / case 0 / proposal 0 / edge 205 / task / audit_event / stat_daily / redteam_sample / sync_state）+ knowledge-ops 接口 + Obsidian 导出(539 行) + 论坛审核队列 | 见 v1 §0 |

**结论**：v2 的架构思想（分层、DAG 编排、仲裁、知识沉淀、Obsidian 治理、红队、主动学习）可以完整落地；
但"四库"必须以**存储端口（Port）+ 适配器（Adapter）**的方式落地，**默认用 SQLite 系适配器**，
Qdrant/Neo4j/ES 作为可替换实现，**不在本期强行引入外部中间件**。

### 0.1 端口与默认适配器（本期的"四库"落地方式）

| 端口（接口） | 本期默认适配器 | 未来可替换 | 承载规格中的 |
|---|---|---|---|
| `RelationalStore` | SQLite（现有） | PostgreSQL/MySQL | 元数据/状态机/申诉/政策版本/审计索引 |
| `DocumentStore` | SQLite JSON 列 + **FTS5** 全文索引 | MongoDB / Elasticsearch | 原文快照/多模态结果 JSON/政策全文/检索 |
| `VectorStore` | SQLite BLOB + numpy 余弦检索（HNSW 参数留空） | Qdrant / Weaviate | 文本/图像/多模态融合嵌入 |
| `GraphStore` | SQLite 邻接表（复用 `cg_edge`，必要时扩 `kg_edge`） | Neo4j | 事件/主体/客体/传播路径/政策关联 |
| `ObjectStore` | 本地 `var/media/`（pHash 去重） | S3 / OSS | 图片/关键帧/OCR 产物 |

> 原则：**审核链路只依赖端口，不依赖具体库**。换库 = 加一个适配器 + 改配置，不动审核逻辑。

## 1. 角色定位：审核层 / 研判层 / 治理层

| 角色层 | 核心职责 | 自动化边界（硬约束） |
|---|---|---|
| **审核层**（硬约束） | 对明确违规内容执行阻断/降权/标记 | 高置信度违规**可**自动执行；边界案例必须进研判或人工 |
| **研判层**（软判断） | 对"不违规但有风险"的内容评估意图、语境、传播潜力 | **只输出分级建议，不直接处置** |
| **治理层**（知识） | 把每次审核与研判沉淀为规则、案例、图谱关系 | AI 只能**提议**知识变更，人类确认后才写入 |

**定位铁律**：审核动作可以自动化，但**"定义什么是违规"的权力不能交给 AI**。
系统内建"政策—审核"显式映射：每一次判定必须能回溯到 `cg_policy` 具体条款 ID，
不允许只输出一个黑箱分数。

## 2. 多 Agent 架构：1 编排器 + 4 执行 Agent + 2 治理 Agent

### 2.1 执行层（实时链路）

| # | Agent | 职责 | 本期落地 |
|---|---|---|---|
| ① | **采集与归一化** | 多模态分流、去重（pHash+SimHash）、元数据标注 | 文本全量；图片做 pHash 去重 + OCR **留接口**（OCR 依赖未装，P3 接入）；视频/音频 P3 |
| ② | **广谱快筛** | 全量高召回初筛，明显正常/违规快速分流 | 复用 `content_guard.engine`（词库+变体，Aho-Corasick）+ 轻量语义打分（可选小模型；默认规则） |
| ③ | **专项审核 Agent 集群** | 按域并行：政治法治 / 社会伦理 / 文化偏好 | **新建**，LLM + 绑定政策条款集，输出域标签 + 置信度 + 引用条款 |
| ④ | **跨模态关联** | "单模态合规、组合违规" | P3（依赖 OCR/视觉嵌入）；本期只留端口与数据结构 |

### 2.2 治理层（近实时/离线）

| # | Agent | 职责 |
|---|---|---|
| ⑤ | **仲裁与分级** | 专项 Agent 分歧时，按 **政策优先级 + 置信度校准 + 历史同类案例** 裁决，输出结构化"判定依据链" |
| ⑥ | **知识运营** | 生成变更提案 + 证据链接、冲突检测、去重合并；**不直接改知识库** |

> 仲裁不是多数投票：`裁决分 = w_policy × 条款优先级 + w_conf × 校准置信度 + w_case × 相似案例裁定`，
> 权重与阈值写在 `cg_policy.policy_dsl`，可运营调整。

### 2.3 编排：DAG 条件路由（不是固定流水线）

```
ingest ─► fast_screen ─┬─(高置信 pass)────────────────► pass
                       ├─(高置信 block 且条款明确)─────► block
                       └─(边界)─► domain_agents(并行3域)
                                    └─► cross_modal(P3)
                                          └─► arbitrator
                                                ├─ pass/mask
                                                ├─ review（人审）
                                                └─ shadow（只记录）
```

- 快筛命中高置信 → 短路，不进精审；只有边界样本触发专项 + 仲裁；
- 平均延迟压在精审链路之下，同时不牺牲高风险召回；
- DAG 节点执行结果全部落 `cg_judgment.agent_trace`（可回放）。

## 3. Obsidian：知识资产"权威副本 + 人机审阅界面"

### 3.1 边界（写死）

- Obsidian **不承载**实时评论流、向量索引、图谱查询的生产负载；
- 生产系统 → Obsidian 是**受控双向同步**：结构化知识投射为 Markdown/Canvas，人工结论回写为提案状态；
- 生产库是唯一事实源；Obsidian 是"可读层 + 批注层"。

### 3.2 可视化工作台

| 能力 | 落地 |
|---|---|
| 图谱全库视图 | 复用现有 `content_guard/obsidian.py` 导出 `[[wikilink]]` + 关系段；运营用 obsidian 图谱插件直接看"话术→案例→条款→处置模板" |
| 仪表盘/趋势 | 导出 `00-看板/今日研判.md`（可配 Mermaid/表格）；数据来自 `cg_stat_daily` |
| Mermaid/Canvas | 条款笔记内嵌"政策解读→审核逻辑→典型案例"流程图 |

### 3.3 受控写入管线（obsidian-tc 范式）

```
Agent 提案 → 待审队列(cg_proposal) → 人类在 Obsidian 批注结论
   → 受控导入(import) → 追加审计(JSONL/cg_audit_event) → 编译生效
```

| 约束 | 规则 |
|---|---|
| 权限分级 | 运营=只读+提案；知识管理员=可确认写入；**Agent 无删除权** |
| 写入范围 | 只允许改**提案结论**与**案例标签**；禁止直接改条款正文 |
| 审计 | 每次写入追加 `{ts, client, role, tool, path, before_hash, after_hash}`，外部审计锚 |

## 4. "四库"职责与防膨胀（映射到端口）

| 端口 | 存什么 | 事务性角色 | 防膨胀 |
|---|---|---|---|
| Relational | 元数据、任务状态机、处置、申诉、政策版本、审计索引 | **控制面唯一事实源**（待审/已阻断/已放行/申诉中） | 任务表按时间分区；超期归档只留最小字段 |
| Document | 原文快照、多模态结果 JSON、政策全文、案例叙述 | 派生的可检索视图 | **TTL**：常规 30–90 天；高风险/申诉延长并转冷 |
| Vector | 文本/图像/融合嵌入 + metadata（不存原文） | 派生 | 定期物理删除过期且未被图谱引用的向量；索引分段合并 |
| Graph | 事件/主体/客体/传播路径/政策关联 | 派生 | 节点生命周期分层 + 同主体同类互动合并为带权单边 + PageRank 精简低价值子图 |
| ObjectStore | 图片/关键帧/OCR 产物 + pHash 指纹 | 无 | **pHash 去重**：相似图只存一份对象多处引用；原图合规删除后保留指纹 |

**一致性对账**：关系库状态 vs 文档库快照 vs 向量 metadata vs 图节点存在性，
不一致不自动修复，生成"一致性异常提案"进 Obsidian 运营队列，由知识运营 Agent 分析根因。

## 5. 知识图谱三层本体

| 层 | 节点 | 关系 | 特点 |
|---|---|---|---|
| **政策本体**（稳定） | 政策条款/审核规则 | 属于类别、优先于、引用法律依据 | 变化慢、权重高，判定最终锚点 |
| **审核本体**（运行） | 审核判定实例 | 基于条款、被申诉、修正了条款解释 | 审计与可解释核心 |
| **舆情本体**（演化） | 事件、话题、主体（脱敏）、传播路径 | 时序、因果、转发/引用、情感变化 | 态势感知与预警，Obsidian 可视化重点 |

跨层关联：判定实例 ↔ 舆情事件（"某类违规集中在哪个事件传播中"）；条款 ↔ 高频场景（驱动规则优化）。
落地：复用 `cg_edge`（本期），节点类型扩展 `policy/term/case/judgment/event/subject/object`。

## 6. 可靠性 / 准确性 / 长期稳定性

### 6.1 分级熔断（不是全局崩溃）

| 级别 | 触发 | 动作 | 优先级 |
|---|---|---|---|
| L1 | LLM 延迟升高 | 关解释生成、降专项 Agent 采样 | 审核阻断 > 风险预警 > 知识沉淀 > 报告 |
| L2 | 队列积压 | 快筛保留，精审异步化 | 同上 |
| L3 | 严重故障 | 丢弃冷数据、只保近 1h 热数据 | 实时阻断不丧失 |

### 6.2 红队 Agent 常态化

独立 Agent（不参与生产）持续生成规避样本（同音字、图文拆分、编码隐藏），测生产漏放率；
发现的绕过样本进知识运营提案队列，触发规则/few-shot 更新。

### 6.3 幻觉抑制 = 架构隔离（不是"让模型更谨慎"）

- 快筛与专项判定用**分类/检索增强**，不让生成式推理直接决定阻断；
- 仲裁输出必须附**政策条款 + 检索到的类比案例**证据链；
- 无证据的判定自动降级 `review`；
- HITL **按不确定性路由**：高置信自动执行 / 中置信进 Obsidian 审阅 / 低置信放行但标记观察。

### 6.4 主动学习闭环

Obsidian 中的人类动作（确认/否决/修改提案、override 仲裁）结构化为偏好信号；
知识运营 Agent 定期聚类，识别规则集系统性偏差区，自动生成规则调整/few-shot 更新提案。

### 6.5 性能红线

| 指标 | 目标 |
|---|---|
| 快筛链路 P99 | ≤ 2s |
| 精审链路 P99 | ≤ 30s |
| 峰值写入 | ≥ 日均 5× 突发 |
| 单节点故障 | 10s 内摘除，不影响 SLA |
| 容量预警 | 磁盘/内存 70% 触发归档/精简 |

## 7. 为什么这样落地能同时满足规格与现实

| 规格要求 | 本期如何满足 | 何时升级 |
|---|---|---|
| 多 Agent 分层 | FastAPI 内部模块化 Agent（`moderation/agents/*`），DAG 编排器纯 Python | 量大时拆成独立服务 + 消息队列 |
| 四库分离 | 存储端口隔离，SQLite 系适配器 | 触发条件：向量 >500 万、图查询 >1s、文档 >500 万条 |
| 多模态 | 文本全量；图片 pHash 去重；OCR/视频留端口 | P3（依赖安装 OCR/Whisper） |
| Obsidian 治理 | 复用导出 + 新增受控回写（提案结论/案例标签）+ 审计 | 需要插件化看板时接入 obsidian 插件 |
| 红队/主动学习 | 复用 `redteam.py` + 新增偏好信号表 | 与生产同周期 |

## 9. 排期（按规格给的优先级）

| 阶段 | 内容 | 交付 |
|---|---|---|
| **P1 审核能用 + 可追溯** | 关系库(已有) + 文档库(FTS5) + 快筛(已有) + 专项 Agent(3 域) + 仲裁 + agent_trace | 精审链路可用，判定可回溯 |
| **P2 仲裁与 HITL** | 向量库适配器(numpy) + 仲裁分级 + Obsidian 回写 + 申诉 | 人机协同闭环 |
| **P3 知识图谱与演化** | 图适配器(邻接表) + 三层本体 + 传播路径 | 态势感知 |
| **P4 治理与自生长** | 红队 + 主动学习 + 跨库对账 + 容量预警 | 长期稳定 |

**Obsidian 接入放在 P2 末**（生产链路稳定后），避免知识运营复杂度倒灌核心审核路径。
