T4 六阶段真实进度埋点 + 状态字段 + 预览态贴图接口 验证 (2026-09-29)
文件: backend/app/api/v1/question_import.py

=== A. 真实进度埋点 ===
实现: _extract_text_from_pdf 新增 progress_cb(page_no,total_pages,images_on_page)
      每页处理完后同步触发；_process_import_async 内的 _set_progress() 写库
阶段划分(实测):
  ① READING     5%          文件进入后台任务
  ② EXTRACTING  10% -> 60%  【逐页推进，16页实测16次回调】
  ③ IMAGES      60%          页循环结束、图片已随文本一并暂存
  ④ SPLITTING   60% -> 75%  extract_question_blocks
  ⑤ MATCHING    75% -> 90%  【逐题推进，每20题上报一次】
  ⑥ BUILDING    90%          构建 response_payload
  ⑦ DONE        100%        与 PREVIEW 同一次提交落库

端到端实测(目标PDF, 16页):
  耗时 0.8s | 提交 28 次 | 去重后不同进度值 24 个 (要求>=5)
  序列: 5,10,13,16,19,22,25,28,31,35,38,41,44,47,50,53,56,60,75,79,83,88,90,100
  单调不减 True | 终值 100
  阶段序列: READING->EXTRACTING->IMAGES->SPLITTING->MATCHING->BUILDING->DONE (全覆盖)
  落库: import_status=PREVIEW, progress_percent=100, current_phase=DONE, total_questions=70

踩坑记录(重要):
  初版按两个独立指标上报(文本百分比 + 图片计数)，导致每页互相回跳，
  实测出现 12->45->14->45->16->47 的锯齿。进度条倒退会让用户误判解析出错。
  修正1: _set_progress 加单调守卫(绝不让 progress_percent 变小)
  修正2: _on_page 每页只写单一值 10+ratio*50 (页循环内文本与图片同次推进完成)

=== B. 状态接口扩展 ===
GET /api/questions/import/records/{id}/status 响应新增:
  progress_percent (int, 旧记录NULL回落0)
  current_phase    (str|None)
前端不再需要自己用定时器伪造百分比

=== C. 预览态贴图接口 ===
POST /api/questions/import/records/{import_id}/attach-image
参数: file / target(content|option) / option_key / question_index

关键设计: 不自行写文件，而是把上传内容包成 base64 data URI 交给既有的
_extract_and_save_images()，完整复用其尺寸上限(MAX_IMAGE_SIZE=10485760)、
无关图过滤、压缩与路径安全，避免引入第二套图片写入逻辑。
注意: _compress_and_store 是嵌套函数(依赖闭包 img_dir/_safe_ext)，
      不能直接调用，故走公共入口而非复制其逻辑。

同时同步 preview_data 的两份副本(items 与 _response['questions'])，
否则状态端点返回的 result 与 items 会不一致。

实测:
  题干贴图   -> True /static/questions/1355/img_0_338e5b40.jpg
  选项A贴图  -> True 同上(同图为同一文件，md5命名天然去重，属预期)
  非法入参全部 400 拦截:
    [target 非法] [option 缺 option_key] [索引越界 99999] [类型不支持 .txt]
  落库校验: 题干含<img True | 含<img的选项数 1 ['A']
            items 与 _response.questions 一致 True
