## 2. ★★ 但「dry-run 一直在真实写库」

多次 dry-run 后，DB 出现**未被 rollback 撤销的残留**：

```
question_bank   2657   （基线 2583，+74）
  行测subject_id=1  74   ← 全部 source=「2023…（副省级网友回忆版）题本」
  公专 subject_id=3  2583  ← 未变，红线成立
连带写入：exam_paper +1（行测 paper 14）/ question_groups +6
        / question_knowledge +147 / exam_paper_tag +1
```

### 根因：`_get_or_create_subject` 内部 commit

```
扫描导入链路 commit 调用点：L393、L1654、L2019
L311  def _get_or_create_subject(...)
L393      db.commit()        ← 元凶
```

`_upsert_question_core` 每次插入都调用 `_get_or_create_subject(db, subject_name)`，
该函数内部 `db.commit()` —— **驱动脚本的 `db.rollback()` 会被中途 commit 抵消**。

### 这解释了此前全部账目矛盾

| 现象 | 真正解释 |
|---|---|
| 9 套 dry-run 报「入库 708」但 DB 只有 74 行 | 708 是脚本自报；真正 commit 落库的只有 74 |
| 同一套两次运行报 `入库125/dup5` 与 `入库51/dup79` | 第二次运行时 DB 已有残留 74 行 → 更多命中重复 |
| 国考三变体重复率 4%/37%/68% 递增 | 先导入的卷把数据 commit 落库，后续卷全部命中重复 |

> 前两个「疑点」并非独立缺陷，而是**同一个根因**的下游表现。

## 3. 对计划可行性的影响（须上报）

计划 T16 要求：

> 「事务分批：每 N 题 commit（评估 11,000 题单事务的风险），WAL 模式确认」

**通过 `_upsert_question_core` 无法实现批次事务** —— 既有 helper 会在每题内部commit，
批次边界形同虚设。要满足「单批失败不影响已通过批次」（计划的批次隔离验收项），
只能：

| 方案 | 说明 |
|---|---|
| A. 改造 `_get_or_create_subject` 去掉 commit | 风险：公专/申论现有链路依赖其隐式提交语义，**红线** |
| B. 行测专用落库函数，不走 `_upsert_question_core` | 与「复用不重写」原则冲突，但隔离最彻底 |
| C. 每省独立 DB 连接 + 失败即删该省新增行 | 需精确记录新增行 ID 以便回滚 |
| D. 接受「按省提交」，失败时从备份恢复该省 | 备份已就绪，但恢复粒度粗 |

**未擅自选择** —— A触碰公专/申论既有语义，属红线；B/D 改变计划既定设计。
